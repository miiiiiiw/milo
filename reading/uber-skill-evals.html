企業規模的 SkillsSkills at Enterprise Scale

skill（技能）是一個 Markdown 檔，用來教 AI 代理把一件事做好，例如建立合併請求（pull request）、查詢指標資料庫（metrics store），或是替每週的業務簡報擬大綱。Skills 是 Uber 軟體工廠（software factory）的基本構件之一。Uber 共用的 skill 市集（marketplace），從 2025 年 10 月的 1 個 skill，短短一年就成長到超過 5,000 個。已有數千人寫過 skill，而 AI 代理光是一個月就呼叫了 skill 超過 100 萬次。

到了企業規模，skill 的管理、品質、效率與發布，都帶來許多挑戰和機會。這篇文章是寫給正在全公司推行 AI 代理的團隊。我們分享如何改善 AI 賦能（AI enablement），以及如何讓 AI 代理來幫忙。

什麼是 skillWhat Is a Skill

skill 就是一個工作流程（workflow），而「企業的最小單位就是工作流程（workflow）」[1]。一個 skill 封裝一個工作流程（workflow）：一份操作手冊（runbook）、一個團隊的作業流程，或一項專家手動做的任務。它可以短到只是編輯一個 Linear® 議題（issue），也可以長到一整套根本原因分析（root-cause analysis）。

在磁碟上，skill 是一個目錄。它的 SKILL.md 檔有名稱（name）、描述（description）和一段指示內文（body）。目錄裡也可以放腳本和參考檔案。AI 代理分三個階段載入它，所以就算有數千個 skill，每個也只占一段簡短的描述：

  • 一律載入：名稱和描述，大約 100 個令牌（token）。AI 代理靠描述判斷這個 skill 是否適用。
  • skill 執行時載入：內文，控制在 500 行以內。
  • 需要時才載入：腳本和參考資料，只有需要它們的那一步才會讀。

Agent Skills 規格詳細說明了這個開放格式。

發布 skillDistributing Skills

我們建立了一個讓所有人放 skill 的地方，不論大家在哪裡使用 AI 代理，都能輕鬆載入。最後發現最好的地方是一個 Git® 儲存庫（repository），因為版本控制本來就會替每個 skill 留下負責人、審查和歷史紀錄。

整頓這團混亂：Always-on、Core 與 Domain（Organizing the Madness: Always-On, Core, and Domain）

目標是讓團隊很容易寫 skill，同時預設就提供他們一組精選的 skill。為了讓開發又快、品質又高，我們把市集（marketplace）分成三層，skill 每往上升一級，對品質和效率的要求就更高。要讓一個 skill 升級，我們會跑自己的評測（evals）系統，並做一組品質與實用性檢查。

  • Domain（領域層）。任何團隊都能開一個自己的區域。每個區域指定自己的審查者，所以團隊只要一位同儕核准、通過一項持續整合（CI）檢查就能發布，不必等中央團隊。
  • Core（核心層）。被廣泛使用的 skill 會移到這裡。它們是推薦的、經過測試、由一個團隊維護，平台團隊會審查每一次變更。
  • Always-on（常駐層）。大約 100 個用途廣泛的 skill 對所有人預設開啟，所以新進員工第一次執行就有 skill 可用。它們涵蓋合併請求（pull request）、程式碼審查（code review）、工具存取、資料分析和聊天。

一次安裝，所有 AI 代理通用（One Install for Every Agent）

支援許多不同的 AI 代理，是我們策略的一部分。這是個機會，因為大家會挑最適合任務的 AI 代理；這也是個挑戰，因為每種 AI 代理定義和安裝 skill 的方式都不一樣。

我們做了一個叫 aifx 的命令列工具（CLI），用來啟動各種 AI 代理並儲存設定。後來我們把它擴充到 skill 管理、MCP 呼叫、可觀測性（observability），以及更進階的設定。aifx 處理各平台在 skill 定義和安裝上的差異。人或 AI 代理執行 aifx plugin add data-analyst 就能安裝一組 skill（稱為外掛（plugin）），或執行 aifx skill add analyze 安裝單一 skill。aifx 把這個選擇記在一份設定檔裡，套用到下一個啟動的 AI 代理，不管是哪一種。在 Claude Code™、Codex™ 和 OpenCode™ 之間切換的工程師，會保有同一套 skill。

aifx 分層合併設定：公司預設值、團隊或專案計畫、儲存庫（repository）、工作目錄、使用者，以及本機覆寫。後面的層只會新增外掛（plugin），從不移除，所以一個儲存庫（repository）可以宣告所有在裡面工作的人都需要的外掛（plugin）。

aifx 替工程師、資料科學家和其他角色管理角色設定（persona），設定預設的 skill 和組態。

找到 skillSkill Discovery

有了數千個 skill，幫使用者替某個工作流程（workflow）找到對的 skill 就變得很重要。我們有一個 find-skills skill，能找到並下載一個高品質的 skill，在特定工作流程（workflow）中執行它。為了支援搜尋，我們用評測（evals）和執行次數替 skill 分類、排名，並計算出 skill 品質分數。

透過我們內部的脈絡圖譜（context graph），任何員工都可以問：「給我那些同事在用、而我沒在用的 skill。」

衡量 skill 的使用Measuring Skill Usage

我們在 hook 裡用 OpenTelemetry 從 AI 代理收集使用統計。hook 會送出工作階段（session）開始、工具呼叫（tool call）之類的事件，讓我們記錄 skill 的使用情形和它的脈絡（context）。當工具是一個 skill 時，事件會記下是哪個 skill、它的版本，以及是 AI 代理自己選的，還是使用者輸入了它的指令。事件裡不含提示詞（prompt）文字，也不含檔案內容。

我們從這些事件替每個 skill 算出 12 項指標，其中包括使用者數、留存率（retention）、成本、延遲（latency）和錯誤。作者可以在我們的撰寫工具 Skill Workshop 裡、該 skill 的頁面上看到這些數字。

skill 品質是一場永無止境的仗The Never-Ending Battle for Skill Quality

skill 建立的是 AI 代理工作流程（agent workflows），帶來的挑戰和 AI 代理本身不一樣。它們被期待在許多不同的脈絡（context）中運作、在需要人類判斷才能得出正確答案的領域中運作，也要在許多不同的 AI 代理環境中運作。我們打造了 Skill Workshop，它是一個外掛（plugin）加一個網頁應用程式，透過科學方法、系統化評測和使用者回饋，幫 skill 的作者和使用者改進 skill。

Skill Workshop

skill 有它的生命週期。作者寫好它、測試它，透過市集（marketplace）發布出去。接著作者依它實際執行的結果改進它，直到某個更好的模型讓它變得多餘，它就退役。Skill Workshop 為每個階段都準備了工作流程（workflow），也替每個 skill 做了一頁，顯示它的使用量、成本和品質。

skill 從一份定義清楚的規格文件（spec）開始。模型和工作環境（harness）變化得很快，我們希望在反覆修改實作的同時，skill 仍能持續運作。規格文件（spec）保存了 skill 的意圖：它的目標、它的輸出、必須或禁止的工具動作，以及它針對的 AI 代理和模型。Skill Workshop 從規格文件（spec）編譯出 SKILL.md 和它的測試提示詞（prompt），並在模型或 AI 代理改變時重新編譯。

把 skill 的程式碼異味提煉成一個 linter（Skill Code Smell Distilled Into a Linter）

我們把「好 skill 有什麼共通點」「什麼會造成問題」、研究論文，以及各模型的提示詞撰寫指南，提煉成一個程式碼檢查工具（linter），裡面是通過或不通過的檢查。以下是一些最有用的：

  • 步驟有編號，每一步只有一個目標，而且至少有某種方式可以軟性驗證（soft verify）它。
  • 每一步給出具體的指令，並在進入下一步前檢查結果。
  • skill 有錯誤復原的章節：一張列出失敗情況和修正方式的表。「再試一次」不算。

評測（Evals）

我們需要超越「靠使用者手動回饋 skill 品質」的做法。我們建立了好幾套系統，在我們眾多的 AI 代理介面上評測 skill。我們做了人工標註的提示詞（prompt），以及用來測試它們的執行環境。我們對一套評測（eval）組合的建議是：大約 5% 是黃金案例（golden cases），有固定的輸入和預期的輸出，並搭配工具模擬（tool mocks）；80% 是依行動路徑（trajectory）評分的真實提示詞（prompt）；15% 由作者評斷。行動路徑（trajectory）指的是 AI 代理有沒有依正確順序使用正確的 skill 和工具。

我們在三個地方跑評測（evals）：我們的背景 AI 代理平台 Minion；我們的託管式 AI 代理沙箱（sandbox）AES；以及我們的遠端開發機 devpods。這種無塵室能抓出對作者筆電的依賴。就像每個說「在我的電腦上可以跑」的開發者一樣，強制使用遠端環境找出了許多問題。有些 skill 預期有特定的檔案路徑、快取的文件，或特定的作業系統工具才能運作。

面對非確定性（non-deterministic）的大型語言模型（large language model，LLM），評測（evals）仍然一半是藝術、一半是科學。根據我們的經驗，通過率 70%–90% 的評測（evals），可能比通過率 100% 的更有用。答案會變，評審也會變。100% 的通過率可能代表這個評測（eval）漏掉了答案中有意義的變化。

判定一次評測（eval）執行是否通過，就是在判定什麼才重要。用字需要完全一致嗎？哪些東西可以改而不改變意思？AI 代理自己未必能一致地做出這些區分。它們可能會專注在無關緊要的細節上，或在答案其他部分都符合預期格式時，漏掉一個嚴重的幻覺（hallucination）。

以 LLM 當評審（LLM-as-judge）時，有一組人工標註的資料效果最好。skill 作者必須建立這些資料、向使用者蒐集，並反覆評分。這就是為什麼我們把評測（eval）組合分成黃金資料集（golden sets）、真實提示詞（prompt）和作者自建的案例。

行動路徑（trajectory）評測看的是 AI 代理試圖做什麼、為什麼這樣做，不看結果。AI 代理有沒有照預期使用 MCP 或流程？它有沒有查那張資料表、讀那份 Google 文件、查脈絡圖譜（context graph）？它有沒有查看自己的錯誤復原指示？我們用結果分數和行動路徑（trajectory）分數來評估 skill 和工作流程（workflow）的變更。

有時候少即是多：消融測試（Less Is Sometimes More: Ablation）

我們在隔離的評測環境中，用相同的輸入提示詞（prompt），測試從工作流程（workflow）中拿掉字句、甚至拿掉整個 skill 的效果。對整個 skill，我們把真實提示詞（prompt）重播（replay）兩次，一次有 skill、一次沒有，由一位盲評評審（blind judge）挑出比較好的答案。我們用真實提示詞（prompt）測試了使用量大的 skill，分別試了有 skill、沒有 skill，以及只用 skill 的一部分。隨著模型變好，字越多反而可能拉低表現，所以我們也測試從 skill 裡刪字。

譯註：圖中的 Absorbed（被吸收）是指有沒有這個 skill 差別落在雜訊範圍內，也就是模型本身已經會做，skill 的效果被「吸收」掉了。這是依圖意補充的說明。

在大多數案例中，skill 讓工作階段（session）更成功、成本也更低。最大的成效來自那些給了 AI 代理它自己不容易找到或理解的東西的 skill，例如存取內部文件，或執行資料倉儲（warehouse）查詢的方法。

skill 的效率Skill Efficiency

skill 讓我們能衡量一項任務的成本，所以我們把更多工作階段（session）轉成使用 skill。沒有使用 skill 的工作階段（session）可能會嘗試很多方法、找到錯的答案和錯的資料表，還把工具用得一團亂。有了 skill，得到正確答案、而且有效率地得到的機率就會上升。在我們對一個執行資料倉儲（warehouse）查詢的 skill 做的消融測試（ablation）中，沒有這個 skill 的工作階段（session）多了 13% 的工具呼叫（tool call）、工具錯誤是六倍、耗時多 31%，而有 skill 的答案在 87% 的比較中勝出。

能改善答案的 skill 也有成本。它的指示、它的工具呼叫（tool call）和結果，都會進到 AI 代理的脈絡（context），而工作階段（session）之後的每一個回合都要再為這些脈絡（context）付一次費。我們衡量每個 skill 的成本，並用幾個槓桿降低成本。

我們怎麼衡量一個 skill 的成本（How We Measure the Cost of a Skill）

AI 代理會持續累計一個工作階段（session）到目前為止花了多少，我們的遙測（telemetry）會定期以快照回報這個總額。當 AI 代理呼叫一個 skill 時，我們取呼叫前最後一次回報的總額和呼叫後第一次回報的總額，兩者相減。差額就是那次呼叫的成本。我們把每個 skill 每天的呼叫加總，再除以呼叫次數，得到這個 skill 每次呼叫的成本。

這個數字包括模型讀取 skill、接下來的回合，以及那段期間內的其他工具呼叫（tool call）。我們用這個數字看成本花在哪裡，並比較一個 skill 在變更前後的差異。

我們用來降低 skill 成本的槓桿（The Levers We've Used to Reduce the Cost of a Skill）

一個中央團隊負責提升所有最常用 skill 的效率，平台負責人也像對待使用者介面（UI）或軟體的負責歸屬一樣，對待 skill 的負責歸屬。他們為品質和效率設定了關鍵績效指標（KPI）。

  • 用程式碼取代 LLM。永遠不變的步驟放在腳本裡執行，模型就不必讀每一個工具定義和每一個結果。這就是下面說的 Code Mode。
  • 讓 skill 在一個用較便宜模型的工作者（worker）裡執行。skill 派出一個子代理（subagent），由呼叫方挑選它的模型：查找用小模型，彙整比對結果用最強的模型。大型工具結果留在工作者（worker）的脈絡（context）裡，只回傳一段有長度上限的摘要，所以之後的回合不必再為它付費。在一次前後對照中，一個追蹤（tracing）skill 的每次呼叫成本降了 46%。一個部署 skill 在第一週沒有看到下降，所以每個 skill 改完之後我們都會各自衡量。
  • 在 skill 載入時就執行腳本。當結果很小又一定需要時，skill 在載入時就執行它的腳本，把輸出放進提示詞（prompt），省掉一個模型回合。有一個搜尋 skill 從四個回合降到三個，平均成本降了 32%。
  • 把輪詢（polling）移出主要工作階段（session）。在我們花費最高的 20 個工作階段（session）中，通知回合大約占了三分之一的花費。9 月時，我們把合併請求（pull request）監控 skill 的輪詢（polling），移到一個用較便宜模型的背景 AI 代理（background agent）上。

Code Mode：能用程式碼就別用 LLM（Code Mode: Use Code Over LLMs When You Can）

對確定性（deterministic）的工作，程式碼比 LLM 便宜、比較好測試，結果也比較好。我們發現很多令牌（token）都花在同樣的工具呼叫（tool call）上：執行查詢並讀取回應、讀取和傳送 Slack® 訊息、搜尋遠端程式碼、讀取和寄送電子郵件。AI 代理只想要結果，卻得把所有東西都載入、經過 LLM 和它的脈絡視窗（context window）跑一遍，又慢又貴。

在 LLM 用戶端預設安裝 MCP，讓情況更糟，因為它會把每個工具的完整描述載入每一次呼叫。工具超過 100 個時，使用者還沒打任何字，這些定義就占了 5 萬到 7 萬個令牌（token）。

受到 Cloudflare 的 Code Mode 啟發，我們把這些流程搬進透過我們的閘道（gateway）呼叫工具的工具腳本。在我們的設定下，這避免了預先載入那些工具定義，AI 代理也只讀它需要的那部分結果。這些腳本改善了我們最常用流程的成功率、延遲（latency）和成本。

這些 code mode 的 skill 成了套件，公司其他的 skill 用名稱引用它們，讓這些 skill 的流程可以依賴高品質的實作。我們也在 skill 和外掛（plugin）中封鎖會安裝工具伺服器的 .mcp.json 檔。

持續改進，讓 AI 代理自己回報 bugContinuous Improvement and Agents Filing Their Own Bugs

skill 可能因為一千種原因停止運作。模型升級改變了 AI 代理讀指示的方式、某個工具改了它的旗標（flag），或者 AI 代理的工作環境（harness）改了執行 skill 的方式。

AI 代理知道什麼時候某個 skill、工具或流程不對勁。AI 代理會察覺自己很難完成被交代的事，而且已經花了 100 個回合在跟某個怪錯誤奮戰。它會看到說明文字列出、工具卻拒收的旗標（flag），遇到錯誤卻以 0 結束的指令，或是明明該有結果卻什麼都沒回傳的查詢。

AI 代理有時能找到變通辦法，但這麼做會浪費一大堆令牌（token）和寶貴的脈絡（context）。我們發現，加入一個隨時可用的 skill，讓 AI 代理把它遇到的阻礙或 bug 提報出來，就能建立一個強大的改進飛輪（flywheel）。

發現問題（Problem Discovery）

我們把每份回報稱為一個 papercut（紙割傷，意指小卻惱人的問題）。AI 代理用 log-papercut 這個常駐（always-on）skill 提報，所以每個 AI 代理都看得到這個 skill，不用被要求就能提報。這不只改善了之後的工作階段（session），也改善了發生 bug 的那個工作階段（session）本身，因為 AI 代理知道事情有時候就是會出錯，也知道自己應該察覺什麼時候卡住了。它甚至可以查查別人是怎麼繞過這個問題的。

回報會說明 AI 代理試了什麼、預期什麼、實際發生什麼，以及什麼能修好它。所有回報都進到同一個儀表板（dashboard），依 skill 分組。

解決問題（Problem Resolution）

一個 papercut 會經過分組、分類（triage）、根本原因（root cause）分析、修正、評測和核准。修正上線之後，會先衡量它的效果並檢查有沒有迴歸（regression），才關閉這張工單。

AI 代理在短短三個月內就提報了數千個 papercut。其中數百個已經修好，這些修正改善了工作流程（workflow），也讓它們更省令牌（token）。以下是一些有趣的修正：

  • 合併請求（pull request）skill 把 commit 訊息寫到一個共用的暫存檔，所以兩個同時進行的工作階段（session）會改到彼此的合併請求（pull request）。
  • 一個部署 skill 叫 AI 代理傳入以秒為單位的 epoch 時間，但 API 要的是毫秒。
  • 一個設定查詢 skill 在要求的鍵不存在時，沒有報錯，而是回傳了另一個屬性。
  • 一個合併請求（pull request）skill 在一個根本沒有持續整合（CI）檢查的儲存庫（repository）上等待 CI 檢查，一再重複同一個 404，直到逾時。

人類訊號（Human Signals）

不管 AI 代理怎麼想，我們都有人類評分者在檢視 AI 代理的工作階段（session）。在 Uber 的自動化軟體維護工廠 Fawkes 裡，我們有會開合併請求（pull request）的程式碼維護 skill。如果一個合併請求（pull request）收到留言、經過多輪修改，或沒有被接受，我們就用這些訊號改進產生它的 skill。被擋下的合併請求（pull request）會成為評測（eval）集的一部分。我們在許多領域和 AI 代理平台上都用同樣的模式。

結論Conclusion

skill 把文字變成了行動和成果。隨著使用量成長、模型進步，我們的重心從「寫 skill」轉向 skill 的品質和評測。尚未解決的問題是：如何評測那些很少執行、影響很大、又很難判斷的工作流程（workflow）。在持續投入的同時，我們正在實驗行動路徑（trajectory）與軌跡（trace）分析、結構化的人工標註，以及 skill 路由（routing）。

重點摘要TL;DR

  • 所有 AI 代理共用一種格式、一個儲存庫（repository）。同一個 skill 能在筆電上的 Claude Code™、OpenAI Codex™、OpenCode™ 和 SpaceXSI Cursor® 中執行，也能在我們所有的託管式 AI 代理中執行。我們的命令列工具 aifx 服務每一種 AI 代理介面，負責身分、skill 發布和 MCP 連線。
  • skill 是給所有人用的，不只工程師。工程師什麼都用 skill，像是根本原因分析（root-cause analysis）和實驗結果報告。其他團隊用 skill 取得指標、準備待審的文件草稿，以及協助客戶經理回答商家的支援問題。
  • 先寫規格文件（spec）。一份 spec.md 記錄 skill 必須產出什麼、支援哪些 AI 代理和模型。我們的撰寫工具 Skill Workshop 從它編譯出 SKILL.md 和測試提示詞（prompt），所以模型和 AI 代理改變時，skill 仍能持續運作。
  • 有時候少即是多。我們把真實提示詞（prompt）在有和沒有 skill 的情況下各重播（replay）一次，由盲評評審挑出比較好的答案。隨著模型變好，有些 skill 需要修改或退役。
  • 從軌跡（traces）改進 skill。作者在自己的工作階段（session）裡讀出 skill 實際執行時哪裡出錯，再把每一次失敗變成一個測試案例。
  • AI 代理自己回報 bug。當 AI 代理遇到壞掉的旗標（flag）、錯誤的文件或無聲的錯誤時，它會提報一份結構化的回報，稱為 papercut，交到負責人手上。

接下來呢？What's Next?

以下是我們接下來在做的事：

  • skill 的 A/B 測試。我們想對 skill 的內容做 A/B 測試，以大規模評估它們。這也能讓我們對重要 skill 的變更做金絲雀發布（canary）。
  • 依模型編譯 skill。隨著各模型的提示詞撰寫指南和建議逐漸分歧，我們發現不同模型家族適合不同措辭和長度的 SKILL.md 檔。
  • 蒐集並處理 skill 執行的軌跡（traces）。我們會依評測（eval）替工作階段（session）建立索引，記錄使用者想做什麼、發生了什麼、有沒有遇到麻煩，以及是否成功。我們會問：還能做什麼來改進？哪些做得非常好、應該分享給更多工作階段（session）？
  • skill 推薦。我們會告訴使用者他們應該用哪些 skill。
  • 任務路由器（task router）。使用者想做的每一件事，都可以到同一個地方問，它會把任務導向對的 AI 代理、skill 和脈絡（context）。

以下為譯者整理，非原文內容。

這篇在說什麼

Uber 工程團隊分享他們怎麼在全公司管理 5,000 多個 AI 代理 skill：skill 是一份教 AI 代理把一件事做好的說明書，一個月被呼叫超過 100 萬次。文章從「放在哪裡、怎麼安裝」一路講到「怎麼知道它好不好、怎麼讓它更省錢、壞了怎麼發現」。

核心想法是：把 skill 當成正式的產品來經營。每個 skill 有負責人、有版本、有使用數據、有評測（evals），還有一條讓 AI 代理自己回報問題的管道。整個流程可以濃縮成封面上的五個階段，而且最後一步會回到第一步。

為什麼值得學

很多人寫過一兩個 skill，但很少人想過一千個人一起寫、五千個 skill 同時在用時會發生什麼事：找不到、互相重複、悄悄壞掉、偷偷變貴。這篇是少見的「大規模實戰紀錄」，而且每個做法都附了數字，例如有 skill 的答案在 87% 的比較中勝出、工具定義一開場就吃掉 5 萬到 7 萬個令牌（token）。

就算你不是工程師、只有幾個 skill，裡面的原則一樣適用：說明書要分層、要用對照測試確認它真的有幫助、固定的步驟交給程式、出錯時要有人（或 AI）記下來。文中的數字是 Uber 自己公布的內部數據。

你可以帶走的重點

1. skill 是寫成檔案的工作流程，分三段載入

一個 skill 就是把一件事「怎麼做」寫進一個資料夾：SKILL.md 裡有名稱、描述和步驟，旁邊可以放腳本和參考資料。妙的是它分段載入：AI 代理平常只看名稱和描述（約 100 個令牌），真的要用才讀步驟，某一步需要時才打開腳本。所以裝了幾千個 skill，也不會把 AI 代理的「工作記憶」塞爆。

換成日常說法：就像書架上每本書只露出書背，需要時才翻開那一本，再只看需要的那一章。

2. 放在同一個地方，分三層管理品質

Uber 把所有 skill 放進同一個 Git 儲存庫（repository），因為版本控制天生就有「誰負責、誰審過、改過什麼」。再分成三層：任何團隊都能在 Domain 層自己開區域、一位同事核准就上架；用的人多了升到 Core 層，由團隊維護、平台團隊審查；最通用的約 100 個放進 Always-on 層，新人第一天就有。

另外用一個叫 aifx 的命令列工具，讓同一套 skill 在 Claude Code、Codex、OpenCode 等不同 AI 代理之間通用，換工具不用重裝。

3. 用「有 vs. 沒有」的盲測，確認 skill 真的有幫助

Uber 不靠感覺判斷 skill 好不好。他們拿真實的提問各跑兩次，一次有 skill、一次沒有，再請一位不知道哪個是哪個的評審（盲評）挑比較好的答案。結果大多數 skill 有幫助，例如資料倉儲查詢 skill 讓答案在 87% 的比較中勝出，工具錯誤少了很多；但也有幾個 skill 的效果落在雜訊範圍內，代表模型自己已經會了。

兩個反直覺的發現：模型越強，說明寫太多字反而會拉低表現，所以他們也測試刪字；另外，通過率 70%–90% 的評測（evals）有時比 100% 更有用，因為全部通過可能代表測試根本沒抓到差異。

4. 固定的步驟交給程式，省下大量成本

AI 代理每做一步都要「讀進腦子裡」，讀越多越貴。Uber 發現，預設安裝的工具伺服器會在你還沒開口前，就把 100 多個工具的說明（5 萬到 7 萬個令牌）全塞進去；查一張 50 列的寬表，結果也整包倒進來。改用 Code Mode 後，skill 用一行指令呼叫工具，結果寫進檔案，AI 代理只讀它需要的那幾行，同一個查詢估計從約 140 萬個令牌降到約 900 個。

其他省錢槓桿也很實用：查資料這類小事派給便宜的小模型、結果很小又一定要用時在載入時就先算好、反覆「去看一下好了沒」的輪詢工作移到背景。原則就是：不需要判斷的事，別讓最貴的大腦去做。

5. 讓 AI 代理自己回報「卡住的地方」

skill 會因為模型升級、工具改版等一千種原因悄悄壞掉，而最先發現的往往是正在用它的 AI 代理。Uber 給每個 AI 代理一個常駐的 log-papercut skill：遇到旗標不能用、文件寫錯、指令出錯卻顯示成功這類小毛病，就寫一份格式固定的回報（試了什麼、預期什麼、發生什麼、怎麼修），送到 skill 負責人的儀表板。

回報會被分組、寫成測試案例、由 AI 代理起草修正、人審查合併，再重跑測試；之後再出現同樣問題就重新開啟。三個月內累積數千份，修好數百個。人只在「挑出要處理的」和「審查修正」兩步出手。

可以怎麼開始

  1. 把你最常重複交代 AI 的一件事寫成 skill：描述寫清楚「什麼時候用」，步驟編號、一步一個目標，並附上「出錯時怎麼辦」的對照表。
  2. 挑幾個真實的提問，分別在有和沒有這個 skill 的情況下各跑一次，比比看哪個答案比較好；沒有差別就考慮刪掉或精簡它。
  3. 把每次都一樣、不需要判斷的步驟改成腳本，讓 AI 代理只讀結果中需要的部分。
  4. 在 skill 裡加一句：遇到卡住或說明不符的地方，就照「試了什麼、預期什麼、發生什麼、怎麼修」記下來，定期回頭修正。

以上步驟取自原文的 TL;DR、linter 檢查項目與 papercut 做法，順序與措辭是譯者整理的。
