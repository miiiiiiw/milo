你的程式代理讓你成了主管

Your coding agents made you a manager

作者：Addy Osmani（@addyosmani）

原文：https://x.com/addyosmani/status/2119332146485891501

日期：2026-11-08（台北時間 15:32；UTC 07:32）

備註：繁體中文翻譯，僅供個人閱讀。

管理代理所需的技能，幾乎就是管理團隊所需的技能，而你不必當上主管才能學會它們。

如果你整天都在跟程式代理（coding agent）打交道，那你就是在做管理。你反覆挑選任務、撰寫指示、委派、追蹤進度、評估結果，並決定什麼可以上線。能把代理用得最出色的工程師，不一定是最擅長提示詞工程（prompt engineering）的人；而是那些有意或無意學會了如何管理的人。

這也許是個不太受歡迎的想法。我欣賞的許多工程師選擇了個人貢獻者（IC）職涯路線，正是因為他們想貼近實際工作。他們看過朋友變成主管後，整個人消失在行事曆裡。但我並不是要你變成那種主管。我這裡用的「管理」有特定含義：透過促成他人的工作，產出好的結果。我也絕不是在說代理可以取代主管或同事。

你對壞主管的每一個抱怨，都是一份與代理互動的錯誤回報（bug report）。想想交接（handoffs）。如果你經歷過糟糕的交接，可能拿到的是模糊的要求、缺少脈絡，或期望一直在變。對 IC 來說好消息是：你當了多年接收端，或許就知道好的交接長什麼樣子。

我以前寫過，你的程式代理需要一位主管。我也寫過委派的潛在風險——認知投降（cognitive surrender）。這篇文章會把優秀工程主管的做法，與我們在使用與打造 Claude Code 過程中學到的東西對照。各節大致依影響力排序，所以槓桿最大的習慣（most high-leverage habit）會先出現。

給它一個檢驗自己工作的方式（Give it a way to check its work）

最佳實踐（Best practice）： 提供代理一個驗證其工作的機制，例如測試套件、建置或螢幕截圖，並要求它把結果拿給你看作為證明。

反模式（Anti-pattern）： 把「看起來完成了」（looks done）當成確認。這會迫使你親自做所有驗證，等於自己變成代理的測試套件。

問一位經驗豐富的主管，他們如何在不讀完一切的情況下，確信團隊產出的是好工作——他們會談防護欄（guardrails）：CI、程式碼審查、儀表板、on-call 等等。沒有建立防護欄的新手主管，最後會什麼都自己驗證，一個季度內就成了瓶頸（bottleneck）。代理也一樣。如 Claude Code best-practices guide 所說明的，代理會在工作「看起來完成」時停下。如果沒有驗證機制，「看起來完成」就是代理僅有的驗證。提供驗證機制，能讓代理完成工作、跑驗證、看到失敗，再自行修正。對 UI 變更來說，這可能意味著真的在瀏覽器打開頁面，反覆調整直到能用、也好看。

驗證機制幾乎可以是任何東西，只要能產出明確的通過／失敗（pass/fail）結果。想想測試、建置結束碼（build exit codes）、linter、diff 腳本，以及螢幕截圖。該指南指出，執行這些驗證的那道指令，是你 CLAUDE.md（代理每次工作階段開始時會讀的指示檔）裡最有用的一行。一旦有了驗證機制，你可以用這些方式把它帶進工作流程：

  • 要求（Ask）。「改完之後跑 auth 測試，持續修正直到通過為止。」（"Run the auth tests after, and continue until they pass."）
  • 設定目標（Set a goal）。 用 /goal，會有另一個模型在每一輪之後跑條件檢查，這在做長時間背景工作時最有用。
  • 強制（Enforce）。 Stop hook 可以阻止這一輪結束，直到型別檢查通過。
  • 讓它被審查（Have it reviewed）。 /code-review 會把 diff 送給一個新的子代理（subagent）（沒看過你們對話的那個）審查，就像作者不會核准自己的 PR。

你甚至可以控制審查的範圍。如果你叫它找問題，它總會找到東西。但如果你叫它找正確性問題、忽略風格，它就會那麼做。這也是優秀主管學會如何索取回饋的方式。Claude Code 工具組裡大部分功能，都是在收緊這個迴圈。Skills、hooks、子代理與 MCP，都是為了橋接「做完工作」與「驗證工作」之間的落差，好讓你的注意力只放在代理無法自行驗證的事上。這正是經驗豐富的工程主管在做的事。

設定清楚的脈絡（Set clear context）

最佳實踐（Best practice）： 提供一份代理無法只靠檢查 repo 就知道的清楚摘要，包括：任務目標與為何重要、限制條件、範圍外項目，以及成功標準。

反模式（Anti-pattern）： 只丟一行任務，真正的期望卻還留在你腦子裡；或在簡報裡塞滿代理讀程式碼就會發現的東西。

有效的主管會清楚描述期望的結果、限制與目標。他們說明工作該達成什麼，但把「怎麼做」的自由留給執行者。在軍方，這叫指揮官意圖（commander's intent）。在 Netflix，他們叫它「脈絡，而非控制」（context, not control）。

與代理共事的挑戰在於，很難知道代理缺了哪些脈絡。程式代理在每個任務上做的第一件事，就是讀你的程式碼。目前的模型很擅長從你的資料夾結構、慣例與測試設定裡抓重點，速度快到你根本來不及描述完。

在動筆之前，先想想代理自己能弄清楚什麼。如果代理能在你的程式碼裡讀到、而且它真的會去讀，你就不必說。把字數花在 repo 裡沒有的部分——例如會議決策、某人部署的內部流程、為什麼這件事重要，以及這一次「完成」代表什麼。

拿一個模糊任務「讓儀表板更快」當例子，把它寫成提示詞。這裡的數字只是舉例。

原文（English）
Get p95 load time for the /team dashboard under 2s for orgs with 10k+ members.

Why: enterprise admins open it daily, and slow loads are their top support ticket.

Constraints: no schema changes; keep the API response shape.

Out of scope: UI changes; caching the whole page.
Check: run scripts/perf/team.sh and show before and after numbers.
繁中（Traditional Chinese）
讓 /team 儀表板在成員數 1 萬以上的組織中，p95 載入時間低於 2 秒。

原因：企業管理員每天都會打開它，載入緩慢是他們最常提的支援工單。

限制：不可變更 schema；維持 API 回應形狀不變。

範圍外：UI 變更；快取整個頁面。
檢查：執行 scripts/perf/team.sh，並出示前後數字。

你不必每個任務都這樣做。如果是探索性工作，寫個籠統的提示詞完全沒問題。你之後再一點一點收斂就好。若你還沒準備好寫提示詞，可以讓代理面試你，直到它能寫出規格，把規格存成檔案，再開一個新工作階段讓代理依規格實作。之後你也可以用那份規格來回顧對照。

你可能還需要給代理存取其他工具的權限，例如議題追蹤器、錯誤儀表板或團隊聊天。把代理當成你團隊裡的新人一樣對待。如果是它本來就知道的 CLI 工具，像 gh，你常常什麼都不用交代。

讓每次修正都能累積（Make every correction compound）

最佳實踐（Best practice）： 當你糾正同一件事超過一次，就把它寫進團隊的 CLAUDE.md，或做成共享 skill。過一段時間再檢查，新模型是否已降低這些修正的需要。

反模式（Anti-pattern）： 每個工作階段都手動糾正同一件事，或依賴只存在於你自己機器上的默會知識（tacit knowledge）。

能把 CLAUDE.md 價值最大化的團隊，會每隔一陣子就更新它，並把值得預防的錯誤教訓寫下來。有些團隊甚至在程式碼審查裡提到 @claude，把回饋變成永久政策。讓 CLAUDE.md 保持精簡。適合放進去的類型包括：

  • 如何驗證某件事（精確指令）
  • 程式碼裡容易誤導的區塊
  • 不存在於 repo 的決策
  • 任何你糾正過兩次的事

這些都是書面資訊「會複利」（compounding）的例子。它比人員換隊、模型被替換活得更久。

讓它自行決定，只強制不能通融的事（Let it decide, and enforce only what can't bend）

最佳實踐（Best practice）： 預設讓代理自行決定；只有對「必須永遠發生／永遠不能發生」的少數事項，才使用硬性強制（hard enforcement）（例如 hooks、deny rules）。

反模式（Anti-pattern）： 用全大寫寫規則、為可有可無的偏好定義 hooks，或在新模型早已超越舊習慣之後，還死守那些舊習慣。

Andy Grove 的《High Output Management》把這描述為任務相關成熟度（task-relevant maturity）：監督程度應取決於某人在該特定任務上的表現歷史，而非其整體能力。

給新主管的一句老建議也說了同樣的事：給人們比你舒服一點還多一點的空間，同時支援他們、並要他們負責。

Claude Code 把這點講得很明白：prompts、CLAUDE.md 與 skills 是模型可以斟酌、選擇是否執行的「請求」（requests）；hooks、deny rules 與 managed settings 則是一律強制的「要求」（requirements）。多數情況下，你會希望代理做判斷。常常是模型看著真實程式碼，比你事先設好的規則更適合判斷某條準則是否適用。用強制來設定硬性要求，例如「永遠不要編輯產生出來的 client」或「一定要跑 license-header 腳本」。特別是，新的終端機與 VS Code 工作階段會以自動模式（auto mode）啟動，並有一個分類器（classifier）過濾不安全行為，例如部署到正式環境，或強制推送蓋過別人的工作。

該指南的建議有兩面。如果你不斷加重 CLAUDE.md 某一行的語氣，代理卻還是沒聽進去，那就該變成 hook。如果某個 hook 表達的是偏好而非要求，就該拿掉，改讓代理做主。這就像你的團隊決定淘汰一個不再有用的流程。這也意味著換了新模型時要調整。該指南維持一份你可以停掉的習慣清單：全大寫指示、「think harder」（現在努力程度是設定了），以及「don't be lazy」。對目前模型來說，這些往往導致過度強制（over-enforced）的規則與過度勞動（overwork）。對代理而言，過度流程（over-process）就是新的微觀管理（micromanagement）。

先規劃再動手寫（Plan before it builds）

最佳實踐（Best practice）： 在代理開始寫程式前，先談定一份雙方同意的計畫；審視底層假設，並把任務切成互不重疊的平行工作。

反模式（Anti-pattern）： 讓多個代理同時處理重疊任務，然後整個下午都在解 merge conflict 與重複決策。

一個好的工作流程是：先進入計畫模式（plan mode），反覆打磨計畫到正確為止，再委派寫程式。有了好計畫，模型常常能一次做完。對較大任務，用第二個工作階段以 staff engineer 的眼光審計畫；這是設計審查（design review），也是抓到走錯方向最便宜的地方。審計畫時，找底層假設（在一對一裡，這會是問：「你對什麼不確定？」）。

拆解工作越來越常被委派給代理。Claude Code 的 /batch 會把一個大型機械式變更拆成 5 到 30 個任務、顯示計畫、在各自的工作樹（worktree；repo 的獨立 checkout）裡執行，並為每個任務建立一個 PR。你不再需要自己切工作，只要檢查切片有沒有重疊，並確保共用介面先落地。沒有這一層，你可能會得到假性的平行度（false level of parallelism）。五個代理搶重疊任務，不會帶來五倍產出，而是一份有五個作者的 merge conflict。

及早導航，果斷重來（Steer early, reset fast）

最佳實踐（Best practice）： 盯著第一分鐘並導航代理。一看到它偏離就糾正。若你已經兩次糾正失敗，就開一個全新工作階段、用更好的提示詞重來。

反模式（Anti-pattern）： 再加第三次、第四次糾正，而不是改請求本身。

經驗豐富的主管知道：若一個有能力的人連續失手多次，問題可能在上游——指示、脈絡或範圍。代理版更直接：代理一偏離，就按 Esc。若你已兩次糾正失敗，清掉工作階段、寫更好的提示詞，把學到的教訓寫進去。第三次糾正多半只是再塞更多資訊讓模型反覆重讀、重處理（包括失敗的嘗試）。

便宜的回滾（rollback）也在改變遊戲。/rewind 會把程式碼與對話捲回更早的時間點，讓你能低風險地先試更大膽的作法。好主管對員工也一樣：若撤銷錯誤很便宜，就讓他們試大膽作法。然後事後做回顧（retro），若適用，就把修正通則化進 CLAUDE.md。

委派任務，但絕不委派判斷（Delegate the task, never the judgment）

最佳實踐（Best practice）： 代理做工作，你決定重要的事：產品取捨、安全邊界、什麼可以上線。把每一份 diff 都當成你會因此被叫起來處理事故那樣對待。

反模式（Anti-pattern）： 因為測試全綠、名稱看起來合理，就核准大型 diff。這不是程式碼審查，這是程式碼背書（code ratification）。

沒有主管能說「那是我下屬交付的，不是我」。你跑的每一個代理也一樣。我自己也掉進過這個陷阱。我叫代理研究與競爭對手的落差，並寫本地 PR 來補齊。我讀了研究、掃過程式碼，幾乎就要推上去——那些變更會為使用者增加複雜度、卻幾乎沒有收益。我委派了工作，也幾乎委派了決策。這很容易掉進去：600 行的 diff、名稱看起來合理、測試全綠，就核准。

這樣拆任務是合理的：讓代理處理風格、linting、審查後續、典型 bug 與單元測試；但讓人類處理安全邊界、合規與產品決策。

協調也一樣。代理可以追蹤交接，但在互相競爭的請求之間做決定、以及讓人真正承諾，仍是人類的工作。

你不必身處每一次變更的內迴圈（inner loop）。你需要擁有的是外迴圈（outer loop）：限制是什麼、你實際讀了多少輸出、你保留什麼證據，以及什麼必須由人類簽核。並保持變更小（keep changes small），因為審查的單位就是理解的單位（the unit of review is the unit of comprehension）。

設計不需要你盯著的執行流程（Design the run that doesn't need you）

最佳實踐（Best practice）： 在部署一個自主任務之前，定義完成條件、自我驗證、邊界、防護欄，以及人類核准點。

反模式（Anti-pattern）： 睡前啟動一個長跑行程，卻沒有完成定義或停止點，隔天早上才發現模型整晚都在錯誤前提下工作。

跨層主管（skip-level managers）不管理個別工程師的工作；他們管理的是目標、防護欄、檢查點與負責人。AI 代理正走上一條類似軌跡。它們已經把任務的一部分委派給子代理，也能依排程、在 CI 失敗後，或在新 PR 開啟後自主執行。前沿是能自主啟動、自我驗證，並只在需要決策時才呼叫人類介入的自治系統（self-governing systems）。

角色從「控制工作階段」轉向「設計你的迴圈」（designing your loops）。設計無人值守（unattended）執行時要問自己的五個問題，跟好主管在給資深工程師一個專案然後去度假前問的問題一樣：

  1. 它知道「完成」長什麼樣子嗎？（目標條件、規格檔，或它必須變綠的失敗測試。）
  2. 它有自我驗證機制嗎？（測試套件、Stop hook，或審查步驟。）
  3. 它的邊界是什麼？（權限控制、沙箱（sandbox）、工作樹（worktree），或它被允許推送的那一個分支。）
  4. 它的防護欄是什麼？（輪次上限或花費上限。）
  5. 輸出放哪裡、誰核准？（一份 PR 或摘要，以及任何不可逆動作的人類核准。）

該指南還有兩個主管會認出是好做法的習慣：試點（pilot）——先讓批次工作在三個檔案上跑、迭代提示詞，再跑其餘；以及在信任任何新東西無人值守之前，先看前幾次執行（watch the first few runs）。把它想成試用期（probation period）。

擴充驗證，而非注意力（Scale verification, not attention）

最佳實踐（Best practice）： 只有在檢查、目標與全新脈絡的審查者（fresh reviewers）能接手監看的速度下，才擴大代理使用量；除了吞吐量，也要量測品質。

反模式（Anti-pattern）： 開了比你能仔細審查還多的工作階段，並用「AI 寫了多少程式碼」來衡量成功。

主管很快就學會自己的控制幅度（span of control）。超過某個直屬人數，每個人分到的主管時間變少，品質也跟著掉。代理也一樣。我稱之為編排稅（orchestration tax）：過了最初幾個代理之後，每多一個代理，需要你的注意力會比上一個更多。多數日子我跑四到五個背景代理與幾個本機工作階段，有些日子那已經太多了。

管理大量工作階段，靠的不是超級專注，而是把大部分監看委派給自我評估、目標與新脈絡審查者（new-context reviewers），把注意力留給決策。用通知取代輪詢、以及背景工作的集中視圖也很有幫助。你無法靠「監看得更多」來擴充代理數量，只能靠「需要監看得更少」。然後量測系統而非活動（measure the system rather than the activity）。有用的指標包括 PR 週期時間（cycle time）、新進員工上手時間，以及 revert 或重做的頻率。量測「AI 寫的程式碼百分比」不是有用的目標，因為你要的是品質與可靠性。Grove 用「對應的反指標（countermeasure）」來量測的規則在此適用：如果你量測合併的 PR 數，那就也要量測 revert 與重做。

決定什麼不該做（Decide what not to build）

最佳實踐（Best practice）： 問誰需要它、你如何知道它有效、什麼會讓你停手，並限制進行中工作／在製品（WIP）。

反模式（Anti-pattern）： 把每個看起來合理的點子都丟進 PR；畢竟建起來很便宜。你現在會有一個團隊必須審查、做安全把關與維護的雜物抽屜（junk drawer）。

主管最重要的詞往往是「不」。有了代理，說「不」更難。開工幾乎免費，你中午前就能把任何合理點子丟進 PR。但你現在會有一堆 PR，團隊得審查、做安全把關、支援與維護。審查與驗證才是現在的稀缺資源（scarce resources）。

事實上，那些老派的管理問題現在比以前更重要。誰要求的？我們如何量測成功？我們如何知道何時該停？若建起來很便宜，難問的不是「能不能？」（can we?），而是「該不該？」（should we?）。

類比失效之處（Where the analogy breaks）

最佳實踐（Best practice）： 遵循管理最佳實踐，但要把代理模型的差異算進去，例如便宜的重做、它們多麼容易同意，以及每換一次模型就會變動的強項。

反模式（Anti-pattern）： 以為代理就像初階工程師，或以為你能跑五個代理，就準備好管理五個人。

這個類比有用但不完美，而這份工作的最佳實踐者清楚它不完美之處：

  • 管理人更難，而且技能不會反向轉移。 你跑過五個代理，並不代表你準備好管理五個人。動機、衝突、職涯發展，或長達數月的信任建立，都沒有對等物。
  • 重做幾乎免費。 你可以問代理一些你絕不會問人的事。若白板前發生技術辯論，代理可以做出兩三種選項讓你比較。
  • 代理沒有經驗，只有筆記本。 Auto memory 只在一台機器上記筆記。它們不會轉移到隊友的工作階段。它們不是你職涯中累積的經驗與判斷，那些教訓你得為整個團隊寫下來。
  • 代理急切又自信。 若你叫優秀工程師做錯事，他們會推回。代理更可能照做，而你容易過度信任它們。在沃頓商學院關於認知投降的研究中，參與者多數時候接受了錯誤的 AI 答案，而且變得更有自信。你可以要求代理反駁自己的答案，來對抗這種過度自信。
  • 你只有一種代理原型，而且每隔幾個月就變一次。 人類團隊有多元技能與強項。你所有的代理都有相同的強項與弱點，並隨每次模型發布而改變。
  • 你仍得訓練初階工程師。 當代理接管了初階工程師用來學習基本功的入門工作，你就必須作為主管，有意地創造那些練習機會。
  • 人類團隊仍然重要。 有時你可能花一整天管理代理，卻沒意識到你擠掉了打造凝聚團隊所需的時間。別這樣做。

你不需要那個職稱（You don't need the title）

最佳實踐（Best practice）： 把心力放在讓好軟體發生：設定脈絡、定義完成，以及好好審查。

反模式（Anti-pattern）： 一邊用程式碼行數評估自己，一邊跑著指示不足、未經檢查的代理。

優秀的 staff engineer 一直都是這樣。他們寫設計文件。他們設定脈絡。他們做徹底的審查。他們讓身邊的人變得更好。代理讓所有工程師在第一天就能這樣做。它們給你一堂管理速成課（crash course on management）。你在幾分鐘內得到回饋，而不是幾個季度。你可以撤銷自己的錯誤。這份工作正變得比較不是「寫出程式碼」，而是「成為好程式碼之所以被寫出來的原因」。

沒有人生來就是偉大的主管（或偉大的工程師）。你用一直以來的方式建立技能：透過練習。但有了代理，練習很便宜。

試試這些做法：

  • 每個任務都需要一個它能跑的檢查。要求看證明。
  • 告訴代理它看不到的，省略它看得到的。
  • 寫程式前先把計畫談清楚。
  • 糾正過兩次？記進 CLAUDE.md。重複的工作流程？做成 skills。
  • 兩次糾正失敗？重來並改寫提示詞。
  • 審查 diff 時，想像你會因此被叫起來處理事故。

你不必想當主管。但能把代理用得好的工程師，終究都會在這一路上學會管理。

以下為譯者整理，非原文內容。

這篇在說什麼

「程式代理」（coding agent）是一種能自己讀程式碼、動手修改、執行測試的 AI 助手，Claude Code 就是一例。你交代一件事，它會自己拆步驟去做。

Addy Osmani 的觀點是：整天和這種代理一起工作的人，其實已經在當主管了。挑任務、下指示、委派、追進度、驗收、決定什麼能上線，這些都是管理的工作。他把好的工程主管怎麼帶人，和他們使用與打造 Claude Code 學到的經驗，一節一節對照，共十二節，大致依影響力排序，最有槓桿的習慣排在最前面。

為什麼值得學

你不必是工程師，這些原則也用得上。只要你曾把工作交給 AI，不論是整理資料、寫文案或做研究，就會遇到同樣的問題：它說做完了，到底做對沒有？要交代多少才夠？錯了要糾正幾次？

反過來也成立：作者說，你對爛主管的每一個抱怨，都是一份「怎麼跟代理合作」的錯誤回報。你當過被交辦的一方，就知道好的交接長什麼樣子。這篇把這份直覺整理成可以照著做的習慣。

你可以帶走的重點

1. 給它一個檢查自己的方法

這是作者排在第一、影響最大的習慣。代理（agent）做事有個傾向：看起來做完了就停下來。如果沒有任何檢查，「看起來做完了」就是它唯一的標準，而替它把關的工作全落回你身上。

所以交辦時，順便給它一個會明確回答「過／不過」的檢查：自動測試、建置是否成功、一張畫面截圖都行。讓它自己跑、自己修，最後把結果拿給你看，當作完成的證明。

就像請人整理報表時說「做完請跟上個月的總數對一下，對得上再交」，而不是交來後由你一格一格核。

2. 只說它不知道的事

程式代理接到任務的第一件事，就是去讀你的程式碼，資料夾怎麼放、慣例是什麼，它很快就摸清楚。所以不必重述它自己看得到的東西。

你的字數該花在它看不到的地方：會議上做的決定、某人私下的部署流程、這件事為什麼重要，以及這一次怎樣才算完成。原文把一句含糊的「讓儀表板更快」改寫成一段交辦：目標、原因、限制、範圍外、怎麼檢查，五項一目了然。

軍隊叫這個「指揮官意圖」（commander's intent），Netflix 叫「脈絡，而非控制」：講清楚要達成什麼，怎麼做留給執行的人。

3. 同一件事糾正兩次，就寫下來

如果每次開新對話都要重講同一件事，就把它寫進一份代理每次開工都會先讀的說明檔（Claude Code 裡叫 CLAUDE.md），或做成可以共用的 skill。

適合寫進去的：怎麼驗證（確切的指令）、程式裡容易誤導人的地方、沒寫在程式裡的決定，以及任何你糾正過兩次的事。寫下來的東西會「複利」：換了隊友、換了模型，它都還在。

4. 大多讓它判斷，只對底線硬性規定

Claude Code 把規則分成兩種：「請求」是模型可以斟酌的建議，「要求」則一律強制執行。大部分時候，看著實際程式碼的模型，比你事先定好的規則更會判斷。

只有「永遠不能做」或「一定要做」的少數事，才值得變成硬規定。反過來，用全大寫寫規則、叫它「think harder」或「don't be lazy」這些老習慣，對現在的模型多半只會造成過度執行。作者一句話總結：對代理而言，流程過多就是新的微觀管理。

管理學老話也是這樣說：給人比你舒服的程度再多一點空間，同時支援他、要他負責。

5. 先對好計畫，再動手

在代理開始寫之前，先跟它談出一份雙方都同意的計畫，並特別找出它的隱含假設，就像一對一面談時問同事「你對哪裡沒把握？」。計畫好，模型常常一次就能做完。

要同時派好幾個代理時，先把工作切成互不重疊的片段。否則五個代理搶著做重疊的事，得到的不是五倍產出，而是一場有五位作者的合併衝突（merge conflict，也就是幾個人改到同一處、得手動擺平）。

6. 早點導正，兩次不行就重來

開頭第一分鐘最值得盯。一看到它走偏，立刻糾正。但如果已經糾正兩次還不行，不要再試第三次，因為問題多半出在你的交辦本身。這時應該清掉這次對話，把學到的教訓寫進一個更好的提示詞，重新開始。

原文的理由很實際：第三次糾正只是讓模型多讀一堆資訊，連同之前失敗的嘗試，一再重讀、重新消化。

7. 工作可以交出去，判斷不行

代理負責做，你負責決定重要的事：產品取捨、安全邊界、什麼可以上線。沒有主管能說「那是我下屬做的，不是我」。

作者自己就差點中招：他請代理研究和競爭對手的差距、寫好補齊的修改，讀了研究、掃過程式碼，差點就推上去，但那些改動只會替使用者增加複雜度、好處很少。這種陷阱很容易掉進去：600 行的修改、名稱看起來合理、測試全綠，按下核准。作者說那不叫審查，叫「背書」（code ratification）。

合理的分工：格式、例行修正、常見 bug、單元測試交給代理；安全、合規、產品決策，以及在互相衝突的需求之間做取捨，留給人。

8. 放手讓它自己跑之前，先問五個問題

代理已經能排程自動執行，甚至在你睡覺時工作。最怕的是睡前丟一個沒有終點的任務，隔天才發現它整晚在錯的前提上努力。

作者給的五個問題，就像好主管把專案交給資深工程師、自己去度假前會問的：它知道「完成」長什麼樣嗎？它有自我檢查的方法嗎？它的活動範圍到哪裡？有沒有次數或花費上限？成果放哪裡、誰來核准？

新東西先小規模試跑，例如批次工作先跑三個檔案，修好提示詞再跑其餘的；前幾次也要親自看，作者稱這是「試用期」。

9. 能管多少代理，看檢查，不看你多專注

主管很快就會發現自己管得動的人數有上限。代理也一樣，作者稱之為「編排稅」（orchestration tax）：過了最初幾個，每多開一個代理，都要比上一個更費你的注意力。他自己多數日子跑四、五個背景代理加幾個本機工作，有些日子就已經太多。

要擴大規模，不是靠盯得更緊，而是讓自動檢查、目標和全新的審查者接手監看，你只把注意力留給決策。衡量成果時也別看「AI 寫了多少程式碼」，要看品質與可靠度，例如改動被退回或重做的頻率。

10. 做得出來，不代表該做

主管最重要的一個字，往往是「不」。有了代理，開工幾乎免費，任何聽起來合理的點子中午前就能變成一份 PR（pull request，送交團隊審核的修改）。但每一份都要有人審查、把關、維護，真正稀缺的是審查與驗證的人力。

所以老派的問題反而更重要：誰需要它？怎麼知道它成功了？什麼情況該停？當「做不做得到」不再是問題，難問的就變成「該不該做」。

11. 代理不是人：這個比喻的極限

作者也提醒，「把代理當下屬管」只是好用但不完美的比喻：

管人比管代理難得多，跑得動五個代理不代表帶得動五個人；代理重做幾乎不花成本，可以叫它一次做兩三個方案來比較；它沒有經驗，只有一本筆記（Auto memory 只記在一台機器上）；它急著配合又充滿自信，叫它做錯事也不太會反駁，可以請它反駁自己的答案；所有代理的長處和短處都一樣，而且每次換模型就變。

還有兩件人的事不能忘：初階工程師需要靠入門工作練基本功，主管得刻意替他們保留練習機會；也別讓管理代理擠掉經營團隊的時間。

12. 不需要主管頭銜，也能練管理

好的資深工程師一直都在做這些事：寫設計文件、設定脈絡、仔細審查、讓身邊的人變更好。代理讓每個人第一天就能練習，而且回饋幾分鐘就到，不必等好幾個季度。

作者的結論是：這份工作正從「寫出程式碼」，轉向「成為好程式碼能被寫出來的原因」。

怎麼開始

  1. 下一次交辦時，附上「怎麼檢查」。告訴 AI 做完要用什麼標準自己核對，並請它把核對結果一起交給你。
  2. 交辦前先刪一刪。它自己看得到的資料不用重述；把它看不到的寫清楚：為什麼要做、有哪些限制、什麼不用做、怎樣算完成。
  3. 大一點的任務，先要計畫。請它先列出打算怎麼做，並問它「你對哪裡沒把握？」，確認了再讓它動手。
  4. 開一份「重複糾正」筆記。同一件事講第二次時就記下來，下次開工前先給它讀。
  5. 糾正兩次沒用，就重新開始。開一個新對話，把剛學到的教訓寫進新的交辦裡。
  6. 驗收時，當成要由你負責。原文的說法是：審查每一份修改時，都想像出事時被叫起來處理的會是你。
