讓 Claude Code 發揮更大效用：告訴 Claude 它看不見的東西、給它一個可以執行的檢查，並強制執行不能有例外的規則。

Claude Code 的設計，讓你在全新的工作階段（session）裡下的第一個一般提示詞（prompt），在大多數情況下就已經能做對事，你不需要做任何設定。

例如：

  • 為了讓指令不必由你逐一核准就能執行，新的終端機和 VS Code 工作階段都從自動模式（auto mode）開始。
  • 為了讓你的主要對話保持專注，同時讓彼此獨立的工作平行進行，Claude 會把工作委派給子代理（subagent），只有在必要時才回來向你報告。
  • 為了讓長時間的工作階段不必靠你管理也能繼續下去，你的對話會在脈絡視窗（context window）填滿之前自動壓縮（compact）。

這一頁談的，是預設值不夠用的時候該怎麼辦。這通常發生在你的專案有一些 Claude 光看程式碼看不出來的知識、規則或限制：

  • 只存在於某個人腦袋裡的部署流程
  • 一個絕對不能被讀取的檔案
  • 一項必須通過才算完成的檢查
  • 一筆你必須控制在額度內的預算

沒有任何預設值能知道你專案的這些事，所以這正是你在自己這邊做一點設定就會有回報的地方。

當工作階段沒有照你預期的方向走，幾乎都是下面這幾種情況之一：

  • Claude 做出來的東西和你心裡想的不一樣，或者每次工作階段一開始，它都得重新摸索同一件事。它缺少無法靠讀儲存庫（repo）取得的資訊。請看告訴 Claude 它看不見的東西（Tell Claude what it can't see）。
  • Claude 說它做完了，但其實沒有完全做完，通常是因為它沒有辦法檢查自己的工作。請看給 Claude 一個可以執行的檢查（Give Claude a check to run）。
  • Claude 做了這個儲存庫（repo）裡絕對不能發生的事，或跳過了一個一定要做的步驟。光靠提示詞（prompt）無法保證這兩件事。請看強制執行不能有例外的規則（Enforce the rules that can't have exceptions）。
  • Claude 做對了，但花的時間、令牌（token）或權限提示，比這項任務值得的還多。請看調整預設值（Change a default）。

讓 Claude 在沒有你的情況下執行（Let Claude run without you）會把同樣這四點套用到無人看管的執行上，而你可以不用再做的事（What you can stop doing）則列出了現在的模型已讓它變得不必要的建議。

註（Note）

整個團隊的設定在另一頁：為你的組織設定 Claude Code（Set up Claude Code for your organization）。

確定性與非確定性的指示Deterministic and non-deterministic instructions

你給 Claude Code 的每一則指示，都屬於下面兩種之一：

  1. 非確定性（non-deterministic）：由你寫下指示，由 Claude（模型）來讀。這可以是你的提示詞（prompt）、CLAUDE.md，或技能（skill）。接著由模型決定要怎麼運用這些資訊。它通常會照你的指令做，而且現在的模型很擅長在不需要太多脈絡的情況下理解你的意圖，但無法保證它一定會照你的指示做。它仍然可能決定不做，或去做別的事。
  2. 確定性（deterministic）：由你設定指示，由 Claude Code（工作環境〔harness〕）必須執行。這可以是 hook、拒絕規則（deny rule）或受管設定（managed setting）。不論模型當時決定怎麼做，Claude Code 每一次都會套用。

大部分時候，你會希望由 Claude 來決定。幾乎每一條準則都有例外，而現在的模型很擅長閱讀眼前的程式碼，並判斷一條準則是否適用於當下的情況。面對實際的程式碼，Claude 通常比你事先寫好的規則，更適合做出這個判斷。

確定性（deterministic）的那一種，是用在你想確保某些事一定會發生（或絕對不會發生），不論模型怎麼決定。這不必是什麼大事。自動模式（auto mode）已經會擋下那些重大的事，像是正式環境的部署，或是強制推送（force push）蓋掉別人的工作。它通常是針對你的專案的某個具體規定，可以細到你想要的程度：

  • 絕不編輯 src/gen/ 裡自動產生的用戶端程式碼
  • 建立檔案之後，一律執行授權標頭（license-header）腳本

這兩條你都可以寫成 CLAUDE.md 或提示詞（prompt）裡的一行，Claude 幾乎每次都會照做。但不論你把措辭寫得多強烈，Claude 在某一輪是否照那一行去做，終究還是由 Claude 決定。

提示（Tip）

如果你一直在 CLAUDE.md 的某一行加重強調，Claude 還是漏掉，那就表示這一行該放進 hook。反過來也成立：如果你為了只是偏好的事設了 hook，就把它們刪掉，讓 Claude 自己決定。

告訴 Claude 它看不見的東西Tell Claude what it can't see

提示（Tip）

只寫下 Claude 讀儲存庫（repo）找不到的東西，或是它否則每個工作階段都得花時間重新摸索的東西。

Claude 每個任務一開始都會先讀你的程式碼，而現在的模型在這件事上非常厲害。它們會找出你的檔案結構、慣例、測試框架，以及現有元件是怎麼建的，通常比你解釋的速度還快。這表示你可能忍不住想寫給它的東西，Claude 大多早就知道了。

它找不到的，是那些從來不在儲存庫（repo）裡的資訊：

  • 你的團隊在某次會議上做的決定
  • 只存在於某個人腦袋裡的部署流程
  • 整合測試需要的環境變數

另外還有一種資訊，確實在儲存庫（repo）裡，但要花幾分鐘挖掘才找得到，而 Claude 每個工作階段一開始都得重新挖一次。

在你為 Claude 寫下任何東西之前，可以先做一個好用的測試：

  1. 它能不能靠讀程式碼找到這件事？
  2. 它會不會真的去找？

如果兩個答案都是「會」，就不要寫。

寫一個具體的提示詞Write a specific prompt

具體的提示詞之所以有幫助，是同樣的道理：它給了 Claude 它原本沒有的資訊。如果你一開始就指名檔案、描述症狀，並說明「修好」是什麼樣子，通常就能省下之後一輪的修正。

兩種合理做法之間的偏好也一樣：Claude 無法從程式碼讀出這一點，所以如果你在意它選哪一個，就一開始說清楚。

不要這樣（Instead of）改試這樣（Try）
"fix the login bug"
「修好登入的錯誤」		"users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"
「使用者回報工作階段逾時後登入會失敗。去看 src/auth/ 裡的令牌（token）重新整理，寫一個會失敗的測試來重現它，然後修好它」
"add a calendar widget"
「加一個日曆小工具」		"follow the pattern in HotDogWidget.php and build a calendar widget that lets you pick a month and page between years. no new libraries"
「照著 HotDogWidget.php 的寫法，做一個日曆小工具，讓人可以選月份，並在不同年份之間翻頁。不要用新的函式庫」

如果你手上已經有 Claude 需要的東西，就直接交給它，不要用描述的：

  • 檔案：輸入 @ 和路徑，把檔案內容放進你的訊息。
  • 圖片：把設計稿或錯誤的截圖貼進提示詞（prompt）。
  • 指令輸出：用 cat error.log | claude -p "what's going on here"，從你的 shell 以管線（pipe）傳進去。

think step by step 或 be thorough 這類片語，是普通的提示詞（prompt）文字，不是關鍵字。控制 Claude 思考多用力的主要方式，是費力等級（effort level），這部分在更換模型與費力等級（Change the model and effort）裡談。這類措辭仍然可以在 Claude 的費力設定（effort setting）範圍內輕推它一下，但無法把它推到超過那個設定。

有一句話確實仍然有用：be ambitious。Claude 傾向保守地解讀請求，只做出剛好滿足請求的最小東西，因為它看不出你原本期待多少。當你想要比較完整的版本，把邊界情況處理好、連自然的後續也一併做進去時，就明說：

範例提示詞（英文原文）

build the settings page from the mockup. be ambitious: empty and error states, the save flow wired up, keyboard navigation, not just the layout

繁體中文對照

照著模擬稿（mockup）做出設定頁面。要有野心：包含空白狀態和錯誤狀態、把儲存流程接起來、鍵盤操作，而不只是版面

這是在告訴 Claude 範圍，只有你知道的事，而不是要它思考多用力。

而當你是在探索，而不是修正某個特定的問題時，像 what would you improve in this file? 這樣模糊的提示詞（prompt）完全沒問題。你會一路多修正一些，而這就是取捨。

先和 Claude 腦力激盪Brainstorm with Claude first

當你還不確定自己到底要什麼，你不必先全部想清楚才下提示詞（prompt）。可以改請 Claude 來訪談你：

範例提示詞（英文原文）

I want to add rate limiting to the public API but haven't thought it through yet. Interview me until you could write the spec, then write it to SPEC.md.

繁體中文對照

我想替公開的 API 加上速率限制，但還沒有想清楚。請訪談我，直到你能寫出規格文件（spec），然後把它寫進 SPEC.md。

Claude 會回來問你選擇題，針對你還沒定下來的部分：每位使用者各自限制，還是每把金鑰各自限制、超過限制的請求會怎麼處理、哪些不在範圍內。它會一直問，直到答案湊成一份規格文件（spec）。

SPEC.md 一旦存在，就開一個新的工作階段來照它建置，讓建置從乾淨的脈絡和一份寫好的完成定義（definition of done）開始。之後在給 Claude 一個可以執行的檢查（Give Claude a check to run）裡，你要把審查者指向的也是這個檔案。

讓 CLAUDE.md 保持簡短Keep CLAUDE.md short

Claude Code 會把 CLAUDE.md 載入每一個工作階段，這表示它裡面的每一行，在每一個任務上都會佔用 Claude 一點注意力，不論相不相關。這就是為什麼這個檔案只放 Claude 光看程式碼推不出來的東西時效果最好：

  • 如何確認這個儲存庫（repo）裡的工作：確切的測試、型別檢查（typecheck）和 lint 指令，以及如何只跑單一個測試檔
  • 程式碼會誤導人的地方：到處都是、但新程式碼絕不能照抄的舊寫法，或是一個看起來沒在用、其實有在用的目錄
  • 不在儲存庫（repo）裡的決定：團隊選定了哪個錯誤處理輔助函式、部署怎麼運作、哪些東西需要經過遷移審查
  • 任何你已經糾正過兩次的事

通過這個測試的 CLAUDE.md 會保持簡短：

CLAUDE.md（英文原文）

# Commands
- Install: pnpm install
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit

# Conventions
- Use the error helpers in src/lib/errors.ts, never throw raw strings
- src/legacy/ is still live but don't copy its patterns into new code

# Gotchas
- Integration tests need DATABASE_URL set, see .env.example

繁體中文對照（指令、檔名與變數名稱不變，只翻譯文字說明）

# 指令（Commands）
- 安裝：pnpm install
- 執行單一測試檔：pnpm vitest run path/to/file.test.ts
- 型別檢查：pnpm tsc --noEmit

# 慣例（Conventions）
- 使用 src/lib/errors.ts 裡的錯誤輔助函式，絕不要直接丟出原始字串
- src/legacy/ 仍在使用，但不要把它的寫法複製進新程式碼

# 陷阱（Gotchas）
- 整合測試需要設定 DATABASE_URL，請看 .env.example

在工作階段裡，執行 /context all，確認 Claude 已載入這個檔案。

請注意，型別檢查（typecheck）那一行只有指令。Claude 需要知道這個指令，才能邊做邊檢查自己的工作。如果你還希望由 Claude Code 強制在 Claude 結束前通過型別檢查，那是 Stop hook 的工作。在這個檔案裡寫一句像 Always typecheck before you finish（結束前一律做型別檢查）的話，大部分時候有效，但不是每次都有效。

你不必從頭寫這個檔案：

  • /init 會根據你的程式碼庫產生一個起始版本。從那裡開始，工作大多是刪行。記憶指南（memory guide）建議控制在 200 行以內。
  • /doctor 會建議刪掉任何 Claude 本來就能從程式碼推出來的內容。
  • /doctor prompt-audit 會標出那些為舊模型寫的指示、指向已不存在檔案的指示，或是互相矛盾的指示。

你的個人偏好放在 CLAUDE.local.md，而不是 CLAUDE.md，並把那個檔案加進 .gitignore，讓它不進入儲存庫（repo）。

註（Note）

如果 Claude 一直忽略確實寫在 CLAUDE.md 裡的某一行，加上 IMPORTANT 大概也沒用。不是這個檔案已經長到那一行被淹沒了，就是那一行是一條不能有例外的規則，這種情況下它該放進 hook。

把規則限定在程式碼庫的某一部分Scope rules to one part of the codebase

如果某條規則只在程式碼庫的某一部分有意義，就把它放進 .claude/rules/，並加上 paths: 篩選條件，讓它只在 Claude 真的在那裡工作時才載入。例如，這個 .claude/rules/api.md 會在處理 src/api/ 底下的 TypeScript 檔案時載入：

.claude/rules/api.md（英文原文）

---
paths:
  - "src/api/**/*.ts"
---
- Validate request bodies with the zod schemas in src/api/schemas/, don't hand-roll checks
- Every new endpoint needs an entry in openapi.yaml, CI fails without it

繁體中文對照（欄位名稱、路徑與檔名不變，只翻譯文字說明）

---
paths:
  - "src/api/**/*.ts"
---
- 請求內容（request body）用 src/api/schemas/ 裡的 zod 結構描述（schema）驗證，不要自己手寫檢查
- 每個新的端點（endpoint）都要在 openapi.yaml 裡加一筆，沒有的話 CI 會失敗

把團隊的作業流程放進技能（skills）Put team procedures in skills

更強的模型懂更多工程知識，但不知道你的團隊怎麼做發布、你的事故處理手冊（incident runbook）寫了什麼，或你希望 API 文件怎麼寫。這類知識要放進技能（skill）：一份存在 .claude/skills/<name>/SKILL.md 的作業流程，或一份團隊知識。

這類東西放在技能（skill）裡，佔用的脈絡也比 CLAUDE.md 少。對於 Claude 能自己啟動的技能（skill），它在每個工作階段都會看到名稱和說明，但只有在任務需要時，才會讀完整個檔案。一份很長的發布流程放在技能（skill）裡，不會像放在 CLAUDE.md 那樣，拖累你無關的錯誤修正。

註（Note）

CLAUDE.md 的規則同樣適用於技能（skills）：只寫下 Claude 自己找不到的東西。

對於有副作用的工作流程（workflow），像是真的去切出那次發布，就加上 disable-model-invocation: true。這樣 Claude 就不能自己啟動這個技能（skill），只有在你自己輸入 /release 時才會執行。把它存成 .claude/skills/release/SKILL.md，看起來可以像這樣：

.claude/skills/release/SKILL.md（英文原文）

---
name: release
description: Cut a new release. Bumps the version, writes the changelog entry, tags it and pushes the tag so CI can publish.
disable-model-invocation: true
---
1. Make sure you're on main with a clean tree. If not, stop and ask.
2. Run `pnpm changeset version` and commit the result.
3. Summarize the PRs merged since the last tag into CHANGELOG.md, one line each, user-facing changes only.
4. Tag `v<new version>` and push the tag. CI publishes from there, never publish from your machine.

繁體中文對照（欄位名稱、指令與檔名不變，只翻譯文字說明）

---
name: release
description: 切出新的發布版本。更新版本號、寫下變更紀錄（changelog）條目、打上標籤，並推送標籤，讓 CI 可以發布。
disable-model-invocation: true
---
1. 確認你在 main 分支上，而且工作目錄（working tree）是乾淨的。如果不是，就停下來詢問。
2. 執行 `pnpm changeset version`，並提交（commit）結果。
3. 把上一個標籤之後合併的合併請求（PR）整理進 CHANGELOG.md，每個一行，只寫使用者看得到的變更。
4. 為 `v<new version>` 打上標籤並推送標籤。CI 會從那裡發布，絕不要從你自己的機器上發布。

連接 Claude 需要的工具Connect the tools Claude needs

Claude 看不見的東西，有些完全存在另一個系統裡，例如你的問題追蹤系統（issue tracker）或錯誤儀表板。如果那個系統有 CLI，通常那就是最容易的入口。例如，裝好並登入 gh 之後，Claude 不需要你任何說明，就會開合併請求（PR）並讀審查留言。對於它沒看過的 CLI，指向 --help 就夠了。

對於沒有 CLI 的系統，有 MCP。你從 shell 加入一個伺服器：

指令（程式碼，不需翻譯）

claude mcp add --transport http notion https://mcp.notion.com/mcp

這個伺服器接著會出現在工作階段裡的 /mcp 底下。已連接的伺服器，即使你沒在用，也會把它們的工具名稱和說明加進脈絡，所以值得在那裡把不需要的關掉。

而如果你用的是有型別的語言，程式碼智慧外掛（code intelligence plugin）能讓 Claude 直接跳到定義，不必讀過許多檔案才找到它。

給 Claude 一個可以執行的檢查Give Claude a check to run

Claude 在工作看起來完成時就會停下來。如果它沒有任何可以執行、能告訴它工作是不是真的完成的東西，它能依據的就只有「看起來完成了」。實務上，這會讓你變成測試套件（test suite），而每一個錯誤都會待在那裡，直到你碰巧注意到。

如果你給它一個會回報通過或失敗的東西，Claude 就能自己把迴圈閉起來。它做出修改、執行檢查，如果有東西壞了，就讀輸出並修好它，然後再執行一次檢查。

提示（Tip）

給 Claude 一個它能執行、會回報通過或失敗的東西。一旦有了這個，它就能自己繼續做下去，你不必盯著。

檢查幾乎可以是任何東西，只要 Claude 讀得到結果：

  • 一個測試檔
  • 建置（build）的結束代碼（exit code）
  • 一個 linter
  • 一個把輸出和測試資料檔（fixture）做比對（diff）的腳本
  • 和模擬稿（mockup）並排的瀏覽器截圖

如果你的儲存庫（repo）已經有其中一種，那麼你的 CLAUDE.md 裡最有用的一行，就是執行它的指令。

檢查要多嚴格，由你決定。選項從「由 Claude 自己決定」一路到「由 Claude Code 強制執行」：

  • 在提示詞（prompt）裡：run the auth tests after, and keep going until they pass（做完後執行認證測試，一直做到通過為止）。Claude 自己決定什麼時候滿意。這對任何任務、今天就能用，不需要設定。
  • 當作目標（goal）：/goal all tests in tests/auth pass and lint is clean（tests/auth 裡的所有測試通過，而且 lint 乾淨）會設定一個條件，由另一個模型在每一輪之後對照對話來檢查，Claude 會一直做到條件達成為止。你在工作階段裡很少需要這個。它對長時間的背景執行很重要，因為 Claude 有時會在還有項目未完成時，以一份進度摘要結束一輪，而目標會把它送回去。
  • 當作 Stop hook：Stop hook 會在 Claude 嘗試結束它這一輪時執行你的腳本，如果腳本以代碼 2 結束，就把 Claude 送回去工作。這一種由 Claude Code（工作環境〔harness〕）強制執行，所以這一輪要到型別檢查（typecheck）通過，或達到阻擋上限（block limit）才會結束。後面有一個範例。
  • 由沒有寫這份程式碼的人：在終端機裡，/code-review 會在一個從未看過你對話的全新子代理（subagent）裡審查差異（diff）。它不會被產生這份程式碼的推理所左右。

不論你用哪一種，都要向 Claude 要求證據：它執行的指令和輸出，或是截圖。光是一句「所有測試都通過」，告訴你的東西很少，而讀輸出比自己重跑一次檢查更快。對於你沒有在旁邊看的工作階段，這也是你唯一擁有的證據。

提示（Tip）

Claude 說它做完之後，你也可以在工作階段裡執行 /verify，讓 Claude 建置並執行應用程式，然後看結果。這能抓到測試和型別檢查（typecheck）漏掉的那類問題。

對照你的規格審查Review against your spec

如果你想讓審查是對照你的計畫來檢查工作，而不是泛泛地找錯誤，就自己寫審查的提示詞（prompt）：

範例提示詞（英文原文）

use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style

繁體中文對照

用一個子代理（subagent）對照 SPEC.md 審查速率限制器的差異（diff），檢查每項要求都已實作、列出的邊界情況（edge cases）都有測試，回報會影響正確性的缺口，並略過風格（style）

註（Note）

不要拿掉那個提示詞（prompt）裡的 skip style。被要求找問題的審查者，一定會找到一些東西。如果你把每一項發現都修掉，最後就會多出一堆抽象層，還有為不可能發生的情況寫的測試。

用 Stop hook 強制執行檢查Enforce the check with a Stop hook

型別檢查（typecheck）規則的 Stop hook 版本，是 .claude/settings.json 裡的幾行。阻止停下來的是結束代碼 2。指令往 stderr 印出的任何內容，都會被送回 Claude，當作它還不能結束的理由，所以編譯器的輸出才會被重新導向到那裡：

.claude/settings.json（設定，不需翻譯）

{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" }
        ]
      }
    ]
  }
}

想看它運作，就請 Claude 做一個會弄壞型別的修改：它不會結束，而是會收到編譯器的錯誤，一直做到 tsc 通過為止。如果 hook 連續八次阻止停下，而且中間沒有任何工具呼叫，Claude Code 會推翻下一次阻擋，並結束這一輪。要調高上限，請設定 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP。

強制執行不能有例外的規則Enforce the rules that can't have exceptions

提示（Tip）

如果某件事每一次都必須發生，就把它做成 hook、拒絕規則（deny rule）或受管設定（managed setting）。CLAUDE.md 是給準則用的，而 Claude 可以決定某條準則不適用。

以你今天可能放在 CLAUDE.md 裡的三條規則為例：Never read .env（絕不讀取 .env）、Always run the formatter after editing（編輯後一律執行格式化工具）、Don't touch the migrations folder（不要動 migrations 資料夾）。Claude 幾乎每次都會遵守這些。對於那少數「幾乎」不夠好的規則，就把它們從 CLAUDE.md 搬出來，放進由 Claude Code（工作環境〔harness〕）自己套用的設定裡。從那之後，結果就不再取決於模型記得什麼或決定什麼。

用 hook 強制執行步驟Enforce steps with hooks

Hook 會在 Claude 迴圈（loop）裡的固定時間點，執行你的某樣東西：工具呼叫之前或之後、Claude 嘗試停止時、工作階段開始時，等等。這個「某樣東西」可以是：

  • 一個 shell 指令（最常見的情況）
  • 對某個 HTTP 端點的 POST
  • 對你其中一個 MCP 伺服器的工具呼叫
  • 一個 prompt 或 agent hook，由模型來決定

prompt 或 agent hook 是請另一個模型來決定，所以它也不是確定性（deterministic）的。要真正強制執行，請用 command、http 或 mcp_tool hook；如果在 hook 本身當掉或逾時時，也應該停止該動作，就加上 onFailure: "block"。比如一個掃描提交（commit）有沒有密鑰的 hook，你寧可擋下提交，也不想在掃描器停擺時讓未掃描的提交通過。

這是格式化工具規則寫成 PostToolUse hook 的樣子。它在每次 Edit 或 Write 之後執行，而 Claude 記不記得這條規則已經不重要，因為執行它的不是 Claude：

.claude/settings.json（設定，不需翻譯）

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "f=$(jq -r '.tool_input.file_path') && npx prettier --write --ignore-unknown \"$f\"" }
        ]
      }
    ]
  }
}

要檢查這個 hook，請 Claude 在一個 Prettier 會格式化的檔案裡，加一行縮排很糟的內容。儲存後的檔案回來時，縮排已經被修好了。

migrations 規則會變成一個 PreToolUse hook，對 migrations/ 底下的任何路徑，以代碼 2 結束。你不必自己寫：write a hook that blocks edits to the migrations folder（寫一個擋下 migrations 資料夾編輯的 hook）這樣當提示詞（prompt）就行，而 /hooks 會顯示結果。不過不要做過頭：hook 是給零例外的規則用的，而 Prefer named exports（偏好具名匯出）有很多例外，所以那一條留在 CLAUDE.md。

用權限規則和沙箱限制存取Limit access with permission rules and the sandbox

權限規則（Permission rules）決定 Claude 被允許執行、讀取和擷取什麼。deny 規則在每一種權限模式下都有效，包括自動模式（auto mode）和 bypassPermissions，這正是 .env 規則該放在這裡的原因：

.claude/settings.json（設定，不需翻譯）

{
  "permissions": {
    "allow": ["Bash(pnpm tsc --noEmit)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]
  }
}

存好這個之後，問 Claude .env 裡有什麼，會失敗，不論是透過 Read 工具，還是 cat .env，都一樣。

規則比對的是工具呼叫，而不是意圖，所以值得知道它的邊界在哪裡：

  • Read 規則確實會擋下 cat .env，因為 Claude Code 認得常見的讀檔指令。
  • 它擋不住一個會打開該檔案的腳本。
  • 針對某個網域的 WebFetch 拒絕規則，對同一個網域的 curl 沒有任何作用，除非沙箱（sandbox）是開著的。

如果要在作業系統層級限制檔案系統或網路存取，請在工作階段裡用 /sandbox 開啟沙箱（sandbox）。它會把 Claude 的 shell 指令限制在 macOS、Linux 和 WSL2 上，也會套用你的 Read 拒絕規則和 WebFetch(domain:...) 規則，所以只要是和安全有關的事，兩者你都會想要。

預設情況下，Claude 仍然可以請求在沙箱（sandbox）之外重試一個被擋下的指令，而那個請求會走一般的權限流程。嚴格沙箱模式（Strict sandbox mode），位於 /sandbox 的 Overrides（覆寫）分頁，會把那個重試關掉。

警告（Warning）

自動模式（auto mode）是一個分類器模型在判斷每個動作，而不是一條硬性規則。它很擅長這件事，但和任何判斷一樣，也可能出錯。你也可以調整它把什麼視為有風險，你的組織也可以把它整個關掉，所以你的「絕不」規則應該放在拒絕規則（deny rules）或 hook 裡。

選擇規則適用於誰Choose who a rule applies to

規則放在哪裡，決定它適用於誰：

  • .claude/settings.local.json 和 ~/.claude/settings.json 只屬於你自己。當你對某個指令選擇 Yes, and don't ask again（是，而且不要再問）時，Claude Code 會把那條規則存進本機檔案。
  • .claude/settings.json 和其中的 hook 屬於儲存庫（repo）。一旦你把它們提交（commit），它們就適用於每個在這個儲存庫（repo）工作的人。它的拒絕規則會立刻生效。它的 allow 規則要等每個人接受該資料夾的信任對話框（trust dialog）後才生效，而工作區信任（workspace trust）也決定它的 hook 何時開始在他們的機器上執行。
  • 受管設定（Managed settings）屬於組織。它們來自管理主控台（admin console）、MDM，或一個 managed-settings.json 檔案，沒有任何個人設定檔能覆寫它們，這讓它們成為資安團隊政策唯一的歸宿。如果你是設定它們的人，請看為你的組織設定 Claude Code（Set up Claude Code for your organization）。

不論是哪個範圍，都要讓強制執行的那一組保持少量。每一個 hook 和拒絕規則偶爾都會在不該觸發時觸發，而且每一個都需要有人維護。如果你發現自己有四十個，其中大多數大概只是 Claude 自己就能權衡的偏好。

調整預設值Change a default

提示（Tip）

預設值已經夠好，在某項任務花的時間、令牌（token）或打斷次數超出應有的程度之前，都可以不去動它。發生這種情況時，在工作階段裡執行 /usage，看看花到哪裡去了。

新的工作階段已經替你做了幾個決定：

  • 互動式的終端機和 VS Code 工作階段從自動模式（auto mode）開始。
  • 在大多數方案和供應商上，它以 medium 費力等級（effort）執行 Claude Opus 5.5。
  • 它看到有理由時，會把工作委派給子代理（subagent）。
  • 隨著對話變長，它會壓縮（compact）對話。

大部分時候你根本不會想到這些。當某項任務的花費確實超出應有的程度，原因通常是這四項之一。

更換權限模式Change the permission mode

權限範圍的兩端都有代價：

  • 手動模式（Manual mode）：每一個編輯，以及每一個不是唯讀的指令，都由你自己核准。安全，但到了第十次提示之後，你就會開始不看內容直接核准，而且你離開鍵盤時，什麼都不會動。
  • bypassPermissions：核准你的拒絕規則和詢問規則沒有涵蓋的所有事情，這只有在用完即丟的容器裡才合理。

自動模式（Auto mode）介於兩者之間，也是互動式終端機和 VS Code 工作階段開始時使用的模式。Claude 不會為例行的核准停下來，而是一個獨立的分類器（classifier）模型，在動作執行前，依固定的順序檢查這些動作。它專注在你會希望有人去攔下的事：

  • curl | bash
  • 正式環境的部署與遷移（migrations）
  • 強制推送（force push）蓋掉別人的工作
  • 把敏感資料送到外部端點
  • 看起來是由 Claude 讀到的內容、而不是由你所驅動的動作

當自動模式（auto mode）擋下一個動作，你會收到通知，這個動作也會出現在 /permissions 的 Recently blocked（最近被擋下）底下，你可以在那裡核准這個動作，讓 Claude 重試。在連續三次被擋（或總共二十次）之後，自動模式（auto mode）會暫停，並回頭來問你。

這一切都不會取代你的確定性（deterministic）控制，因為它是在那些控制之後才執行。拒絕規則、詢問規則和 PreToolUse hook 在分類器（classifier）看到任何東西之前就已經套用，所以拒絕規則在自動模式（auto mode）下擋下的方式，和在其他地方完全一樣。沙箱（sandbox）仍然會限制它所包住的 shell 指令。

註（Note）

你也可以在對話中說 don't push until I've reviewed（我審查完之前不要推送），分類器（classifier）會把它當作阻擋訊號。但它終究是一個模型在讀對話紀錄，而這句話可能在對話被壓縮（compact）時遺失，所以任何重要的事都該放進拒絕規則（deny rule）。

相反的問題是，分類器（classifier）一再攔下在你的環境中屬於例行的事。與其每次都手動核准，不如把它加進 autoMode.allow，或在自動模式設定（auto mode configuration）裡描述你信任的基礎設施。它用的是白話英文，而不是比對模式，而且 /auto-mode-setup 可以根據你的專案和最近的工作階段，替你起草 environment 的部分：

~/.claude/settings.json（英文原文）

{
  "autoMode": {
    "environment": [
      "$defaults",
      "Source control: github.com/example-org and every repo under it",
      "Trusted internal domains: *.internal.example.com"
    ],
    "allow": [
      "$defaults",
      "Deploying to the staging namespace is fine, it's isolated from production and resets nightly"
    ]
  }
}

繁體中文對照（欄位名稱與 $defaults 不變，只翻譯文字說明）

{
  "autoMode": {
    "environment": [
      "$defaults",
      "原始碼控制：github.com/example-org 和它底下的每一個儲存庫",
      "受信任的內部網域：*.internal.example.com"
    ],
    "allow": [
      "$defaults",
      "部署到 staging 命名空間沒問題，它和正式環境隔離，而且每晚都會重置"
    ]
  }
}

警告（Warning）

在你設定的每一份清單裡都要保留 "$defaults"，因為沒有它的話，你的項目可能會取代那份清單的內建規則，而不是加在它們之上。你可能會失去 environment 裡內建的脈絡、allow 裡的例外，以及 soft_deny 裡對強制推送和正式環境部署的阻擋。

autoMode 區塊也必須放在 ~/.claude/settings.json，而不是專案裡，因為分類器（classifier）會忽略專案設定裡的 autoMode。

如果你寧可在每個編輯和指令發生之前都看過，在工作階段裡按 Shift+Tab 會在各個權限模式之間循環，包括手動模式（Manual），或是從你的 shell 用 claude --permission-mode manual 開始。而如果手動模式問得太頻繁，/fewer-permission-prompts 會掃描你最近的對話紀錄（transcripts）中常見的唯讀 Bash 和 MCP 呼叫，並把它們加進 .claude/settings.json 裡的允許清單（allowlist）。

更換模型與費力等級Change the model and effort

費力等級（Effort）是控制 Claude 思考多久的主要方式，它取代了人們過去用提示詞（prompt）措辭做的大部分事情。Claude Fable 5.2、Opus 5.5、Sonnet 5.5 和 Haiku 5.5 預設為 medium，對範圍明確的日常功能開發來說綽綽有餘。你會想調整它的時機，在工作階段裡用 /effort 調：

  • 當做對取決於容易被忽略的情況時，用 /effort high 或 /effort xhigh 調高。例如在不是你寫的程式碼裡找錯誤、一個不穩定的測試（flaky test），或是 Claude 得找出舊結構每一個讀取者的結構描述（schema）變更。這時 Claude 會檢查更多邊界情況，並在回答前驗證更多自己的工作，額外的時間和令牌（token）就花在這裡。
  • 當你正在快速來回，而且反正每個結果都會自己審查時，用 /effort low 調低：腦力激盪、第一版草稿、跨幾個檔案的改名。Claude 會更快給你一個起點，而且因為每一步都由你在掌舵，多出來的深思除了等待之外，不會改變太多東西。
  • 把 max 留給你想讓 Claude 在沒有你的情況下去解的困難問題，例如找資安漏洞。在一般任務上，它容易想太多，所以你多付了錢，換來的答案可能不會比 high 給你的更好。
  • 當只有下一則訊息需要時，例如在一堆例行工作中間有一個棘手的問題，就把 ultrathink 放進那則提示詞（prompt），而不是更改設定。

至於模型本身，預設的 Opus 5.5 能處理大多數的程式開發，而 Sonnet 在例行工作上比較省。要使用 Claude Fable 5.2，請執行 /model fable。Haiku 很適合用在做簡單工作的子代理（subagents）。模型設定（Model configuration）有各方案和供應商的完整清單。

了解子代理的成本Know what subagents cost

Claude 會自己委派給子代理（subagents）：

  • 大範圍的程式碼庫搜尋，交給內建的 Explore AI 代理。
  • 只要分叉模式（fork mode）開著（預設如此），旁支的任務會被分叉（fork）出去。
  • 它啟動的子代理（subagents）預設在背景執行，所以你的主要對話可以繼續進行。

這些你很少需要要求，但知道自己得到什麼、要付出什麼成本，是有幫助的。

子代理（subagents）在這些情況下划算：

  • 同時執行彼此獨立的工作，讓整項任務更快完成
  • 把很長的輸出（像是完整的測試執行結果或大範圍搜尋）留在你的主要對話之外，否則它會在接下來整個工作階段裡一直跟著走
  • 取得一位沒看過程式碼是怎麼寫出來的審查者
  • 給任務比主要工作階段更少的工具，例如一位能讀、但不能編輯的審查者

它們讓你付出的成本，主要是令牌（token），因為每個子代理（subagent）都會送出自己的請求，而且它們和你的主要對話算在同一份用量裡。有時也會花時間：全新的子代理（subagent）得先收集你的對話原本就有的脈絡，所以它可能比直接在你這邊做那項任務更慢。

而且預設情況下，它是在同一項任務上使用同一個模型（或更小的模型）。你從中得到的是平行處理，或一雙全新的眼睛，但不是更聰明的答案。

要少花一點在它們身上：

  • 如果子代理（subagent）的工作很簡單，例如收集匯入某個模組的檔案，或檢查文件裡的連結，就在它的定義裡設定 model: haiku。這類工作不需要較大的模型，而 Haiku 每個請求便宜很多。
  • 要求它們回傳簡短的摘要，這樣二十個結果才不會還是塞滿你的脈絡。
  • 查看 /usage，了解每種子代理（subagent）類型佔你用量的比例，這樣你就能分辨哪些物有所值。
  • 在 .claude/agents/ 裡，給自訂的子代理（subagent）只設 tools: Read, Grep, Glob。這樣它就是一位什麼都不能編輯的審查者，而且這個限制是由 Claude Code 強制執行，而不是用提示詞（prompt）去請求。

那位審查者就是一個很短的檔案，.claude/agents/reviewer.md：

.claude/agents/reviewer.md（英文原文）

---
name: reviewer
description: Reviews changed files against the spec they were built from. Use after implementing a feature, before opening the PR.
tools: Read, Grep, Glob
---
You're reviewing code you didn't write. Compare the changed files against the spec you're given,
check that every requirement is implemented and the listed edge cases have tests,
and report only the gaps that affect correctness. Skip style.

繁體中文對照（欄位名稱與工具名稱不變，只翻譯文字說明）

---
name: reviewer
description: 對照變更檔案原本依據的規格文件（spec）來審查它們。在實作完功能之後、開合併請求（PR）之前使用。

你正在審查不是你寫的程式碼。把變更的檔案拿來和你拿到的規格文件（spec）比對，
檢查每項要求都已實作、列出的邊界情況（edge cases）都有測試，
並且只回報會影響正確性的缺口。略過風格（style）。

請 Claude have the reviewer compare the rate limiter against SPEC.md（讓審查者把速率限制器和 SPEC.md 做比對），缺口就會回到你的工作階段，讓 Claude 去修。

壓低成本與脈絡Keep cost and context down

現在大多數模型都有 100 萬令牌（token）的視窗，而壓縮（compaction）發生在接近上限的地方，所以你很少會用完脈絡。不過，你仍然可能花錢在你不需要的脈絡上。每個請求都會送出整段對話，所以一個累積了三項無關任務的工作階段，在第四項任務的每一輪，都會重讀這三項。這在快取（cache）還熱的時候有折扣，一旦過期就是全價。

/usage 是第一個該看的地方。在 Pro、Max、Ultra、Team 和 Enterprise 方案上，它會依技能（skill）、子代理（subagent）、外掛（plugin）和 MCP 伺服器拆解你的用量。一旦長脈絡或頻繁的快取未命中（cache miss）這類模式之一超過你用量的 10%，它也會標示出來。從那裡開始，常見的修正方法是：

  • 在無關的任務之間用 /clear。它不花任何成本，而且讓下一項任務不必繼續為上一項任務的歷史付費。/clear oauth-migration 會為你要離開的工作階段命名，讓你之後可以回到它。
  • 用帶有重點的 /compact，像是 /compact keep the API changes and the test commands（保留 API 的變更和測試指令）。在長的工作階段上，/compact 本身就是一個很大的請求，因為它要讀完整段對話才能做摘要，快取（cache）過期之後更是如此。
  • 留意背景工作：/loop、每一輪之後的目標（goal）檢查，以及 Claude 自己的子代理（subagents），在你沒有打字的時候，都會持續送出請求。

註（Note）

提示詞快取（prompt cache）在訂閱方案上大約持續一小時，在應用程式介面金鑰（API key）、雲端供應商或用量額度（usage credits）上是五分鐘。子代理（subagents）預設是五分鐘，除非你更改。

在一小時的快取（cache）上，一個超過約 20 萬令牌（token）、而且閒置的工作階段，會在快取（cache）過期前不久被壓縮（compact），所以午餐後你是從一份摘要繼續。如果你完全不需要那段歷史，全新的工作階段還是比較省。

引導工作階段Steer the session

提示（Tip）

看著最開始的那一分鐘，Claude 一偏離就按 Esc，而在兩次修正失敗之後，就執行 /clear，改寫一個更好的提示詞（prompt），而不是做第三次修正。

再多的設定，也無法取代看著最開始的那一分鐘，並在 Claude 朝你不想去的方向走時介入。能做到這點的控制只有少數幾個，值得背起來：

  • Esc 會在 Claude 動作到一半時停下它，並保留到那個時間點為止的一切，所以你可以改變方向而不丟掉工作。
  • /rewind，或在空白的提示上按兩次 Esc，會打開回溯選單（rewind menu），你可以在那裡把程式碼、對話，或兩者一起，退回到較早的某個提示。這讓你可以低風險地先試比較大膽的做法，不行再回溯。同一個選單在對話變得過時時，也能摘要對話的一部分。
  • /clear 會重新開始。如果你同一件事糾正了兩次，結果還是不對，第三次糾正主要只是讓一段已經包含兩次失敗嘗試的對話變得更長，讓 Claude 一再重讀。/clear 加上一個把你學到的東西融入其中的新提示詞（prompt），幾乎每次都更有效。

警告（Warning）

檢查點（Checkpoints）涵蓋的是 Claude 在你的主要對話裡用自己的檔案工具編輯過的檔案，所以只被 Bash 指令碰過的檔案不會被還原。它們是和 git 搭配運作，而不是取代它。

另外兩個較小的：/btw 回答一個快速的問題，而不會在歷史紀錄裡加入任何東西。而對於橫跨好幾天的工作，在工作階段裡用 /rename oauth-migration 替它命名，這樣之後從你的 shell 執行 claude --resume oauth-migration 就能把它接回來，連檢查點（checkpoints）也在內。claude --continue 則接續最近的一個。

讓 Claude 在沒有你的情況下執行Let Claude run without you

提示（Tip）

在一次執行變成無人看管之前，確認它知道完成長什麼樣子、能檢查自己的工作，而且只能碰它該碰的東西。給它回合數或花費的上限，並讓人在最後核准結果。

這一頁的一切，在你不在場、無法抓出錯誤時，都變得更重要一點。當你在看著的時候，Claude 缺了某一塊脈絡不是什麼大事：你一兩則訊息之內就會注意到並告訴它。在你睡前啟動的一次執行裡，沒有人告訴它，你隔天早上才發現它整晚都在錯誤的假設上建構。

在你讓一項任務自己跑之前，值得針對那項特定任務，過一遍這五個問題：

  1. 它知道完成長什麼樣子嗎？一個目標條件（goal condition）、一份規格檔，或一個它必須讓其轉綠的失敗測試。
  2. 它能檢查自己的工作嗎？測試套件（test suite）、Stop hook，某種審查步驟。
  3. 它被允許碰什麼？權限規則、dontAsk、沙箱（sandbox）、一個工作樹（worktree）、它唯一可以推送的那個分支。
  4. 什麼會讓它停下來？--max-turns、--max-budget-usd、花費上限（spend limit）。
  5. 結果送到哪裡，由誰簽核？一個合併請求（PR）、一則留言，或一份摘要，然後由一個人核准合併、部署，或任何其他你無法收回的事。

一旦開始跑，Claude 自己就會把一項長任務做完。仍然留在你手上的部分，是啟動它、決定這一次「完成」的意思，以及在最後核准合併。

從腳本執行 ClaudeRun Claude from a script

claude -p "prompt" 會執行一次後結束，這就是 Claude Code 會出現在 CI 工作、git hook 和 shell 迴圈裡的方式。

在腳本裡，你幾乎一定會想要再多幾個旗標（flag）：

  • --bare 會跳過你的 hook、技能（skills）、外掛（plugins）、MCP 伺服器，以及儲存庫和你家目錄裡的 CLAUDE.md 檔案。它也不使用你的 claude.ai 登入：認證來自 ANTHROPIC_API_KEY、你用 --settings 傳入的檔案裡的 apiKeyHelper，或你的雲端供應商的憑證。
  • --append-system-prompt、--mcp-config 和 --settings 會明確傳入這次執行確實需要的東西。你用 --settings 傳入的 hook 在 --bare 之下不會執行，所以需要它們的執行就不要用 --bare。
  • --allowedTools 會預先核准它的工具，而 --permission-mode dontAsk 會拒絕任何其他本來會跳出提示的事。
  • --output-format json 給你一個單一的結果物件可以解析，而搭配 --verbose 的 stream-json 則會在事件發生時即時串流輸出。

放在一起，看起來像這樣：

shell 腳本（英文原文）

for file in $(cat files.txt); do
  claude --bare -p "Migrate $file to the new logger API and commit. Reply OK or FAIL." \
    --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
    --permission-mode dontAsk \
    --max-turns 20
done

繁體中文對照（指令與旗標不變，只翻譯提示詞字串）

for file in $(cat files.txt); do
  claude --bare -p "把 $file 遷移到新的 logger API 並提交（commit）。回覆 OK 或 FAIL。" \
    --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
    --permission-mode dontAsk \
    --max-turns 20
done

一次執行結束時，Claude 會回覆 OK 或 FAIL，而碰到回合數上限的執行，會以錯誤結束。先用三個檔案試試看，看哪裡出問題，修好提示詞（prompt），再跑剩下的。

如果你傳入 --permission-mode auto，自動模式（auto mode）也能搭配 -p 使用。在非互動式的執行裡，分類器（classifier）的一次阻擋會拒絕那一個動作，Claude 則繼續往下做，而重複的阻擋不會像在終端機裡那樣讓執行暫停。在你仰賴它之前，請先讀門檻在那裡如何適用。

依排程或事件啟動執行Start runs on a schedule or an event

一次執行開始之後，其餘的 Claude 可以自己處理。它唯一無法做的事，是決定要開始，所以得有東西來做：你、一個計時器，或是像 CI 檢查失敗或新的合併請求（PR）這樣的事件。

在一個開著的工作階段裡，就是 /loop，它會每隔一段時間重複一個提示詞（prompt）：

範例（英文原文）

/loop 15m check CI on this branch, and if it's red pull the failing job's log, fix it and push

繁體中文對照

/loop 15m 檢查這個分支上的 CI，如果是紅燈，就拉下失敗工作的紀錄、修好它並推送

每一次執行都是同一個工作階段裡的另一輪，所以不要在一段很長的對話裡讓它一直跑。對於任何應該在你的筆電闔上時發生的事，/schedule 會設定一個依計時器執行的雲端定時任務（cloud scheduled task）。它需要的是 claude.ai 登入，而不是應用程式介面金鑰（API key）。你可以請 Claude 加上一個 GitHub 事件的觸發條件，或在 claude.ai/code/routines 加上一個應用程式介面（API）觸發條件。

警告（Warning）

在你讓雲端定時任務（cloud scheduled task）一直跑之前，先用任務無法繞過的 GitHub 分支規則保護 main。而且在信任任何新東西無人看管地執行之前，先看它最初的幾次執行。

平行執行工作階段Run sessions in parallel

當你有各自獨立的工作同時進行時，給每一個自己的簽出（checkout），這樣編輯才不會互相衝突。claude -w feature-auth 會在新的工作樹（worktree）裡啟動一個工作階段，桌面應用程式（desktop app）可以並排執行好幾個這樣的工作階段，而雲端工作階段（cloud sessions）則是在雲端而不是你的機器上執行它們。

工作樹（worktree）是一份全新的簽出（checkout），這表示像 .env 這種被 gitignore 排除的檔案不在那裡，相依套件也沒有安裝。對於第一個問題，把你需要的、被 gitignore 排除的檔案，列在儲存庫根目錄的 .worktreeinclude（語法和 .gitignore 相同），Claude Code 就會把它們複製進它建立的每一個工作樹（worktree）：

.worktreeinclude（檔案內容，不需翻譯）

.env
.env.local
config/dev-credentials.json

只放小檔案：它是複製而不是連結，所以把 node_modules 放進去，就表示每個工作樹（worktree）都要完整複製一份。對於大型目錄，有 worktree.symlinkDirectories 這個設定，或者把安裝指令放在 CLAUDE.md 裡，讓 Claude 每次在新的簽出（checkout）裡啟動時就執行它。

你很少需要自己清理這些：

  • 當你結束一個未命名的工作樹（worktree）工作階段時，如果裡面沒有東西，Claude Code 會移除它用 git 建立的工作樹（worktree）。對於已命名的工作階段，或是有變更的，它會問你要怎麼處理。
  • 子代理（subagent）的工作樹（worktree），在子代理（subagent）沒有變更就結束時會消失。
  • 被留下來的子代理（subagent）和背景工作階段（background-session）的工作樹（worktree），一旦比 cleanupPeriodDays 更舊而且裡面沒有工作，就會被清掉。

註（Note）

claude -p --worktree 的執行，是你要自己清理的，因為它結束時不會詢問。用 git worktree remove <path> 移除這些，而如果 git 因為工作樹（worktree）被鎖住而拒絕，就先執行 git worktree unlock <path>。

對於橫跨許多檔案的一次大規模機械式變更，/batch migrate every handler to the v2 response helpers（把每個 handler 都遷移到 v2 回應輔助函式）會把工作拆成 5 到 30 個單元，並向你展示計畫。你核准之後，每個單元都有自己的工作樹（worktree），並開一個合併請求（PR）或回報發生了什麼事。從你的 shell，claude agents（仍是研究預覽版）給你一個畫面，看到你機器上所有在背景執行的東西。

第二個工作階段，也是你能得到的最容易取得的獨立審查者。一個工作階段寫速率限制器，另一個審查 @src/middleware/rateLimiter.ts，而沒有看過它是怎麼被寫出來的，然後你把發現貼回第一個。和 /code-review 是同一個概念，只是由你來傳遞訊息。

你可以不用再做的事What you can stop doing

這些每一條在被寫下來的時候，都是好建議。大多數是針對模型當時還做不可靠的事所用的變通辦法，而模型後來已經跟上了。如果其中幾條仍是你的習慣，下面是為什麼可以放心放掉。

過去的建議（The old advice）為什麼不再需要（Why it's gone）
脈絡視窗（context window）是你最主要的限制，要積極管理它現在大多數模型都有 100 萬令牌（token）的視窗，而且壓縮（compaction）會自動發生，所以用完很少見。在任務之間用 /clear 仍然值得做，因為專注的脈絡能給你更好的答案，也更省。
在 Claude 一直漏掉的指示上加 IMPORTANT 或全大寫較舊的模型有時需要這種強調。現在的模型會照著措辭平實的一行去做，而堆疊強調，多半只會讓 Claude 把那條規則套用過頭。如果它是一條不能讓步的規則，就把它變成 hook 或拒絕規則（deny rule）。如果那一行在長長的檔案裡被淹沒了，就是這個檔案需要變短。
用子代理（subagents）來保護你的脈絡視窗（context window）用完脈絡已經很少是問題了。子代理（subagents）對於平行工作、把吵雜的輸出擋在你的視線之外，以及獨立審查，仍然很棒，但這些每一項都會花額外的令牌（token）。
委派給子代理（subagent）以得到更好的答案把同一項任務交給子代理（subagent），並不會讓答案更好。全新的審查者確實有幫助，因為它沒看過你的推理，但這和委派是不同的事。
在提示詞（prompt）裡寫 think hard、think harder、be thorough費力等級（effort）才是控制這件事的方式。這些片語是普通的提示詞（prompt）文字，會在 Claude 的費力設定（effort setting）範圍內輕推它，而不是會把它調高的關鍵字。ultrathink 仍然有效：它要求在那一輪做更深的推理，而不碰你的費力設定（effort setting）。
告訴 Claude 要繼續做、循環到完成、不要偷懶現在的模型通常不必被告知，也會把一項講定的任務做到底，而這類話比較可能造成過度工作，而不是解決停住不動的問題。給 Claude 一個要通過的檢查是不同的事，仍然值得做。如果一次執行確實提早停下，就說 continue（繼續），而對於沒人看著的執行，/goal 或 Stop hook 會強制執行。
在 CLAUDE.md 裡描述你的架構和檔案配置Claude 自己會讀儲存庫（repo）。只寫下不在那裡面的東西。

這篇在說什麼

這是 Anthropic 放在 Claude Code 官方文件裡的〈Claude Code 最佳實踐〉。它的核心意思是：Claude Code 的預設值大多已經夠用，真正需要你動手的，是「專案裡 Claude 光看程式碼看不出來的事」。

文章把你可能碰到的問題歸成四類：它做出來的東西和你想的不一樣、它說做完了但其實沒有、它做了不能做的事，或是它花的時間和錢超出任務該有的程度。每一類對應一個做法：告訴它看不見的東西、給它一個可以檢查對錯的東西、把不能有例外的規則做成強制設定、在確實變貴變慢時才調整預設值。後半段再談怎麼邊看邊修，以及要讓它在你不在場時自己跑，該先確認什麼。

為什麼值得學

就算你不寫程式，只要身邊有人用 Claude Code 做事，這篇都給了一個很實用的分辨方式：哪些事交給 Claude 判斷就好，哪些事一定要用設定鎖死。讀的時候留意：這是官方文件，裡面的指令、功能和模型名稱（例如 Opus 5.5、Fable 5.2）會隨版本改變，譯文只對應我抓取當下的頁面；很多細節是給開發者看的，不懂的指令可以先略過，抓住每一節開頭的「提示（Tip）」就夠。

你可以帶走的重點

1. 「請你這樣做」和「一定會這樣做」是兩回事

你寫給 Claude 的提示詞、CLAUDE.md（放在專案裡的說明檔）和技能（skill），都是「請求」：Claude 讀了之後自己決定要不要照做，通常會，但不保證。hook（在固定時機自動執行的小程式）、拒絕規則和受管設定則是「規定」：不論模型怎麼想，Claude Code 每次都會執行。大部分事交給 Claude 判斷就好；只有「一定要發生、或絕對不能發生」的事，才值得做成規定。

原文的檢測方式：如果你一直在加強某一行的語氣，Claude 還是漏掉，那一行就該改成 hook；反過來，如果有 hook 只是為了偏好，就刪掉。

2. 只寫 Claude 自己找不到的東西

Claude 一開始就會讀你的程式碼，檔案結構、慣例、測試怎麼跑，它多半比你解釋得還快。所以真正該寫給它的，是沒有留在程式碼裡的事：會議上做的決定、只存在某個人腦袋裡的部署流程、整合測試需要的環境變數。寫之前問兩句：它讀程式碼找得到嗎？它會真的去找嗎？兩個都是，就不要寫。

原文的例子：CLAUDE.md 只放確認工作的指令、容易誤導人的地方、不在儲存庫裡的決定，以及你已經糾正過兩次的事。檔案一長，重要的那一行反而會被淹沒。

3. 給它一個會回答「過」或「不過」的檢查

Claude 在工作「看起來」完成時就會停下來。如果它沒有任何東西能告訴它是不是真的完成，那你就成了測試員，每個錯誤都躺在那裡等你發現。給它一個能回報通過或失敗的東西，它就能自己做修改、跑檢查、讀錯誤、再修正，直到通過。檢查可以是一組測試、一個程式檢查工具，甚至是畫面截圖和設計稿的對照。

檢查有四個嚴格程度：在提示詞裡請它跑到通過為止；用 /goal 設一個完成條件；用 Stop hook 強制它通過才能結束；或請沒看過你對話的全新子代理（subagent）來審查。不論哪一種，都要它附上證據（執行的指令與輸出、截圖），而不是只說「都通過了」。

4. 絕對不能出錯的事，交給設定，不要靠叮嚀

原文舉的三個例子是：絕不讀 .env、編輯後一律跑格式化工具、不要動 migrations 資料夾。Claude 幾乎每次都會遵守，但對「幾乎不夠好」的少數規則，就從說明檔搬到設定裡：格式化可以做成每次編輯後自動執行的 hook，不能讀的檔案寫進拒絕規則，連 cat .env 這種指令也會被擋下。要注意兩件事：規則比對的是工具呼叫，不是意圖，有些繞法擋不住；而且這類規則要保持少量，每一條都需要有人維護，原文說如果你有四十條，多半大部分只是偏好。

規則放哪裡，決定它管誰：個人設定檔只管你自己；專案裡的設定提交後管每個人；組織的受管設定誰也覆寫不了，是資安團隊政策唯一的歸宿。

5. 預設值夠好，覺得太貴、太慢、太常被打斷時再調

原文把可能要調的東西列成四項，並建議先用 /usage 看錢和時間花到哪裡去：

  • 權限模式：手動模式每一步都問你，安全但你會開始不看就按；自動模式由另一個模型擋下重大動作，是現在的預設，但你的「絕不」規則仍然要放在拒絕規則或 hook。
  • 費力等級（effort）：預設 medium 夠日常功能開發；碰到容易漏掉的情況（別人寫的程式碼裡的錯誤、不穩定的測試）調高，快速來回時調低，max 留給你不在場時要解的難題。
  • 子代理（subagent）：能平行處理、能把很長的輸出擋在主對話外，但主要成本是令牌（token），而且不會讓答案更聰明；簡單的工作可以指定較小的模型。
  • 脈絡與成本：無關的任務之間用 /clear，因為每個請求都會把整段對話再送一次。

6. 放手讓它自己跑之前，先問五個問題

你在場時，Claude 缺了某個資訊，一兩句話就補上了；你睡著時，它可能整晚都在錯誤的假設上做事。所以任務要無人看管地跑之前，原文建議先逐項確認：

  1. 它知道「完成」長什麼樣子嗎？
  2. 它能檢查自己的工作嗎？
  3. 它被允許碰什麼？
  4. 什麼會讓它停下來（回合數或花費上限）？
  5. 結果送到哪裡，由誰簽核？

有你在場時也一樣有控制手段：看著最開始的一分鐘，Claude 一偏離就按 Esc；用 /rewind 退回較早的狀態，所以大膽試一下風險不高；如果同一件事糾正了兩次還是不對，就用 /clear 重開並寫一個更好的提示詞，不要做第三次修正。

原文最後也列了「可以不用再做的事」：在指示裡加 IMPORTANT 或全大寫、叫它「別偷懶」、用子代理換更好的答案。現在的模型不需要這些，做了反而容易過度。

怎麼開始

  1. 下一次下提示詞時，指名檔案、描述症狀，並說明「修好」是什麼樣子；不確定自己要什麼時，請 Claude 先訪談你、寫成規格檔再動手。
  2. 把你專案裡「執行測試、型別檢查」的指令寫進 CLAUDE.md，並請 Claude 每次都附上它跑過的指令與輸出。
  3. 想一條「絕對不能發生」的規則，請 Claude 幫你寫成 hook 或拒絕規則；其餘偏好留在說明檔，讓它自己權衡。
  4. 覺得變慢或變貴時，先執行 /usage，再從四項預設值裡挑一項調整，而不是一次全改。
  5. 要讓任務無人看管地跑之前，把第 6 點的五個問題逐題過一遍；剛設定好的排程任務，先看最初的幾次執行。
