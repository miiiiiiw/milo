原文標題：How the Claude Code team thinks about verification

本篇與收件匣中已有的〈Claude Code 團隊如何做程式碼審查〉（addy-claude-code-review.html）是同一位作者談同一個團隊的姊妹篇：前一篇講審查流程，這一篇講怎樣讓 AI 代理用證據驗證自己的工作。原文為單篇 X 文章，不是討論串。

在 Claude Code 團隊，絕大多數的程式碼（約 90%）是由 Claude 撰寫並審查的。在這種規模下，我們怎樣讓 AI 代理具備用證據驗證自身工作的能力，就變得極為重要。

驗證迴圈（verification loops）是讓你能把更多工作交給 Claude 的基本構件。沒有它們，你同一時間大概只能跑一兩個 Claude，因為每樣東西都得自己檢查。有了它們，你可以平行跑幾十個、甚至幾百個。

這是因為，給 AI 代理一個驗證自身產出的方法，是提升品質的有效做法。在一項關於結構化檔案產生的內部測試中，讓一個獨立的評分者（grader）依照評分規準（rubric）檢查 Claude 的工作，相較於標準的提示詞（prompt）迴圈，任務成功率最多提升了 10 個百分點，而且越難的問題進步越大。

過去驗證起來很昂貴的東西（測試、基準測試（benchmark）、規格（spec）、真實的端到端執行），現在向 AI 代理要求起來很便宜。和程式碼一樣，AI 代理可以很快地產生測試、基準測試（benchmark）和規格（spec）。而且一旦產生，這些測試和基準測試（benchmark）就以軟體的形式執行，所以可以經常跑，不必多花很多 token。

你還可以利用結果來改善 AI 代理在該任務上的表現，藉此把驗證迴圈（verification loop）閉合起來。例如，如果 AI 代理一再沒通過某個「檢查日誌裡有沒有使用者資料」的測試，你可以建立一個鉤子（hook），或在 CLAUDE.md 裡寫一條更明確的規則，避免日後再出問題。這（大致上）能讓問題不再發生。

既然驗證對於高速產出高品質程式碼這麼關鍵，你該用哪些類型的測試？又該怎樣把它們用在整條流程上？這篇文章會回答這些問題，也分享 Claude Code 團隊所用的流程。

測試不是生而平等：值得投資的 3 種測試Not all tests are created equal: 3 tests worth investing in

無論你選哪種測試，都有幾種失敗模式要避開。

如果你的測試不穩定（flaky），你會把 AI 代理訓練成「再跑一次」，而不是去修正失敗的程式碼。如果你的測試很慢，AI 代理在各批次之間會少跑測試，這會讓找出問題變得困難。較重的測試，最好在你提交（commit）變更之前就執行。

接下來是我認為最值得投資的三種測試。

端到端測試E2E tests

如果你只能專注於一種測試，就選端到端測試（end-to-end tests）。這類測試描述的是真實的使用者流程，例如把商品加入購物車、結帳，然後進入確認頁面。

端到端測試（E2E tests）之所以這麼有效，是因為它們很難被唬弄：整個功能要嘛能用，要嘛不能用。它們也有明確的完成標準，能具體告訴你哪裡壞了。

單元測試（unit tests）雖然比較快、也比較不容易不穩定（flaky），但有可能全部通過，功能卻還是壞了。這是因為 AI 代理和測試都不了解完整的任務。

有了端到端測試（E2E tests），讓 AI 代理對真正執行中的系統擁有「手和眼睛」會很有效。你可以用一個技能（skill），搭配 CDP、模擬器或 API 測試框架（harnesses）等工具，來啟動、操作並檢查應用程式。

功能地圖（feature map）可以作為 AI 代理的指引和評分規準（rubric），因為它通常從使用者的角度列出各項功能，並描述路徑、鍵盤快捷鍵、選擇器（selectors）和預期結果。

屬性測試：不能被打破的約束Property tests: constraints that can’t break

很多測試是根據「你以為可能出什麼錯」寫出來的。屬性測試（property tests）看的是人們容易忽略的邊界情況（edge cases），而那正是 AI 代理經常失敗的地方。

做法是先寫一句你認為不可能失敗的陳述，再用測試函式庫（JS／TS 用 fast-check、Python 用 Hypothesis、Rust 用 proptest 等）產生數千個輸入，試圖證明它是錯的。

幾乎每個軟體專案裡都有很多這類屬性，例如：

  • 往返編碼（round-trip encoding）：「如果你把 X 編碼後再解碼回來，會得到 X。」這也適用於解析（parsing）和序列化（serialization）。
  • 不變量（invariants）：必須永遠成立的事，例如「帳戶餘額永遠不能變成負數」。
  • 冪等性（idempotency）：把一個動作（遷移（migration）、正規化（normalization）、重試（retry））做兩次，效果和做一次相同。
  • 等價性（equivalence）：最佳化過的程式碼，產生的結果和樸素但正確的程式碼相同。

屬性測試（property test）函式庫是讓 AI 代理保持誠實的好方法，因為它用的邊界情況（edge cases），不是帶著「寫出原始程式碼的那個 AI 代理」的同一種偏誤產生的。在改寫（rewrite）時它們也特別有幫助：這時規格（spec）往往已經和正式環境的實際行為脫節，不再是可靠的驗證依據。

差異測試：舊系統就是判定基準Differential tests: the old system is the oracle

差異測試（differential tests）特別適合功能預期維持不變的大規模遷移（migration）情境。做這類測試時，你用相同的輸入同時執行舊系統和新系統，看結果是否不同。如果不同，就有一個需要修正的錯誤，或破壞性變更（breaking change）。

差異測試（differential tests）的關鍵，是使用隨機產生的輸入，或正式環境流量的樣本。你還要把空白字元這類無關的因素正規化（normalize），並維護一份核准變更清單，用在新環境本來就應該和舊環境不同的情況。

Claude Code 團隊如何看待驗證How the Claude Code team thinks about verification

我們之前寫過 Anthropic 的程式碼審查是怎麼運作的，這篇則想更深入地談我們怎樣驗證自己的工作。

驗證就是把變更跑起來Verification means running the change

把應用程式端到端跑一遍，比測試更重要。你不會沒在模擬器裡試過就推出一個 iOS 變更，Claude 也一樣。

Claude 可以像人類或 QA 工程師那樣測試整個應用程式。網頁變更就叫它用 Claude Chrome 擴充功能；行動裝置就用 iOS 或 Android 的 MCP；桌面程式用電腦操作（computer use）；後端工作就讓它在本機把服務跑起來。

為了把「怎樣啟動模擬器、怎樣執行你的應用程式」寫成固定做法，建立一個名為 verify 的技能（skill）。把它放在儲存庫裡的 .claude/skills/ 資料夾，盡量靠近相關的程式碼，需要幾個就加幾個。Claude 知道在提交（commit）變更之前要使用 verify 技能（skill）。

接著，投入心力讓你的 verify 技能（skill）又快又可靠。請 Claude 反覆改進它、對它做壓力測試。它是你的冒煙測試（smoke test）測試框架（harness），所以你希望它堅如磐石。

當你讓 Claude 有辦法對自己的變更做端到端的冒煙測試（smoke test），結果會好很多。你會看到它像人一樣反覆修改，更快抓到真正的錯誤。Anthropic 幾乎所有的變更都是這樣測試的。

失敗的測試需要人來處理Failing tests require human attention

沒有人能讀完每一個變更，所以我們把「失敗」當作判斷哪些事需要人介入的一種方式。Claude 會執行各項檢查，並嘗試修好任何失敗的部分。如果某項檢查經過三輪仍然失敗，Claude 就會停下來，找人處理。

程式碼負責人自己寫檢查Code owners write their own checks

負責這段程式碼的人替它寫檢查，並持續調整，直到檢查會標出負責人自己會標出的問題。當某項檢查需要把審查者拉進來時，它應該說明原因，讓審查者不必從差異（diff）裡自己推敲。

可靠性檢查依差異觸發Reliability checks trigger on the diff

我們維護一份有 39 個項目的可靠性檢查清單，每一項都有一個可以從差異（diff）讀出來的觸發條件、一項檢查，以及促成這一項的事故（incidents）或合併請求（PR）。其中一項是「--resume 會載入舊的紀錄稿（transcripts）」。當工作階段（session）的儲存方式或訊息類型有變動時，我們會問：新的欄位能不能安全載入？因為較舊的紀錄稿（transcripts）裡不會有這個欄位。

Claude 讀取差異（diff），只檢查觸發條件相符的項目（通常是 3 到 10 項），這樣就沒有人需要記住過去的每一次故障。

一位審查者，多輪審查One reviewer, multiple rounds

我們不靠堆疊更多審查者來改善審查。在主要審查者之上再加一個更貴的第二審查者，往往不如把主要審查者調校好。我們的做法是寫一份 REVIEW.md，說明審查者在這份程式碼裡應該注意什麼。

我們也認為，審查和驗證的各輪應該一層一層往上疊。我們讓每一輪都看到前幾輪的脈絡和過去的失敗，而不是每次從頭全部重查一遍。這樣更便宜，也找到更多問題。

變更不能修改自己的檢查Changes can't modify their own checks

如果一個變更能修改評判它的那項檢查，這項檢查就是壞的。Code Review 會從基底分支（base branch）或預設分支（default branch）讀取 REVIEW.md 檔案，絕不從合併請求（pull request）的變更裡讀取。Claude Code 團隊確保把關變更的規則，放在變更本身改不到的分支（branch）上。

Claude Code 團隊也只對提交（commits）做審查。如果審查進行中還有人在推送，那這次的審查結果就不再有用。一個過時提交（commit）上的「審查通過」毫無意義。

團隊也會先跑便宜的檢查。如果 AI 代理沒在本機測試就推送，它就耗用了共用的審查與持續整合（CI）時間，而那個錯誤它本來可以自己抓到。在我們團隊，Claude 會在開出合併請求（pull request）之前，先跑測試、建置（build）和程式碼檢查工具（linter）。你可以用一個在 Claude 完成時執行測試的鉤子（hook），或一個以「測試套件全數通過」為目標的 /goal 來強制做到這點。

新的關卡先用觀察模式啟動Start a new gate in observe mode

在我們自己的儲存庫裡，每個提交（commit）都會蓋上一個「它是怎樣被驗證的」標記。這個標記甚至包含「none（無）」，讓我們可以查詢哪些提交（commits）沒有經過驗證。

我們也建立了一道提交關卡（commit gate）：如果工作階段（session）裡沒有執行過 /code-review 或 /verify，它可以擋下這次提交（commit）。我們替它設了 off（關閉）、observe（觀察）、enforce（強制）三種模式。

觀察模式（observe mode）會記錄哪些提交（commits）「本來會被擋下」，讓我們能檢視任何誤報（false positives），並確保沒有人受到影響。

強制模式（enforce mode）則會擋下提交（commit）。任何提交（commit）都可以在訊息裡附上說明，解釋它為什麼沒有經過驗證。如果同一個工作階段（session）裡已經有提交（commit）被擋了兩次，下一次就會放行，免得 Claude 卡住，畢竟 Claude Code 並不完美。

用真正重要的事來測試你的檢查Test your checks on what actually matters

Claude Code 團隊也會定期「審查審查者」。我們追蹤有多少已合併的變更被回滾（reverted）、有多少變更在合併前被維護者退回，以及一組規模相當、一直沒出問題的變更子集。

這也可以用正式的評測（evaluation）來做。在我們的程式碼審查文章裡，我們描述了 Code Review 團隊怎樣根據過去的事故和回滾（reverts）建立評測（evaluation）。他們為每個範例把儲存庫還原到當時審查的狀態，並提供一句話的標準答案，說明那個錯誤是什麼。只有正確描述出該錯誤的發現才得分。他們用已合併且穩定的變更作為對照組（control），防止過度標記。他們的調校集（tuning set）與用來評估系統的固定測試集（test set）是分開的。

他們也分別評估了原始發現、驗證後、以及最終審查這三個階段的召回率（recall）。這讓他們能看出系統是否把已經找到的錯誤又弄丟了。任何把這些合併成一個端到端分數的評測（evaluation），都抓不到這種細節。

除了正確性之外，我們在意的另一個面向，是這項修改有多重要。好的審查者會抓到大多數技術上正確的問題，但人們在意的是：某個錯誤是非修不可、應該修，還是吹毛求疵（nit）。

Code Review 正是這個想法，它會把問題標成 Important（重要）、Nit（吹毛求疵）或 Pre-existing（既有問題）。「既有問題（pre-existing）」標籤的意思是：對於本來就已經存在的錯誤，審查者不該要作者負責。

最後，Claude Code 團隊會把召回率（recall）一路調高，直到下一步的改進會變成對評測（eval）過度擬合（overfitting），而不是真的抓到更多錯誤為止。

把漏抓變成規則Turn misses into rules

在 Claude Code 的儲存庫裡，我們有兩種把漏抓案例變成規則的方法。第一種是從人工程式碼審查的留言和合併請求（PR）回滾（reverts）中萃取模式，找出常見問題。一個模式必須至少出現在兩個合併請求（PR）裡，而且可以從差異（diff）辨識出來，才會被視為可能的規則。接著會有三個 AI 代理試著推翻它，最後在一個合併請求（PR）裡由人審查並核准。

第二種方法，是拿一個與已知事故相關的合併請求（PR），讓三個找錯工具重新跑一遍。如果至少有兩個找到了這個錯誤，它就是一個可被偵測的錯誤。如果這個錯誤在一個小的差異（diff）上被漏掉了，這就是一個值得寫成 REVIEW.md 規則的缺口。

不穩定（flaky）的測試也受到同樣的處理。Claude 不能跳過它們、加入等待（sleep），或重試（retry）到它們通過為止。如果找不到根本原因（root cause），它就刪掉這個測試，並寫下原因。

規則也需要清理。測試套件、驗證步驟和 .md 檔案，只要你放任，就只會越長越多，所以我們會定期整理它們。

好的測試，好的結果Good tests, good results.

我們發現，給你的 AI 代理一個能用強力回饋迴圈（feedback loop）驗證自身工作的方法，會帶來決定性的差別。像對待任何其他系統一樣，對待你的驗證層：讓它不受它所評判的變更影響；用對你真正重要的錯誤來替它評分；當它漏掉什麼時，寫下教訓，讓同樣的事不會發生第二次；再修剪這些教訓，讓它們一直值得執行。

做到這些，你的工作就會從讀每一個差異（diff），轉變成定義「完成」長什麼樣子、並審查證據。這正是讓你能同時跑很多個 Claude 的關鍵。

以下為譯者整理，非原文內容。

這篇在說什麼

Claude Code 團隊約 90% 的程式碼由 Claude 撰寫並審查。這篇說明他們怎樣讓 AI 代理「用證據證明自己做對了」：先介紹三種最值得投資的測試，再分享團隊實際的驗證規則，從把應用程式真正跑起來，到讓檢查不被變更本身修改、把漏抓的錯誤寫成規則。

核心主張是：有了驗證迴圈（verification loop），你才能放心同時跑很多個 Claude；你的工作也從讀每一個差異（diff），轉成定義「完成」的樣子並審查證據。

為什麼值得學

多數人讓 AI 寫程式時，卡在「每一行都得自己看」。這篇把「怎樣信任 AI 的產出」拆成可以實作的機制：哪種測試最難被唬弄、什麼時候該找人、檢查要放在哪裡才不會被改掉、怎樣檢驗檢查本身。即使你不寫程式，「讓產出附上證據，再把漏網之魚變成規則」這套想法，也適用於任何要大量把關的工作。

你可以帶走的重點

1. 驗證迴圈（verification loop）決定你能交出多少工作

沒有驗證，你只能同時跑一兩個 Claude；有了驗證，可以平行跑幾十、幾百個。產生測試、基準測試（benchmark）、規格（spec）現在很便宜，產生之後就能反覆執行，不必多花很多 token。

2. 先避開不穩定（flaky）和太慢的測試

不穩定（flaky）的測試會教 AI 代理「再跑一次」而不是修程式；太慢的測試會讓它少跑測試、難以定位問題。較重的測試放在提交（commit）之前。

3. 三種最值得投資的測試

只能選一種就選端到端測試（E2E tests）：整個功能要嘛能用、要嘛不能用，很難唬弄，還能告訴你哪一步壞了。屬性測試（property tests）用上千個隨機輸入去打破「不可能失敗」的陳述，抓 AI 代理容易漏的邊界情況（edge cases）。差異測試（differential tests）讓舊系統當判定基準（oracle），適合功能應維持不變的遷移（migration）。

4. 驗證就是把變更真正跑起來

端到端地跑應用程式比測試更重要：網頁用 Claude Chrome 擴充功能，行動裝置用 iOS／Android 的 MCP，桌面用電腦操作（computer use），後端就在本機跑服務。把啟動方式寫成一個 verify 技能（skill），放進 .claude/skills/，並讓它又快又可靠。

5. 用失敗決定什麼時候找人

Claude 自己跑檢查、自己修；同一項檢查三輪仍失敗才找人。檢查由程式碼負責人撰寫，拉人進來時要說明原因。39 項可靠性清單依差異（diff）觸發，每次通常只檢查 3 到 10 項。

6. 檢查要放在變更改不到的地方

能修改自己評判標準的變更，等於沒有檢查：REVIEW.md 從基底分支（base branch）讀取，不從合併請求（PR）讀。審查只對固定的提交（commit）有效；先跑便宜的檢查，可以用鉤子（hook）或 /goal 強制。與其堆更多審查者，不如調好一位審查者，讓多輪審查互相接續。

7. 新關卡先觀察，再強制

每個提交（commit）都標記怎樣被驗證過（含「none」）。提交關卡（commit gate）有 off、observe、enforce 三種模式：先用觀察模式（observe mode）找出誤報（false positives），再切到強制模式（enforce mode）；被擋兩次就放行，免得 Claude 卡住。

8. 審查審查者，把漏抓變成規則

追蹤回滾（revert）數與退回數，用過去的事故建立評測（eval），分階段量召回率（recall），並用穩定變更當對照組（control）防止過度標記；召回率（recall）調到快要過度擬合（overfitting）就停。漏抓的模式至少出現在兩個合併請求（PR）、可從差異（diff）辨識，經三個 AI 代理試著推翻、人核准後才寫成規則。規則也要定期修剪。

怎麼開始

  1. 替你最重要的一條使用者流程寫一個端到端測試（E2E test），讓它失敗時能說出是哪一步壞了。
  2. 建立一個 verify 技能（skill），寫清楚怎樣啟動你的應用程式並檢查結果，放進 .claude/skills/。
  3. 規定 AI 代理在開合併請求（PR）前先跑測試、建置和程式碼檢查工具（linter），可以用鉤子（hook）強制。
  4. 找出一個「不可能失敗」的陳述（例如編碼後解碼得回原值），用 fast-check、Hypothesis 或 proptest 寫成屬性測試（property test）。
  5. 每次 AI 代理漏掉錯誤，就把教訓寫進 CLAUDE.md 或 REVIEW.md，並定期刪掉不再有用的規則。
