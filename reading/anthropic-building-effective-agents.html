打造有效的 AI 代理

原文標題：Building effective agents

作者：Erik S.、Barry Zhang（Anthropic）

原文：https://www.anthropic.com/research/building-effective-agents

日期：2024-12-19

備註：繁體中文翻譯，僅供個人閱讀。

注意：自 2024 年 12 月以來，本文所描述的工具生態有許多已經改變。關於我們目前的做法，請參閱我們如何打造 Claude Managed Agents（how we built Claude Managed Agents）以及 Managed Agents 文件（Managed Agents documentation）。

過去一年，我們與各行各業數十個團隊合作，一起打造以大型語言模型（large language model，LLM）為基礎的 AI 代理。一再出現的情形是：最成功的實作並不是使用複雜的框架（framework）或專門的函式庫，而是用簡單、可組合（composable）的模式來打造。

在這篇文章裡，我們分享從與客戶合作、以及自己打造 AI 代理的過程中學到的東西，並給開發者一些關於如何打造有效 AI 代理的實用建議。

什麼是 AI 代理？（What are agents?）

「代理」（Agent）有好幾種定義方式。有些客戶把 AI 代理定義成完全自主的系統：能長時間獨立運作，使用各種工具來完成複雜任務。也有些客戶用這個詞來指稱比較有規範性的實作，也就是遵循預先定義好的工作流程（workflow）。在 Anthropic，我們把所有這些變體都歸類為代理式系統（agentic systems），但在架構上對工作流程（workflow）與 AI 代理做出一個重要的區分：

  • 工作流程（workflow）是透過預先定義好的程式碼路徑，來編排 LLM 與工具的系統。
  • 另一方面，AI 代理則是由 LLM 動態主導自己的流程與工具使用、並掌控如何完成任務的系統。

接下來，我們會詳細探討這兩種代理式系統（agentic systems）。在附錄 1（「AI 代理的實際應用」，“Agents in Practice”）中，我們會介紹兩個客戶發現使用這類系統特別有價值的領域。

何時該用 AI 代理（何時不該用）（When (and when not) to use agents）

用 LLM 打造應用程式時，我們建議先找出盡可能簡單的解決方案，只有在需要時才增加複雜度。這可能意味著根本不要打造代理式系統（agentic systems）。代理式系統往往以延遲（latency）與成本，換取更好的任務表現，你應該考慮這樣的取捨在什麼情況下合理。

當確實需要更高的複雜度時，工作流程（workflow）能為定義明確的任務提供可預測性與一致性；而在需要大規模的彈性與由模型驅動的決策時，AI 代理是比較好的選擇。不過，對許多應用來說，只要用檢索（retrieval）與脈絡內範例（in-context examples）來優化單一一次 LLM 呼叫，通常就已經足夠。

何時以及如何使用框架（When and how to use frameworks）

有許多框架（framework）能讓代理式系統（agentic systems）更容易實作，包括：

  • Claude Agent SDK；
  • AWS 的 Strands Agents SDK；
  • Rivet，一個可拖放（drag and drop）的圖形介面（GUI）LLM 工作流程（workflow）建構工具；以及
  • Vellum，另一個用來建構與測試複雜工作流程（workflow）的圖形介面（GUI）工具。

這些框架（framework）把呼叫 LLM、定義與解析工具、把多次呼叫串接起來這類標準的底層任務加以簡化，因此讓人很容易上手。然而，它們往往會多加幾層抽象（abstraction），遮住底層的提示詞（prompt）與回應，讓除錯（debug）變得更困難。在簡單的設定就夠用的時候，它們也會讓人忍不住去增加複雜度。

我們建議開發者一開始先直接使用 LLM API：許多模式只要幾行程式碼就能實作。如果你確實使用框架（framework），請務必理解底層的程式碼。對底層運作方式的錯誤假設，是客戶常見的出錯來源。

範例實作請見我們的 cookbook。

基本單元、工作流程與 AI 代理（Building blocks, workflows, and agents）

在這一節，我們會探討在正式環境（production）中看到的代理式系統（agentic systems）常見模式。我們從最基礎的基本單元——增強型 LLM（augmented LLM）——開始，逐步提高複雜度：從簡單的組合式工作流程（workflow），到自主的 AI 代理。

基本單元：增強型 LLM（Building block: The augmented LLM）

代理式系統（agentic systems）的基本單元，是一個經過增強功能（augmentations）強化的 LLM，這些增強功能包括檢索（retrieval）、工具與記憶。我們目前的模型能主動運用這些能力——自己產生搜尋查詢、挑選合適的工具，並決定要保留哪些資訊。

我們建議把重點放在實作的兩個關鍵面向：讓這些能力貼合你的特定使用情境，並確保它們為你的 LLM 提供一個容易使用、文件完整的介面。實作這些增強功能（augmentations）的方式有很多種，其中一種做法是透過我們最近推出的模型上下文協定（Model Context Protocol，MCP），開發者只要寫一個簡單的用戶端（client）實作，就能與日益成長的第三方工具生態系整合。

在本文接下來的部分，我們會假設每一次 LLM 呼叫都能使用這些增強的能力。

工作流程：提示詞串接（Workflow: Prompt chaining）

提示詞串接（prompt chaining）把一個任務拆解成一連串步驟，每一次 LLM 呼叫都處理上一次的輸出。你可以在任何中間步驟加上程式化的檢查（見下圖中的「閘門」，“gate”），確保整個流程仍在正軌上。

何時使用這種工作流程（When to use this workflow）：當任務可以輕易且乾淨地拆解成固定的子任務時，這種工作流程（workflow）最理想。主要目標是讓每一次 LLM 呼叫都變成比較簡單的任務，以延遲（latency）換取更高的準確度。

提示詞串接（prompt chaining）有用的範例（Examples where prompt chaining is useful）：

  • 產生行銷文案，然後把它翻譯成另一種語言。
  • 寫出文件大綱，檢查大綱是否符合某些標準，然後根據大綱撰寫文件。

工作流程：路由（Workflow: Routing）

路由（routing）會對輸入進行分類，並把它導向專門的後續任務。這種工作流程（workflow）能做到關注點分離（separation of concerns），並讓人建立更專門的提示詞（prompt）。如果沒有這種工作流程（workflow），針對某一種輸入做優化，可能會損害其他輸入的表現。

何時使用這種工作流程（When to use this workflow）：路由（routing）適合複雜任務：當任務有幾個明顯不同的類別，分開處理會比較好，而且分類可以被準確地處理——不論是由 LLM，或由比較傳統的分類模型／演算法來做。

路由（routing）有用的範例（Examples where routing is useful）：

  • 把不同類型的客服詢問（一般問題、退款請求、技術支援）導向不同的下游流程、提示詞（prompt）與工具。
  • 把簡單／常見的問題導向較小、較省成本的模型，例如 Claude Haiku 4.5；把困難／少見的問題導向能力更強的模型，例如 Claude Sonnet 4.5，以達到最佳表現。

工作流程：平行化（Workflow: Parallelization）

LLM 有時可以同時處理一項任務，再由程式把它們的輸出彙整起來。這種工作流程（workflow），也就是平行化（parallelization），主要有兩種變化：

  • 分段（Sectioning）：把任務拆成彼此獨立的子任務，平行執行。
  • 投票（Voting）：把同一個任務執行多次，以取得多樣化的輸出。

何時使用這種工作流程（When to use this workflow）：當切分出來的子任務可以平行處理以提高速度，或是需要多種觀點或多次嘗試，來得到更有信心的結果時，平行化（parallelization）很有效。對於需要考量多個面向的複雜任務，通常讓每個考量由獨立的一次 LLM 呼叫來處理，LLM 的表現會比較好，因為可以把注意力集中在每個特定面向上。

平行化（parallelization）有用的範例（Examples where parallelization is useful）：

  • 分段（Sectioning）：
    • 實作護欄（guardrails）：由一個模型實例處理使用者的查詢，另一個則負責篩檢其中是否有不當內容或請求。這樣做的表現，往往比讓同一次 LLM 呼叫同時處理護欄（guardrails）與核心回應來得好。
    • 自動化評估（evals）來評量 LLM 的表現，其中每一次 LLM 呼叫，評估模型在某個給定提示詞（prompt）上的不同面向表現。
  • 投票（Voting）：
    • 審查一段程式碼是否有漏洞：用幾個不同的提示詞（prompt）去審查，只要發現問題就標記這段程式碼。
    • 評估某段內容是否不當：用多個提示詞（prompt）評估不同面向，或要求不同的投票門檻（vote thresholds），以平衡偽陽性（false positives）與偽陰性（false negatives）。

工作流程：協調器—工作者（Workflow: Orchestrator-workers）

在協調器—工作者（orchestrator-workers）這種工作流程（workflow）中，由一個中央 LLM 動態地拆解任務、把任務委派給工作者（worker）LLM，並綜合它們的結果。

何時使用這種工作流程（When to use this workflow）：這種工作流程（workflow）很適合你無法預測需要哪些子任務的複雜任務（例如在寫程式時，需要修改的檔案數量，以及每個檔案要做的修改性質，很可能取決於任務本身）。雖然它在結構上（topographically）與平行化（parallelization）很相似，但關鍵的差異在於它的彈性——子任務不是預先定義好的，而是由協調器（orchestrator）根據特定的輸入來決定。

譯註：原文此處寫的是 topographically（地形上的）；從語意看，作者指的應該是兩者的「結構」相似，因此譯為「在結構上」並保留原詞。

協調器—工作者（orchestrator-workers）有用的範例（Example where orchestrator-workers is useful）：

  • 每次都要對多個檔案做複雜修改的寫程式產品。
  • 需要從多個來源蒐集並分析資訊，以找出可能相關內容的搜尋任務。

工作流程：評估者—優化者（Workflow: Evaluator-optimizer）

在評估者—優化者（evaluator-optimizer）這種工作流程（workflow）中，一次 LLM 呼叫負責產生回應，另一次則在迴圈（loop）中提供評估與回饋。

何時使用這種工作流程（When to use this workflow）：當我們有明確的評估標準，而且反覆精修能帶來可衡量的價值時，這種工作流程（workflow）特別有效。判斷是否適合的兩個徵兆是：第一，當人類說出他們的回饋時，LLM 的回應確實能被明顯改善；第二，LLM 本身也能提供這樣的回饋。這類似於人類作者在產出一份完善文件時可能經歷的反覆寫作過程。

評估者—優化者（evaluator-optimizer）有用的範例（Examples where evaluator-optimizer is useful）：

  • 文學翻譯：其中有些細微之處，翻譯用的 LLM 一開始可能抓不到，但評估用的 LLM 可以提供有用的批評。
  • 需要多輪搜尋與分析才能蒐集到完整資訊的複雜搜尋任務，由評估者決定是否有必要再繼續搜尋。

AI 代理（Agents）

隨著 LLM 在幾項關鍵能力上逐漸成熟——理解複雜的輸入、進行推理與規劃、可靠地使用工具、從錯誤中復原——AI 代理開始出現在正式環境（production）中。AI 代理一開始是從人類使用者下達的指令，或與使用者的互動式討論開始工作。一旦任務明確，AI 代理就會自行規劃並獨立運作，有可能回頭向人類索取更多資訊或判斷。在執行過程中，AI 代理很重要的一點，是在每一步都從環境取得「真實依據」（ground truth）（例如工具呼叫的結果或程式碼執行的結果），以評估自己的進度。接著，AI 代理可以在檢查點（checkpoints）或遇到阻礙時暫停，等待人類回饋。任務通常在完成時結束，但也常會加入停止條件（stopping conditions）（例如最大迭代次數）來維持控制。

AI 代理能處理精密複雜的任務，但它們的實作往往很直接。它們通常只是 LLM 在迴圈（loop）中，根據環境的回饋來使用工具。因此，清楚而周全地設計工具組與它們的文件至關重要。我們會在附錄 2（「為你的工具做提示詞工程」，"Prompt Engineering your Tools"）進一步說明工具開發的最佳實踐。

何時使用 AI 代理（When to use agents）：AI 代理可用於開放式的問題：所需步驟數很難甚至不可能預測，而且你無法把固定路徑寫死。LLM 可能會運作許多回合，你必須對它的決策有一定程度的信任。AI 代理的自主性，讓它們很適合在受信任的環境中擴大任務規模。

AI 代理的自主特性，意味著更高的成本，以及錯誤累積（compounding errors）的可能。我們建議在沙箱（sandbox）環境中進行大量測試，並搭配適當的護欄（guardrails）。

AI 代理有用的範例（Examples where agents are useful）：

以下範例來自我們自己的實作：

  • 一個用來解決 SWE-bench 任務的程式開發 AI 代理（coding agent），這類任務需要根據任務描述修改許多檔案；
  • 我們的「電腦操作」（computer use）參考實作，讓 Claude 使用電腦來完成任務。

組合與客製這些模式（Combining and customizing these patterns）

這些基本單元並不是硬性規定。它們是常見的模式，開發者可以依不同的使用情境加以調整與組合。和任何 LLM 功能一樣，成功的關鍵是衡量表現，並反覆改進實作。再說一次：只有在複雜度能明確改善成果時，你才應該考慮增加它。

總結（Summary）

在 LLM 領域，成功不在於打造最精密複雜的系統，而在於打造適合你需求的系統。從簡單的提示詞（prompt）開始，用完整的評估來優化它，只有在比較簡單的解法不夠用時，才加入多步驟的代理式系統（agentic systems）。

在實作 AI 代理時，我們試著遵循三項核心原則：

  1. 讓你的 AI 代理在設計上保持簡潔（simplicity）。
  2. 優先考慮透明度（transparency），明確顯示 AI 代理的規劃步驟。
  3. 透過完整的工具文件與測試（documentation and testing），謹慎打造你的 AI 代理—電腦介面（agent-computer interface，ACI）。

框架（framework）可以幫助你快速上手，但當你邁向正式環境（production）時，不要猶豫，減少抽象層（abstraction layers），用基本元件來打造。遵循這些原則，你就能打造出不只強大、而且可靠、可維護、並且受使用者信任的 AI 代理。

附錄 1：AI 代理的實際應用（Appendix 1: Agents in practice）

我們與客戶合作的經驗顯示，有兩種特別有前景的 AI 代理應用，能展現上述模式的實際價值。這兩種應用都說明了，AI 代理在哪些任務上能加值最多：任務同時需要對話與行動、有明確的成功標準、能形成回饋迴圈（feedback loops），並且納入有意義的人為監督。

A. 客戶支援（A. Customer support）

客戶支援結合了大家熟悉的聊天機器人介面，並透過工具整合強化其能力。這很自然地適合比較開放式的 AI 代理，原因是：

  • 支援互動自然會依循對話的流程，同時又需要存取外部資訊並採取行動；
  • 可以整合工具來調出客戶資料、訂單紀錄與知識庫文章；
  • 像是核發退款或更新工單這類動作，可以用程式處理；以及
  • 成功與否，可以透過使用者定義的問題解決來清楚衡量。

有幾家公司已經透過以用量計價的模式，證明了這種做法的可行性：他們只對成功解決的案件收費，顯示出對自家 AI 代理成效的信心。

B. 程式開發 AI 代理（B. Coding agents）

軟體開發領域已展現出 LLM 功能的驚人潛力，能力從程式碼補全，演進到自主解決問題。AI 代理在這裡特別有效，因為：

  • 程式碼解法可以透過自動化測試來驗證；
  • AI 代理可以把測試結果當作回饋，反覆改進解法；
  • 問題空間定義明確、結構清楚；以及
  • 輸出品質可以客觀衡量。

在我們自己的實作中，AI 代理現在只憑合併請求（pull request）的描述，就能解決 SWE-bench Verified 基準測試（benchmark）中的真實 GitHub 議題（issues）。然而，雖然自動化測試有助於驗證功能，但要確保解法符合更廣泛的系統需求，人工審查仍然至關重要。

附錄 2：為你的工具做提示詞工程（Appendix 2: Prompt engineering your tools）

不論你打造的是哪一種代理式系統（agentic systems），工具很可能都會是你的 AI 代理的重要部分。工具讓 Claude 能透過在我們的 API 中指定外部服務與 API 的確切結構與定義，來與它們互動。當 Claude 打算呼叫工具時，它的回應會在 API 回應中包含一個工具使用區塊（tool use block）。工具定義與規格，應該得到和你整體提示詞（prompt）同樣多的提示詞工程（prompt engineering）關注。在這個簡短的附錄中，我們說明如何為你的工具做提示詞工程（prompt engineering）。

指定同一個動作，往往有好幾種方式。例如，你可以用寫出差異（diff）的方式來指定檔案編輯，也可以重寫整個檔案。對於結構化輸出，你可以把程式碼放在 markdown 裡回傳，也可以放在 JSON 裡。在軟體工程中，這類差異只是表面的，可以無損地互相轉換。然而，對 LLM 來說，有些格式比其他格式難寫得多。寫差異（diff）時，必須在寫出新的程式碼之前，就先知道區塊標頭（chunk header）裡有多少行會改變。把程式碼寫在 JSON 裡（相對於 markdown），則需要對換行與引號做額外的跳脫（escaping）。

我們對於決定工具格式的建議如下：

  • 在模型把自己寫進死胡同之前，給它足夠的令牌（token）去「思考」。
  • 讓格式貼近模型在網際網路上的文字中自然看過的樣子。
  • 確認沒有格式上的「負擔」（overhead），例如必須精確計算數千行程式碼的行數，或是必須對它寫出的任何程式碼做字串跳脫（string-escaping）。

一個經驗法則（rule of thumb）是：想想你在人機介面（human-computer interfaces，HCI）上投入了多少心力，並且計畫在打造良好的 AI 代理—電腦介面（agent-computer interfaces，ACI）上投入同樣多的心力。以下是一些做法的想法：

  • 設身處地站在模型的立場想想。光看描述與參數，就能明顯看出這個工具該怎麼用嗎？還是你得仔細想一想？如果是後者，那對模型來說大概也是如此。好的工具定義通常包含使用範例、邊界情況（edge cases）、輸入格式要求，以及與其他工具之間的清楚界線。
  • 你要如何修改參數名稱或描述，讓事情更明顯？把這想成是在為團隊裡的初階開發者（junior developer）寫一份很棒的文件字串（docstring）。在使用許多相似工具時，這一點尤其重要。
  • 測試模型如何使用你的工具：在我們的 workbench 裡跑大量的範例輸入，看看模型會犯什麼錯誤，然後反覆改進。
  • 為你的工具做防呆（Poka-yoke）設計。修改參數，讓人更難犯錯。

在為 SWE-bench 打造我們的 AI 代理時，我們其實花了比整體提示詞（prompt）更多的時間來優化我們的工具。例如，我們發現，在 AI 代理離開根目錄之後，模型在使用相對檔案路徑的工具上會出錯。為了解決這個問題，我們把工具改成一律要求使用絕對檔案路徑——結果我們發現模型使用這個方法時毫無失誤。

以下為譯者整理，非原文內容。

這篇在說什麼

Anthropic 兩位作者 Erik S. 與 Barry Zhang 根據與數十個團隊合作的經驗，說明怎麼打造有效的 AI 代理：最成功的做法不是複雜的框架（framework），而是簡單、可組合的模式。

文章先區分「工作流程（workflow）」與「AI 代理」，再依序介紹從增強型 LLM（augmented LLM）、五種工作流程（workflow）模式，到自主 AI 代理的做法，最後提出三項原則，以及客戶支援、程式開發兩個實際應用，和為工具做提示詞工程（prompt engineering）的建議。

為什麼值得學

就算你不寫程式，也能從這篇學到一個很實用的判斷方式：遇到事情時，先用最簡單的做法，確實不夠用，才一步步加上複雜度。原文也提醒，AI 代理通常要用更高的成本，換取更好的表現，還可能出現錯誤累積。讀的時候留意一點：原文開頭註明，文中描述的工具生態自 2024 年 12 月以來有許多已經改變，所以重點放在這些設計思路，而不是個別工具。

你可以帶走的重點

1. 從最簡單的做法開始，需要時才增加複雜度

原文建議，用 LLM 打造應用程式時，先找出盡可能簡單的解決方案；這可能意味著根本不要打造代理式系統（agentic systems），因為它們往往以延遲（latency）與成本，換取更好的任務表現。對許多應用來說，只要用檢索（retrieval）與脈絡內範例（in-context examples）來優化單一一次 LLM 呼叫，通常就已經足夠。框架（framework）能幫你快速上手，但會多加抽象層（abstraction），讓除錯（debug）更困難，所以原文建議一開始先直接使用 LLM API，並確實理解底層的程式碼。

2. 工作流程走寫好的路，AI 代理自己決定路

Anthropic 把這兩者統稱為代理式系統（agentic systems），但做了架構上的區分：工作流程（workflow）是透過預先定義好的程式碼路徑，來編排 LLM 與工具；AI 代理則是由 LLM 動態主導自己的流程與工具使用。工作流程（workflow）適合定義明確、需要可預測性與一致性的任務；需要大規模彈性與由模型驅動的決策時，才輪到 AI 代理。

3. 五種工作流程模式，各解決一種情況

原文從增強型 LLM（augmented LLM）這個基本單元出發——它是加上檢索（retrieval）、工具與記憶的 LLM，再介紹五種工作流程（workflow）：提示詞串接（prompt chaining）把任務拆成一連串步驟；路由（routing）先分類再交給專門的後續任務；平行化（parallelization）分為分段（sectioning）與投票（voting）；協調器—工作者（orchestrator-workers）由中央 LLM 動態拆解任務；評估者—優化者（evaluator-optimizer）一個產生、一個評估並回饋。原文強調這些模式不是硬性規定，可以依使用情境調整與組合，而且只有在複雜度能明確改善成果時才增加。

4. AI 代理就是 LLM 在迴圈中用工具，要設好停止條件與護欄

原文說，AI 代理的實作往往很直接：通常只是 LLM 在迴圈（loop）中，根據環境的回饋來使用工具。執行時要在每一步從環境取得真實依據（ground truth），並可以在檢查點（checkpoints）或遇到阻礙時暫停，等待人類回饋；也常會加入停止條件（stopping conditions），例如最大迭代次數。因為自主特性意味著更高的成本與錯誤累積（compounding errors），原文建議在沙箱（sandbox）環境中大量測試，並搭配適當的護欄（guardrails）。

5. 工具介面要花和提示詞一樣多的心力

原文的三項核心原則是：設計簡潔（simplicity）、優先考慮透明度（transparency）、並透過完整的工具文件與測試，謹慎打造 AI 代理—電腦介面（agent-computer interface，ACI）。附錄給了幾個具體做法：站在模型的立場想想工具好不好懂；把參數名稱與描述寫得像給初階開發者（junior developer）的文件字串（docstring）；在 workbench 裡跑大量範例輸入、看模型犯什麼錯；對工具做防呆（Poka-yoke）設計。原文的實例是：在打造 SWE-bench 的 AI 代理時，他們花在優化工具上的時間比整體提示詞（prompt）還多；把工具改成一律要求絕對檔案路徑後，模型使用起來毫無失誤。

怎麼開始

  1. 先問自己：單一一次 LLM 呼叫，加上檢索（retrieval）與範例，是不是已經夠用？夠用就不必打造代理式系統（agentic systems）。
  2. 需要更多時，先判斷任務是否能拆成固定的步驟：能的話，從五種工作流程（workflow）模式挑一種；步驟數無法預測，才考慮 AI 代理。
  3. 用框架（framework）之前，先直接呼叫 LLM API 試試；真的用了，要理解底層的程式碼。
  4. 做 AI 代理時，設好停止條件（stopping conditions），在沙箱（sandbox）環境裡大量測試，並加上護欄（guardrails）。
  5. 把每個工具的名稱、參數與描述寫清楚，並在 workbench 裡實際試用，依模型犯的錯誤反覆調整。
