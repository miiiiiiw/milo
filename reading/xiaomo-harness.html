研究了這麼多 AI 代理（Agent），我越來越覺得，工作環境（Harness）才是最值得深入研究的方向。

最近看到 Anthropic 分享的一篇關於長時間任務 AI 代理的文章，裡面的一些思路讓我滿有感觸的。

因為不管是研究還是實際使用，我自己都折騰過不少工作環境（Harness），包括 Pi Agent、DeepSeek Harness、Claude Code、Codex，還有 Hermes Agent。

在這個過程中我發現，每一個工作環境（Harness）本質上其實都很像，表現出來的結果卻各不相同，同一個模型放到不同的工作環境（Harness）上，表現可能就不一樣。

我總結下來，差別一般出在這幾個問題上：

1、首先是脈絡管理

因為 AI 代理在執行複雜任務的時候，會不斷累積脈絡。如何保留重要資訊、壓縮無用的內容，以及在脈絡切換之後繼續理解先前的任務，其實很考驗工作環境（Harness）的設計。

2、其次是長時間任務的執行能力

這方面我自己踩過不少雷，有時候一個任務跑了幾十分鐘突然卡死，或是中途出了問題，只能從頭再來。

所以我覺得，一個成熟的工作環境（Harness）不應該只是能執行任務，還要考慮任務狀態、異常復原，以及怎麼從中斷的位置繼續執行。

3、最後是結果驗證

這也是我覺得很容易被忽略的地方。很多時候 AI 代理告訴你任務已經完成了，實際結果卻可能並不符合預期。

如果缺少可靠的驗證機制，模型再強，也很難保證複雜任務的最終品質。

我希望市面上的工作環境（Harness）越來越好，尤其是中國自家的工作環境（Harness），不管是 DeepSeek Harness 還是 WorkBuddy。只有強大的模型搭配強大的工作環境（Harness），才是唯一的出路。

為什麼值得學

很多人比較 AI 代理時只比模型。這篇提醒你把眼光放到模型外面那一層：脈絡怎麼留、任務中斷怎麼接、完成了怎麼驗。這三點也剛好對應附圖表格裡 Anthropic 的具體做法（功能清單、進度筆記、git 提交、init.sh），可以直接拿來檢查自己在用的工具。要注意的是，作者的三點是個人使用心得，沒有附測試數據；具體做法以 Anthropic 原文為準。

你可以帶走的重點

1. 比 AI 代理時，別只比模型

作者用過的幾套工作環境（Harness）本質都很像，結果卻各不相同，同一個模型換個工作環境（Harness）就可能表現不一樣。他的結論是：強大的模型要搭配強大的工作環境（Harness）才行。評估工具時，同一個任務、同一個模型，換不同的工作環境（Harness）跑跑看，差異會比看規格表清楚。

2. 脈絡管理：留下什麼，下一段才接得起來

複雜任務會不斷累積脈絡。好的工作環境（Harness）要決定保留哪些重要資訊、壓縮哪些沒用的內容，並在脈絡切換之後還能接回先前的任務。Anthropic 的附圖說得更直白：每個新的工作階段都不記得上一段，就像輪班的工程師，所以要靠留下的產出物交接。

3. 長時間任務：要能記住狀態、從斷點接著做

作者踩過的雷是任務跑幾十分鐘突然卡死，或中途出錯只能從頭來。成熟的工作環境（Harness）要管任務狀態、異常復原，以及從中斷的位置繼續執行。附圖表格裡對應的做法是：初始化時建好 git 儲存庫與進度筆記檔，每個工作階段開頭先讀進度筆記與 git 提交紀錄，結束前寫一次 git 提交（commit）並更新進度。

4. 結果驗證：AI 代理說「完成了」不算數

作者認為最容易被忽略的是驗證：AI 代理常說任務完成，結果卻不符合預期。表格裡兩個問題都跟這有關：Claude 太早宣告整個專案完成、過早把功能標成完成。解法是先建一份結構化的功能清單，每次只做一項，自我驗證並仔細測試後才標成「passing」（通過）。

怎麼開始

  1. 先讀作者推薦的 Anthropic〈Effective harnesses for long-running agents〉，特別是附圖二那張失敗模式表。
  2. 挑一個你常交給 AI 代理的長任務，用同一個模型在兩套工作環境（Harness）各跑一次，記下哪一套卡住、哪一套謊報完成。
  3. 替長任務準備一份功能清單（例如 JSON 檔），要求 AI 代理每次只挑一項做。
  4. 要求 AI 代理每個工作階段結束前更新進度筆記並做一次 git 提交（commit），下一段開頭先讀這兩樣。
  5. 把「怎麼啟動與測試」寫成一支腳本（例如 init.sh），並規定只有實際測過的功能才能標成完成。
