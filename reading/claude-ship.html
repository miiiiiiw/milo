推出 Claude Ship

開一個合併請求（PR, pull request），然後回去繼續做東西。Claude 現在可以審查合併請求（PR）、修正它們，並核准團隊政策允許的那些。

開過合併請求（PR）的人都知道流程是怎麼走的。他們開始做下一件事，然後審查結果回來了。於是他們停下來，重新鑽回舊的程式碼，推上一個修正，再等審查重新跑一次。接著還得去找人來核准。

會這樣運作是有道理的。大多數團隊希望每個變更都由一個人來核准；當每一行程式碼都是人寫的，要跟上這個節奏並不難。但現在很多開發者是和 AI 代理（agent）一起開發的。在 Claude Code 團隊，我們大部分的程式碼是 Claude 寫的，我們希望合併請求（PR）之後的每一步也能跑得一樣快。

這就是我們打造 Claude Ship 的原因，今天起以測試版（beta）推出。它可以審查合併請求（PR）、修正它們，並根據各團隊設定的政策，判斷哪些已經可以合併（merge）。團隊仍然掌控它在哪裡運作，以及哪些變更需要人來看。目標是：程式碼寫得多快，就交付得多快。

符合資格的 Claude Enterprise 組織可以領取至少 10,000 美元的 Claude Ship 額度，須在領取後 30 天內使用。請在 2027 年 1 月 15 日前領取。適用相關條款。

Claude Ship 怎麼運作：審查、修正、核准How Claude Ship works: review, fix, and approve

Claude Ship 由已經正式開放（generally available）的 Code Review，以及兩個以測試版（beta）推出的新 AI 代理（agent）組成：PR Steward 和 Claude Approvals。它們一起帶著一個合併請求（PR）走完審查、修正和核准決定，讓團隊不必手動管理每一步。

Code Review 會從多個角度，對照整個程式碼庫（codebase）深入審查合併請求（PR）。它收集發現（findings），以對抗式（adversarial）的方式驗證它們、加以分類，再張貼到合併請求（PR）上。在 Claude Code 團隊，Claude 的審查只是更大流程中的一層；從 6 月到 9 月，合併的合併請求（PR）數量成長了一倍以上，而被回滾（revert）的比例下降了超過 40%。Code Review 給團隊快速的審查、清楚的發現，而且每個儲存庫（repository）都能選擇 Quick、Standard 或 Deep 三種審查等級。

PR Steward 負責讓合併請求（PR）保持綠燈，但它的設計是不會核准或合併合併請求（PR）。遇到失敗的持續整合（CI）檢查、合併衝突（merge conflict），以及來自 Code Review、其他審查工具或團隊成員的審查意見，它都會介入。每次推送之後，它會留言說明改了什麼、要怎麼復原。開發者可以留言 @claude 加上指示來引導它的工作，或留言 @claude stop 讓它退開。

接下來，Claude Approvals 會套用團隊寫成檔案放在儲存庫（repository）裡的核准政策。如果政策允許，Claude 可以自己核准例行的變更；在某些情境下，也可以要求更深入的人工簽核（sign-off）。它的作用就像一個更聰明的 CODEOWNERS 檔案。團隊可以讓 Claude Approvals 在做決定時參考各種訊號，包括 Code Review 的發現，或團隊自己用自然語言寫成的分類器（classifier）。對大多數客戶，我們建議先在只觀察模式（observe-only mode）下啟用，建立信心之後，再設定分支保護（branch protection），要求必須取得 Claude Approvals 的綠燈。

兩種開始的方式Two ways to get started

給開發者：在 Claude Code 裡用 /ship 送出For developers: /ship it from Claude Code

開發者可以用 Claude Code 新的 /ship 指令，在自己的合併請求（PR）上試用 Claude Ship。變更準備好時，執行 /ship。Claude 會推送變更、開啟合併請求（PR）、審查變更，並處理審查意見和失敗的檢查，幫它達到可以合併的狀態。能合併什麼，取決於開發者的權限和儲存庫（repository）的分支規則。

給管理員和工程主管：一次一個儲存庫，設定規則For admins and engineering leaders: set the rules, one repository at a time

為整個儲存庫（repository）開啟 Claude Ship，它就會在團隊掌控的設定與核准政策下，自動處理團隊所有的合併請求（PR）。開發者不需要手動呼叫 /ship 指令。

  • 管理員選擇它在哪裡運作。管理員為每個儲存庫（repository）分別開啟 Code Review 和 PR Steward。當連接的儲存庫在預設分支（default branch）上有政策檔時，Claude Approvals 就會啟動，管理員也可以把它關掉。
  • 每個儲存庫都有自己需要的設定。管理員選擇審查等級（Quick、Standard 或 Deep）、選擇審查什麼時候執行，並設定支出上限。
  • 團隊保留既有的工具。Claude Ship 可以和現有的分支保護（branch protection）與必要檢查（required checks）一起運作。

節奏由團隊決定。他們可以從一個儲存庫（repository）開始，選擇審查等級和審查執行的時機，設定每月支出上限，並讓核准政策在觀察模式（observe mode）下運作，直到信任它為止。

Claude Code 團隊怎麼交付How the Claude Code team ships

我們自己的很多合併請求（PR）都在用 Claude Ship。最大的改變之一，是誰能根據客戶回饋採取行動。例如，Claude Code 團隊的一位產品經理現在可以讀一則回饋，和 Claude Tag 討論想法和取捨，讓它開一個合併請求（PR），然後去做下一件事，同時由 Claude Ship 帶著這個合併請求走完審查、修正和核准決定。

最近有一位客戶感到困惑，因為我們的 Analytics API 文件暗示 Admin 金鑰可以拉取 Pro 和 Team 方案的用量。這位產品經理問 Claude Tag 是否已經有修正在進行中，它就開了一個。Code Review 沒有找到阻擋合併的問題，一位文件審查者簽核，Claude Approvals 通過，修正在當天晚上就合併了。

客戶怎麼說What customers are saying

「我們有很多次，Claude Code Review 在人類審查者看到合併請求（PR）之前就抓到真正的問題，而 PR Steward 幫助貢獻者把它們修好。我們的審查者原本就在用 Claude Code 跟上大量的工作，所以讓 Code Review、PR Steward 和 Claude Approvals 在合併請求一開啟就自動啟動，讓事情更簡單。我們保留迴圈中把關的人（human in the loop），而人的時間現在花在真正需要的變更上。」

適用方案與計費Availability

Claude Ship 適用於 Claude Team 和 Enterprise 方案，支援 GitHub 上的儲存庫（repository）。Code Review 已正式開放（generally available），PR Steward 和 Claude Approvals 則是測試版（beta）。

Claude Ship 的用量依令牌（token）計費，所以開啟它可能會增加組織的成本。金額取決於涵蓋的合併請求（PR）數量和大小、審查等級、審查執行的頻率，以及 PR Steward 做了多少工作。管理員可以為 Code Review 和 PR Steward 設定支出上限。Claude Approvals 沒有基本費用，但政策中的分類器（classifier）會依使用的令牌（token）計費；而用到 Claude 審查的政策會觸發一次計費的 Code Review，即使在觀察模式（observe mode）下也一樣。執行 /ship 算作一般的 Claude Code 用量。

採用零資料保留（Zero Data Retention）、HIPAA 設定或客戶自管加密金鑰（customer-managed encryption keys）的組織，無法使用 Claude Ship。

開始使用Get started

開發者可以更新 Claude Code，在下一個變更上執行 /ship。/ship 今天起在 Claude Code 和桌面應用程式陸續推出。

已經在用 Code Review 的團隊，可以在儲存庫（repository）上加入 PR Steward，以及一份在觀察模式（observe mode）下運作的核准政策。

剛接觸 Code Review 的團隊，可以閱讀設定指南，連接 GitHub 並開啟第一個儲存庫。更多內容請見說明文件。

以下為譯者整理，非原文內容。

這篇在說什麼

這是 Anthropic 推出新產品 Claude Ship 的官方公告。寫程式的人改完一段程式碼後，要先送出一份「請大家檢查我的修改」的申請，也就是合併請求（PR）；以前要等人審查、自己回頭修、再找人核准。Claude Ship 把這三步交給三個 AI 代理接力：Code Review 負責挑毛病，PR Steward 負責修，Claude Approvals 依團隊事先寫好的規則決定能不能放行。

文章也說明了團隊怎麼一步步開啟它、怎麼保留人的把關，以及費用怎麼算。適用 Claude Team 和 Enterprise 方案、GitHub 上的專案；其中兩個新 AI 代理還是測試版（beta）。

為什麼值得學

當 AI 寫程式寫得很快，卡住的地方就從「寫」變成「檢查和放行」。這篇示範了一家 AI 公司怎麼把「檢查和放行」也交給 AI，同時把「哪些事一定要人看」寫成明確規則。這個思路不只適用寫程式：任何需要層層審核的工作，例如報銷、合約、文件發布，都可以借用。

你可以帶走的重點

1. 把一件事拆成三個角色接力

Claude Ship 沒有讓一個 AI 從頭包到尾，而是分成三個角色：一個專門挑毛病，一個專門修，一個專門依規則決定放不放行。修的人被刻意設計成「不能自己核准、不能自己合併」，就像公司裡寫報告的人不能自己簽核自己的報告。

換成日常說法：餐廳裡試菜、改菜、店長點頭上菜單，是三個不同的人。

2. 規則寫成一份檔案，依風險決定要幾個人

Claude Approvals 看的是團隊放在專案裡的一份規則檔。原文範例把修改分成三類：只改文件，AI 審查通過就直接放行，不需要人；一般程式碼要兩個人看，AI 審查通過時減為一個人；碰到帳務的程式碼，一定要兩個不是作者本人的人，其中一位來自付款團隊。

換成日常說法：公司報帳，500 元以下自動過，一般金額主管簽，牽涉大額付款一定要財務簽。

3. 每一步都留下說明，而且能撤回

PR Steward 每推上一次修改，就留言說明改了什麼、要怎麼復原；人隨時可以留言叫它換方向，或叫它停手。核准時也會留下「規則如何得出這個判定」的紀錄。讓 AI 動手的前提，是看得懂它做了什麼，而且隨時拉得回來。

換成日常說法：請家事服務來整理房間，最好每次都附一張清單：動了哪些東西、原本放在哪裡。

4. 先觀察，再放權

原文建議大多數團隊先用「只觀察模式」：AI 照規則判斷，但判斷結果暫時不算數，團隊可以拿來對照人的決定。等信任建立了，才把它設為「沒有它點頭就不能合併」。也可以從一個專案開始，不必一次全開。

換成日常說法：新同事先跟著看一個月，確定判斷跟你差不多，再讓他自己簽。

5. 先看懂費用怎麼算

Claude Ship 依令牌（token）計費，令牌可以想成 AI 讀寫文字的計量單位。修改申請越多、越大，審查越深、越頻繁，PR Steward 做越多事，費用就越高。管理員可以設每月支出上限。要特別注意：即使在只觀察模式下，用到 Claude 審查的規則仍然會觸發一次要付費的 Code Review。

換成日常說法：像計程車跳表，距離、等待時間都會算錢，「試坐看看」也一樣在跳表。

怎麼開始

  1. 如果你是開發者、團隊已經在 Team 或 Enterprise 方案：更新 Claude Code，在下一個修改上執行 /ship 試試看。注意它會在你的工作階段裡持續關注最多 7 天，期間電腦要保持開著。
  2. 如果你管理團隊：挑一個風險低的專案，先開 Code Review，再加 PR Steward，核准規則先用只觀察模式，並設好每月支出上限。
  3. 就算你不寫程式，也可以借用「依風險分級」的想法：把自己團隊的審核流程寫下來，哪些可以直接過、哪些要一個人、哪些一定要兩個人，再決定哪一級可以交給自動化。
