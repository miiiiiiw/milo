每個任務都有專屬的工作環境：Claude Code 的動態工作流程

原文標題：A harness for every task: dynamic workflows in Claude Code

日期：2026-06-03（台北時間 04:26；UTC 2026-06-02 20:26）

上週，我們在 Claude Code 推出了動態工作流程（dynamic workflows）。Claude 現在可以當場為手上的任務，自行寫出一套量身打造的工作環境（harness）。

預設的 Claude Code 工作環境（harness）是為寫程式而打造的，但它也適用於許多其他類型的任務，因為事實證明，很多任務都跟寫程式的任務很像。不過，有幾類任務，我們必須在 Claude Code 之上另外打造客製的工作環境（harness），才能達到最佳表現，例如 Research、安全性分析、agent teams（AI 代理團隊），或 Code Review。

工作流程（workflow）讓你動態建立各種工作環境（harness），讓 Claude 能在 Claude Code 內原生地解決上述所有問題，甚至更多。你也可以和其他人分享、重複使用這些工作流程（workflow）。

在這篇文章裡，我會分享我最初使用工作流程（workflow）的經驗與心得，讓你能充分發揮它的威力。

話雖如此，最佳實踐（best practices）仍在發展中！動態工作流程（dynamic workflows）通常會消耗更多令牌（token），所以請仔細考慮何時、如何使用。

範例提示詞Example prompts

在深入技術細節之前，我想先從一些範例提示詞（prompt）開始，讓你想想工作流程（workflow）有哪些可能性：

  • 「這個測試大概每 50 次執行會失敗 1 次。設定一個工作流程（workflow）來重現它、提出各種理論，並在工作樹（worktree）中以對抗式方式測試這些理論。/goal 在其中一個理論行得通之前不要停。」
  • 「用一個工作流程（workflow），檢視我最近的 50 個工作階段（session），從中挖掘我一再做出的修正，並把反覆出現的那些整理成 CLAUDE.md 規則」
  • 「用一個工作流程（workflow）翻查 Slack 上 #incidents 過去六個月的內容，找出沒有人開過工單、卻反覆出現的根本原因（root cause）。」
  • 「拿我的商業計畫，跑一個工作流程（workflow），讓不同的 AI 代理分別從投資人、客戶和競爭對手的角度把它拆解批判。」
  • 「這裡有一個放了 80 份履歷的資料夾，用一個工作流程（workflow）依後端職缺幫它們排名，並再次檢查前十名。用 AskUserQuestion 工具訪問我，來訂出評分規準（rubric）。」
  • 「我需要為這個 CLI 工具想個名字。用一個工作流程（workflow）腦力激盪出一堆選項，並辦一場淘汰賽（tournament）選出前 3 名。」
  • 「用一個工作流程（workflow）把我們的 User 模型到處都改名為 Account。」
  • 「看一下我的部落格文章草稿，用一個工作流程（workflow）對照程式碼庫驗證每一項技術主張，我不想發布任何錯誤的內容。」

動態工作流程如何運作How dynamic workflows work

動態工作流程（dynamic workflows）會執行一個 JavaScript 檔案，其中有幾個特殊函式，用來產生並協調子代理（subagents）：

動態工作流程（dynamic workflows）也包含標準的 JavaScript 函式，例如 JSON、Math 和 Array，用來協助處理資料。

特別值得知道的是，動態工作流程（dynamic workflows）可以決定 AI 代理使用哪個模型，以及子代理（subagents）是否在各自的工作樹（worktree）中執行，讓 Claude 能選擇所需的智慧程度與隔離程度。

如果工作流程（workflow）被中斷，例如因使用者操作或關閉終端機，恢復該工作階段（session）後，工作流程（workflow）就能從中斷的地方接續。

為什麼要用動態工作流程Why dynamic workflows

當你要求預設的 Claude Code 工作環境（harness）做一項任務時，它必須在同一個脈絡視窗（context window）裡同時規劃與執行。對許多寫程式的任務來說，這非常有效，但在長時間執行、大規模平行，以及／或高度結構化的對抗式任務中，有時會失靈。

這是因為 Claude 在單一脈絡視窗（context window）裡處理複雜任務的時間越長，就越容易出現幾種特定的失敗模式：

  • 代理惰性（Agentic laziness）指的是 Claude 在完成一項特別複雜、包含多個部分的任務之前就停下來，做了部分進度就宣布工作完成，例如在一次安全審查中只處理了 50 項中的 20 項。
  • 自我偏好偏誤（Self-preferential bias）指的是 Claude 傾向偏好自己的結果或發現，尤其是在被要求對照評分規準（rubric）來驗證或評判這些結果時。
  • 目標漂移（Goal drift）指的是在許多輪對話中，對原始目標的忠實度逐漸流失，尤其是在壓縮（compaction）之後。每一次摘要都會有損失，像是邊界情況（edge cases）的需求，或「不要做 X」這類限制，都可能遺失。

建立工作流程（workflow）有助於對抗這些問題，做法是調度多個各自擁有獨立脈絡視窗（context window）、目標專一且彼此隔離的 Claude。

動態與靜態工作流程Dynamic vs static workflows

你以前可能用 Claude Agent SDK 或 claude -p 建立過靜態工作流程（static workflow），把多個 Claude Code 實例協調在一起。

但因為靜態工作流程（static workflows）必須能應付所有邊界情況（edge cases），它們通常比較通用。有了 Claude Opus 4.8 和動態工作流程（dynamic workflows），Claude 現在夠聰明，可以寫出為你的使用情境量身打造的客製工作環境（harness）。

使用動態工作流程時的實用模式Helpful patterns when using dynamic workflows

你只要請 Claude 做一個，就能開始使用動態工作流程（dynamic workflows）；或者用觸發詞（trigger word）「ultracode」，確保 Claude Code 會建立工作流程（workflow）。

但建立對動態工作流程（dynamic workflows）如何運作的心智模型（mental model），能幫你理解何時該用、以及如何透過提示詞（prompt）來引導 Claude。

Claude 在建立工作流程（workflow）時，可能會使用並組合幾種常見模式：

分類後行動（Classify-and-act）

用一個分類器 AI 代理（classifier agent）判斷任務的類型，再依任務把工作導向不同的 AI 代理或行為。或者，在最後用分類器來決定輸出。

扇出再彙整（Fan-out-and-synthesize）

把任務拆成許多較小的步驟，對每個步驟各跑一個 AI 代理，再把這些結果彙整（synthesize）起來。當小步驟數量很多，或每個步驟都適合有自己乾淨的脈絡視窗（context window）以免彼此干擾或交叉污染時，特別有用。彙整（synthesize）這一步是一道屏障（barrier）——它會等所有扇出（fan-out）的 AI 代理完成，再把它們的結構化輸出合併成一個結果。

對抗式驗證（Adversarial verification）

對每一個被派出的 AI 代理，再派出另一個獨立的 AI 代理，依據評分規準（rubric）或標準，以對抗式方式驗證它的輸出。

生成後篩選（Generate-and-filter）

針對某個主題產生一批點子，再依評分規準（rubric）或驗證來篩選，去除重複（dedupe）的項目，只回傳品質最高、且經過測試的點子。

淘汰賽（Tournament）

不是把工作分開，而是讓 AI 代理彼此競爭。派出 N 個 AI 代理，各自用不同的方法嘗試同一項任務。接著由提示詞（prompt）或模型，透過一個評審 AI 代理（judging agent），以兩兩比較（pairwise）的方式評判結果，直到產生優勝者。

迴圈直到完成（Loop until done）

對於工作量未知的任務，迴圈地派出 AI 代理，直到滿足停止條件（沒有新的發現，或日誌中不再有錯誤），而不是跑固定的次數。

使用情境Use cases

請發揮創意，想想何時、如何請 Claude Code 建立動態工作流程（dynamic workflows）。我發現工作流程（workflow）有時對非技術性的工作甚至更有用。

遷移與重構Migrations and refactors

Bun 是用工作流程（workflow）從 Zig 改寫成 Rust 的。你可以在 Jarred 的 X 串文中讀到更多做法。

關鍵是把任務拆成一系列需要逐一處理的步驟，例如呼叫點（callsites）、失敗的測試、模組等。為每一個修正在一個工作樹（worktree）中派出一個子代理（subagent）去做修正，再讓另一個 AI 代理以對抗式方式審查，然後合併。可以考慮告訴 AI 代理不要使用耗費資源的指令，這樣你就能最大程度地平行化，又不會把你機器上的資源用光。

深度研究Deep research

我們在 Claude Code 內發布了一個使用動態工作流程（dynamic workflows）的深度研究 skill（技能）（/deep-research）。具體來說，它會扇出（fan-out）網路搜尋、擷取來源、以對抗式方式驗證來源中的主張，並彙整（synthesize）出一份附引用的報告。

不過，你可以把這類研究用在網路搜尋以外的地方。例如，請 Claude 從 Slack 的脈絡（context）彙整一份狀態報告，或透過深入探索程式碼庫來研究某個功能如何運作。

深度驗證Deep verification

另一方面，如果你有一份報告，想要檢查並查證它所引用的每一項事實主張的來源，你可以產生一個工作流程（workflow）：由一個 AI 代理找出所有事實主張，再派出一個子代理（subagent）逐一詳細檢查。你也可以讓一個驗證 AI 代理檢查來源子代理（subagent），確保它的來源品質夠高。

排序Sorting

你可能有一份清單，想依某種定性的衡量標準排序，而你相信 Claude Code 擅長評估這類標準，例如：依錯誤的嚴重程度排序的客服工單。但如果你試著在一個提示詞（prompt）裡排序 1000 多列資料，品質會下降，也塞不進脈絡（context）。取而代之的是，跑一場淘汰賽（tournament）、一條由兩兩比較（pairwise-comparison）AI 代理組成的流水線（pipeline）（比較式判斷比絕對評分更可靠），或平行分桶排名（bucket-rank）後再合併。每一次比較都是它自己的 AI 代理，所以由確定性（deterministic）的迴圈掌握對戰表（bracket），只有目前的排名順序留在脈絡（context）中。

記憶與規則遵循Memory and rule adherence

如果有一組特定規則是你發現 Claude 會漏掉或做不好的，即使已經寫進 CLAUDE.md 檔案也一樣，那就建立一個工作流程（workflow），列出必須由驗證器 AI 代理（verifier agents）檢查的規則——每條規則一個驗證器（verifier）。再建立一個扮演懷疑論者（skeptic persona）的子代理（subagent）來審查這些規則，確保它們彼此相符，有助於避免過多的誤報（false positive）。

反方向也行得通：挖掘你最近的工作階段（session）與程式碼審查（code review）意見中你一再做出的修正，用平行的 AI 代理把它們分群，對每個候選規則以對抗式方式驗證（這條規則是否能防止一個真實的錯誤？），再把留下來的提煉回 CLAUDE.md。

根本原因調查Root-cause investigation

除錯在你提出幾個獨立的假說並逐一測試時效果最好，但如果你只用一個脈絡視窗（context window），Claude 可能會陷入自我偏好偏誤（self-preferential bias）。

工作流程（workflow）可以從結構上防止這一點，做法是派出 AI 代理，從互不重疊的證據產生假說。例如，分別由不同的 AI 代理負責日誌、檔案和資料。接著每個假說都要面對一組驗證器（verifier）與反駁者（refuter）。

這不只適用於程式碼。工作流程（workflow）也可用於銷售（為什麼 3 月的銷售下滑？）、資料工程（這條流水線（pipeline）為什麼失敗？），或任何事後檢討（post-mortem）的情境。

大規模分類處理Triaging at scale

每個團隊都有客服佇列、錯誤回報，或其他人力無法完全處理完的待辦事項。

分類（triage）工作流程（workflow）會替每個項目歸類，與已在追蹤的項目去重（dedupe），然後採取行動。這可能是嘗試修正，或升級轉交給人類使用者。

分類（triage）工作流程（workflow）有個實用的模式叫隔離（quarantine）。做法是禁止讀取不可信公開內容的 AI 代理執行高權限的動作，那些動作改由負責依據資訊採取行動的 AI 代理來執行。

把分類（triage）工作流程（workflow）搭配 /loop，就能讓 Claude 持續地做這件事。

探索與品味Exploration and taste

在探索解決方案的不同做法時，工作流程（workflow）可以派上用場，尤其是以品味（taste）為基礎的事，像是設計或命名，而且適合搭配評分規準（rubric）。

試著請 Claude 探索一堆解決方案，並給一個審查 AI 代理一份評分規準（rubric），說明好的解決方案長什麼樣子。當審查 AI 代理覺得已達到標準時，任務就算完成。也可以依據評分規準（rubric），透過淘汰賽（tournament）來排序或挑選解決方案。

評估Evals

你可以替特定任務執行輕量的評估（evals）：在工作樹（worktree）裡派出各自獨立的 AI 代理，再派出比較用的 AI 代理，依據評分規準（rubric）比較並評分各項具體輸出。例如，依據某項標準，評估並進一步改進你建立的 skill。

模型與智慧路由Model and intelligence routing

建立一個針對你的任務調校過的分類器 AI 代理（classifier agent），由它決定使用哪個模型。當你的任務會涉及大量工具呼叫，而且在執行之前先做研究就能找出最適合的模型時，這會很有幫助。

例如，「說明 auth 模組如何運作」這個任務的最佳模型，取決於 auth 模組裡有多少個檔案，以及程式碼庫的形狀。分類器 AI 代理可以做這項研究，再依任務預期的複雜度，路由（routing）到 Sonnet 或 Opus。

何時不該使用動態工作流程When not to use dynamic workflows

工作流程（workflow）是新東西。雖然在許多使用情境下會產生超乎預期的成果，但並非每項任務都需要，而且最後可能會用掉多得多的令牌（token）。

最好創意地運用工作流程（workflow），把 Claude Code 推到你以前沒試過的地方。對於一般的寫程式任務，試著問問自己：它真的需要更多運算資源（compute）嗎？例如，大多數傳統的寫程式任務並不需要一個由 5 位審查者組成的小組。

建構動態工作流程的訣竅Tips for building dynamic workflows

提示詞撰寫（Prompting）

針對動態工作流程（dynamic workflows），使用我們上面描述的特定技巧進行詳細的提示，能得到最好的結果。

工作流程（workflow）不只適用於大型任務。你可以提示模型使用「快速工作流程（quick workflow）」。例如，你可以對某項假設做一次快速的對抗式審查。

搭配 /goal 與 /loop（Combine with /goal and /loop）

當使用可以重複執行的工作流程（workflow），例如分類（triage）、研究或驗證時，搭配 /loop 以固定間隔執行，並搭配 /goal 設定硬性的完成要求。

令牌（token）用量預算（Token usage budgets）

你可以替動態工作流程（dynamic workflows）設定明確的令牌（token）用量預算，限制一項任務用掉多少令牌（token）。你可以用像「use 10k tokens」（使用 1 萬個令牌（token））這樣的預算來提示它，這樣就會設定上限。

儲存與分享動態工作流程（Saving and sharing dynamic workflows）

你可以在工作流程（workflow）選單中按「s」來儲存工作流程（workflow）。你可以把它們放進 ~/.claude/workflows，或透過 skill 發行。

要透過 skill 分享，把你的 JavaScript 工作流程（workflow）檔案放進 skill 的資料夾，並在 SKILL.MD 中引用它們。為了有更大的彈性，你可能會想提示 Claude，把 skill 裡的工作流程（workflow）當成範本，而不是必須逐字執行的腳本。

為什麼值得學

即使你不寫程式，也能從中學到「把一件大事拆給多個互相檢查的 AI 代理」這種思路：原文的範例就包含排序 80 份履歷、替產品想名字、驗證部落格文章的每項主張。讀的時候留意兩點：原文沒有附效果數據，作者也明說「最佳實踐仍在發展中」，而且動態工作流程（dynamic workflows）通常會消耗更多令牌（token），要先想清楚值不值得。

你可以帶走的重點

1. 靜態流程是固定步驟，動態流程是為任務量身打造

靜態工作流程（static workflow）要能應付所有邊界情況（edge cases），所以通常比較通用。有了 Claude Opus 4.8 與動態工作流程（dynamic workflows），Claude 夠聰明，能為你的使用情境寫出客製的工作環境（harness）。原文的例子：問「要不要把結帳服務遷移到新供應商」，靜態做法只會得到一份泛泛的報告；動態做法會先讀自家帳務程式碼，再逐項對照新供應商文件、以自家交易量算價格，最後讓唱反調者提出最有力的反對理由，得到具體建議。

2. 為什麼要拆開：單一脈絡視窗會出現三種失敗

預設做法是在同一個脈絡視窗（context window）裡同時規劃與執行，Claude 做得越久，越容易出現三種狀況：代理惰性（agentic laziness，只做一部分就宣布完成）、自我偏好偏誤（self-preferential bias，偏愛自己的結果）、目標漂移（goal drift，經過多次壓縮（compaction）後離原本目標越來越遠）。建立工作流程（workflow）的作用，就是調度多個各自擁有獨立脈絡視窗（context window）、目標專一且彼此隔離的 Claude。

3. 六種常見模式，可以組合使用

分類後行動（Classify-and-act）、扇出再彙整（Fan-out-and-synthesize）、對抗式驗證（Adversarial verification）、生成後篩選（Generate-and-filter）、淘汰賽（Tournament）、迴圈直到完成（Loop until done）。理解這些模式，就能判斷何時該用，也能在提示詞（prompt）裡引導 Claude。你可以直接請 Claude 建一個，或用觸發詞（trigger word）「ultracode」確保它建立工作流程（workflow）。

4. 適合的情境很多，連非技術工作也行

原文列出的情境：遷移與重構（每個修正一個子代理（subagent））、深度研究、深度驗證（每項主張一個子代理（subagent））、排序（1,000 筆以上用淘汰賽（tournament））、記憶與規則遵循（每條規則一個驗證器（verifier））、根本原因調查（多個互相競爭的假說）、分類（triage）、探索與品味（taste）、評估（evals）、模型與智慧路由（routing）。作者說工作流程（workflow）有時對非技術性的工作甚至更有用。

其中分類（triage）有個值得記住的設計：隔離（quarantine）。讀取不可信內容的 AI 代理只能唯讀，不准做高權限的動作；真正動手的 AI 代理只看它們整理好的摘要。

5. 先想值不值得，再用預算和分享把它管起來

作者提醒：工作流程（workflow）是新東西，不是每項任務都需要，可能多用很多令牌（token）。一般的寫程式任務，先問自己「它真的需要更多運算資源（compute）嗎？」，例如大多數傳統任務並不需要一個由 5 位審查者組成的小組。需要的話，可以用「use 10k tokens」這類提示設定令牌（token）用量上限；可重複的流程搭配 /loop（定期執行）與 /goal（硬性的完成要求）；好用的工作流程（workflow）在選單按 s 儲存，放進 ~/.claude/workflows，或放進 skill 資料夾分享。

怎麼開始

  1. 挑一件你手上已有、需要「多面向檢查」的事，用一句話請 Claude「用一個工作流程（workflow）」去做；原文範例包括為 80 份履歷排名、替工具想名字、驗證部落格文章的每項主張。
  2. 想確保它真的建立工作流程（workflow）時，在提示詞（prompt）裡加上觸發詞（trigger word）「ultracode」。
  3. 先想好「怎樣算好」的標準：原文範例是請 Claude 用 AskUserQuestion 工具訪問你，來訂出評分規準（rubric）。
  4. 先設令牌（token）用量上限（例如「use 10k tokens」）；小事也可以只要求一個「快速工作流程（quick workflow）」。
  5. 會重複做的流程，搭配 /loop 定期執行，並用 /goal 設定完成條件。
  6. 一般的寫程式任務，先問自己真的需要更多運算資源（compute）嗎；好用的工作流程（workflow）再按 s 儲存，並用 skill 分享給別人。
