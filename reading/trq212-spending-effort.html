使用 Claude Code：花費你的費力等級

原文標題：Using Claude Code: Spending your effort

作者：Thariq（@trq212）

原文：https://x.com/trq212/status/2103576349499855160

日期：2026-09-26（台北時間 04:04；UTC 2026-09-25 20:04）

備註：繁體中文翻譯，僅供個人閱讀。

我們最新的 Claude 模型最棒的地方之一，是它們在 Claude Code 裡對費力等級（effort）的反應，而且不會破壞提示詞快取（prompt cache）；不過我收到使用者針對這點的許多提問。費力等級（effort）到底是什麼？什麼時候該用哪一個費力等級（effort level）？我們為什麼需要費力等級（effort）？

為了回答這些問題，我決定深入研究評估（evals），並針對一般的日常工作，親自測試不同的費力等級（effort）。

註：這篇文章更多的互動式圖表與解說，可以在 https://claude.dev/blog/spending-your-effort/ 看到。

整體來說，我發現費力等級（effort）是調整 Claude 做多少驗證（verification）與邊界情況測試（edgecase testing）、以及它運用多少自身判斷的好辦法。

在驗證（verification）與邊界情況測試（edgecase testing）更有用的領域，例如硬體、程式碼審查（code review）和資安，額外的費力等級（effort）帶來了更好的結果。

但 low 與 medium 費力等級（effort）很適合用來快速把事情做完，並讓人留在迴圈中（in the loop）與 Claude 一起工作。

對一般的軟體工程，我現在的做法是跑一個迴圈（loop）：先讓模型訪談我，然後在 low／medium 費力等級（effort）下實作，檢視它做出來的東西，再在 high 費力等級（effort）下執行驗證（verification）。

什麼是費力等級？（What is effort?）

大致來說，費力等級（effort）是給模型一個概略的訊號，表示你希望它在這項任務上花多少運算量（compute）。這多少和你對任務難度的估量有關。

你可以這樣想：如果有人要你連續花 12 小時做一件事，你可能會認為對方就是要你把它做出來，而且盡全力去做。如果有人要你在 1 小時內做同一件任務，你會盡量交給他一個符合任務要求的最佳版本，然後預期之後再從那裡反覆調整。

或者，你也可能會反駁，說這件任務至少需要 3 小時，然後花 3 小時把它交出來。

你應該用同樣的方式看待費力等級（effort）。Claude 一定會合理地嘗試完成你的任務，但更高的費力等級（effort）會讓 Claude 在判斷與驗證（verification）上採取更多自主的行動。

費力曲線（Effort curves）

Fable 5.1 與 Opus 5.5 的費力曲線（effort curves）是我們目前最好的：在每一個等級上，基準測試（benchmark）分數與消耗的令牌（token）都有所提升。下圖是依費力等級（effort）列出的 Terminal Bench 3.0 分數，是我為這篇文章跑評估（eval）時量測的。

但這在實務上代表什麼？為了評估這點，我在不同的費力等級（effort level）下嘗試了好幾項任務，並仔細研究了基準測試（benchmarks）。

用費力等級做開發（Building with effort）

了解模型如何運作的最好方法，就是做實驗。我在 Opus 5.5 上，用好幾個不同的費力等級（effort level）做同樣的任務，藉此了解它會做哪些工作。我在各式各樣的工作上都做過這件事，但這裡只用幾個玩具範例（toy examples）來說明。

規格不明確的開發任務（Underspecified build task）

如果我請 Claude「做一個個人健身與重訓追蹤應用程式（App）」，費力等級（effort）會大幅改變這個應用程式（App）的完整程度，但也會讓 Claude 在過程中做出更多選擇。在 low 費力等級（effort）下，這個健身應用程式（App）只有一份紀錄和一張簡單的圖表。在更高的費力等級（effort level）下，應用程式（App）更複雜，細節也更多。在 max 費力等級（effort）下，還有一張熱度圖（heat chart）。

如果我想要一個簡單的基礎來反覆調整，low 費力等級（effort）就能做到。如果我想要 Claude 最好的一次成果（one shot），才會選 max 費力等級（effort）。

規格略為明確的設計任務（Lightly specified design task）

如果我的任務已經相當明確，但我還是想跟 Claude 一起做些探索呢？舉例來說，我試著請它重新設計 Claude Code 的 /config 選單。每一輪的想法大致相同：使用子選單（submenus）和更好的搜尋。

在 low 費力等級（effort）下（花了 1 分鐘），我得到一份可互動的草圖（sketch），能傳達想法，但看起來不太像 Claude Code。

在 max 費力等級（effort）下（花了 28 分鐘），我得到一份看起來非常像 Claude Code 的模擬稿（mockup），還附了一堆針對不同流程（flows）的操作演示（walkthroughs）。

如果我的目標是反覆調整並給出回饋，low 費力等級（effort）會快得多。但 max 費力等級（effort）一開始就給我精緻得多的成品。就這項特定任務而言，我想我比較偏好用 low 費力等級（effort）來理解 Claude 的構想。

規格非常明確的開發任務（Highly specified build task）

如果我給 Claude 很多細節呢？我試著請 Claude 針對那個健身應用程式（App）深入訪談我，再把產出的規格（spec）交給不同模型、在不同費力等級（effort level）下實作。

我發現有了這份規格（spec），各個模型的表現相近得多。我得到的設計看起來相當類似，實作也相似，只是細節不同；在 max 費力等級（effort）下，Claude 花了一些時間簡化其中幾個細節。

小結（Takeaways）

對一般的軟體工程，尤其是新功能開發，該用哪個費力等級（effort level），很大程度取決於我想讓自己有多深地留在迴圈中（in the loop）。low 費力等級（effort）讓 Claude 能很快回應並給出一個起點；更高的費力等級（effort level）會做完更多工作，但 Claude 也會替我做更多假設。

我一直在用、特別有成效的功能開發迴圈（loop）是：

  • 給 Claude 一份規格（spec），請它針對我遺漏的任何細節訪談我
  • 用 low 費力等級（effort）實作
  • 檢視，確認它正確掌握了大意，必要時繼續用 low 費力等級（effort）反覆調整
  • 用 high 費力等級（effort）做驗證（verification）與測試

費力等級如何影響困難任務的產出（How effort levels impact output on difficult tasks）

但這些顯然都是玩具範例（toy examples），Claude 完全有能力完成。如果差別在於 Claude 能不能完成任務呢？

要找出這類困難的問題，就得去看基準測試（benchmarks），所以我深入研究了一個我喜歡的：Terminal Bench 3，一個由社群提供題目的基準測試（benchmark）。

Terminal-Bench 3.0 的問題大致可分為資安（security）、硬體（hardware）、機器學習（ML）、科學（science）、軟體（software）、營運（operations）與媒體（media）等類別。你可以在這裡看到所有問題：https://github.com/harbor-framework/terminal-bench/releases/tag/v3.0.0，它們來自社群，所以任何人都可以貢獻。

值得讀一讀，感受這些模型面對的是哪一類問題。我發現自己對其中許多任務的規模與企圖心感到驚訝。它們比我平常會遇到的一般任務複雜得多。

舉例來說，其中一些任務包括：

  • 硬體（Hardware）（retro-console-soc）：用 Verilog 打造一台 8 位元遊戲主機，要能放進一片小型 FPGA，並渲染出一個測試 ROM。
  • 科學（Science）（takens-embedding-lean）：在 Lean 4 中形式化證明 Takens 嵌入定理（Takens’ embedding theorem）。
  • 機器學習（ML）（mp-checkpoint-consolidation）：把一個專家混合（mixture-of-experts）模型檢查點（checkpoint）的 16 個分片（shards）合併成單一檔案，並且能重現參考的 logits。
  • 營運（Operations）（intrastat-meldung）：從頭到尾完成一家公司的月底歐盟貿易統計申報。
  • 媒體（Media）（layout-config-recreation）：把一張海報圖片重建成可編輯的版面配置檔（layout file）。

較高的費力等級在邊界情況很多時有幫助（Higher effort levels help when there are many edge cases）

我讀完 Terminal Bench 3 結果後最主要的心得是：較高的費力等級（effort）最適合有大量隱藏邊界情況（hidden edge cases）的任務。

一個很乾淨的例子是 html-js-filter，這是一項 Terminal-Bench 3.0 任務，要求寫出一個 HTML 淨化器（sanitizer），把所有把 JavaScript 偷渡進網頁的方式都剔除。Fable 5.1 從 low 的 1/5，提升到 xhigh 的 5/5。

在 low 費力等級（effort）下，一次典型的嘗試約花 2 分鐘。每次嘗試大致一輪就寫完過濾器（filter），然後只拿一個手寫的頁面來測試。

在 high 費力等級（effort）下，一次執行約 33 分鐘跑完。在我追蹤的那次執行裡，它先以對抗式（adversarial）的方式審查自己的初稿，接著閱讀已安裝的剖析器（parser）原始碼來檢查有沒有錯誤，跑了許多乾淨的測試案例，直到輸出和輸入一模一樣，跑了一套標準的 XSS 測試套件（test suite），最後寫了一個隨機文件模糊測試器（fuzzer）。

對於像 HTML 淨化器（sanitizer）這種邊界情況這麼多的東西，這份額外的費力（effort）非常值得。為了周全而多花令牌（token），對於正式環境（production）要求高的複雜任務也合理，例如效能最佳化或資安審查（security review）。

但並不是每項任務都需要這種程度的費力等級（effort）。

下圖呈現了所有 Terminal-Bench 3.0 的結果，以及它們是怎麼失敗的，涵蓋不同模型與費力等級（effort level）。整體而言，提高費力等級（effort）傾向於減少因漏掉邊界情況（edgecases）造成的失敗（紫色方塊），但並不能解決模型用錯方法的情況（藍色方塊）。

費力等級有幫助的問題領域（Problem areas where effort helps）

我在 TerminalBench 上評估這些模型時，最有趣的心得之一是：有些問題領域從費力等級（effort）中得到的好處比其他領域多。你可以在下圖看到分項結果：

為了說明這點，我從 Terminal Bench 3.0 的不同領域挑了幾個問題，Opus 5.5 在 low 費力等級（effort）下失敗，在 high 下成功——多半是因為它做了測試，並把邊界情況（edge cases）納入考量：

mvcc-lsm-compaction：一項 Terminal-Bench 3.0 任務，要求根據當機報告（crash report）修正儲存引擎（storage-engine）的一個錯誤，同時不能破壞壓縮（compaction）。Opus 5.5 從 low 的 0/5 提升到 xhigh 的 4/5。

在 low（每次嘗試約 1 分鐘）下，Claude 會在建置程式或執行重現程式（reproducer）之前就先改程式碼，也沒有確認自己新寫的測試是否真能抓到原本的錯誤。

在 xhigh（約 11 分鐘）下，Claude 先重現了當機，針對一個從不做壓縮（compaction）的參考實作寫了隨機化測試，並確認它的測試在只修了一半的修補上會失敗。

cli-2ph-simple：是一項 Terminal-Bench 3.0 任務，要求用 Python 寫一個命令列（CLI）的線性規劃（linear-program）求解器。Opus 5.5 從 low 的 0/5 提升到 high 的 5/5。

low 的嘗試一輪就寫完求解器，用幾個小問題檢查過，並在約 10k 令牌（token）時停下。在最後的訊息裡，Claude 提醒它在大型問題上可能會很慢，但沒有去檢查。

在 high 的嘗試中，Claude 拿隨機問題對照另一個暴力解（brute-force）求解器來測試它的求解器，然後替更大的問題計時，碰到執行時間遠遠過長或當機的情況，並重新調整了它的搜尋方法。

gsea-proteomics：一項 Terminal-Bench 3.0 任務，要求對蛋白質體學（proteomics）資料做基因集富集分析（gene set enrichment analysis，GSEA），找出八種處理（treatments）中哪些和目標組織相似。Opus 5.5 從 low 的 0/5 提升到 high 的 4/5。

在 low 費力等級（effort）下，Claude 挑了一個聽起來合理的資料前處理方式，只用那一種方式跑分析，然後回報結果。

在 high 下，Claude 試了兩種資料前處理方式，注意到顯著處理的清單變了，並在選擇正確的那一種之前深入追查原因。

如果有使用者留在迴圈中（in the loop），Claude 可能會就問題該怎麼設定去問使用者；但在沒有使用者留在迴圈中（in the loop）的情況下，high 費力等級（effort）表現更好。

在 Claude Code 裡何時用哪個費力等級（When to use different effort levels in Claude Code）

以下是我對「何時用哪個費力等級（effort level）」的經驗法則（rule of thumb）：

  • Low：當我想要快速的回應、並讓自己留在迴圈中（in the loop）時，例如腦力激盪（brainstorming）、畫草圖（sketching）、簡單的修改。
  • Medium：我大部分的日常軟體工程工作，例如實作新功能。
  • High：驗證（verification）很重要、或有邊界情況（edge cases）的工作，例如在棕地（brownfield）程式碼庫（codebase）中修 bug。
  • Max：當我希望 Claude 完全自主地運作，去解決困難的問題，例如端到端地打造並驗證一個應用程式（App）、在關鍵軟體中找出資安漏洞。

請依你的任務來調整 Opus 5.5 與 Fable 5.1 的費力等級（effort），甚至可以在對話進行到一半時，在 Claude Code 裡用 /effort 調整，再告訴我這是否符合你的直覺。

以下為譯者整理，非原文內容。

這篇在說什麼

Thariq（@trq212）解釋 Claude Code 的「費力等級（effort）」是什麼：它是你給模型的一個訊號，表示你希望它花多少力氣；等級越高，Claude 越會自己做判斷、多做驗證、多測邊界情況。他用幾個小實驗和 Terminal-Bench 3.0 的評估發現：low／medium 適合快速來回，high／max 適合需要驗證、邊界情況很多的工作。

文章先用健身應用程式和選單重新設計兩個小例子看差異，再用困難的基準測試任務看「做不做得出來」的差異，最後給出四個等級的經驗法則。

為什麼值得學

只要你用 Claude Code，就會碰到「該選哪個費力等級」的問題。這篇把它從感覺變成可以套用的判準：快速探索與日常開發用低、中檔，要驗證時再拉高，而不是一律開到最高。讀的時候留意：數字是作者自己用特定模型（Opus 5.5、Fable 5.1）跑出來的結果，小例子也是他自己挑的玩具範例，換成你的任務時，建議自己試一輪。

你可以帶走的重點

1. 費力等級＝你希望它花多少力氣

作者用時限來比喻：被要求連做 12 小時，你會以為對方要你全力做出來；被要求 1 小時內做完，你會先交出最佳版本再反覆調整；你也可以反駁說至少要 3 小時，然後做滿 3 小時。Claude 一定會合理地嘗試完成任務，但等級越高，它越會採取更多自主的行動來判斷與驗證。

2. 規格越清楚，各檔位的成品越接近

同樣是健身應用程式，規格不明確時，low 只做出一份紀錄和簡單圖表，max 還多了熱度圖，花的時間從 1.5 分鐘到 67 分鐘。先請 Claude 訪談你、拿到完整規格後再實作，各個模型的設計與實作變得相當類似，只有細節不同。選單重新設計的例子則說明：想快速給回饋，low（1 分鐘）就夠；想一開始就要精緻成品，max（28 分鐘）才給得出來。

3. 日常開發的迴圈：低檔做出來，高檔來驗證

作者一直在用的功能開發迴圈：先給規格並請 Claude 訪談自己補上遺漏的細節，用 low 實作，檢視有沒有抓到大意、必要時繼續用 low 調整，最後再用 high 做驗證與測試。低檔讓你留在迴圈中、快速得到起點；更高的檔位做更多事，但 Claude 也會替你做更多假設。

4. 高檔補的是「漏掉的邊界情況」，不是方向

在 Terminal-Bench 3.0 裡，較高的費力等級最適合有大量隱藏邊界情況的任務。例如 HTML 淨化器任務，Fable 5.1 從 low 的 1/5 升到 xhigh 的 5/5：低檔約 2 分鐘、只拿一個手寫頁面測試；高檔約 33 分鐘，先對抗式審查初稿、讀剖析器原始碼、跑標準 XSS 測試套件、最後寫模糊測試器。分領域看，資安（64%→87%）和硬體（34%→75%）進步最大，營運這類照規則手冊辦事的工作（12%→22%）仍然偏低。但提高費力等級並不能解決「用錯方法」，下圖裡「選了錯誤的解讀」甚至從 25 次增加到 47 次。

5. 四個等級的經驗法則

作者的分法：low 用在想要快速回應、留在迴圈中的場合；medium 用在大部分的日常軟體工程；high 用在驗證重要或有邊界情況的工作；max 用在要 Claude 完全自主解決困難問題。他也提到沒有使用者在迴圈中時，高檔表現比較好，因為 Claude 沒辦法回頭問你問題該怎麼設定。

怎麼開始

  1. 下次動手前，先問自己：這件事是要快速來回（low／medium）、需要驗證或邊界情況很多（high），還是要整個交出去（max）？
  2. 做新功能時，先給 Claude 一份規格，請它針對你遺漏的細節訪談你。
  3. 用 low 或 medium 實作，自己檢視它有沒有抓到大意；確定方向後，再用 high 做驗證與測試。
  4. 在 Claude Code 裡用 /effort 隨時調整，甚至可以在對話進行到一半時調整，看看是否符合你的直覺。
  5. 想看更多互動式圖表與解說，可以到作者提供的 claude.dev 文章。
