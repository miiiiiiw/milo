使用 Claude Code：HTML 有效到離譜

原文：https://x.com/trq212/status/2052809885763747935

這篇現在也登在Claude Blog上了。

Markdown 已經成為 AI 代理與我們溝通時最主要的檔案格式。它簡單、可攜，具備一些富文字能力，而且你很容易編輯。Claude 甚至已經出乎意料地擅長用 ASCII 在 Markdown 檔案裡畫圖表。

但隨著 AI 代理變得越來越強大，我覺得 Markdown 已經成了一種受限的格式。超過一百行的 Markdown 檔案，我讀起來就很吃力。我想要更豐富的視覺化、色彩與圖表，也希望能輕鬆地分享它們。

我也越來越少自己編輯這些檔案，而是把它們當作規格文件（spec）、參考檔案、腦力激盪的產出等等來用。真的要修改時，我通常是用提示詞（prompt）請 Claude 去改，這就抹去了 Markdown 最大的好處之一。

我已經開始偏好用 HTML 取代 Markdown 作為輸出格式，也越來越常看到 Claude Code 團隊的其他人這麼做，原因就在下面。

（如果你想先看一些範例，這裡有一大堆：https://thariqs.github.io/html-effectiveness，但一定要回來讀完「為什麼」。）

為什麼是 HTML？Why HTML?

資訊密度Information Density

與 Markdown 相比，HTML 能傳達豐富得多的資訊。它當然可以做簡單的文件結構，像是標題與格式，但它也能表達各式各樣的其他資訊，例如：

  • 用表格（tables）呈現的表格式資料
  • 用 CSS 表達的設計資料
  • 用 SVG 畫的插圖
  • 用 script 標籤放的程式碼片段
  • 用 HTML 元素搭配 JavaScript 加 CSS 做出的互動
  • 用 SVG 與 HTML 畫的工作流程
  • 用絕對定位與畫布（canvas）表達的空間資料
  • 用 img 標籤放的圖片

我甚至敢說，Claude 能讀到的資訊，幾乎沒有哪一種是你無法用 HTML 相當有效率地表達出來的。這讓它成為模型向你傳達深入資訊、也讓你審閱這些資訊的高效方式。

我發現，一旦沒辦法這麼做，模型可能會在 Markdown 裡做出更沒效率的事，像是 ASCII 圖表，或是我最愛的——用 Unicode 字元去估算顏色，就像這張 Claude Code 的截圖。

視覺清晰度與易讀性Visual Clarity & Ease of Reading

隨著 Claude 能做更複雜的工作，它寫出的規格文件（spec）與計畫（plan）也越來越龐大。實際上，我發現自己通常不會真的去讀超過 100 行的 Markdown 檔案，而我當然更不可能讓組織裡的其他人去讀。

但 HTML 文件好讀得多，Claude 可以在視覺上安排結構，用分頁、插圖、連結等讓瀏覽變得理想。它甚至可以做成行動裝置響應式（mobile responsive），讓你依裝置的外形尺寸（form factor）以不同方式閱讀。

易於分享Ease of Sharing

Markdown 檔案相當難分享，因為大多數瀏覽器原生都不太能把它們渲染好。你常常得把它們當成附件，附在電子郵件或訊息裡。

用 HTML 的話，只要把檔案上傳（例如傳到 S3），就能輕鬆分享連結。你的同事想在哪裡開都可以，也很容易拿來參考。

如果是 HTML，別人真的會去讀你的規格文件（spec）、報告或合併請求（PR）說明的機率，會高得多得多。

雙向互動Two-way Interaction

HTML 能讓你與文件互動，例如你可以要求它加上滑桿或旋鈕來調整設計，或是讓你微調演算法裡的各種選項、看看會發生什麼事。你也可以要求它讓你把這些調整複製成一段提示詞（prompt），再貼回 Claude Code。

想看這種雙向互動的範例，可以閱讀我那篇談 playgrounds（互動實驗場）的文章：https://x.com/trq212/status/2017024445244924382

資料攝取Data Ingestion

為什麼要用 Claude Code 來做 HTML 檔案，而不是用 ClaudeAI 或 Claude Design 之類的？最大的原因之一，就是 Claude Code 能攝取的所有脈絡。

例如在寫這篇文章時，我請 Claude Code 讀過我的程式碼資料夾，找出我生成過的所有 HTML 檔案，將它們分組、分類，再做出一個 HTML 檔案，用圖表呈現每一種類型。你在這篇文章裡看到的圖表，就是直接由此而來。

除了檔案系統之外，Claude Code 還能透過你的 MCP（例如 Slack、Linear 等）、你的網頁瀏覽器（搭配 Claude in Chrome）、你的 git 歷史紀錄等等，找到額外的脈絡。

它很愉悅It’s Joyful

和 Claude 一起做 HTML 文件就是比較好玩，也讓我覺得自己對這個創作投入得更深、更有參與感，光是這一點就夠了。

如何開始How to Get Started

我有點擔心大家讀完這篇文章後，會把它做成一個 /html 技能（skill）之類的東西。這樣做也許有些價值，但我想強調，要讓 Claude 這麼做並不需要花多大功夫。你只要請它「做一個 HTML 檔案」（“make a HTML file”）或「做一個 HTML 產物（artifact）」（“make a HTML artifact”）就行了。

訣竅在於知道你希望這個產物（artifact）做什麼，以及你可能會怎麼用它。久而久之你或許會做成一個技能（skill），但現階段我建議先從零開始下提示詞（prompt），去摸索在不同情境下該怎麼用。

使用情境Use Cases

為了讓這一切更具體，我針對不同的使用情境做了許多不同的 HTML 檔案。你可以在這裡看到全部：https://thariqs.github.io/html-effectiveness/，不過下面先給個概覽。

規格文件（spec）、規劃與探索Specs, Planning & Exploration

HTML 是讓 Claude 深入探究問題的豐富畫布。當我開始處理一個問題時，我預期做出的不是一份簡單的 Markdown 計畫（plan），而是一張由多個 HTML 檔案組成的網。例如，我可能先請 Claude Code 腦力激盪，針對不同選項做一些探索。接著我會請它針對其中一個再往下展開，也許做出模擬稿（mockup）或程式碼片段。最後，等我覺得差不多了，就請它寫一份實作計畫（implementation plan）。當我對計畫滿意之後，我會開一個新的工作階段（session），把這些檔案全部交給它去實作。

在驗證時，我也會請驗證 AI 代理（verification agent）把這些檔案讀進去，這樣它對需要什麼會有廣泛得多的脈絡。

範例提示詞（Example Prompts）：

範例提示詞（Example prompt）1（英文原文）

I'm not sure what direction to take the onboarding screen. Generate 6 distinctly different approaches — vary layout, tone, and density — and lay them out as a single HTML file in a grid so I can compare them side by side. Label each with the tradeoff it's making.

範例提示詞1（繁體中文對照）

我不確定新手引導（onboarding）畫面該走哪個方向。請產生 6 種截然不同的做法——在版面、語氣和資訊密度上做出變化——並把它們排成網格，放在同一個 HTML 檔案裡，讓我可以並排比較。請替每一種標出它所做的取捨。

範例提示詞（Example prompt）2（英文原文）

Create a thorough implementation plan in a HTML file, be sure to make some mockups, show data flow and add important code snippets I might want to review. Make it easy to read and digest.

範例提示詞2（繁體中文對照）

請用一個 HTML 檔案寫出一份完整的實作計畫（implementation plan），務必做一些模擬稿（mockup），呈現資料流，並加入我可能想審閱的重要程式碼片段。讓它容易閱讀與消化。

適用情境（Use Cases）：

  • 探索用程式碼實作某件事的其他方式
  • 探索多種視覺設計

程式碼審查（code review）與理解Code Review & Understanding

程式碼放在 Markdown 檔案裡很難讀。但用 HTML，我們可以渲染出差異（diff）、註解、流程圖、模組等等。可以用它來理解 AI 代理寫出的程式碼、取得程式碼審查（code review），或是向審查你程式碼的人說明一份合併請求（PR）。我發現這通常比 GitHub 預設的差異（diff）檢視更好用，而且我現在提交的每一份合併請求（PR）都會附上一份 HTML 程式碼解說頁（explainer）。

範例提示詞（Example prompt）：

範例提示詞（Example prompt）（英文原文）

Help me review this PR by creating an HTML artifact that describes it. I'm not very familiar with the streaming/backpressure logic so focus on that. Render the actual diff with inline margin annotations, color-code findings by severity and whatever else might be needed to convey the concept well.

範例提示詞（繁體中文對照）

請幫我審查這份合併請求（PR）：做一個 HTML 產物（artifact）來描述它。我對串流／背壓（streaming/backpressure）邏輯不太熟，所以請把重點放在那裡。請把實際的差異（diff）渲染出來，並加上行內的邊註，依嚴重程度為發現的問題標上顏色，以及其他任何有助於把概念傳達清楚的東西。

適用情境（Use Cases）：

  • 建立合併請求（PR）
  • 審查合併請求（PR）
  • 理解程式碼中的某個主題

設計與原型Design & Prototypes

Claude Design 是以 HTML 為基礎，因為 HTML 在設計上的表現力極強，即使你最終的呈現介面不是 HTML 也一樣。Claude 可以先用 HTML 勾勒出設計，再用你選擇的語言寫出來，無論是 React、Swift 等等。

你也可以為互動做原型（prototype），例如動畫、操作等等。可以考慮請 Claude 做出滑桿、旋鈕等，把你要的效果精準調出來。

範例提示詞（Example prompt）：

範例提示詞（Example prompt）（英文原文）

I want to prototype a new checkout button, when clicked it does a play animation and then turns purple quickly. Create a HTML file with several sliders and options for me to try different options on this animation, give me a copy button to copy the parameters that worked well.

範例提示詞（繁體中文對照）

我想為一個新的結帳按鈕做原型（prototype）：點擊時先播放一段動畫，然後很快變成紫色。請做一個 HTML 檔案，附上幾個滑桿和選項，讓我試這段動畫的不同設定，並給我一個複製按鈕，把效果好的參數複製下來。

適用於（Use this for）：

  • 建立設計規範（design system）的產物（artifact）
  • 調整元件
  • 將元件庫視覺化
  • 為令人愉悅的動畫（Joyful Animations）做原型（prototype）

報告、研究與學習Reports, Research & Learning

Claude Code 極其擅長跨多個資料來源整合資訊，並把它轉成易讀的報告。你可以用提示詞（prompt）請 Claude 去搜尋你的 Slack、你的程式碼庫（codebase）、git 歷史紀錄、網路等等，再用這些資料替你自己、替領導層、替你的團隊等等產生極易閱讀的報告。

你可以把它組成一份長篇 HTML 文件、一份互動式解說頁（explainer），甚至是投影片簡報。請 Claude 用 SVG 畫圖表，幫助視覺化。

例如在寫我那幾篇談提示詞快取（prompt caching）的文章時，我請 Claude 讀過 git 歷史紀錄後，替我準備一份 HTML 格式的深度研究檔案，內容是我們對提示詞快取所做的所有變更，供我閱讀。

範例提示詞（Example prompt）：

範例提示詞（Example prompt）（英文原文）

I don't understand how our rate limiter actually works. Read the relevant code and produce a single HTML explainer page: a diagram of the token-bucket flow, the 3–4 key code snippets annotated, and a "gotchas" section at the bottom. Optimize it for someone reading it once.

範例提示詞（繁體中文對照）

我搞不懂我們的速率限制器（rate limiter）到底是怎麼運作的。請讀相關的程式碼，產出一個單一的 HTML 解說頁（explainer）：包含一張令牌桶（token bucket）流程圖、加上註解的 3–4 段關鍵程式碼片段，以及底部的「陷阱」（gotchas）區塊。請針對只會讀一次的人來優化它。

適用於（Use this for）：

  • 總結某個功能是怎麼運作的
  • 向我解釋一個概念
  • 給主管的每週狀態報告
  • 給領導層的事故報告
  • SVG 插圖、流程圖、技術圖表等等

自訂編輯介面Custom Editing Interfaces

有時候，光用文字框很難描述你想要什麼。這時我會請 Claude 為我正在處理的那件事，做一個用完即丟的編輯器。不是產品，也不是可重複使用的工具，而是一個單一的 HTML 檔案，專為這一份資料量身打造。

訣竅永遠是以匯出收尾：做一個「複製為 JSON」（“copy as JSON”）或「複製為提示詞」（“copy as prompt”）的按鈕，把我在介面上做的任何操作，轉回我可以貼進 Claude Code 的內容。

範例提示詞（Example prompts）：

範例提示詞（Example prompt）1（英文原文）

I need to reprioritize these 30 Linear tickets. Make me an HTML file with each ticket as a draggable card across Now / Next / Later / Cut columns. Pre-sort them by your best guess. Add a "copy as markdown" button that exports the final ordering with a one-line rationale per bucket.

範例提示詞1（繁體中文對照）

我需要重新排定這 30 張 Linear 工單（ticket）的優先順序。請幫我做一個 HTML 檔案，把每張工單做成可拖曳的卡片，分布在 Now／Next／Later／Cut 四個欄位。請先依你的最佳判斷預先排序。再加一個「copy as markdown」按鈕，匯出最終的排序，並為每個分組附上一行理由。

範例提示詞（Example prompt）2（英文原文）

Here's our feature flag config. Build a form-based editor for it,  group flags by area, show dependencies between them, warn me if I enable a flag whose prerequisite is off. Add a "copy diff" button that gives me just the changed keys.

範例提示詞2（繁體中文對照）

這是我們的功能旗標（feature flag）設定。請為它做一個表單式的編輯器，依區域將旗標分組，顯示它們之間的相依關係，如果我啟用了某個旗標、而它的前置條件是關閉的，就警告我。再加一個「copy diff」按鈕，只給我有變動的鍵。

範例提示詞（Example prompt）3（英文原文）

I'm tuning this system prompt. Make a side-by-side editor: editable prompt on the left with the variable slots highlighted, three sample inputs on the right that re-render the filled template live. Add a character/token counter and a copy button.

範例提示詞3（繁體中文對照）

我正在調整這份系統提示詞（system prompt）。請做一個並排的編輯器：左邊是可編輯的提示詞（prompt），變數欄位會被標示出來；右邊是三組範例輸入，會即時重新渲染填好內容的範本。再加一個字元／令牌（token）計數器，以及一個複製按鈕。

適用於（Use this for）：

  • 重新排序、分類（triage）或分組任何東西（工單、測試案例、意見回饋）
  • 編輯結構化設定（功能旗標、環境變數、有限制條件的 JSON／YAML）
  • 一邊即時預覽，一邊調整提示詞（prompt）、範本或文案
  • 整理資料集：核准／駁回資料列、為範例加標籤、匯出所選內容
  • 為文件、逐字稿或差異（diff）加註解，並匯出這些註解
  • 挑選難以用文字表達的值：顏色、緩動曲線（easing curves）、裁切範圍、cron 排程、正規表示式（regex）。

常見問題Frequently Asked Questions

我一直跟很多人說我已經改用 HTML，也看到一些重複出現的問題。

它的令牌（token）效率不是比較低嗎？Isn’t it less token efficient?雖然 Markdown 通常用的令牌（token）比較少，但我發現 HTML 多出來的表現力，加上我讀它的機率高得多，整體來說我得到更好的產出。在 Opus 4.7 有 1MM（100 萬）令牌（token）脈絡視窗（context window）的情況下，令牌（token）用量增加在脈絡視窗裡其實不太明顯。

你現在什麼時候還會用 Markdown？When do you use markdown for now?老實說，我幾乎所有事情都已經完全不用 Markdown 了，不過我大概站在相當極端的 HTML 至上主義者（HTML maximalist）那一邊。

我要怎麼檢視 HTML 檔案？How do I view the HTML file?我通常就是在本機用瀏覽器打開（你可以請 Claude 幫你打開），如果想要可分享的連結，就上傳到 S3。

這樣不是比 Markdown 更花時間生成嗎？Doesn’t this take longer to generate than markdown?確實比較久！HTML 可能比 Markdown 多花 2 到 4 倍的時間，但我發現成果值得。

版本控制（version control）呢？What about version control?老實說，這是 HTML 最大的缺點之一：和 Markdown 相比，HTML 的差異（diff）雜訊很多，也很難審閱。

我要怎麼讓 Claude 符合我的品味／不要做得很醜？How do I get Claude to match my taste / not make it ugly?frontend design 外掛（plugin）能幫助 Claude 做出好的 HTML 檔案。但若要符合你自己公司的風格，你可以把 Claude 指向你的程式碼庫（codebase），建立一份單一的設計規範（design system）HTML 檔案，之後就能把這份設計規範檔案當成其他 HTML 檔案的參考。

讓自己留在迴圈中Stay in the Loop

以上種種，想說的是：我認為我使用 HTML 的真正原因，是我覺得自己和 Claude 的協作更「在迴圈中」（in the loop）。我曾開始擔心，因為我已經不再深入閱讀計畫（plan），我就只能放手讓 Claude 自己做選擇。

但我很高興地說，結果正好相反：用 HTML 的時候，我比以往任何時候都更「在迴圈中」。希望你也是。

這篇在說什麼

Thariq（@trq212）說，他現在幾乎所有事情都不再用 Markdown，而是請 Claude Code 產出 HTML 檔案：規格文件（spec）、計畫、合併請求（PR）說明、報告，甚至是用完即丟的小型編輯器。他的理由是 HTML 能放進更多種資訊、比較好讀、比較好分享，而且可以讓你在頁面上互動、再把結果貼回 Claude Code。

文章分成幾塊：為什麼選 HTML（資訊密度、易讀、易分享、雙向互動、資料攝取、愉悅感）、怎麼開始、五大類使用情境與範例提示詞（prompt），最後是常見問題與作者的限制說明。

為什麼值得學

即使你不寫程式，只要你常請 AI 寫計畫、報告或比較方案，這篇都有用：它告訴你，把輸出格式從純文字換成網頁這個小動作，會讓你更願意真的讀完，也更容易轉給別人看。讀的時候留意兩點：這是作者的個人經驗，他自己說站在「HTML 至上主義者（HTML maximalist）」的極端那一側，文中沒有附實測數據；成本（生成慢 2 到 4 倍、令牌（token）用量較多）也要自己評估。

你可以帶走的重點

1. 先問：這份文件是誰在讀、誰在改？

Markdown 的最大好處是人很容易自己編輯，但作者現在多半是用提示詞（prompt）請 Claude 去改，這個好處就用不上了；同時他說自己很難讀完超過 100 行的 Markdown 檔案，也很難讓同事去讀。HTML 則能用分頁、插圖、連結把結構排好，甚至做成手機版面也能自適應，只要上傳檔案、分享連結，別人真的去讀的機率高得多。

例：把規格文件（spec）、報告或合併請求（PR）說明做成 HTML，再傳連結給同事。

2. HTML 能裝的東西比你以為的多，所以要把「想看到的樣子」說出來

作者列出 HTML 能承載的八類資訊：表格、設計（色彩、字型、間距）、SVG 插圖、程式碼片段、用 JavaScript 加 CSS 做的互動、工作流程、空間資料（絕對定位與畫布），以及圖片。他認為 Claude 能讀到的資訊，幾乎沒有哪一種不能用 HTML 相當有效率地表達；沒辦法這麼做時，模型就會退而求其次，畫 ASCII 圖表，或用 Unicode 字元去估算顏色。

例：請它把 6 種截然不同的做法排成網格並排比較，每一種都標出所做的取捨。

3. 把一個問題做成「一批 HTML 檔案」，而不是一份計畫

作者處理問題的順序是：先請 Claude Code 腦力激盪出不同選項，再針對其中一個展開（模擬稿（mockup）或程式碼片段），最後寫成實作計畫；滿意後開新的工作階段（session），把全部檔案交給它去實作。驗證時也請驗證 AI 代理（verification agent）讀這些檔案，它就會對「需要什麼」有更完整的脈絡。

例：新手引導（onboarding）畫面不確定怎麼做時，先要 6 種做法，再選一種往下做。

4. 讓頁面能「雙向」：調整完要有匯出

有些東西很難用文字描述，作者會請 Claude 做一個專為眼前這份資料打造、用完即丟的編輯器，訣竅是結尾一定要有「複製為 JSON」或「複製為提示詞」的按鈕，把你在畫面上的操作轉回可以貼進 Claude Code 的內容。範例包括：把 30 張工單（ticket）拖曳到 Now／Next／Later／Cut 四欄、依區域分組並警告相依關係的功能旗標（feature flag）設定表單、並排編輯系統提示詞（system prompt）並即時預覽。

例：做動畫原型（prototype）時，用滑桿調時長、縮放與陰影，滿意後按「Copy as prompt」貼回 Claude Code，請它套用到真正的元件。

5. 先用一句話開始，並先認清代價

作者擔心大家把這篇文章做成一個 /html 技能（skill），他強調只要請 Claude「做一個 HTML 檔案」或「做一個 HTML 產物（artifact）」就好，關鍵是你知道希望它做什麼、怎麼用；用久了再考慮做成技能。要讓成品不醜，可用 frontend design 外掛（plugin），或讓 Claude 讀你的程式碼庫（codebase），建立一份設計規範（design system）HTML 檔案當參考。代價是：HTML 可能比 Markdown 多花 2 到 4 倍的生成時間、令牌（token）較多（作者說在 Opus 4.7 的 1MM（100 萬）令牌（token）脈絡視窗（context window）下不明顯），而且版本控制（version control）的差異（diff）雜訊多、難審閱，作者自己也說這是 HTML 最大的缺點之一。

怎麼開始

  1. 下次請 AI 寫計畫、報告或比較方案時，加上一句「做成一個 HTML 檔案」。
  2. 先想清楚這個檔案要拿來做什麼（比較、審閱、調整、分享），再把用途寫進提示詞（prompt）。
  3. 需要調整數值或排序時，請它加上滑桿或可拖曳的卡片，並在結尾加一個「複製為提示詞」或「複製為 JSON」的按鈕。
  4. 要分享就把檔案上傳（例如傳到 S3）、拿連結給同事；想符合公司風格，先請 Claude 建一份設計規範（design system）HTML 檔案當參考。
  5. 先接受兩個代價：生成時間約多 2 到 4 倍，版本差異（diff）雜訊多、不好比對。
  6. 想看更多範例，可以到作者整理的頁面逛逛：thariqs.github.io/html-effectiveness。
