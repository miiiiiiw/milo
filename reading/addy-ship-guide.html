用 Claude Code 交付程式碼的實用指南

原文標題：A practical guide to shipping with Claude Code

作者：Addy Osmani（@addyosmani）

原文：https://x.com/addyosmani/status/2125492213903978917

日期：2026-11-25（台北時間 15:30；UTC 2026-11-25 07:30）

備註：原文為英文；繁體中文翻譯，僅供個人閱讀。

我們剛推出了 Claude Ship，它可以審查你的合併請求（PR）、處理修正，並核准團隊政策允許的那些。你可能已經有自訂的技能（skill）或工作流程（workflow）來處理這些步驟，但我們想提供另一個選擇。這份指南根據我在 Claude Code 團隊的經驗，一步步帶你走過這些步驟。

當你開了一個合併請求（PR），通常會有一堆後續工作要做：

  • 持續整合（CI）失敗
  • 一份審查回來，帶著六則意見
  • 一次主分支（main）的合併造成衝突

這些全都是小小的任務，但每一件都會把你從專注的工作中拉走。

在我們團隊，這些後續工作通常由 AI 代理來做。例如，它可以接手審查者發現的一個問題，所以等作者回來時，合併請求（PR）已經更新過一次了。

以我的經驗，這是一種更有生產力、也更愉快的寫程式方式。它把情境切換（context switching）降到最低，讓我保持在心流狀態（flow state）。

我們談過 Claude Code 團隊做程式碼審查（code review）的流程（見這裡），也談過它底下的驗證（verification）流程（見這裡）。

Claude Ship 是為這樣的開發者或技術主管（tech lead）設計的：團隊在 GitHub 上工作，而自己沒有管理員權限。你現在就可以自己開始，只要執行幾個指令，再把學到的東西存成儲存庫（repository）裡的檔案，讓團隊審查。只有在團隊希望 AI 代理自動處理團隊的合併請求（PR）時，才需要管理員介入。

你仍然是這個流程的架構師，所以由你定義要做什麼、怎麼做，以及合併的標準是什麼。

合併請求之後的流程The post-PR process

開了合併請求（PR）之後，你會想找出問題、處理問題，最後決定這個變更能不能合併。

Claude Ship 是三個處理這些工作的 AI 代理：Code Review、PR Steward（測試版，beta）和 Claude Approvals（測試版，beta）。

Code Review 會從多個角度，對照整個程式碼庫（codebase）深入審查合併請求（PR）。它收集發現（findings），以對抗式（adversarial）的方式驗證它們、加以分類，再張貼到合併請求（PR）上。

PR Steward 負責讓合併請求（PR）保持綠燈，但它的設計是不會核准或合併合併請求（PR）。遇到失敗的持續整合（CI）檢查、合併衝突（merge conflict），以及來自 Code Review、其他審查工具或團隊成員的審查意見，它都會介入。每次推送之後，它會留言說明改了什麼、要怎麼復原。

接下來，Claude Approvals 會套用團隊寫成檔案、放在儲存庫（repository）裡的核准政策。如果政策允許，Claude 可以自己核准例行的變更；在某些情境下，也可以要求更深入的人工簽核（sign-off）。它的作用就像一個更聰明的 CODEOWNERS 檔案。團隊可以讓 Claude Approvals 在做決定時參考各種訊號，包括 Code Review 的發現（findings），或團隊自己的分類器（classifier）。

Code Review 已正式開放（generally available），另外兩個是測試版（beta）。/ship 是你在 Claude Code 裡自己執行的指令，用來在你自己的合併請求（PR）上試用 Claude Ship。它隨最新版的 Claude Code 提供，而且在管理員開啟任何 AI 代理之前就能用。

前兩個步驟你今天就能部分自動化。最後一個步驟是一個決定，由你在分支保護（branch protection）設定，以及（如果團隊採用的話）政策檔裡決定。以下用 Claude Ship 的三個 AI 代理，說明怎麼分工：

在你自己的合併請求上On your own PRs

今天就從 /code-review 開始Getting started today with /code-review

如果這篇文章你只做一件事，那就是在推送分支（branch）之前先審查它。在這個階段抓到的錯誤，比較不會在之後變成審查意見或失敗的檢查，把你從下一個任務拉走。在 Claude Code 的提示列輸入這個指令：

/code-review

它會審查你分支（branch）上的提交（commit）以及尚未提交的變更，找出正確性錯誤（correctness bugs）。有幾種變化要記住：

指令（英文原文）

/code-review high 1234       # review PR 1234 at high effort
/code-review --fix           # apply the findings to your working tree
/code-review --comment 1234  # post the findings on the PR
/code-review ultra           # run a deeper review in the cloud

繁體中文對照

/code-review high 1234       # 以 high 費力等級（effort）審查 PR 1234
/code-review --fix           # 把發現（findings）套用到你的工作區（working tree）
/code-review --comment 1234  # 把發現張貼到這個 PR 上
/code-review ultra           # 在雲端執行更深入的審查

費力等級（effort）從 low 到 max：low 只回傳審查最有把握的發現（findings），等級越高給你的範圍越廣（包括一些它比較沒把握的）。這個指令會記住你上次的費力等級（effort），所以風險程度改變時，要輸入新的等級。

幾點注意事項：

  • 使用 ultra 設定時要特別小心：它在雲端執行，需要登入 claude.ai，而且可能和你的方案分開計費。試用之前先讀 ultrareview 說明文件。
  • 背景審查期間由 --fix 做的修改，可能不會被 /rewind 涵蓋。如果想要有簡單的退路，先提交（commit）。
  • 本機的 /code-review 會讀你的 CLAUDE.md 檔案，但不會讀 REVIEW.md。這點後面會用到。

你該做的第一件事，是執行幾次 /code-review，了解它能抓到什麼、在哪裡會出錯。之後會用到這些。

在下一個合併請求執行 /shipRun /ship for your next PR

準備好之後，輸入：

/ship

如果你的分支（branch）還沒有合併請求（PR），/ship 會：

  1. 提交（commit）你尚未提交的變更。它的行為就像你執行了 git add -A，所以會遵守你的 .gitignore。必要時它會建立一個分支（branch），並用你的工作階段（session）來寫提交訊息。提交之前會通知你，你可以按 Esc 中止。
  2. 以你的身分推送並建立合併請求（PR）。
  3. 用 /code-review 做程式碼審查，除非這個提交（commit）已經被 Code Review 審查過。如果程式碼審查回報了任何問題，它會替你修正它判斷為成立的那些。
  4. 持續關注（watch）這個合併請求（PR）最多七天。它會處理失敗的檢查、衝突和審查意見，並在合併請求（PR）被合併或關閉時結束。

第一步，也就是 /ship 像執行了 git add -A 那樣提交你尚未提交的變更，有時會讓人嚇一跳，所以執行 /ship 之前，務必先執行 git status。

這個指令不會提交以下變更：碰到檔名看起來像機密（secrets）的檔案，或是設定規則的檔案，例如 CLAUDE.md、REVIEW.md，或 .claude/、.github/ 目錄裡的任何東西。這些提交（commit）你需要事先自己手動完成。

另外，如果你在公開儲存庫（repository）裡工作，這個指令不會替你提交任何變更。你需要先手動提交所有尚未提交的變更，才能繼續；而如果合併請求（PR）已經存在，它不會包含你尚未提交的變更。

選用：指定費力等級、合併請求或機器人Optional: specifying effort level, PR, or bot

指令（英文原文）

/ship high            # run at high effort
/ship 41              # work on pull request #41
/ship +my-lint-bot    # also read comments from my-lint-bot
/ship stop            # end the watch

繁體中文對照

/ship high            # 以 high 費力等級（effort）執行
/ship 41              # 處理合併請求（pull request）#41
/ship +my-lint-bot    # 也讀取 my-lint-bot 的留言
/ship stop            # 結束持續關注（watch）

這個指令預設會讀取你、有寫入權限的人，以及 Claude GitHub App 的留言。你可以用 +name 的形式指定其他機器人。如果那個機器人留言，它的留言會被當成一項主張，拿來對照程式碼檢查。

讓 Claude 持續關注合併請求Letting Claude watch the PR

Claude 會以你的身分、在你的電腦上持續關注這個合併請求（PR），並使用你的用量額度。闔上筆電就會停止，所以要保持工作階段（session）開著、電腦不要睡眠。你也需要登入 GitHub CLI（先執行 gh auth login），而且它只會持續關注你自己開的合併請求（PR）。

除了自動模式（auto mode）以外，持續關注在其他模式下每遇到一個提示都會停下來，需要你回應。在略過權限模式（bypass-permissions mode）下，它不會持續關注。注意，在 Windows 上，/ship 會開啟合併請求（PR）並審查，但持續關注不會啟動。

確保持續關注有自己的簽出（checkout）。你需要讓那個分支（branch）維持簽出狀態。如果你打算直接跳進下一個任務，就要確保其中一個用的是另一個工作樹（worktree）。

如果持續關注無法啟動，Claude 會說明原因，但仍然會審查合併請求（PR）。例如，如果你的儲存庫（repository）的 .claude/settings.json 裡，在 Bash 上設了 PreToolUse 或 PermissionRequest hook，就無法執行持續關注。

此外，持續關注會在你離開時消耗模型回合（turn），所以會計入你的方案用量或 API 帳單。第一次使用時，最好待在電腦附近，確認用量在你的預期之內。

只在你信任的儲存庫上執行持續關注Only run the watch on repos you trust

必要時，持續關注會把基底分支（base branch）合併進你的分支（branch），然後執行像是測試這類的指令。換句話說，任何有能力把變更送進基底分支（base branch）的人，都有能力在持續關注期間於你的電腦上執行指令。只在你信任每一個能把變更送進基底分支（base branch）的人的儲存庫（repository）上，在本機執行持續關注。

Claude 被告知永遠不要合併這個合併請求（PR），而且 Claude Code 也會限制它在無人看管的回合（turn）中能執行的 gh 和 git 指令，防止直接合併或強制推送（force push）。持續關注自己的提交（commit）也會排除設定規則的檔案：.github/、CODEOWNERS、CLAUDE.md、.claude/、git hooks 等等。

不過，這並不能防住所有攻擊途徑。例如，測試腳本也是用你的憑證（credentials）執行的；而如果你在某個回合（turn）中輸入訊息，那一回合的限制就會被解除。此外，如果開啟了自動合併（auto-merge），持續關注推上的一個修正，可能就是讓 GitHub 得以合併的那一步。

再者，Claude 在持續關注期間做的提交（commit）與推送，不受你儲存庫（repository）裡的 git hooks 影響，所以要確保所有必須存在的檢查，都已經加進持續整合（CI）和分支規則。

要看持續關注的完整條款，第一次使用前在產品裡執行 /ship terms。

用 /steward 處理既有的合併請求/steward for existing PRs

很多合併請求（PR）不需要再審查一次，而是需要有人把它們帶到合併為止。如果你有這樣的合併請求（PR），簽出（check out）那個分支（branch）並執行：

/steward 41

它只會執行 /ship 的持續關注部分。它會持續關注你開的合併請求（PR），處理失敗的檢查、衝突和留言之類的事，而不會先審查。

如果你沒有指定合併請求（PR）編號，它會持續關注目前分支（branch）的合併請求（PR）。它同樣接受 +name 機器人，前面提到的注意事項也同樣適用。

不過，如果一個合併請求（PR）已經被加上 Steward 標籤，它就不會執行本機的持續關注。而如果無法執行持續關注，/steward 什麼都不會做。

如果你想停止持續關注，可以用 /steward stop 或 /ship stop。因為一個工作階段（session）一次只能執行一個持續關注，開始新的就會結束前一個。

不要把 /steward 和 PR Steward 搞混。PR Steward 是團隊服務，由管理員開啟後以 claude[bot] 的身分執行。/steward 指令則是以你的身分、在你的工作階段（session）中執行。

檢查亮紅燈的合併請求（PR），是很好的起點。卡在衝突循環裡的合併請求（PR），也是很好的候選。反過來說，正在進行設計辯論的合併請求（PR）就不適合，因為那是該由你來解決的辯論。

Claude 會把較大的決定交回給你Claude escalates bigger calls to you

在持續關注的過程中，Claude 被告知要做小的修改，把大的往上交給你。例如：

  • 要求重新設計某樣東西，像是新的 API 或更大的範圍
  • 它無法解決的安全問題

對同一個問題，它最多推送 3 次，然後回報嘗試過的解法。

這大致等同於我們在驗證那篇部落格文章裡的主張：如果我們一直跑同一個檢查，而它在三輪之後仍然失敗，那麼做法大概就是錯的。

到了這個時候，它會把問題交給程式碼的作者。

在你的儲存庫裡In your repo

等你累積了幾個合併請求（PR）的經驗，就會開始注意到一些模式。例如：

  • 同一個審查者留下同一則意見
  • Claude 每次都得自己摸索的一個設定步驟
  • 一個不穩定（flaky）的檢查

你可以開始替團隊把這些寫下來，依照哪個工具需要讀它，寫進幾個檔案中的一個：

重複的意見，變成審查規則Repeat comments become review rules

假設同事已經兩次要求你確保新的查詢有租戶（tenant）檢查。如果你用本機審查，可以把這條寫進 CLAUDE.md，因為 /ship 是用 /code-review 來審查的。而如果你的儲存庫（repository）有開 Code Review，只跟審查有關的規則可以放進根目錄的 REVIEW.md：

REVIEW.md（英文原文）

# Review instructions

## What Important means here

Wrong results, leaked data or anything that blocks a rollback.
Style and naming are Nit at most.

## Always check
- Database queries are scoped to the caller's tenant.
- New API routes have an integration test.

## Keep it quiet
- Report at most five Nits.
- Skip generated files and lockfiles.
- Behavior claims need a file and line.

繁體中文對照

# 審查指示

## 這裡的 Important（重要）指什麼

錯誤的結果、外洩的資料，或任何會擋住回滾（rollback）的東西。
風格和命名最多只算 Nit（吹毛求疵）。

## 一律檢查
- 資料庫查詢都限定在呼叫者的租戶（tenant）範圍內。
- 新的 API 路由要有整合測試（integration test）。

## 保持安靜
- 最多回報五個 Nit。
- 略過自動產生的檔案和鎖定檔（lockfile）。
- 關於行為的主張，要附上檔案和行號。

Code Review 不會讀取正在被審查的那個合併請求（PR）裡的 REVIEW.md 檔案。另外，只有在預設分支（default branch）受到保護時，它才會遵守某些指示，例如排除路徑和限制吹毛求疵（nits）的數量。

不是每一則意見都該升格成規則。在我們團隊，有一條原則：一個模式至少要在 2 個合併請求（PR）上重複出現，才會被考慮寫成規則。接著由一個人核准新增這條規則的合併請求（PR）。這是值得採用的門檻。你也應該視需要刪除規則。

重複的設定步驟，變成 verify 技能Repeat setup becomes verify skills

如果你發現自己一直在告訴 Claude 怎麼啟動應用程式、怎麼進到特定頁面，就應該直接寫下來。建立 .claude/skills/verify/SKILL.md。它可以放在根目錄，或放在程式碼所在的目錄。

SKILL.md 開頭（英文原文）

---
name: verify
description: Run the web app and exercise a change end to end. Use before committing.
---

繁體中文對照

---
name: verify
description: 執行網頁應用程式，端到端（end to end）實際操作一次變更。在提交（commit）之前使用。
---
  1. 用 npm run dev:stack 啟動整套服務。
  2. 等待連接埠 3000 上的 /healthz 回傳 200。
  3. 用預先建立的測試帳號登入。
  4. 在瀏覽器裡實際操作改動過的流程，並截圖。
  5. 回報你執行過的步驟和看到的結果。沒有這些，不要回報成功。

記得依你的專案調整這些指令。

讓 Claude 執行幾次，並修好任何不穩定（flaky）的行為。人們會忽略他們不信任的驗證。

重複的合併請求維護工作，變成 steward 規則Repeat PR maintenance becomes steward rules

這一點很容易被忽略。本機的持續關注會從你的工作目錄讀取 .claude/skills/steward/SKILL.md 檔案，而在 Anthropic 雲端執行的 PR Steward，則是從預設分支（default branch）讀取。以下是一個範例：

SKILL.md 開頭（英文原文）

---
name: steward
description: House rules for looking after PRs in this repository
user-invocable: false
disable-model-invocation: true
---

繁體中文對照

---
name: steward
description: 在這個儲存庫裡照顧合併請求（PR）的內部規則
user-invocable: false
disable-model-invocation: true
---
  • 用 npm install 重新產生鎖定檔（lockfile），不要手動編輯。
  • e2e-nightly 不穩定（flaky）。先重跑一次，再去找原因。
  • 推送修正之前，先執行 npm test 和 npm run lint。
  • 關於 API 設計的意見，留給作者處理。

在這個範例中，最上面的兩個設定，讓它不會出現在 / 選單裡，也不會被 Claude 自己挑選技能（skill）時選到。

steward 檔案無法改變持續關注的限制。不過，任何能合併進這個儲存庫（repository）的人都能編輯這個檔案，所以要像審查持續整合（CI）的任何變更一樣，仔細審查對它的修改。

如果你的團隊之後開啟 PR Steward，這些準則一旦進到預設分支（default branch），就會在 Anthropic 的雲端生效。

擴及團隊的合併請求Across your team's PRs

把合併請求之後的流程標準化Standardizing the post-PR process

在你自己的幾個合併請求（PR）上執行過 /ship 之後，你就會很清楚 Claude Ship 能在團隊的合併請求（PR）上做到什麼。這篇文章接下來的內容，是給你跟管理員談這件事的時候用的，所以涵蓋了你該向他們要求什麼，以及如何安全地推行。

要開始，你需要向管理員要一個儲存庫（repository）、幾位自願者，以及一段有限的時間，在你們自己的合併請求（PR）上測試 Claude Ship。

  1. 事先講好預算限制。
  2. 保護這個儲存庫的預設分支（default branch）。儲存庫（repository）管理員可以設定這項要求，確保任何更新都必須透過一個在最新一次推送上取得核准的合併請求（PR），而且 Claude GitHub App 不在略過名單（bypass list）上。
  3. 替這個儲存庫開啟 Code Review。Owner（擁有者，也就是你的 Claude 組織裡的管理員角色）可以開啟 Code Review。
  4. 以手動模式（Manual mode）開啟 PR Steward。同一位 Owner 可以開啟 PR Steward，讓它在有寫入權限的使用者留言 @claude steward 時介入，或在作者選擇加入時自動介入。留言 @claude stop 可以讓 Steward 停下。
  5. 建立一份觀察模式（observe mode）的核准政策。這個檔案和其他檔案一樣；你可以在自己的合併請求（PR）裡建立它，但因為合併這個檔案就會替這個儲存庫（repository）啟用 Approvals，所以要先跟 Owner 確認。

PR Steward 的設計是不會核准或合併合併請求（PR），所以務必用分支保護（branch protection）要求合併前必須取得你想要的核准。

PR Steward 會讀取審查者的留言，並根據留言採取一些行動。就像任何解析文字的 AI 代理一樣，它可能被別人說的話騙。務必只在協作者都值得信任的儲存庫（repository）裡使用它，並檢查 PR Steward 根據不受信任使用者的留言所做的修改。

設定你的第一份核准政策Configure your first approval policy

關於核准政策，Claude Approvals 會讀取預設分支（default branch）上的 .claude/approvals.yml 檔案。一份簡單的第一版政策可以是：

.claude/approvals.yml（英文原文）

# .claude/approvals.yml

version: 1
mode: observe

rules:
- purpose: "A change takes two people."
paths: ["**"]
verdict: { claude: comments, seats: 2 }
advisory: [claude/code_review]

- purpose: "A change to the review rules takes two people."
paths: ["**/.claude/**", "**/REVIEW.md", "**/CLAUDE.md", "**/CODEOWNERS", ".github/**"]
nested: inherit

verdict: { claude: comments, seats: 2 }

繁體中文對照（只翻 purpose 說明文字）

- purpose: "一個變更需要兩個人。"
- purpose: "修改審查規則的變更需要兩個人。"

seats（席位）是必須核准的人數，作者可以佔其中一個席位。

這裡有一個陷阱：持續關注把基底分支（base branch）合併進來之後，最新的提交（commit）會是一個合併提交（merge commit），而這個提交沒有人坐在作者的席位上。所以合併請求（PR）的作者應該留言 @claude approve。

當一條規則的判定（verdict）是 claude: comments 時，Claude 不會核准。如果有多條規則符合，最嚴格的那條勝出。在觀察模式（observe mode）下，這項檢查會印出結果，但不會核准。

務必保留 advisory 那一行。政策檔一旦進到預設分支（default branch），Code Review 就只會在符合「有點名它的規則」的合併請求（PR）上自動啟動，所以少了那一行，你的自動審查就會停止。參考性（advisory）審查不影響判定（verdict），並依照你現有的設定執行。點名 Code Review 的政策可能會啟動計費的審查，即使在 Code Review 已關閉的地方也一樣。

如果想看看 Claude 審查通過，會在哪些地方降低某個路徑的要求，你可以把 advisory 那一行換成一個覆寫（override），並更新規則的 purpose（用途）來配合（例如：「When Claude's review passes, one is enough and Claude approves.（Claude 的審查通過時，一個人就夠了，而且由 Claude 核准。）」）。

 override:
      - { if: "claude/code_review = pass", verdict: { claude: approves, seats: 1 } }

因為覆寫（override）也點名了 Code Review，那些合併請求（PR）仍然會觸發自動審查。審查通過時，覆寫會拿掉這條規則原本的決定，換成一個席位加上 Claude 的核准。作者可以填上那一個席位，所以這項檢查現在可以回報 Claude 本來會核准。但合併請求（PR）裡的文字可能左右 Claude 的審查，而一旦發生這種事，這個覆寫就會降低那個合併請求（PR）需要的條件。

如果有些路徑一定要有人，就把它們放進一條沒有覆寫（override）的規則（下一節的第 1 步）。合併之前先告訴預算負責人，因為這樣設定的政策會啟動計費的 Code Review，即使在觀察模式（observe mode）下也一樣，只要你推送就會啟動，不管你的 Code Review 設定是什麼。

你也可以自己打造分類器（classifier），回答像是「這個合併請求（PR）跟遷移（migration）有關嗎？」這類問題。自訂分類器（classifier）放在預設分支（default branch）上的 .claude/classifiers/<name>/def.yml，每次執行都會計費，即使在觀察模式（observe mode）下也一樣。一開始先專注在路徑和 Code Review 的結果上。

監看，並轉為強制執行Monitoring and transitioning to enforcement

我們團隊自己內部的提交關卡（commit gate），用的就是和觀察模式（observe mode）一樣的流程。它會記錄在觀察模式下本來會做出的決定，讓我們在把它變成強制之前，先分析誤報（false positive）。你會在 Claude Approvals 檢查和相關留言裡看到這些決定。

記住，只有在你真的去監看時，觀察模式（observe mode）才有價值。上線一兩週之後，回頭看已合併的合併請求（PR），比較這些決定和你的審查者實際的做法。

前兩列在你加上覆寫（override）之後才適用。

看過幾個範例合併請求（PR）。換作是你，會怎麼決定？是哪條規則做出決定的？你會改什麼？最要注意第二列，在放寬任何規則之前，先把那些修好。

開始強制執行之前，有一件事要知道：Claude 的核准在 GitHub 上算是真正的核准。如果規則集（ruleset）只需要一個核准，Claude 的核准本身就可能足夠。所以要把你的政策和分支規則放在一起讀。

如果你使用自動合併（auto-merge），而且有只有作者能滿足的政策（像上面的覆寫），你可能會遇到沒有任何人做任何事、合併請求（PR）就被合併的情況。針對每個路徑，明確決定這樣是否可以接受，並寫下來。

接著依照這個順序把它鎖緊：

  1. 對於永遠需要第二雙眼睛的路徑，使用一條沒有 if 也沒有覆寫（override）的規則。任何分類器（classifier）結果都無法覆寫它，而 nested: inherit 會把它帶進有自己政策的子目錄。

    規則（英文原文）

    - purpose: "Auth, billing and CI take a person who isn't an author."
    paths: ["src/auth/**", "src/billing/**", ".github/**"]
    nested: inherit
    verdict:
      claude: comments
      seats: [{ count: 1, from: [humans, "!pr/authors"] }]

    繁體中文對照（只翻 purpose 說明文字）

    - purpose: "驗證、帳務和持續整合（CI）需要一位非作者的人。"
  2. 移除 mode: observe 並合併。現在，在規則說 Claude 核准的地方，Claude 就可以核准了。
  3. 大約五分鐘後，在開著的合併請求（PR）上留言 @claude approvals rerun，把所有過時的結果清掉。重跑可能會再次產生分類器（classifier）費用。
  4. 請儲存庫（repository）管理員把 Claude Approvals 檢查設為必要檢查（required check），並選擇 Claude 應用程式作為它的來源。在那之前，不管這項檢查說什麼，你的合併請求（PR）都可能被合併。

Claude Ship 和本機指令都使用 AI，可能漏掉錯誤、安全問題和其他問題，所以要保留你現有的所有測試、掃描工具和審查者。

這週可以試的事Things to try this week

我想說清楚：在 Claude Code 團隊，呼叫 AI 代理的那個人要為變更負責，就好像那是他們自己打出來的一樣。

你的團隊仍然要為合併請求（PR）的範圍、設計、證據，以及什麼時候可以合併的規則負責。把這些原則放在心上，以下是你可以開始的地方：

  1. 今天：在你目前的分支（branch）上執行 /code-review。記下它哪裡錯了、漏了什麼。
  2. 下一個合併請求：在一個你信任所有能合併的人的儲存庫（repository）裡，試試 /ship，並且待在旁邊。在一個既有的合併請求（PR）上試試 /steward，用另一個終端機和另一份 git 簽出（checkout）。
  3. 星期五之前：開一個小的合併請求（PR），把你重複最多次的那條規則寫進 CLAUDE.md、REVIEW.md 或一個技能（skill）。這個提交（commit）要自己做，因為 /ship 不會提交規則檔。把這個合併請求（PR）和觀察模式（observe mode）的範例政策分享給你的團隊。

如果你這麼做了，我很想知道哪個規則檔影響最大，以及你選擇哪些任務繼續自己做。

以下為譯者整理，非原文內容。

這篇在說什麼

寫程式的人開了一份「請大家看看、同意後就合併」的申請（合併請求，PR）之後，常常還有一堆零碎雜事：自動測試失敗、審查意見要改、跟別人的修改撞在一起。這篇是 Claude Code 團隊的實用指南，教你怎麼讓 AI 代理接手這些雜事，而「能不能合併」這個決定仍然留在人和團隊規則手上。

文中的工具是 Anthropic 剛推出的 Claude Ship（由 Code Review、PR Steward、Claude Approvals 三個 AI 代理組成），以及你自己就能執行的三個指令：/code-review、/ship、/steward。

為什麼值得學

就算你不寫程式，這篇也示範了一套把工作交給 AI 的穩健順序：先自己小規模試用、把反覆出現的經驗寫成規則、讓 AI 在「只觀察、不動手」的模式下跑一陣子，比對它的判斷和人的判斷，最後才逐步放手。同時清楚劃出「AI 負責雜事、人負責決定與責任」的界線。

你可以帶走的重點

1. 把合併前的工作拆成三段：找問題、處理問題、做決定

Code Review 負責找問題，PR Steward 負責處理（修測試、解衝突、回應意見），Claude Approvals 依團隊寫好的政策判斷能不能核准。前兩段可以交給 AI，最後一段的標準由你和團隊設定。

2. 三個指令，看時機用

推送之前用 /code-review 自己先抓錯；準備開合併請求時用 /ship，它會提交、開合併請求、審查，並持續關注最多七天；合併請求已經開了、只缺人帶到終點時，用 /steward。這三個都在你自己的工作階段（session）裡、用你的身分和用量執行，不需要管理員。

例：寫完功能先跑 /code-review 看看，滿意了再 /ship；同事丟來一個卡在紅燈的舊合併請求，就用 /steward。

3. 讓 AI 代你值班之前，先想清楚誰能在你電腦上執行指令

持續關注（watch）會把別人推進基底分支（base branch）的變更合併進來，再跑測試。等於任何能改那個分支的人，都能間接在你的電腦上執行指令。所以只在你信任所有協作者的儲存庫上使用；AI 雖然被禁止直接合併或強制推送，但不是所有漏洞都擋得住。

4. 同一件事重複兩次，就寫成檔案裡的規則

團隊的原則是：一個模式至少在 2 個合併請求上出現，才考慮寫成規則，而且新增規則的合併請求要由人核准，也要記得刪掉過時的規則。依照「誰要讀」決定放哪裡：程式慣例放 CLAUDE.md，審查規則放 REVIEW.md，啟動與測試步驟寫成 verify 技能（skill），照顧合併請求的習慣寫成 steward 技能。

例：同事第二次提醒「新的查詢要檢查租戶（tenant）」，就把這句寫進規則檔，以後 AI 審查會自己檢查。

5. 先「只觀察」，比對過再放手

核准政策先用觀察模式（observe mode）：AI 只記錄「本來會怎麼判」，不真的核准。一兩週後拿已合併的合併請求比對：AI 說會核准、人卻要求修改的那一類最要緊，先修好規則再放寬。確認後才依序鎖緊：一定要人看的路徑先寫死、移除觀察模式、重跑一次清掉舊結果、請管理員把檢查設為必要。

還要記得：Claude 的核准在 GitHub 上算真的核准；觀察模式下，有點名 Code Review 的政策照樣會計費。

怎麼開始（作者建議的本週練習）

  1. 今天：在目前的分支上跑一次 /code-review，記下它錯在哪、漏了什麼。
  2. 下一個合併請求：在你信任所有協作者的儲存庫試 /ship，並待在旁邊看；另開一個終端機和簽出（checkout），在舊的合併請求上試 /steward。
  3. 星期五前：把你最常重複的那條規則寫進規則檔，自己提交（/ship 不會替你提交規則檔），再把它和觀察模式的範例政策分享給團隊。

譯者提醒：PR Steward 與 Claude Approvals 在原文發表時仍是測試版（beta），功能、計費方式與限制（例如 Windows 上不會啟動持續關注、公開儲存庫不會自動提交）可能隨版本改變，實際使用前請以官方說明文件為準。
