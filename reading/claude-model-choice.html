該用哪個 Claude 模型來開發？Fable、Opus、Sonnet 還是 Haiku

原文標題：Which Claude model should you build with? Fable, Opus, Sonnet, or Haiku

作者：Addy Osmani（Member of Technical Staff，Anthropic；claude.dev Blog・Playbooks）

原文：https://claude.dev/blog/which-claude-model-should-you-build-with/

日期：2026-11-09（原文僅標示日期，未標時間；閱讀時間約 15 分鐘）

該選哪個 Claude 模型、它們各要多少錢，以及如何把它們搭配起來使用。

目前的 Claude 產品線有四個正式開放（generally available）的模型：Claude Haiku 5.5、Claude Sonnet 5.5、Claude Opus 5.5 和 Claude Fable 5.2。Claude Mythos 5.2 是我們在資安與生命科學研究上能力最強的模型，透過我們的驗證計畫提供。

如果你在 Claude Platform 上開發，或在 Claude Code 裡工作，你可能會想知道常見的任務該用哪個模型。這篇文章會幫你回答這個問題，並說明該如何思考其中的取捨。

重點摘要TL;DR

簡單的答案是：大多數工作，你都應該從 Opus 5.5、搭配它的預設費力等級（effort level）medium 開始。

它會是 Claude Code 的預設模型是有原因的。它每個輸入和輸出 token 的價格是 Fable 5.2 的一半，也是我們建議大多數程式開發與知識工作一開始就用的模型。

從這裡出發：

  • 往下換到 Sonnet 5.5，處理範圍明確的日常工作，例如修一個錯誤，或依照規格文件（spec）做一個功能。不過，有清楚的規格文件（spec），不代表就該用 Sonnet。一次遷移（migration）或效能優化，也可能有清楚的規格文件（spec），卻仍然難到值得用 Opus 5.5；如果是大型的，甚至值得用 Fable 5.2。
  • 再往下換到 Haiku 5.5，處理最簡單、大量的工作，例如分類、路由（routing）和擷取（extraction）。Haiku 5.5 也很適合搭配子代理（subagents），處理較大模型的周邊任務。
  • 往上換到 Claude Fable 5.2，處理程式開發、金融和科學領域最困難的技術專案。當 Opus 5.5 在 high 仍然不夠，或需要長時間無人看管的執行時，也該往上換。

在換模型之前，先試著調整費力等級（effort level）。它是一個對成本和能力都更精細的旋鈕。超過 high 之後，再多一個費力等級（effort level）的花費，可能就跟換一個更大的模型一樣多，所以要在你自己的工作上比較兩者。如果你已經超過 high，改用下一個更大的模型、搭配較低的費力等級（effort level）來測試。反過來說，降低一個等級，也可能用更低的費用得到你需要的結果。

當模型需要想得更久、呼叫更多工具，或更仔細檢查自己的工作時，較高的費力等級（effort）會有幫助。只是要記得，它也會增加延遲（latency）。此外，提高費力等級（effort level），並不會給模型它原本沒有的知識或技能。要得到那些，你仍然得換到更大的模型。

取捨The trade-offs

在模型之間做選擇，就是在做取捨。舉例來說，當你挑選較大的模型，你是在選擇能力而不是延遲（latency）。以下是需要想清楚的主要取捨。

能力與每個完成任務的成本Capability and cost per finished task

一般來說，較大的模型每個 token 比較貴，也比較有能力，但在任務層級上，成本與能力的取捨並不是一律成立。

每個 token 價格較高，不一定代表每個任務的成本較高，也不一定代表結果更好。正如我們在〈Spending your effort〉中所示，在 Anthropic 自己跑的 Terminal-Bench 3.0 上，前一代的 Fable 5.1 在 max 得到 58.0%，而 Opus 5.5 在 high 用一半的 token 得到 58.9%。

在最困難的工作上，價差可能會縮小。在 FrontierCode 2.0 上，Fable 5.2 在 high 的分數，和 Opus 5.5 在 max 差不多（45.3% 對 45.5%），每個任務的成本卻大約只有一半。所以在困難任務上把 Opus 5.5 調到 high 以上之前，先測試 Fable 5.2。日常工作仍然以 Opus 5.5 在 medium 為起點。基準測試（benchmark）結果請見發布文章。

不過，Claude Platform 的成本與智慧程度量測也顯示了小模型的極限。小模型通常很擅長大量、輸出可以檢查的工作，比較不適合長時間的代理式迴圈（agentic loops）。

比較兩個模型時，除了典型任務之外，也要替你任務集合中最困難的那些估價，因為大部分花費都落在最困難的任務上。在某個 20 題的搜尋基準測試（benchmark）中，有兩題就佔了 43% 的花費。

延遲與準確度Latency against accuracy

比較快的設定完成得比較早，也可能漏掉比較多。在挑選模型和費力等級（effort level）之前，先想清楚使用者能等多久。對於使用者正在等待的回覆，先從 Sonnet 5.5 搭配 low 或 medium 開始。

新一代的模型通常比前一代快。Fable 5.2 產生輸出的速度，最多比 Fable 5.1 快 30%。Sonnet 5.5 比 Sonnet 5 快 30%。

費力等級（effort level）和延遲（latency）大致正相關。判斷你得到的準確度，是否值得多出來的延遲（latency）。舉例來說，在 SWE-bench Pro 上，Opus 5.5 在 medium 的分數比 high 低約 2.5 分，成本約為 high 的 70%。在 low 時分數低約 8 分，成本約為三分之一。在 xhigh 時分數高約 1.4 分，成本是 high 的 2.5 倍。

提供一種讓模型自我驗證的方法，往往比調整費力等級（effort level）更划算，增加的延遲（latency）也更少。當一個模型不足以勝任某個任務時，依序採取這些步驟：

  1. 確認模型能驗證自己的工作，例如透過一項測試、一次建置，或一支呼叫端點（endpoint）的腳本。
  2. 把費力等級（effort）調高一級。
  3. 換到下一個更大的模型，並從比你在小模型上用的更低的費力等級（effort level）開始。

如果你能自動檢查結果，就用低等級跑完所有任務，只把失敗的用高等級重跑。在同一組 SWE-bench Pro 子集上，Opus 5.5 以 low 執行、失敗的再以 high 重跑，通過了約 97% 的任務，每個約 0.17 美元；相比之下，每個任務都用 high，通過率為 95.3%，每個 0.29 美元。

如果你需要同一個模型更快回覆，可以付費換取速度，而不必犧牲能力。在 Claude API 上，Opus 5.5 和 Fable 5.2 都提供快速模式（fast mode），以較高的價格換取更高的輸出速度。

脈絡與成本Context against cost

這一代的每個模型都有 100 萬 token 的脈絡視窗（context window）。大量的脈絡可以幫助模型完成任務，但每一個回合你都要為它付費，因為每個回合都會重新送出它。話雖如此，在長時間的執行中，大部分輸入都是以快取讀取（cache reads）計費。

Opus 5.5 的快取讀取（cache read）每百萬 token 收 0.20 美元，Sonnet 5.5 收 0.10 美元。Fable 5.2 同樣收 0.20 美元，所以在一次長時間、大量使用快取的執行中，Fable 和 Opus 的差距就落在未快取的輸入與輸出上，而 Fable 在這部分每個 token 的價格是兩倍。

在〈What a task costs on Opus 5.5〉中，脈絡為 15 萬 token 時，一個回合的快取讀取（cache read）約 0.03 美元；在 2 萬 token 時約 0.004 美元。

從這裡可以得到一個結論：主模型越大，保持精簡的主脈絡就越重要。把昂貴模型的脈絡留給決策，讓較便宜的子代理（subagents）去做冗長的閱讀。

Haiku 5.5 是唯一一個 token 價格會隨提示詞（prompt）長度改變的模型。10 萬 token 以內的提示詞（prompt）以較低的級距計費，超過 10 萬 token 的提示詞（prompt）則以該費率的五倍計費。這個長提示詞（long-prompt）級距的每 token 價格，仍然只有 Sonnet 5.5 的四分之一。所以 Haiku 5.5 在短提示詞（short prompts）上最划算，此時它的輸入價格只有 Sonnet 5.5 的二十分之一。

當每次呼叫都需要很長的提示詞（prompt）時，請用每個完成任務的成本、而不是牌價，來比較 Haiku 5.5 和 Sonnet 5.5。

混用模型Mixing models

在自然的段落切換Switch at a natural break

提示詞快取（prompt cache）屬於寫入它的那個模型。換到新模型後的第一個回合，要對整段對話支付快取寫入的價格。要讓那個回合小一點，可以先在 Claude Code 裡執行 /compact，或用一份簡短的書面計畫開始一個新的工作階段。在 API 上，則用目前為止的工作摘要、而不是完整的歷史紀錄，來開啟新模型的對話。

每個思考區塊（thinking block）都會記錄產生它的模型，而每個模型只讀得懂其他部分模型的思考區塊（thinking blocks）。在 Claude API 和 Claude Models on Google Cloud（Google 代管）上，Opus 5.5 讀得懂 Sonnet 5.5 和 Haiku 5.5 的思考區塊（thinking blocks）。Sonnet 5.5 讀得懂 Haiku 5.5 的。Fable 5.2 讀得懂 Opus 5.5、Sonnet 5.5 和 Haiku 5.5 的。在 Claude API 上，Fable 5.1 讀得懂 Opus 5.5 的。

往下換一個級別，會失去先前的推理，因為模型永遠讀不了比它高級別模型的思考區塊（thinking blocks）。其他方向的切換也可能失去推理。當新模型讀不了先前模型的思考區塊（thinking blocks）時，API 會把它們丟掉，請求仍然會成功。新模型接著就在沒有那段推理的情況下工作。

保留思考（Preserved thinking）列出了所有情況。從 Fable 5.2 換到任何其他正式開放的模型，都會丟掉它的推理。

把子代理放在較小的模型上Put subagents on smaller models

子代理（subagent）在它自己的脈絡視窗（context window）裡執行，最後交回一份摘要。你以它所執行的模型的費率，為它的 token 付費。在 Claude Code 裡，在子代理（subagent）的定義中設定 model: haiku 或 model: sonnet。CLAUDE_CODE_SUBAGENT_MODEL 環境變數，則為沒有指定模型的子代理（subagents）設定預設值。

把這個存成 .claude/agents/log-reader.md：

Markdown（英文原文）

---
name: log-reader
description: Reads test output and logs, and reports each failing case. Use after a test run.
tools: Read, Grep, Glob, Bash
model: haiku
---
Read the logs you're given. For each failure, report the file, the test name and the first error line. Don't edit any files.

繁體中文對照（欄位名稱與設定值不變，只翻譯文字說明）

---
name: log-reader
description: 讀取測試輸出和紀錄檔，並回報每一個失敗的案例。在跑完測試後使用。
tools: Read, Grep, Glob, Bash
model: haiku
---
讀取交給你的紀錄檔。對每一個失敗，回報檔案、測試名稱和第一行錯誤訊息。不要編輯任何檔案。

把小模型留給錯誤很容易發現的工作，例如找檔案、跑測試和讀紀錄檔。把程式碼修改和需要判斷的事留在主模型上。當小模型讀錯一筆搜尋結果，主模型就會打開錯的檔案，並在上面浪費 token。

在目前版本的 Claude Code 中，內建的 Explore 子代理（subagent）會使用你工作階段的模型，而不是一律用 Haiku 執行。在 Claude API 上，這個模型最高只到 Opus。要讓探索保持便宜，可以自己定義一個名為 Explore 的子代理（subagent），並設定 model: haiku。你可以用 ANTHROPIC_DEFAULT_HAIKU_MODEL 固定 haiku 別名（alias）所使用的模型。

在 Anthropic API 上，haiku 別名（alias）現在會對應到 Haiku 5.5，這需要 Claude Code v2.1.293 或更新版本。在 Amazon Bedrock、Google Cloud、Microsoft Foundry 和 Claude Platform on AWS 上，它仍然對應到 Haiku 4.5。詳細資訊請見 Claude Code 的模型設定（model configuration）文件。

Claude Code 也有 opusplan 別名（alias），它在規劃模式（plan mode）中用 Opus 規劃，再用 Sonnet 執行計畫。這會把你的程式碼修改交給 Sonnet。上面的建議正好相反：它把程式碼修改留在主模型上，只把錯誤很容易發現的工作交給較小的模型。在把 opusplan 設為預設之前，先在你自己的任務上量測它。

把困難的決定升級給顧問Escalate hard decisions to an advisor

顧問工具（advisor tool）（測試版）把一個更快、更便宜的執行者（executor）模型，和一個更強的顧問（advisor）模型配成一對。執行者（executor）負責執行任務，並可以在中途向顧問（advisor）尋求指引。大部分 token 都以執行者（executor）的費率計費。只有當顧問（advisor）能補上執行者（executor）缺少的能力、而且執行者（executor）真的開口求助時，顧問（advisor）才幫得上忙；而在低費力等級（effort）下，執行者（executor）比較少開口。

可能划算的情況：大部分回合都是例行工作的代理式工作。平台的成本指南態度很謹慎：在它顧問（advisor）表格裡的四種組合中，沒有一種明顯勝過執行者（executor）單獨執行，而且顧問（advisor）只有在執行者（executor）諮詢它時才能幫忙。先量測你的執行者（executor）的諮詢率。確認你的執行者（executor）接受哪些顧問（advisors）。舉例來說，Sonnet 5.5 執行者（executor）接受 Fable 5.2、Opus 5.5、Opus 5 和 Sonnet 5.5，而 Fable 5.2 執行者（executor）只接受 Fable 5.2 或 Mythos 5.2。

幫助不大的情況：其中一種組合，是在一項內部程式開發基準測試（benchmark）上，以 high 執行的 Opus 5.5 執行者（executor）搭配 Fable 5.1 顧問（advisor）。它得到 90.1%，每次嘗試 2.92 美元。這比 Opus 5.5 單獨在 high 執行高了 1.7 分，花費卻約為 2.1 倍。這麼小的提升，落在每次執行間雜訊的邊緣，也差不多就是提高費力等級（effort）能買到的效果。

把大量工作委派給較便宜的工作者Delegate bulk work to cheaper workers

前面提到的子代理（subagents），是在一個主模型掌握主線的同時處理周邊任務。這個模式則是用在超過一個脈絡視窗（context window）的工作上。一個頂級模型負責帶領，把任務拆開，平行交給許多較便宜的工作者（workers），再把回傳的結果合併起來。在一項內部的缺陷搜尋基準測試（benchmark）上，針對約 2,200 萬 token 的原始碼，由 Opus 5.5 帶領 Sonnet 5.5 工作者（workers）、最多同時 25 個，成本比 Opus 5.5 在預設費力等級（effort）下單獨執行少了約三分之一，分數則差不多。

在 Claude Platform 上，Claude Managed Agents 的多代理編排（multiagent orchestration）給你一個協調者代理（coordinator agent）和一組工作者（workers）。如果是一連串彼此依賴的步驟，或是一個脈絡視窗（context window）就裝得下的工作，就別用它。在那些情況下，規劃和合併的成本會比省下的更多。〈When to fold subagents into your main agent loop〉說明了什麼時候一個代理迴圈會勝過一整組子代理（subagents）。

遷移前先檢查相容性Check compatibility before migrating

選擇模型主要是能力和成本的問題，但你不一定能只改模型名稱、其他什麼都不動。目前的每個模型都支援工具使用（tool use）和圖片輸入，但把一個請求從一個模型搬到另一個之前，有些差異需要測試。

  • Fable 5.2 把保留思考（preserved thinking）擴大到所有 API 帳號。只要 Fable 5.2 思考區塊（thinking block）之前的任何內容改變了——包括系統提示詞（system prompt）、工具或先前的訊息——API 就會以 400 錯誤拒絕這個請求，除非你選擇讓受影響的思考內容被丟棄。如果你是透過 Claude Code、Claude Agent SDK 或 Claude Managed Agents 建立請求，就不需要改任何東西。如果你自己的程式碼會編輯歷史紀錄，就讓它保持只能追加（append-only），並在切換之前先測試。
  • 思考（Thinking）。Opus 5.5 和 Fable 5.2 一律會思考，把思考關掉的請求會回傳錯誤。Sonnet 5.5 預設會思考，between_tools 會把思考限制在工具呼叫之間的空檔。Haiku 5.5 預設會思考，在 high 以下的費力等級（effort）可以關掉思考。在所有模型上，都要依 type 讀取內容區塊，因為回應可能以一個思考區塊（thinking block）開頭。
  • 強制使用工具（Forced tool use）。在 Sonnet 5.5、Opus 5.5 和 Fable 5.2 上，tool_choice 設為 any 或 tool 會回傳 400 錯誤。改送 auto，把工具標為 strict: true，並在提示詞（prompt）中說明何時使用它。
  • 電腦操作（Computer use）。Opus 5.5、Sonnet 5.5、Haiku 5.5 和 Fable 5.2，只有在 Claude API 和 Claude Models on Google Cloud（Google 代管）上透過 computer_toolset_20260801 工具組，才支援電腦操作（computer use）。
  • 從 Haiku 4.5 到 Haiku 5.5。把 budget_tokens 換成一個費力等級（effort level），並拿掉非預設的 temperature、top_p 和 top_k 值，因為它們會回傳 400 錯誤。讓 messages 以使用者回合結尾，因為以助理回合結尾、要模型接著寫，也會回傳 400 錯誤。
  • 安全備援（Safety fallbacks）。Opus 5.5、Sonnet 5.5 和 Fable 5.2 會執行安全分類器，最常標記的是資安和生物學內容。在 Claude Code 裡，被標記的請求可能會改用較舊的模型重跑，紀錄稿（transcript）中會有通知告訴你是哪一個。Fable 5.2 沿用 Fable 5.1 的備援模型：被標記的資安請求會退回 Opus 4.8，被標記的生物學請求則退回 Opus 5。

如果一個系統會用到好幾個模型，就以其中最嚴格的那個為準來建構每一個請求：讓歷史紀錄保持只能追加（append-only）、以嚴格工具送出 tool_choice: auto、依 type 讀取內容區塊，並把提示詞（prompts）和工具說明寫得足夠精確，讓最照字面理解的模型也能懂。這樣一來，某個步驟就能往上或往下換級別，而不用改程式碼。當路由（routing）規則很簡單時，例如每種步驟各用一個模型，就讓程式碼來選模型，而不是請一個模型來選。

在你自己的工作上量測Measure on your own work

公開的結果，例如上面的 SWE-bench Pro 和 Terminal-Bench 數字，能給你一個起始模型。接著，在你正式採用之前，先在自己的任務上測試候選模型。

  1. 抽出一批真實任務的樣本。替每一項寫一個結果檢查，例如一項通過的測試、一張關閉的工單，或一個正確的資料列數。
  2. 讓每個候選模型以兩到三個費力等級（effort levels）執行，每次都在各自的工作階段中進行，讓不同的執行不會共用快取。從每個回應的 usage 欄位，記錄每個完成任務的成本。
  3. 把分數對花費畫成圖。只有當多模型的設定勝過這張圖上每一個單一模型的點時，才保留它。
  4. 在正式切換之前，先讓勝出者在一部分真實流量上以影子模式（shadow）執行。

如果想在 Claude Code 裡快速檢查一下，就從待辦清單中挑一個任務，用 /model 在兩個模型上各跑一次，再比較 /usage 回報的結果。

以下為譯者整理，非原文內容。

這篇在說什麼

Claude 有好幾個模型，越大的越聰明也越貴。這篇是 Anthropic 給開發者的選擇指南：大多數工作先用 Opus 5.5（預設的 medium 費力等級（effort）），簡單、量大的往下換 Sonnet 或 Haiku，最難的才往上換 Fable 5.2。

文章也說明了怎麼比較「完成一件事」的真實成本、如何把大小模型搭配使用，以及換模型前要注意的技術相容性。

為什麼值得學

很多人選模型只看「哪個最強」或「哪個最便宜」。這篇提醒：每個 token 的價格高，不代表完成一個任務比較貴；有時大模型用更少的 token 就做完了。學會用「每個完成任務的成本」來比較，並在自己的工作上實測，才能同時顧到品質和花費。

你可以帶走的重點

1. 從中間開始，再往上或往下調

起點是 Opus 5.5。範圍明確的日常工作換 Sonnet 5.5；分類、路由（routing）這類簡單又大量的工作換 Haiku 5.5；程式、金融、科學裡最難的專案，或 Opus 5.5 在 high 仍不夠時，換 Fable 5.2。

2. 模型不夠用時，照順序升級

先讓模型能自己驗證（跑測試、建置或呼叫端點的腳本）；還不夠，再把費力等級（effort）調高一級；最後才換大一號的模型，而且從較低的費力等級（effort）開始。超過 high 之後，多一級的花費可能跟換大模型一樣多。

3. 比的是「完成一件事」的成本，不是牌價

文中的例子：在 SWE-bench Pro 上，Opus 5.5 先用 low 跑、失敗的再用 high 重跑，通過約 97%、每個任務約 0.17 美元；全部用 high 則是 95.3%、每個 0.29 美元。也別忘了把最難的任務算進去，它們通常吃掉大部分預算。

4. 大模型做決定，小模型跑腿

主模型的脈絡越精簡越好。找檔案、跑測試、讀紀錄檔這類「錯了也很容易發現」的工作，交給 Haiku 或 Sonnet 的子代理（subagents），它們只交回摘要；修改程式碼和需要判斷的事留給主模型。

5. 換模型不只是改名字

不同模型對思考、強制使用工具、歷史紀錄的修改等規則不同，有些情況會直接回傳 400 錯誤。文中的建議是：以最嚴格的模型為準來寫請求，例如歷史紀錄只追加不修改、用 tool_choice: auto，這樣之後換模型就不必改程式碼。

怎麼開始

  1. 先用 Opus 5.5 的預設設定做你手上的工作，記下每個任務花了多少。
  2. 挑幾個真實任務當考題，替每個寫好「怎樣算完成」的檢查，例如測試通過。
  3. 讓兩三個候選模型、各用兩三個費力等級（effort）跑一遍，把分數和花費畫在同一張圖上比較。在 Claude Code 裡可以用 /model 切換、/usage 看花費。
  4. 把讀資料、跑測試這類雜事交給便宜的子代理（subagents），例如照文中的 log-reader.md 範例設定 model: haiku。
