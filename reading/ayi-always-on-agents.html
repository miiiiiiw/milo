第 1 則：主貼文

Anthropic 剛剛發布了一份含金量極高的工程指南，手把手教大家怎麼搭建全天候運作的 AI 代理（Agent）。

但整篇最反直覺的結論竟然是：所謂全天候運作，

根本不是讓模型 24 小時不停地轉。

老實說，很多朋友一開始搭 AI 代理，就喜歡寫個無窮迴圈，讓它一直在線上盯著，

結果不僅 token 帳單燒穿，狀態還常常寫亂。但在 Anthropic 的實戰架構裡，一個成熟的 24/7 AI 代理，

其實幾乎一整天都在深度休眠，只有被觸發時才短暫醒來跑幾秒，存好狀態就立刻繼續睡。

我把他們這套工程藍圖提煉成 5 個最核心的元件，打算自己手刻 AI 代理的朋友，建議直接照抄：

1、事件收件匣

別讓外部 webhook 直接打到 AI 代理身上，中間一定要墊一張資料庫表當緩衝。收到請求先立刻回覆確認，嚴格保證每個使用者同一時間只跑一個執行中的程序，順便把幾秒內連續傳來的零碎訊息批次合併，徹底防止並行衝突。

2、計時器

把排程任務另外拆成一張表來存，分成一次性的後續追蹤和週期性的計畫兩種。後台放一個輕量的輪詢器，哪個任務時間到了，就把它當成一則普通事件，推進上面的收件匣去喚醒模型。

3、精簡記憶加夢境整理

資料庫裡只存那些之後再也查不到的資訊，例如使用者指令、偏好備註和任務進度。每次喚醒只載入一個極小的索引檔，千萬別把歷史紀錄全塞進脈絡裡。另外還要定期跑一次夢境整理，把過時的舊事實清掉。

4、無人值守權限

千萬別把原始 API 金鑰直接塞進 AI 代理執行的沙箱裡，一定要透過外部代理伺服器（proxy）動態注入。遇到刪資料庫、轉帳或對外寄信這類高風險動作，直接用延遲工具呼叫把任務暫停，等人按完核准再繼續，絕對不能讓程序卡在那裡空等。

5、寄件匣

AI 代理產生的回覆，先全部丟進傳送佇列裡排隊，讓系統依照人類正常的作息節奏推送通知。不然半夜三點你的 AI 代理突然暴走，對客戶連發二十則訊息，神仙也救不回來。

我一直覺得，現在圈子裡聊大模型能力的人太多，真正把系統工程講透的人太少。以前我們總以為，全天候 AI 代理比的是模型有多聰明，

這篇在說什麼

作者整理了 Anthropic 一份關於「全天候 AI 代理」的工程指南。重點是：一個 24 小時待命的 AI 代理，其實大部分時間都在睡覺；有事件進來才醒來跑幾秒，做完、存好狀態就繼續睡。

作者把它歸納成 5 個元件：事件收件匣、計時器、精簡記憶加夢境整理、無人值守權限、寄件匣。最後補充：這套做法不一定要用官方框架，用 Python 配 SQLite 或 Redis 也能做出來。

為什麼值得學

很多人做「一直在線」的 AI 助理，第一個念頭是寫一個永遠不停的迴圈。這樣既燒錢，又容易把狀態弄亂。這串貼文提供的是另一種思路：把「等待」交給便宜、穩定的一般程式（資料庫表、排程器、佇列），只在真正需要思考時才叫醒模型。

你可以帶走的重點

1. 全天候 ≠ 一直開著

AI 代理的一天由很多「短暫的執行」組成：收到事件 → 完成任務 → 儲存發生了什麼 → 回去睡。每次執行都很短，但循環不會停。

2. 所有觸發都先進「收件匣」

外部通知、使用者訊息、到點的排程，都先寫進一張資料庫表，再由程式依序叫醒 AI 代理。這樣可以立刻回覆「收到了」、合併幾秒內的零碎訊息，並確保同一個使用者一次只跑一個程序，不會互相打架。

3. 記憶要小，還要定期整理

只記「之後查不到」的東西：使用者指令、偏好、任務進度。每次醒來只載入一個小索引，而不是整段歷史。再定期做一次「夢境整理」，刪掉過時的資訊，就像人睡覺時整理一天的記憶。

4. 危險動作先暫停，等人核准

AI 代理身上不放真正的 API 金鑰，由外部代理伺服器（proxy）代為注入。遇到刪資料、轉帳、對外寄信，就結束這次執行、存好狀態；人按下核准後，這個回答變成新事件，再開一次執行接著做，而不是讓程式卡著空等。

5. 回覆也要排隊，照人的作息送出

AI 代理寫好的訊息先放進佇列，由系統決定什麼時候送、要不要送。避免半夜三點對客戶連發二十則訊息。影片裡的一句話很適合當原則：先保持安靜，再慢慢贏得使用者的注意力。

怎麼開始

  1. 先畫出你的「事件」有哪些：使用者訊息、外部通知、每天固定時間的任務。
  2. 開一張收件匣表、一張計時器表，用 Python 加 SQLite 或 Redis 都可以，讓程式負責等待和排程。
  3. 每次醒來只做一件事，做完就把進度寫進記憶、把回覆放進寄件匣，然後結束。
  4. 把高風險動作列成清單，一律先暫停、等人核准。
