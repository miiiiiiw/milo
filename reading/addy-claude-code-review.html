Claude Code 團隊如何做程式碼審查

原文標題：How the Claude Code team does code review

作者：Addy Osmani（@addyosmani）

原文：https://x.com/addyosmani/status/2114604912520921136

日期：2026-10-26（台北時間 14:27；UTC 2026-10-26 06:27）

備註：原文為英文；繁體中文翻譯，僅供個人閱讀。

我們之前提過，Claude Code 大約 90% 的程式碼是由 Claude 寫的。那麼，在這種規模下，我們怎麼做程式碼審查（code review）？到底還有誰在讀程式碼？程式碼出錯了又會怎樣？

這篇文章介紹 Claude Code 團隊的程式碼審查流程，以及我們如何改進它。從 6 月到 9 月，合併進 Claude Code 程式碼庫（codebase）的合併請求（PR）數量成長了一倍以上，而必須回滾（revert）的合併請求（PR）比例則下降了超過 40%。

我們沒有停止做程式碼審查。相反地，我們把大部分的「閱讀」自動化了，並針對人力的時間與心力做最佳化調整。我們也投入大量資源，讓回滾（revert）錯誤變得更快、更容易。

重新思考程式碼審查的目標Rethinking the goal of code review

當代理（agent）在寫程式碼，變更的數量會快速增加。在我們的單一儲存庫（monorepo）裡，每天合併的變更從今年 5 月的大約 2,500 個，增加到 9 月的超過 30,000 個。

雖然 Claude Code 不在我們的單一儲存庫（monorepo）裡，它承受的壓力也很大。當你動得這麼快，要用人工一行一行做程式碼審查，會變得越來越難，甚至根本不可能。

程式碼審查有兩個目的：

  • 在上線前發現並修正錯誤
  • 讓團隊對程式碼庫（codebase）建立共同的理解

這篇文章主要談第一個目標，第二個目標會在文末討論。

我們認為，「有沒有人讀過這段程式碼？」只是一個不精確的指標，它真正想衡量的是：「這個變更可能出什麼錯？哪一種檢查——自動的或人工的——才是抓到它的正確方式？」

這個問題也改變了程式碼審查的時機。傳統上，程式碼審查是事後才做的檢查：程式碼寫好、合併請求（PR）送出，然後某人等著另一個人來看。我們則把程式碼審查整合進工作流程裡，它更像是你寫作時一直在跑的拼字檢查。

在請人來看之前，大多數變更都已經被 Claude 審查並修正過至少一次。這樣，我們就能抓到大部分例行性的錯誤，把人的注意力留給更高層次的考量。

人的時間與注意力Human time and attention

我們希望把人的時間與注意力，留給只有人能處理的事，同時確保有足夠的自動化來處理其他部分。即使以我們目前的速度，仍然有大量工作需要人來做，團隊幾乎每天都會遇到前所未見的新挑戰。

因此，人的時間是一種雙面成本。我們不只計算大家花在程式碼審查上的時間，也計算他們花在修復爛程式碼所造成的錯誤上的時間。如果只減少前者、沒有減少後者，我們其實並沒有省下人的時間。

所以，我們的目標是：在 Claude Code 的各個儲存庫（CLI、桌面版與網頁版應用程式，以及行動應用程式）中，大多數合併請求（PR）都應該最多只有一個人參與（in the loop，這個人可以就是作者）的情況下合併，而且回滾（revert）或事故（incident）不能因此增加。

我們用這些指標追蹤人的時間：每個合併請求（PR）的人工核准次數中位數（以及第 95 百分位數）、人工留言數，以及合併請求（PR）等待人處理的時間。我們把回滾（revert）率和事故率當作防護欄（guardrails）：如果這些指標上升，代表我們不是減少了人的時間，只是把它挪到別的地方。

一個變更會經歷什麼？What's the journey of a change?

一個典型的變更，不論來自工程師的筆電，還是 Slack 裡的一個 Claude 工作階段，都會經過多層審查。

上圖是一個典型的 Claude Code 變更，從作者的環境一路到正式環境的過程。這個流程大多是自動化的，人的注意力則集中在有風險的部分。

我們有六層檢查，再加上一套回滾（rollback）機制，來處理任何漏網的問題。

每一層都會抓到一些錯誤、漏掉另一些。很少有錯誤能穿過所有層；就算有，我們也有回滾（rollback）機制。

1. 建立合併請求前的驗證1. Pre-PR verification

我們大部分的審查，都在建立合併請求（PR）之前就完成了。我們會要求 Claude 做一些可以實際執行的事，例如跑測試、跑建置，或把截圖拿去和設計稿比對。我們不讓它只說「任務完成了」，而是要它把結果拿出來給我們看。接著，由一個子代理（subagent）用全新脈絡（fresh context）審查 diff。這兩種策略都收錄在我們的最佳實務指南裡。

在開合併請求（PR）之前，我們很多人也會跑幾個內部技能（skills）——抓錯誤、精簡 diff、端到端驗證，以及拿我們的設計準則檢查 UI 變更。

根據 Claude Code 的創造者 Boris Cherny 的說法，替 Claude 配備一套驗證流程，大概是提升成果品質最大的關鍵。

他估計，一套驗證流程能讓 Claude 輸出的品質提升兩到三倍。

不同領域的驗證流程可能差很多：

有時候簡單到只要跑一個 bash 指令。有時候是跑一整套測試。有時候則是在瀏覽器或手機模擬器裡測試應用程式。

如果自動審查者一直標出同一個問題，我們就從源頭修正——透過技能（skill）本身、一條 lint 規則，或更新像這樣的文件檔案：

  • CLAUDE.md——專案說明檔，你可以用它提供 Claude 關於專案的脈絡（技術堆疊、慣例、目標、非目標）。Claude Code 每一次審查都會讀入這個檔案，所以對於大型程式碼庫（codebase），我們會讓它保持簡短，並在這裡引用其餘的文件。當程式碼違反了這個檔案裡的慣例，或某次更新讓檔案裡的內容過時，審查者就會標出來。
  • REVIEW.md——程式碼擁有者在這個檔案裡告訴審查者，他們負責的那部分程式碼中什麼最重要。我們會另外驗證審查者是否真的遵守這些準則。好的 REVIEW.md 很簡短，並聚焦在：
    • 定義什麼叫專案失敗（文件不該說謊；設定不該路由錯誤）
    • 限制吹毛求疵（nit）
    • 定義要忽略的路徑
    • 要求提供檔案＋行號，而不是猜檔名
    • 要求最上方有摘要，包含問題數量，以及明確的「沒有問題」聲明

2. 每個合併請求都有 AI 審查2. AI review on every pull request

每個合併請求（PR）在人工審查之前，都會先接受 Claude 的審查。

系統會拿整個程式碼庫（codebase），以及合併請求（PR）作者所說明的意圖，來分析這份 diff。它會檢查：

  • 這個變更真的解決了它要處理的問題
  • 這個變更符合更大的系統架構
  • 這個變更不會弄壞程式碼庫（codebase）的其他部分

審查錯誤修正時，機器人會試著找出根本原因。

我們的公開產品 Code Review for Claude Code，現在已開放給所有 Team 和 Enterprise 客戶使用。另外也有一個供本機使用的輕量版——/code-review。

自從我們推出研究預覽版以來，內部合併請求（PR）中收到實質審查意見的比例，從 16% 提高到 54%。對於超過 1,000 行的合併請求（PR），Code Review 在大多數情況下都會發現問題；對於大多數較小的合併請求（PR），則會回報沒有問題。管理員可以替各個儲存庫設定 Quick、Standard 或 Deep 模式。當漏掉一個錯誤的代價，比花在審查程式碼上的時間更高時，Deep 模式就很有用。

在交給人審查之前，發現的問題會先經過其他多個代理（agents）把關：

  • 多個代理（agents）平行執行，搜尋錯誤
  • 另外進行一輪投票，決定一個發現是有效問題還是誤報（false positive），只確認票數足夠的發現
  • 只跟風格／診斷／整理有關的發現會被濾掉（這些過濾器在正式推出前，我們先在自己的合併請求（PR）上做過 A/B 測試）

剩下的發現會以行內留言呈現，依嚴重程度排序，並標示為：

  • 重要（Important）
  • 吹毛求疵（Nit）
  • 既有問題（Pre-existing）（這樣我們就不會因為不是這個合併請求（PR）帶進來的錯誤，而不公平地懲罰作者）

所有發現都必須處理——要嘛修好，要嘛附上理由把討論串標為已解決。很多時候，代理（agent）會在夜裡把問題修好，作者回來時，合併請求（PR）已經又經過一輪審查了。

3. 可以擋下合併的安全審查3. Security review that can block

我們也會執行自動化的安全審查。只要還有未處理的發現（不論來自程式碼審查或安全審查），任何合併請求（PR）都不能合併。作者可以修正問題，或附上簡短理由關閉討論串（這就是我們處理誤報（false positive）的方式）。

如果後續的 commit 解決了問題，該發現就會自動關閉。你也可以用開源的 security review GitHub Action，或 /security-review 指令，設定同樣的機制。設定方式請參考「automated security reviews in Claude Code」指南。

4. 會擋下合併的自動檢查4. Automated checks that block

標準檢查：lint、型別檢查、所有平台上的測試、建置。（我們在這篇文章寫過如何擴展持續整合（CI）。）一個典型的 CLI 合併請求（PR），在任何人看它之前，可能就已經跑過幾十項檢查。合併請求（PR）範本裡有問題，問這個變更是怎麼測試的、要怎麼回滾（revert）。Claude 可以幫你回答，但作者有責任審閱這些答案。

5. 依風險調整的人工核准5. Human approval, scaled by risk

有些變更比其他變更更有風險（例如修正文件 vs. 修改自動更新程式），所以需要不同程度的審查。

等級由變更決定，而不是由作者決定。一個分類器會根據變更決定風險等級。另一個分類器會判斷某個變更是否真的需要再一次核准，即使等級上沒有這樣要求。有些路徑一律需要再一次核准——任何被擁有者標為敏感的內容，以及任何持續整合（CI）工作流程檔案。

只有列在儲存庫信任名單上的作者，才能享有較寬鬆的審查要求，通常就是擁有該儲存庫的團隊。其他人都需要第二個人核准。代理（agent）的核准不算人工核准。自動審查可以放行低風險的變更，但在需要人的時候，它不能代替人。

變更的作者要為它負責，所以如果合併請求（PR）是代理（agent）寫的，操作該代理（agent）的人一定會被算作必要審查者之一。一次合併請求（PR）核准只對一個 commit 有效。如果出現一個不能信任的新 commit（例如代理（agent）推了東西，或有人手動完成了合併），合併請求（PR）就必須重新核准。

6. 合併佇列、功能旗標與分階段推出6. Merge queue, feature flags and staged rollouts

合併佇列（merge queue）確保所有檢查都會在套用了這個變更的 main 上執行。這能避免兩個各自成功的合併請求（PR），合併後卻讓 main 壞掉。新功能通常會先藏在功能旗標（feature flag）後面推出，由 Anthropic 員工最先使用。因為我們自己大量使用這個產品，常常在使用者之前就注意到回歸問題（regressions）。

當我們公開推出時，變更會先進入 latest 頻道，stable 頻道則跟在後面。

7. 快速回饋與回滾7. Fast feedback and rollback

難免會有一些不良的合併漏網。這是我們的最後一道防線，重點在盡快把它們找出來。藏在功能旗標（feature flag）後面的變更，不必重新部署就能關閉。

Claude Code 每週輪流值班（on-call），而每一次事故（incident）檢討，都會回頭看應該由哪一層抓到這個問題。除了監看回滾（revert）與事故的儀表板之外，發現不良合併仍然要靠作者和值班（on-call）人員。我們還沒有根據這些指標自動調整核准要求的斷路器（circuit breaker）機制，但隨著我們朝「合併時更少人工介入」前進，這是我們正在研究的方向。

一位團隊成員指出，放慢速度、減少產出，確實可能提升準確度，但那主要是因為整體工作量變少了。我們真正的重點，是提升快速發現並修正問題的能力。

我們如何讓審查者變得更好How we make the reviewer better

我們的程式碼審查流程，是一個持續改進的循環：

我們把事故（incidents）當作評估指標。團隊蒐集了引發事故的合併請求（PR）、它們的往前修（fix-forwards）與回滾（reverts），並請了解程式碼庫（codebase）的工程師確認每個錯誤的位置與正確性。審查系統每天都會拿這套集合來評估。

每一次事故都會加進這套集合，而審查系統的每一次變更，都會拿整套集合來評估。

為了衡量雜訊，我們觀察人對審查留言的反應。如果我們不介意回報一大堆不是錯誤的東西，要提高抓錯率很容易，所以這必須加以控制。我們依合併請求（PR）上的人如何處理每則審查留言來分類：修正了問題、拒絕了它、說明那是刻意的，或認為那不重要。此外，我們也會在已知沒有問題的合併請求（PR）上執行審查系統，觀察它多常回報某些會導致有害變更的東西。

我們明定的優先順序：第一，找出真正的錯誤；第二，減少審查的輪數。

當作者是代理（agent）時，處理一則審查留言的成本更高。人只要一秒就能忽略一個吹毛求疵（nit）的意見，但當代理（agent）必須處理它時，就會多出一個 commit，以及另一輪審查。

審查流程必須收斂。代理（agent）作者和代理（agent）審查者有可能無止境地來回循環。我們曾觀察到 CLI 專案裡的一個合併請求（PR），因為代理（agent）作者和代理（agent）審查者一來一往，一夜之間循環了五十次以上。這次循環是被人工停下的，否則它可能會一直持續下去。

當我們對審查系統反覆標出的內容執行 git blame，約 59% 是從第一輪就已經存在的程式碼。基本上，審查系統很少找到新錯誤，只是每一輪都多找到幾個舊的。

我們自己讓情況更糟，因為我們養成了預設跑好幾輪審查的習慣——每一輪都可能找到不同的錯誤。對高風險的變更來說，反覆跑幾輪審查也許有用，但不是每個合併請求（PR）都需要。團隊開始在召回率（recall）之外，也追蹤「通過所需的輪數」，並把重新審查更新為：

  • 限制輪數。三輪之後，審查系統會請作者重新評估做法。
  • 初始幾輪之後，重新審查只看 diff。
  • 指明錯誤的類別，讓作者能一次修正所有同類錯誤，而不只是一行。
  • 避免重複回報已經看過的問題。

審查代理（agents）也會在夜裡對當前的程式碼庫（codebase）執行，幫助我們在歷史錯誤擴散之前找出它們。

原文此處的圖說：導入收斂（Convergence）改進後，每個內部合併請求（PR）的平均審查輪數下降。

人在迴圈中Humans in the loop

讓一位資深工程師停下手邊工作去審查一個常見錯誤，和把這個流程自動化相比，成本高得多。但對某些任務來說，人工審查者仍然不可或缺：

  • 我們到底該不該做這個？（Should we even build this?）決定要不要做某樣東西，設定產品的願景、品味（taste）與目標。

    有一個宣稱已經解決程式碼審查瓶頸的團隊，對於來自團隊外部的變更，仍然會做人工審查，以確保那是該做的東西。

  • 稽核危險的程式碼（Auditing dangerous code）（帳務、自動更新程式、持續整合（CI）工作流程）。
  • 架構審查（Architecture review），因為這些選擇會設下其他人遵循的慣例。
  • 驗證證據（Verifying proofs）（測試輸出、執行過的指令、截圖、審查者留言）。如果你說不出那些檢查會漏掉什麼，就別只要一個 👍，你需要的是真正的審查！
  • 承擔責任（Taking responsibility）。每一個上線的變更，都有一個人為它負責，不管是誰打出來的。

團隊脈絡Team context

程式碼審查一直都有另一個用途：傳達程式碼庫（codebase）的變化。讀同事變更的 diff，通常是大家了解哪裡改了、以及程式碼庫（codebase）如何運作的方式。如果大部分的閱讀都由機器完成，那麼學習程式碼庫（codebase）的方式會變成什麼？

我們對此沒有任何正式機制。團隊裡沒有任何人腦中有一套 Claude Code 的完整心智模型（mental model），我們也不認為誰需要有。相反地，當任何人想了解程式碼庫（codebase）的某一部分時，就請 Claude 針對那一小塊產生一份解說頁（explainer）。這只要幾分鐘，而且解說頁（explainer）永遠是最新的。

我們有些人會再多走一步，讓 Claude 產生一個小型產物（artifact），把這個區域視覺化，並用自己偏好的方式教會自己。

比起一行一行讀瑣碎的 diff——那幾乎教不了你什麼（例如一行文案的修改）——這是更好的運用人類注意力的方式。替你即將修改的模組產生一份解說頁（explainer），能讓你學到很多。

此外，我們通常預設是公開的：在公開的 Slack 頻道裡工作，在別人動手做的同時就能看到他們在做什麼。

「你合併的，你負責」"You land it, you own it"

如果你合併了一個小型或中型的變更，結果還是出了問題，一般的期待是你通常要自己修。這不會失控，有幾個原因：

  • 變更都很小，容易審查、除錯和回滾（revert）。
  • 一切都能回滾（revert）。功能旗標（feature flags）、回滾（reverts）和分階段推出（staged rollouts），能在幾分鐘內逆轉大多數錯誤。
  • 爆炸半徑（blast radius）決定標準。越昂貴的程式碼，會得到越多人關注和驗證。
  • 回歸問題（regressions）會透過遙測（telemetry）和內部使用很快浮現。
  • 這不是在找戰犯。修好問題的人擁有它，因為他們掌握最多脈絡。事故（incident）檢討考量的是整個系統。

此外，團隊大多數人透過公開頻道分擔責任。任何人都能看到別人在做什麼、加入討論，或請 Claude 找出缺漏。回饋也會來自非程式碼擁有者。這種開放，是我們不必在每一行都設關卡、品質仍能維持很高的一大原因。

改變方向Changing course

有了代理（agents），開始一項新工作很便宜，但有時候你不該開始。這通常發生在頻道裡有人指出提議的變更是一條行不通的路（引用之前的決定，或提出更好的做法），而作者要嘛關掉合併請求（PR），要嘛改變實作方式。

因為一開始寫程式碼就很容易，關掉合併請求（PR）並不會讓人覺得是損失。關鍵是在討論串早期就轉向，而不是等到最後，才在一個已經定案的合併請求（PR）上留下一則擋住合併的意見。

如何實作How to implement

這套做法的大部分元件，你的團隊現在就已經能用了。

建立合併請求之前Before the pull request

  • 給代理（agent）一份它能執行的檢查清單，並把這些檢查列在一份簡短的 CLAUDE.md 檔案裡
  • 設定代理（agent）透過 hooks 呼叫格式化工具和 linter
  • 在本機執行 /code-review 和 /security-review，或讓一個全新脈絡（fresh context）的子代理（subagent）審查變更
  • 建立一份 REVIEW.md，用它追蹤反覆出現的審查問題

每個合併請求On every pull request

  • 強制執行持續整合（CI）
  • 在合併請求（PR）範本中加入「Testing（測試）」「Risk（風險）」和「How to revert（如何回滾）」
  • 先在一個儲存庫加上 AI 審查者（Code Review for Claude Code，或 Claude Code GitHub Action），並花幾週反覆調整你的 REVIEW.md，再推廣到更多儲存庫。
  • 加入自動化安全審查
  • 要求所有審查討論串在合併前都已解決
  • 依風險決定審查的嚴謹程度：例行變更快速看過，高風險區域（錯誤代價高的地方）則徹底審查。Code Review 有 Quick、Standard 和 Deep 三個等級。
  • 限制審查的輪數，幾輪之後只審查新的 diff。

核准Approval

  • 定義風險等級，依變更而不是依作者來設定。一開始從嚴，看到證據後再逐步放寬。
  • 把寬鬆的核准途徑保留給受信任的作者。
  • 機器人的核准不能用來滿足必要核准。有新 commit 推上來時，撤銷所有既有核准。
  • 對於控管驗證、帳務、持續整合（CI）與發布流程的程式碼和政策，以及安裝程式，指定由人擔任核准者。用 CODEOWNERS 和分支保護（branch protection）來做到這一點。

合併與合併之後Merging and post-merge

  • 建立合併佇列（merge queue）
  • 試用功能旗標（feature flags）
  • 先推給內部使用者
  • 分階段推出（roll out in stages）
  • 建立一步到位的回滾（revert）機制
  • 記錄事故（incidents）和回滾（reverts），建立一套評測（evals）
  • 每次修改審查者的提示詞（prompts）、工具或模型，都重新為它評分
  • 追蹤人力投入，並把回滾（revert）率和事故率當作防護欄（guardrails）

接下來的方向Where this is headed

Code Review 在發布時的設計是：最終的核准決定仍由人來做。這個產品做的事只是張貼它的發現。但在我們自己的儲存庫裡，我們走得更遠：擁有者正在決定，哪些低風險變更可以在自動檢查通過時自動合併。而這條界線還會繼續演變。

所以，每當我們的審查者漏掉了什麼，我們就問自己：模型的脈絡裡缺了什麼？然後把它變成一份 CLAUDE.md 檔案、一個技能（skill），或一項新的檢查。我們的目標沒有改變：在讓回滾（revert）率不高於現在的前提下，減少每個變更所需的人力。

所以，如果你也讓代理（agents）建立合併請求（PR），請告訴我們你自動化了哪些檢查、哪些仍需要人，以及我們哪裡做錯了。

以下為譯者整理，非原文內容。

這篇在說什麼

Claude Code 團隊的程式碼大多由 AI 寫成，變更量多到人不可能一行一行看。這篇說明他們怎麼改做程式碼審查：讓 AI 先做大部分的「閱讀」與檢查，人只看真正有風險、需要判斷的地方，同時把「出錯後快速撤回」做得又快又容易。

文中提到，從 6 月到 9 月，合併的合併請求（PR）多了一倍以上，需要回滾（revert）的比例卻下降超過 40%。

為什麼值得學

很多團隊開始讓 AI 寫程式後，會卡在「沒人看得完」。這篇的思路不是「有沒有人看過」，而是「這個變更可能出什麼錯？該由哪一種檢查來抓？」——把檢查分層、依風險分配人力，並用真實出過的事故來持續改進 AI 審查者。即使你不寫程式，這套「分層把關＋快速復原」的想法，也適用於任何有大量產出要把關的工作。

你可以帶走的重點

1. 不靠一道關卡，而是多層檢查加上回滾（rollback）

每一層都會漏掉一些問題，但很少有問題能同時穿過所有層。真的漏網了，還有功能旗標（feature flag）和回滾（revert）能在幾分鐘內撤回。

2. 人的時間要算兩邊

省下審查時間不等於省下人力：如果錯誤變多、要花更多時間修，只是把時間挪到別處。所以他們同時追蹤人工核准次數、等待時間，並把回滾（revert）率和事故率當作防護欄（guardrails）。

3. 依變更的風險，而不是依作者，決定要幾個人看

改文件這類低風險變更，自動檢查通過就不需要人；一般產品變更要一個人；最高風險的程式碼要兩個人。AI 的核准不算人工核准；由 AI 代理（agent）寫的合併請求（PR），操作它的人一定是審查者之一。

4. 用真實事故訓練審查者，並且讓審查「收斂」

每次出事，就把那個變更做成測試案例；每次修改 AI 審查者，都拿全部案例重跑評測（evals），分數上升才保留。同時要防止 AI 作者和 AI 審查者無止境來回：他們限制審查輪數、之後只看新的 diff，一次指出同一類錯誤。

5. 人留給只有人能做的事

決定「到底該不該做」、稽核帳務與自動更新程式等危險程式碼、架構審查、檢查測試輸出與截圖等證據，以及為每個上線的變更負責。想了解程式碼的某一塊時，請 Claude 寫一份解說頁（explainer），比一行一行讀瑣碎的 diff 更有收穫。

怎麼開始

  1. 先讓 AI 自己驗證：給代理（agent）一份它能執行的檢查清單（測試、建置、截圖比對），寫進簡短的 CLAUDE.md。
  2. 在一個儲存庫試 AI 審查：例如 Code Review for Claude Code 或 Claude Code GitHub Action，花幾週調整 REVIEW.md 再推廣。
  3. 定義風險等級：依變更而不是依作者決定，一開始從嚴，看到證據再放寬。
  4. 把撤回變簡單：合併佇列（merge queue）、功能旗標（feature flag）、先給內部用、分階段推出（staged rollouts），以及一步到位的回滾（revert）。
  5. 記下每次事故與回滾（revert），累積成評測（evals），之後每次改審查者都重新評分。
