開場：按問題梳理三十年 Opening: Thirty Years, Organized by Problems

00:021990 年，第一個網頁瀏覽器誕生。三十多年後，前端成了軟體業界變化最快的領域之一。框架和工具一波接一波，名字多到讓人眼花撩亂。

00:15這個系列換個角度：不按年份羅列技術，而是按問題來梳理。每一種技術，都是為了解決某個具體的問題；問題解決了，往往又帶出新的問題。

00:27如果用一句話概括這三十年：在一個本來為文件設計的平台上，一步步造出應用。

00:33上集講從文件到應用，中集講框架與工程化（engineering），下集講渲染（render）的鐘擺、新的平台能力和 AI 浪潮。

文件與連結：網頁的起點 Documents and Links: Where the Web Began

00:54最開始的問題很樸素：歐洲核子研究組織的研究人員分散在世界各地，文件放在不同的電腦上，格式各不相同。怎麼方便地共享，並且從一份文件直接跳到另一份？

01:08Tim Berners-Lee 在 1989 年提出方案，第二年做出了三樣東西：用 URL 給每份文件一個位址，用 HTTP 傳輸，用 HTML 標記內容和連結。他還在 NeXT 電腦上寫出了第一個瀏覽器，名字就叫 WorldWideWeb。

01:26早期的瀏覽器有好幾個：命令列的 Line Mode Browser 和 Lynx，圖形介面的 Viola。

01:34真正讓網頁走向大眾的，是 1993 年的 NCSA Mosaic。它第一次把圖片直接顯示在正文裡。Mosaic 的主要作者後來參與創辦了網景（Netscape）公司，1994 年推出 Netscape Navigator。同一年，W3C 成立，開始為網頁制定標準。

01:53這時的網頁，本質上還是可以互相連結的文件。

互動：JavaScript 與第一次瀏覽器大戰 Interaction: JavaScript and the First Browser War

01:58很快，大家不滿足於靜態文件了。填一張表單，哪怕只是漏寫了一項，也要提交到伺服器，等它檢查完再回傳一個新頁面。能不能在瀏覽器裡就把這些事做了？

02:121995 年，網景請 Brendan Eich 設計一門腳本語言，據說原型只用了十天左右。它先後叫過 Mocha 和 LiveScript，為了借 Java 的熱度，最後改名 JavaScript。

02:26微軟隨即在 IE 裡做了相容的 JScript，還加上自家的 VBScript。為了避免分裂，JavaScript 被交給 ECMA 標準化，1997 年有了 ECMAScript 第一版。

02:38但第一次瀏覽器大戰（browser war）已經打響。兩家都往瀏覽器裡塞私有功能，號稱動態 HTML（DHTML）。想拿到頁面上的一個元素，IE 用 document.all，網景用 document.layers，同一個效果要寫兩套程式碼。

樣式：從 font 標籤到 CSS Style: From the font Tag to CSS

02:56頁面的樣子也是個問題。早期沒有樣式表（stylesheet），大家用 font 標籤改字體，用表格一層層巢狀來排版，再用一像素的透明圖片撐出空白。內容和樣式攪在一起，改個配色要翻遍所有頁面。

03:111996 年，CSS 第一版發布，核心思路是把樣式從內容裡分離出去。2003 年的 CSS Zen Garden 是一個著名的展示：同一份 HTML，換一張樣式表，就是完全不同的設計。

03:26可是 CSS 本來為文件排版而設計，做應用的版面配置（layout）很彆扭。多欄版面要靠浮動（float）、清除浮動（clear）、負外邊距（negative margin）這些技巧，還出現了 960 Grid System、Blueprint 這樣的格線框架（grid framework），後來的 Bootstrap 更是流行一時。

03:43直到 2010 年代，Flexbox 和 Grid 先後普及，版面配置才終於有了真正的原語（primitive）。

03:50同一個三欄頁面，用表格、浮動和 Grid 來寫，複雜程度完全不同。

相容性：IE 的年代與 jQuery Compatibility: The IE Era and jQuery

03:572001 年，IE6 發布，IE 系列隨後占據了九成以上的市場，但 IE6 卻好幾年沒有大的更新。它的盒模型（box model）和標準不一樣，還有怪異模式（quirks mode），hasLayout、PNG 透明這些都是出了名的坑。開發者被迫為不同瀏覽器寫不同的程式碼。

04:17一邊，Web 標準專案（Web Standards Project）這樣的組織推動大家按標準寫；另一邊，Firefox、Safari，以及 2008 年的 Chrome，一點一點打破了 IE 的壟斷。

04:29最實用的辦法，是用一個函式庫（library）把差異抹平。Dojo、YUI、Ext JS 各有擁護者，2006 年出現的 jQuery 最後勝出：一個美元符號選中元素，鏈式呼叫（chaining），統治了前端將近十年。

04:48再往後，相容補丁（polyfill）給舊瀏覽器補上新介面，Babel 把新語法翻譯成舊語法。瀏覽器改為自動更新，2022 年 IE 正式退役。

04:57jQuery 的很多能力也被標準吸收：選擇器（selector）變成了 querySelector，Ajax 變成了 fetch。

Ajax：網頁變成持續運行的程式 Ajax: The Web Becomes a Running Program

05:08另一個痛點是整頁重新整理：每點一次，整個頁面白一下再重新載入。微軟為網頁版 Outlook 做了一個叫 XMLHttpRequest 的物件，可以在背景悄悄地向伺服器要資料。它在 IE5 裡沉睡了好幾年，直到 2004 年的 Gmail 和 2005 年的 Google 地圖，讓人看到網頁也能像桌面軟體一樣流暢。

05:342005 年，這種做法被命名為 Ajax。資料格式上，XML 很快讓位給 Douglas Crockford 推廣的 JSON。跨網域請求（cross-origin request）先有 JSONP 這樣的變通辦法；伺服器要主動推送訊息，先用長輪詢（long polling），後來有了 WebSocket。

05:52網頁從一頁頁的文件，變成了一個持續運行的程式。

外掛：Flash 與 HTML5 Plugins: Flash and HTML5

05:58瀏覽器原生做不到的事，比如動畫、影片和遊戲，就交給外掛（plugin）。Flash 是其中最成功的，網頁遊戲、影片播放器、炫酷的片頭都靠它。此外還有 Java Applet，以及微軟的 ActiveX 和 Silverlight。

06:15外掛（plugin）的問題是封閉、耗電、不安全，搜尋引擎也讀不懂。2007 年的 iPhone 乾脆不支援 Flash，2010 年賈伯斯發表公開信，解釋為什麼不支援。

06:27與此同時，瀏覽器廠商在 WHATWG 推動 HTML5，把影片、Canvas 畫布、本地儲存、背景執行緒（thread）都收進了標準。2020 年底，Flash 正式停止支援。

引擎：JavaScript 的速度與 Node.js Engines: JavaScript Speed and Node.js

06:43應用越做越大，JavaScript 的速度成了瓶頸。2008 年，Google 發布 Chrome，帶著 V8 引擎；火狐的 TraceMonkey、蘋果的 Nitro、微軟的 Chakra 隨即跟進。即時編譯（JIT）的競賽讓 JavaScript 的效能成倍提升。

07:00V8 還帶來一個意外的結果：2009 年，Ryan Dahl 用它做出了 Node.js，讓 JavaScript 可以在伺服器上運行。第二年有了 npm。前端工程師第一次可以用同一門語言寫工具、寫服務。

曇花一現：被淘汰的方案 Short-lived: Approaches That Faded

07:18這個時代也留下了很多曾經風光、後來被淘汰的方案：VRML 想把三維世界搬進網頁；frameset 把一個視窗切成好幾塊；marquee 和 blink 標籤讓文字捲動。

07:33標準也有夭折的：ECMAScript 第四版野心太大，2008 年被放棄；XHTML 2.0 不相容舊網頁，最後無人採用。Google 的 Gears 給瀏覽器加上離線能力，後來被 HTML5 取代；還有 Chrome Frame，一個把 Chrome 核心裝進 IE 的外掛（plugin），2014 年退役；Web SQL 資料庫和 AppCache 離線快取，也都被瀏覽器移除。

08:02它們大多不是失敗的設計，而是完成了探路的任務，被標準吸收或者替代。

08:08一個有趣的餘波：MooTools 當年給陣列（array）加了一個 flatten 方法，2018 年標準想加同名的方法，卻發現會弄壞老網站，只好改名叫 flat。舊方案即使被淘汰，也會在網頁裡留存很久。

小結：下一個問題 Summary: The Next Problem

08:26到 2010 年前後，網頁已經可以當作應用來做了：有 Ajax，有更快的引擎，有更強的標準。但新的問題來了：程式碼越來越多，怎麼組織？介面越來越複雜，資料和介面怎麼保持一致？這是中集的主題。

中集：框架與工程化 Part 2: Frameworks and Engineering

開場：規模帶來的問題 Opening: The Problems of Scale

00:02上集說到，2010 年前後，網頁已經可以當作應用來做了。這一集講接下來的十年，前端怎麼應對規模：程式碼怎麼組織，介面和資料怎麼同步，語言、樣式和多端怎麼跟上，工程化（engineering）又怎麼成了一門手藝。

模組化與套件管理 Modules and Package Management

00:32最早的網頁裡，腳本就是一串 script 標籤。所有變數都掛在全域（global）：順序寫錯了就報錯，名字撞了就互相覆蓋。

00:40大家先用命名空間（namespace），比如 YUI 的 YAHOO. 開頭；再用立即執行的函式把程式碼包起來。接著出現了模組規範（module specification）：Node 採用 CommonJS，同步地 require；瀏覽器要非同步載入，於是有了 AMD 和 RequireJS，中國還有阿里的玉伯的 SeaJS；為了兩邊都能用，又出現了 UMD。

01:03套件從哪裡來也在變。前端先用 Bower 專門管理瀏覽器的套件，後來都轉向了 npm，再有 Yarn 和 pnpm 解決速度和磁碟占用的問題。建置任務（build task）則交給 Grunt、Gulp 這樣的任務執行器（task runner）。

01:19真正統一局面的是打包器（bundler）。Browserify 讓瀏覽器也能用 require；2012 年的 webpack 把一切都當作模組，圖片和樣式也不例外；Rollup 擅長打包函式庫（library），Parcel 主打零設定（zero config）。2015 年，語言終於有了原生模組。

框架：資料與介面怎麼同步 Frameworks: Keeping Data and UI in Sync

01:41第二個問題更棘手。用 jQuery 寫一個複雜介面，資料存在變數裡，介面在 DOM 裡，每次改資料都要記得去改介面。功能一多，兩邊就對不上了，程式碼被戲稱為義大利麵。

01:552010 年前後，一批框架把伺服端的 MVC 思路搬到前端：Backbone 提供模型（model）、集合（collection）和視圖（view），Knockout 帶來了 MVVM 和資料綁定（data binding），Ember 強調慣例優於設定（convention over configuration），Meteor 試圖把前後端打通。當時的 TodoMVC 專案，用同一個待辦應用比較各家框架。

02:18影響最大的是 Google 的 AngularJS。它的雙向綁定（two-way binding）讓資料和輸入框自動同步，寫起來像魔法。但在大型應用裡，資料是從哪裡改的很難追蹤，髒檢查（dirty checking）的效能也成了問題。

02:342013 年，Facebook 開源了 React。它的想法很直接：介面是狀態（state）的函式。狀態（state）一變，就把整個介面重新描述一遍，由虛擬 DOM（virtual DOM）找出前後的差異，只修改真正變化的部分。

02:49React 還帶來了 JSX，把模板寫回 JavaScript 裡，一開始爭議很大；以及單向資料流（unidirectional data flow）：資料從上往下傳，事件從下往上報，問題出在哪裡一目了然。

03:03第二年，尤雨溪發布了 Vue，用反應式資料（reactive data）加模板，上手更平緩，在中國尤其流行。Google 則用 TypeScript 把 Angular 徹底重寫，和 AngularJS 不相容。還有 Preact、Inferno 這樣更輕、更快的同類。

狀態管理與元件化 State Management and Components

03:19元件（component）之間怎麼共享狀態（state）？Facebook 提出 Flux 架構；2015 年的 Redux 把它精簡成一個倉庫（store）加純函式（pure function）；MobX 走反應式路線，風靡一時；後來又有 Zustand、Jotai 和 Vue 的 Pinia。

03:34資料獲取則有 GraphQL、Apollo，以及 TanStack Query、SWR。

03:412019 年，React 推出 Hooks，用函式元件（component）取代類別元件（class component）；Vue 3 也推出了組合式 API（Composition API）。元件化成了所有主流框架的共識。

語言補課：ES2015 與 TypeScript Catching Up: ES2015 and TypeScript

03:53語言本身也在補課。2009 年的 ES5 只做了小修小補。在等待新標準的那幾年，社群先在語言外面加糖：CoffeeScript 一度是 Rails 的預設選擇，Google 推出了 Dart，函式式的 Elm、ClojureScript 也各有擁護者。

04:112015 年，ES2015 一次性補齊了類別、模組、區塊作用域（block scope）、箭頭函式（arrow function）和 Promise，之後改為每年發布一版。非同步寫法也從回呼地獄（callback hell），走到 Promise，再到 2017 年的 async 和 await。

04:29型別（type）是另一條線。微軟 2012 年發布 TypeScript，Facebook 推出 Flow，十多年下來，TypeScript 成了事實標準。State of JS 2025 年的調查裡，四成受訪者只寫 TypeScript。

樣式的失控與五批答案 Style Out of Control and Five Waves of Answers

04:46CSS 在大型專案裡同樣失控：選擇器全域生效，沒有變數，沒有作用域，誰也不敢刪一條規則。

04:53第一批答案是命名慣例，比如 OOCSS、BEM 和 SMACSS，靠紀律避免衝突。第二批是預處理器（preprocessor）：Sass、Less、Stylus 補上變數、巢狀和函式；PostCSS 和 Autoprefixer 在建置時自動加上瀏覽器前綴（vendor prefix）。

05:14第三批把作用域交給工具：CSS Modules 自動給類別名稱加上雜湊（hash）。第四批乾脆把樣式寫進 JavaScript：styled-components、Emotion 一度非常流行，但執行期（runtime）的開銷讓它們後來退潮。第五批是原子化（atomic）的 Tailwind，直接在 HTML 裡拼工具類別（utility class），爭議很大，卻成了今天最常見的寫法之一。

05:38元件庫也一代代更替：Bootstrap，中國的 Ant Design 和 Element，再到只提供無樣式基礎元件（component）的 Radix，以及把程式碼直接複製進專案的 shadcn/ui。原生 CSS 也補上了變數、巢狀、選擇器和容器查詢（container query），預處理器（preprocessor）的很多理由正在消失。

響應式與多端 Responsive Design and Multiple Platforms

06:04智慧型手機普及之後，同一個網頁要在各種螢幕上看。Ethan Marcotte 提出響應式設計（responsive design），用媒體查詢（media query）讓版面隨螢幕變化，行動優先（mobile first）成了新的設計習慣。

06:17網頁和原生 App 也在爭奪使用者。Sencha Touch 想讓網頁長得像 App；PhoneGap，也就是後來的 Cordova，把網頁包進 App 的外殼；2015 年的 React Native 換了思路，用 JavaScript 驅動真正的原生元件（component），阿里的 Weex 也走類似的路線。

06:38桌面端有 Electron，VS Code、Slack 都基於它，後來的 Tauri 主打更小的體積。網頁這邊，Google 提出 PWA，用 Service Worker 讓網頁可以離線、可以安裝。

06:51中國還有一條獨特的路線：2017 年的微信小程式。各家超級 App 紛紛跟進，Taro、uni-app 這樣的框架，讓一份程式碼編譯到多個小程式平台。

工程化：工具成為一門手藝 Engineering: Tooling as a Craft

07:06工具越來越多，前端工程化成了一門手藝。偵錯（debugging）先靠火狐的 Firebug 外掛（plugin），後來被瀏覽器自帶的開發者工具取代。程式碼檢查（linting）從 JSLint、JSHint 走到 ESLint，格式化（formatting）交給 Prettier，不再為空格爭論。

07:24測試也換了好幾代：QUnit、Jasmine，Mocha 加 Karma，再到 Jest 和 Vitest。端對端測試（end-to-end testing）從 PhantomJS 這樣的無頭瀏覽器（headless browser），換成了 Puppeteer、Cypress 和 Playwright。元件（component）可以在 Storybook 裡單獨開發。

07:43專案變大以後，有了 Lerna、Nx、Turborepo 管理的單一程式碼庫（monorepo）；也有了 single-spa、qiankun、Module Federation 這樣的微前端（micro-frontend）方案，讓不同團隊各自發布。工具解決了問題，也把複雜度搬進了設定檔。

曇花一現：這十年被淘汰的 Short-lived: What Faded in This Decade

08:00這十年也是方案更替最快的十年。Gulp 先後讓位給 npm 腳本和打包器（bundler），RequireJS 和 SeaJS 隨著原生模組退場，CoffeeScript 的很多語法被 ES2015 吸收，自己反而沒人用了。

08:18框架方面，AngularJS 在 2021 年底停止維護，Backbone、Knockout 逐漸淡出，Google 的 Polymer 讓位給更輕的 Lit，HTML Imports 和 Object.observe 這樣的標準提案，也被瀏覽器撤回。

08:33工具方面，PhantomJS、TSLint、Karma 先後停止維護，鷹架（scaffold）工具 Create React App 在 2025 年被官方棄用，Facebook 的狀態（state）函式庫（library） Recoil 被封存，Google 的 AMP 加速頁面，也逐漸失去了特殊地位。

08:51被淘汰的原因大致有三種：標準吸收了它的能力，更好的方案出現了，或者它要解決的問題本身消失了。但每一個都在當時推著前端往前走。

小結：下一個問題 Summary: The Next Problem

09:06到 2020 年前後，元件化、TypeScript、npm 和打包器（bundler）構成了前端的主流工作方式。但新的問題又冒了出來：單頁應用（SPA）首屏太慢，工具鏈（toolchain）越來越重。下集講渲染（render）的鐘擺、新的平台能力，以及 AI 浪潮帶來的變化。

下集：鐘擺、新平台與 AI Part 3: The Pendulum, New Platforms and AI

開場：渲染位置的鐘擺 Opening: The Rendering Pendulum

00:02前兩集講到，2020 年前後，元件化的單頁應用（SPA）成了主流。這一集看最近十年：渲染（render）的位置怎麼來回擺動，框架怎麼把工作交給編譯器，工具鏈（toolchain）怎麼提速，瀏覽器又多了哪些能力，最後是 AI 浪潮帶來的變化。

00:18本片的文稿和畫面由 AI 生成，配音由 AI 合成。年份和版本以各項目的官方紀錄為準，示意性的內容會在畫面上標注。

渲染的鐘擺：從伺服器到瀏覽器再回來 The Rendering Pendulum: Server, Browser and Back

00:30單頁應用（SPA）有兩個老毛病：先下載一大包 JavaScript 才能顯示內容，首屏（first screen）是白的；搜尋引擎抓到的也只是一個空殼。

00:40解決辦法是讓渲染（render）重新回到伺服器，而這恰恰是 PHP、JSP、Rails 時代的做法。

00:482016 年，Next.js 和 Nuxt 出現：伺服器先把頁面渲染（render）成 HTML 發給瀏覽器，再在瀏覽器裡補上互動，這一步叫水合（hydration）。Svelte、Solid 也有了各自的全端框架（full-stack framework）。

01:03另一條路是乾脆在建置時把頁面生成好：Jekyll、Hugo、Gatsby、VitePress，配合 Netlify、Vercel 這樣的平台，形成了 Jamstack 的潮流。

01:14但水合（hydration）本身也有代價：整頁的程式碼還是要下載、執行一遍。於是 Astro 提出島嶼架構（islands architecture）：頁面預設是純 HTML，只有需要互動的小塊才載入 JavaScript。Qwik 更進一步，試圖完全跳過水合（hydration）。

01:32React 的答案是伺服器元件（server component）：一部分元件（component）只在伺服器上運行，程式碼根本不發給瀏覽器，隨 React 19 正式穩定。

01:41還有一派乾脆回到 HTML：htmx、Hotwire、Phoenix LiveView，讓伺服器直接傳回 HTML 片段。

01:51鐘擺從伺服端擺到客戶端，現在停在了兩邊混合的位置。

交給編譯器：框架內部的變化 Handing It to the Compiler: Changes Inside Frameworks

01:57框架內部也在變。虛擬 DOM（virtual DOM）每次都要把整棵樹比較一遍，有沒有辦法只更新真正變化的地方？

02:052016 年的 Svelte 給出一個答案：在編譯時就分析元件（component），生成直接修改 DOM 的程式碼，執行期（runtime）不需要虛擬 DOM（virtual DOM）。

02:16SolidJS 則用訊號（signal），也就是 signals：每個資料知道誰依賴它，變化時只通知那幾處。這個思路很快被 Preact、Angular、Vue 採納，Svelte 5 也改用了基於訊號（signals）的 runes，TC39 還有一個把訊號（signals）標準化的提案。

02:34React 選擇了另一條路：2025 年 10 月發布的 React Compiler 1.0，在編譯時自動做記憶化（memoization），開發者不用再手寫 useMemo。

02:44還有一派押注瀏覽器原生的 Web Components，比如 Google 的 Lit。

工具鏈提速：用 Go 和 Rust 重寫 Faster Toolchains: Rewritten in Go and Rust

02:51工具鏈（toolchain）越來越慢，大型專案啟動一次要等幾十秒。2020 年前後，用 Go 和 Rust 重寫的工具接連出現：esbuild、swc，字節跳動的 Rspack，Vercel 的 Turbopack，還有 Biome 和 Oxc。

03:08Vite 也在這時誕生，開發時直接利用瀏覽器原生的模組，不再整體打包。2026 年 3 月的 Vite 8，用 Rust 寫的 Rolldown 統一了開發和正式環境（production）兩套流程。調查裡，Vite 的滿意度高達 98%。

03:24執行環境（runtime）也有了新選手：Deno 和 Bun 挑戰 Node。Node 則加快了更新，現在可以直接運行 TypeScript 檔案。日期處理這個老大難，也終於等來了標準的 Temporal 介面。

新的平台能力：WebAssembly、WebGPU 與標準吸收 New Platform Capabilities

03:39瀏覽器本身也在變強。asm.js 證明了可以把 C++ 編譯成高效的 JavaScript；2017 年，WebAssembly 成為標準，Figma、網頁版 Photoshop 這樣的重量級應用跑進了瀏覽器。

03:56圖形方面，WebGL 讓網頁可以畫三維，Three.js、Babylon.js 把它變得好用。新一代的 WebGPU 對應現代顯示卡介面，到 2025 年底，三大瀏覽器都已支援。

04:10原本需要函式庫（library）來實現的能力，也繼續被標準吸收：頁面切換動畫有了 View Transitions，彈出層有了 Popover 和 dialog 元素，音視訊有了 WebCodecs。這條規律，從 jQuery 時代一直延續到今天。

AI 浪潮：怎麼寫前端 The AI Wave: How Front-End Gets Written

04:28接下來是這幾年最大的變化：AI。GitHub Copilot 開始在編輯器裡補全程式碼；2022 年底 ChatGPT 發布，大家開始用對話的方式寫程式碼。

04:42再往後，Cursor、Windsurf 這樣的 AI 編輯器，以及 Claude Code、Codex 這樣的程式開發 AI 代理（coding agent）出現了。它們不再只補一行，而是讀懂整個程式碼庫（repository）、修改多個檔案、自己運行測試。中國也有通義靈碼、Trae 等工具。

05:00前端是被 AI 最先改變的領域之一。v0、bolt.new、Lovable 這類工具，用一句話就能生成一個可以運行的介面。

05:092025 年初，Andrej Karpathy 提出 vibe coding 這個說法：不看程式碼，只描述想要什麼。

05:18State of JS 2025 年的調查裡，用 Claude 寫程式碼的比例從 22% 漲到了 44%，Cursor 從 11% 漲到了 26%。

05:28前端的工作流程，正在從手寫元件（component），變成描述需求，讓 AI 生成、再由人審查。

AI 浪潮：前端要做什麼 The AI Wave: What Front-End Builds

05:35AI 也改變了前端要做的東西。聊天框和串流輸出（streaming）成了新的常見介面，Vercel 的 AI SDK、LangChain.js、CopilotKit 這樣的函式庫（library）專門處理這些。還有生成式介面（generative UI），由模型決定該渲染（render）哪個元件（component）。

05:53模型也開始跑進瀏覽器：WebLLM 藉助 WebGPU 在本機推論（inference）。Chrome 從 138 版起，內置了摘要、翻譯這樣的 AI 介面，背後是裝在本機的小模型。

06:08更根本的變化是，網頁的讀者裡多了 AI 代理。ChatGPT Atlas、Perplexity 的 Comet 這樣的工具會替人點擊和填表。Google 和微軟提出了 WebMCP，讓網站把可以執行的操作直接開放給代理。原來為無障礙（accessibility）寫的語意化 HTML，現在也成了給 AI 看的介面。

AI 浪潮：新的問題 The AI Wave: New Problems

06:33AI 也帶來了新的問題。模型最熟悉訓練資料裡最多的寫法，生成的介面常常是 React、Tailwind 加 shadcn/ui 的組合。主流方案因此更加強勢，新框架更難出頭。

06:48生成的程式碼看起來能跑，不一定正確，也不一定好維護，所以測試、程式碼審查（code review）和設計系統反而更重要了。網頁裡的文字還可能對代理發起提示注入（prompt injection），這是全新的安全問題。

07:02前端工程師的角色也在變：從親手寫介面，轉向定義需求、約束和驗收標準。這些變化還在發生，方向也可能再調整。

曇花一現：最近十年的方案更替 Short-lived: Solutions of the Past Decade

07:15最近十年同樣有方案來去匆匆。Gatsby 在 Jamstack 熱潮裡風光一時，後來逐漸沉寂；Snowpack 開創了開發時不打包的做法，自己卻在 2022 年停止維護，思路由 Vite 繼承；Remix 後來併入了 React Router。

07:33CSS-in-JS 遇上伺服器元件（server component）後很快退潮，styled-components 在 2025 年進入維護模式。Rome 工具鏈（toolchain）專案停擺，社群接手後改名為 Biome。在 AI 時代，方案的更替只會更快。

總結：三十年的規律 Summary: Patterns Across Thirty Years

07:49回顧這三十年，可以總結出幾條規律。

07:53第一，社群先試，平台再吸收：jQuery、外掛（plugin）、預處理器（preprocessor）、模組打包器（bundler），最後都被標準接手。

08:01第二，渲染（render）的位置像鐘擺，在伺服端和客戶端之間來回擺動，每次都帶著上一次的教訓。

08:10第三，執行期（runtime）的工作越來越多地交給編譯期（compile time）。

08:14第四，複雜度守恆，解決一個問題，往往把複雜度挪到另一層。

08:20第五，前端的很多難題，歸根結底是在一個為文件設計的平台上造應用。

08:27AI 浪潮又添了一條：它正在改變誰來寫前端，也在改變網頁寫給誰看。

08:33但最初的那個問題沒有變：怎麼把資訊和功能，可靠地送到每一個使用者面前。

這支影片在說什麼

题叶用三集（共約 27 分鐘）把前端三十年的歷史，從「技術的年代表」換成「問題的接力賽」來講：上集從 1990 年第一個瀏覽器講到 2010 年前後，網頁怎麼從文件長成應用；中集講接下來十年，程式碼、介面、樣式和多端怎麼跟上規模；下集看渲染（render）位置的鐘擺、框架與工具的提速，以及 AI 浪潮。說明欄是空的，但每一集開頭都說明文稿和畫面由 AI 生成、配音由 AI 合成；年份和版本以各項目官方紀錄為準，畫面上標「示意」的圖表只表示趨勢。

為什麼值得學

前端的名詞多到讓人眼花，連講者自己都說「框架和工具一波接一波」P1 00:10。但他的看法是：每一種技術，都是為了解決某個具體的問題；問題解決了，往往又帶出新的問題P1 00:20。你不必記住每個名字，只要學會問「它在解決哪一個問題」，就比較不容易被新名詞牽著走，也比較看得出哪些工具是真需要、哪些只是熱潮。

你可以帶走的重點

1. 三十年的一句話：在為文件設計的平台上造應用

網頁最初只是讓研究人員互相連結文件的方式。三十年來前端的很多難題，歸根結底，是在一個為文件設計的平台上，一步步造出應用P1 00:29。理解這一句，就能明白為什麼早期要用表格排版、為什麼要一直補上新功能，也明白為什麼講者在結尾說：最初的問題沒有變，是怎麼把資訊和功能可靠地送到每一個使用者面前P3 08:33。

2. 技術是「問題接力」：答案會長出新問題

講者用的例子很具體：填表單漏了一項，也要送到伺服器等它檢查完才知道，於是有了 JavaScriptP1 02:01；整頁一直白一下重新載入，於是有了 AjaxP1 05:08；各家瀏覽器寫法不同，於是 jQuery 把差異抹平P1 04:29；程式碼越寫越多，資料和介面對不上，於是有了 React 這類P2 01:41框架。

3. 社群先試，平台再吸收

講者歸納的第一條規律：社群先用函式庫（library）、外掛（plugin）、預處理器（preprocessor）去解決問題，等大家都在用了，瀏覽器標準再把能力收進去P3 07:53。例如 jQuery 的選擇器變成 querySelector，Ajax 變成 fetchP1 04:57；Flash 能做的影片、畫布，被收進 HTML5P1 06:28；日期函式庫（library）的老大難，等到了標準的 TemporalP3 03:32；頁面切換動畫、彈出層也一樣P3 04:13。

4. 「被淘汰」不等於「失敗」

三集都有一節「曇花一現」。講者說，這些方案大多不是失敗的設計，而是完成了探路的任務P1 08:02。被淘汰的原因大致有三種：標準吸收了它的能力、更好的方案出現了，或它要解決的問題本身消失了；但每一個都在當時推著前端往前走P2 08:51。對一般人的意思是：看到某個工具「過時了」，不必覺得當初選錯，也不必急著追下一個。

5. 渲染（render）的位置像鐘擺：從伺服器，到瀏覽器，再到兩邊混合

早年網頁由伺服器組好再送來（PHP、JSP、Rails）。單頁應用（SPA）把工作搬到瀏覽器，卻帶來首屏白屏、搜尋引擎只看到空殼的老毛病，於是渲染（render）又回到伺服器P3 00:30，加上水合（hydration）補回互動；後來的島嶼架構（islands architecture）、伺服器元件（server component）都是在兩邊之間找平衡P3 01:18。講者的說法是：鐘擺從伺服端擺到客戶端，現在停在了兩邊混合的位置P3 01:51；每次擺動都帶著上一次的教訓P3 08:01。

6. 框架換個不停，是因為「資料和介面對不上」

用 jQuery 寫複雜介面時，資料在變數裡、介面在網頁裡，每次改資料都要記得去改介面，功能一多就對不上，程式碼被戲稱為「義大利麵」P2 01:41。React 的想法是：介面是狀態（state）的函式，狀態（state）一變就重新描述一遍，只修改真正變化的部分P2 02:34。後來的 Svelte 和訊號（signals）想更精準，React 則把力氣花在編譯器上P3 02:05。你不用懂細節，只要知道這些爭論的起點，是同一個問題：怎麼讓畫面和資料保持一致。

7. 越來越多工作交給「編譯期（compile time）」，工具也變快了

第三條規律：執行期（runtime）的工作，越來越多地交給編譯期（compile time）P3 08:10。用白話說，就是把原本打開網頁時才做的事，改成在做網站時先做好。同樣的精神也出現在工具上：大型專案啟動一次要等幾十秒，於是 esbuild、swc、Rspack、Turbopack 這類用 Go 或 Rust 重寫的工具接連出現P3 02:51；Vite 8 也改用 Rust 寫的 Rolldown，講者引用調查說 Vite 的滿意度達 98%P3 03:20。

8. 瀏覽器變強了：連 Figma 都能跑在裡面

2017 年 WebAssembly 成為標準後，Figma、網頁版 Photoshop 這樣的重量級應用跑進了瀏覽器P3 03:46；WebGL 和 WebGPU 讓網頁能畫三維，到 2025 年底三大瀏覽器都已支援 WebGPUP3 03:56。這是為什麼現在很多「軟體」其實只是一個網址。

9. AI 浪潮：寫的人在變，讀的也在變

下集最後一大段：前端是被 AI 最先改變的領域之一P3 05:00。工作流程正在從手寫元件（component），變成描述需求、讓 AI 生成、再由人審查P3 05:28。網頁的讀者裡也多了 AI 代理，會替人點擊和填表；原來為無障礙（accessibility）寫的語意化 HTML，現在也成了給 AI 看的介面P3 06:08。講者同時提醒新問題：AI 最熟悉最常見的寫法，主流方案更強勢、新框架更難出頭；生成的程式碼看起來能跑，不一定正確，也不一定好維護；網頁裡的文字還可能對代理發起提示注入（prompt injection）P3 06:33。他的結論是前端工程師的角色在轉向：定義需求、約束和驗收標準P3 07:02。

怎麼開始

  • 聽到新框架或新工具時，先問一句：「它在解決哪一個問題？」問題如果你們根本沒有，就不必急著換P1 00:20。
  • 看到舊技術「過時」，不要急著說當初錯了：它多半完成了探路的任務；先問是被標準吸收了、被更好的方案取代，還是問題本身消失了P2 08:51。
  • 請 AI 幫你做網頁時，把「怎麼驗收」一起寫進需求：講者提醒生成的程式碼看起來能跑，不代表正確；測試、程式碼審查和設計系統反而更重要P3 06:48。
  • 自己做網站的人：用清楚的語意化 HTML，不只是為了無障礙（accessibility），也是為了讓 AI 代理讀得懂P3 06:26。
