平台層：事件迴圈與影格預算 Platform: Event Loop and Frame Budget

01:08先看最底下的一層。瀏覽器的主執行緒（main thread）只有一條，它既要跑你的 JavaScript，又要處理點擊，還要把頁面畫出來。這些事排成一個佇列（queue）輪流做，這就是事件迴圈（event loop）。

01:21佇列裡有兩種任務。巨集任務（macrotask），例如計時器、點擊事件、網路回呼（callback），一次做一個；微任務（microtask），例如 Promise 的回呼，會在目前任務結束後立刻全部清空，插在下一個巨集任務（macrotask）前面。

01:37這個順序會造成一些反直覺的現象。一個 Promise 的回呼裡又產生新的 Promise，它們會一直占著，計時器永遠排不上。所以用 await 寫的無限迴圈，和用 setTimeout 寫的迴圈，對頁面的影響完全不同。

01:53畫面是另一條線。螢幕每秒更新六十次，每一個影格（frame）只有大約十六毫秒。瀏覽器在每個影格（frame）的開頭處理輸入、執行動畫影格（frame）回呼，然後計算樣式、版面配置、繪製。如果一個任務占住主執行緒（main thread）超過這個時間，這個影格（frame）就畫不出來，使用者看到的就是卡頓。

02:15瀏覽器把超過五十毫秒的任務叫做長任務（long task）。它不一定來自複雜的計算，更多時候來自一次渲染（render）了太多元件（component），或是一個同步的迴圈處理了太多資料。

02:28所以前端效能的第一條規則非常樸素：不要讓任何一件事在主執行緒（main thread）上連續待太久。後面講的很多優化，本質上都是把長任務（long task）切短，或是搬到別的執行緒去。

平台層：渲染管線 Platform: The Rendering Pipeline

02:43主執行緒（main thread）要把一個頁面畫出來，得走一條管線（pipeline）。先把 HTML 解析成 DOM 樹，把 CSS 解析成樣式規則，兩者結合算出每個元素的最終樣式；然後是版面配置（layout），算出每個盒子的位置和大小；再來是繪製（paint），把文字、顏色、邊框變成繪製指令；最後是合成（composite），把分層的圖像在 GPU 上疊在一起，送到螢幕。

03:10版面配置（layout）是最貴的一步，因為它有連鎖反應：一個元素變寬，它後面的同層元素（sibling）要挪位置，父元素可能變高，父元素的同層元素又要挪。一次改動可能波及整棵樹。

03:24改變不同的屬性，會從管線的不同位置重新開始。改寬度，要重新版面配置（layout）、繪製（paint）、合成（composite），全部走一遍；改顏色，跳過版面配置（layout）；改 transform 或 opacity，只需要合成（composite），連繪製（paint）都不用。

03:41這就是為什麼做動畫要用 transform，而不是 left。同樣的視覺效果，一條路要主執行緒（main thread）重新算版面配置（layout），另一條路只是讓 GPU 換個位置貼圖；前者在複雜頁面上可能要幾十毫秒，後者不到一毫秒。

03:59開發者工具的效能面板（Performance panel）能把這條管線每一步的耗時畫出來。看到紫色的版面配置（layout）很長，就知道是結構問題；看到綠色的繪製（paint）很長，就知道是畫得太多。

語言層：TypeScript 與 TypeScript 7 Language: TypeScript and TypeScript 7

04:14往上一層是語言。今天幾乎所有桌面級前端都用 TypeScript 寫。它的型別（type）不參與執行，執行的仍然是 JavaScript；型別（type）是寫給人和工具看的契約。

04:28契約的價值在規模。一個幾十萬行的應用，改一個介面（interface）的欄位，型別檢查（type checking）會立刻列出所有受影響的地方；編輯器的自動補全、重新命名、跳到定義，全部建立在型別（type）之上。沒有型別（type），這些只能靠全文搜尋。

04:45TypeScript 的型別系統比大多數語言都靈活。聯合型別（union type）可以表達「要麼是這個，要麼是那個」；字面值型別（literal type）可以把字串限制在幾個取值裡；泛型（generics）可以從參數推導出回傳值。

04:59靈活也有代價。型別體操（type gymnastics）寫得太複雜，編譯器要算很久，同事也看不懂。實務上的原則是：型別（type）描述資料的形狀，不要拿型別（type）來做計算。

05:11型別檢查本身也有成本，大專案一次檢查要幾十秒。TypeScript 7 把編譯器改用 Go 重寫，速度提升了大約十倍。這意味著型別檢查可以放進「儲存檔案的那一瞬間」，而不是提交（commit）之前才跑。

語言層：CSS Language: CSS

05:29再往上是樣式。過去幾年 CSS 新增的能力，把很多原本必須寫 JavaScript 才能做的事，變成了宣告式（declarative）的寫法。這對桌面應用特別重要，因為它們的介面結構最複雜。

05:42第一個是容器查詢（container query）。以前元件（component）只能根據整個視窗的寬度變化，現在可以根據它所在容器的寬度變化。桌面應用裡，一個面板可以被拖寬拖窄，裡面的元件（component）自己決定怎麼排：寬的時候三欄，窄的時候一欄。

05:59第二個是錨點定位（anchor positioning）。提示框、下拉選單、氣泡，要跟著某個按鈕走，還要在靠近螢幕邊緣時自動翻到另一側。以前要監聽捲動、算座標；現在是幾行 CSS，瀏覽器自己算，而且和捲動同步，不會抖。

06:18第三個是捲動驅動動畫（scroll-driven animation）。進度條、視差效果、隨捲動展開的元素，把動畫的時間軸綁定到捲動位置上，完全不經過主執行緒（main thread）。

06:28第四個是 :has() 選擇器（selector）。父元素可以根據子元素的狀態改變樣式：一個表單項裡面的輸入框無效時整列變紅，以前要用 JavaScript 加類別名稱（class），現在一個選擇器就夠了。

06:43還有原生的彈出層（popover）和對話框（dialog），附焦點管理和一鍵關閉；以及視圖轉場（view transition），讓兩個狀態之間的切換自動產生動畫。這些在 2026 年的 Interop（瀏覽器互通性）計畫裡都是重點，三大瀏覽器引擎正在對齊。

06:58判斷一個特性能不能用，看 Baseline，也就是一個特性在主流瀏覽器都支援了多久。「新可用」（Newly available）是剛剛都支援，「廣泛可用」（Widely available）是都支援了兩年半以上。桌面應用的使用者換瀏覽器很快，通常「新可用」就能用。

框架層：三種反應式模型 Framework: Three Reactivity Models

07:16框架解決的核心問題只有一個：狀態（state）變了，介面怎麼跟著變。不同框架的答案分三種。

07:24第一種是虛擬 DOM 比對（virtual DOM diffing）。狀態一變，重新執行元件（component）函式，產生一棵新的描述樹，和舊的比一比，把差異套用到真實頁面。React 是代表。它的優點是模型簡單：介面就是狀態的函式，不用關心什麼變了。代價是重新執行：父元件（component）更新，所有子元件（component）預設都重新執行一遍，哪怕它們的輸入沒變。大頁面上這會很明顯，所以 React 開發者要手動加快取（cache），告訴它哪些可以跳過。

07:57第二種是編譯期分析（compile-time analysis）。Svelte 和 Solid 在編譯時就知道哪個變數影響哪一段 DOM，執行時直接更新那一處，沒有比對，也沒有重新執行。

08:09第三種是訊號（signals）。每個狀態是一個可訂閱的單元，誰讀過它，誰就被記下來；它變化時，只通知這些訂閱者。Vue、Angular、Preact 都用這種模型，它也正在成為 JavaScript 語言層級的提案。

08:25三種模型的差別，在一次狀態變化上看得最清楚：虛擬 DOM 比對（virtual DOM diffing）要重新執行一整棵子樹再比對；編譯期分析（compile-time analysis）和訊號（signals）只碰真正依賴這個狀態的那幾個節點。

08:38React 的辦法是用編譯器補上這一課。React Compiler 自動分析元件（component），插入快取（cache），避免不必要的重新渲染（re-render），開發者不用再手寫。它在 2026 年又用 Rust 重寫了一遍，轉換速度快了一個數量級。

08:55選框架時，反應式模型只是一個維度，生態系、團隊熟悉度、招募，往往更重要。React 的生態系最大，這是它即使模型不是最優，也仍然是預設選擇的原因。

框架層：狀態的四種來源 Framework: Four Sources of State

09:10狀態管理之所以混亂，常常是因為把不同來源的狀態塞進了同一個倉庫（store）。按來源分，狀態有四種。

09:19本地狀態（local state），只屬於一個元件（component），例如輸入框的內容、一個面板是否展開，它應該留在元件（component）裡，不要往上提。伺服器端狀態（server state），來自 API，它的真相在伺服器上，用戶端拿到的只是一份快照（snapshot），有快取（cache）、有過期、有重新請求的問題。

09:39URL 狀態（URL state），也就是目前的頁面、篩選條件、選中的物件。它應該能被複製貼上、重新整理不會丟、按「上一頁」能回去。桌面應用經常忽略這一條，結果使用者沒辦法把一個檢視分享給同事。持久狀態（persistent state），也就是使用者偏好、面板配置、最近開啟的檔案，關掉再開還在，存在本地儲存（local storage）裡。

10:02伺服器端狀態（server state）值得單獨講。兩個元件（component）同時請求同一個 API，應該只送出一次；資料改了，相關的快取（cache）應該失效；使用者按了儲存，介面應該先假裝成功，失敗再回滾。這些都是通用問題，這類函式庫把它們做成了預設行為。

10:21剩下真正需要全域共享的用戶端狀態，其實很少：目前使用者、主題、通知。這部分用一個小的狀態函式庫就夠了，不需要為整個應用建一個巨大的倉庫。

框架層：頁面在哪裡渲染 Framework: Where Pages Are Rendered

10:35內容型網站關心首屏多快出來，所以有伺服器端渲染（server-side rendering，SSR）、靜態生成（static generation）、串流輸出（streaming）、伺服器元件（server components）這些辦法：把 HTML 在伺服器上先算好，瀏覽器一收到就能顯示。

10:49桌面級應用的情況不同。使用者登入後會待好幾個小時，首屏慢半秒不是主要矛盾，之後每一次操作的回應才是。所以大多數桌面應用用用戶端渲染（client-side rendering）加骨架畫面（skeleton screen）就夠了，把複雜度留給互動。

11:05伺服器元件（server components）是一個值得了解的新方向：元件（component）在伺服器上執行，只把結果以串流傳給用戶端，用戶端不需要下載這些元件（component）的程式碼。它適合資料密集但互動少的頁面。

11:18新能力也帶來新的安全面。2025 年底曝出的 React2Shell 漏洞，就是伺服器元件（server components）的反序列化（deserialization）缺陷：不需要登入就能遠端執行程式碼，評分滿分十分。此後半年，主流框架連續發了安全修補。能力的邊界，就是責任的邊界。

工程層：工具鏈 Engineering: The Toolchain

11:38最外面一層是工具鏈（toolchain）。寫出來的程式碼要被轉換、打包（bundle）、壓縮、檢查格式、跑測試。這一層在過去三年發生了一次整體替換。

11:51原來的工具是用 JavaScript 寫的：Babel 負責轉換，ESLint 負責檢查，Prettier 負責格式，Rollup 和 webpack 負責打包（bundling）。新一代工具用 Rust 重寫：Oxc 負責轉換、檢查和格式化，Rolldown 負責打包（bundling），它們都收攏在 Vite 之下。速度差距是一個數量級。

12:12Vite 8 用 Rolldown，同時替掉了開發用的 esbuild 和正式環境用的 Rollup，建置快十到三十倍。React Compiler 走 Oxc 比走 Babel 快十幾倍。

12:24快的意義不只是省時間。當型別檢查、格式化、程式碼檢查都能在一秒內完成，它們就可以在每次儲存時自動跑，錯誤在寫的時候就被抓住，而不是在提交之後。回饋迴圈（feedback loop）縮短，工程習慣就跟著改變。

12:42測試工具也在同一條線上：Vitest 和 Vite 共用設定，元件測試可以在真實瀏覽器裡跑，覆蓋率（coverage）引擎也剛剛重寫過。一套工具鏈，從寫到測形成閉環。

工程層：供應鏈安全 Engineering: Supply Chain Security

12:57一個前端專案的依賴樹（dependency tree）往往有一兩千個套件，絕大多數程式碼不是你寫的。這就是供應鏈風險（supply chain risk）。

13:052026 年 5 月，攻擊者在六分鐘裡向四十二個 TanStack 套件發布了八十四個帶惡意程式碼的版本。他們沒有偷任何密碼，用的是 持續整合（CI） 快取投毒（cache poisoning），拿到了自動發布用的臨時權杖（token）。

13:19防禦是分層的：鎖定檔（lockfile）保證每次安裝的是同一個版本；來源證明（provenance）讓套件和建置它的提交（commit）對得上；持續整合（CI）只給最小權限，發布要人工確認；稽核工具在安裝時掃描已知問題。沒有一層能單獨解決問題，但每一層都把攻擊面縮小一點。

13:41還有一條土辦法：升級依賴不要太急。一個新版本發布幾天後再用，讓社群先替你踩雷。

度量：Core Web Vitals 與 INP Measure: Core Web Vitals and INP

00:44瀏覽器廠商定義了三個核心指標（Core Web Vitals）。最大內容繪製（Largest Contentful Paint，LCP），衡量頁面主要內容多久出現；累計版面配置位移（Cumulative Layout Shift，CLS），衡量頁面載入時內容跳了多少；互動到下一次繪製（Interaction to Next Paint，INP），衡量使用者每次點擊後多久看到回饋。

01:05三個指標各有門檻：LCP 兩秒半以內算好，CLS 0.1 以內算好，INP 兩百毫秒以內算好。統計的是真實使用者的第 75 百分位（75th percentile），也就是四分之三的使用者都要達到。

01:21對桌面應用來說，最重要的是 INP。它統計整個工作階段（session）裡所有的互動，取接近最差的那一次。一個用了兩小時的應用，只要有幾次點擊卡了半秒，分數就不好看。

01:34一次互動的延遲分三段：輸入延遲（input delay），主執行緒（main thread）在忙別的事，點擊排隊等著；處理時間（processing time），你的事件處理函式跑了多久；呈現延遲（presentation delay），改完狀態到畫面更新的時間。三段裡最容易被忽視的是第一段，它和你的點擊處理函式無關，而是別的任務占了執行緒。

01:56度量要分實驗室和真實使用者。實驗室工具（lab tools）在你的機器上跑，可重複，適合找出問題的原因；真實使用者監控（real user monitoring，RUM）收集每個人的真實資料，適合發現問題的存在。兩者經常不一致：開發機是最快的機器，使用者的不是。

02:15長動畫影格 API（Long Animation Frames API）是新工具，它能告訴你每一個超過五十毫秒的影格（frame），是哪個腳本、哪個函式造成的，直接從線上資料裡定位到程式碼。

載入：關鍵路徑 Loading: The Critical Path

02:27先看打開。瀏覽器下載 HTML，發現腳本，下載腳本，執行；腳本再去請求資料，資料回來再渲染（render）。每一步都在等上一步，這條鏈叫關鍵路徑（critical path）。縮短它有幾個辦法。

02:43程式碼分割（code splitting）：首屏只載入首屏需要的程式碼，其他路由（route）用到時再載入。一個有五十個頁面的後台，首屏不應該下載五十個頁面的程式碼。

02:55預先載入（preload）：在 HTML 裡直接宣告後面會用到的資源，讓瀏覽器提前並行去取，而不是等腳本執行到那一行才發現。資料請求也可以提前：在 HTML 裡就送出第一個 API 請求，和腳本並行。

03:11資源優先級（resource priority）：告訴瀏覽器首屏那張大圖是高優先級，底部的腳本是低優先級。字型：用系統字型，或是先顯示後替換，不要讓文字等字型。圖片：用現代格式，按顯示尺寸提供。

03:27網路層本身也在變。HTTP/3 用 UDP 承載，連線建立更快，掉封包不會阻塞其他請求。對桌面使用者，這些差別在弱網路時才明顯，但它們是免費的。

03:42推測規則（Speculation Rules）是新工具：在 HTML 裡宣告使用者大概率會去的下一個頁面，瀏覽器在閒置時提前渲染（render）它，點擊時瞬間切換。真實使用者資料顯示，用了它的網站互動指標明顯更好。

載入：套件體積與搖樹最佳化 Loading: Bundle Size and Tree Shaking

04:00載入的另一半是套件體積。打包工具會做搖樹最佳化（tree shaking）：沒被用到的程式碼不打進去。但它經常失效，常見原因有三個。

04:10桶檔案（barrel file）：一個 index 檔案把幾十個模組全部匯出，引用其中一個，就可能把全部帶上。副作用（side effect）：模組頂層有執行的敘述，工具不敢刪。動態引用（dynamic reference）：用字串拼出來的模組名稱，工具看不懂。

04:28解決辦法對應著來：直接引用具體的模組；在 package 裡宣告沒有副作用（side effect）；用分析工具看每個依賴占了多少。桌面應用常見的情況是，一個圖表函式庫或富文本編輯器占了一半套件體積，而它只在一個頁面用到，應該延遲載入（lazy loading）。另一種是同一個函式庫被不同依賴引用了兩個版本，打包了兩份。

04:50新一代打包工具還能做屬性名稱壓縮（property mangling）：把物件的屬性名稱也縮短，再省一截。但它要求程式碼裡沒有用字串存取屬性，否則會改壞。

05:01套件體積的度量，要看壓縮後的大小，也要看解析執行的時間。一 MB 的 JavaScript 下載可能只要一秒，但解析和執行在普通機器上可能要兩三秒，這段時間主執行緒（main thread）是滿的。

渲染：版面配置抖動與合成層 Rendering: Layout Thrashing and Compositor Layers

05:17打開之後是執行時期的渲染（render）效能。上集講過管線，最常見的破壞方式叫版面配置抖動（layout thrashing）：在一個迴圈裡，改一個元素的樣式，再讀另一個元素的位置，再改，再讀。每次讀位置，瀏覽器都必須先把剛才的修改算完，才能給你準確的數字，於是本來一次就夠的版面配置（layout），被強制做了一百次。解決辦法是把讀和寫分開：先讀完所有需要的，再一次寫完。

05:47第二個工具是合成層（compositor layer）：把動畫元素提升到自己的圖層，它的移動就只是 GPU 貼圖，不影響別的元素。但圖層也占顯示記憶體（VRAM），每一層都是一張點陣圖（bitmap），不要給幾百個元素都加 will-change。

06:03第三個是跳過看不見的內容：告訴瀏覽器，這塊內容在視口（viewport）外，先不要做版面配置（layout）和繪製（paint）。一個很長的頁面，首次渲染（render）可以快好幾倍。配合 contain，還能把一塊區域的版面配置（layout）變化限制在內部，不波及外面。

06:21第四個是減少 DOM 的總量。桌面應用常見的問題是節點太多，一個頁面幾萬個節點，任何樣式計算都慢。能用 CSS 畫的就不要用元素堆，能重用的就不要重複渲染（render）。

渲染：十萬行表格的虛擬化 Rendering: Virtualizing a 100,000-Row Table

06:39桌面應用最典型的場景是大表格：十萬行資料，每行二十欄。全部渲染（render）成 DOM，兩百萬個儲存格，瀏覽器直接卡死。辦法是虛擬化（virtualization）：只渲染（render）視口裡的幾十行，捲動時重複使用這些行，換上新資料；容器用一個佔位元素撐出完整的高度，讓捲軸看起來是真的。

07:03行高固定的話很簡單：捲動位置除以行高，就是第一行的序號。行高不固定，就要邊渲染（render）邊測量，用測過的平均值估計沒測過的，再修正捲動位置。這是所有虛擬列表（virtual list）函式庫複雜的地方。

07:20再往上是 Canvas 直接繪製：不要 DOM 了，自己在畫布上畫表格。這是線上試算表和大資料網格的做法，捲動時只是重畫一張圖。代價是要自己處理文字選取、無障礙（accessibility）、輸入法，這些 DOM 本來免費給你的東西。

07:37一個實測的量級：同樣十萬行，全部渲染（render）要十幾秒；虛擬化（virtualization）之後，首次渲染（render）幾十毫秒，捲動維持六十影格（frame）。

互動：讓出主執行緒 Interaction: Yielding the Main Thread

07:50一次點擊後要做大量計算，例如篩選十萬行。主執行緒（main thread）被占三百毫秒，畫面就凍住三百毫秒，連滑鼠懸停的高亮都不動。

08:01第一個辦法是切片（time slicing）：把任務拆成小塊，每塊做完就讓出主執行緒（main thread），讓瀏覽器先畫一個影格（frame）、先處理下一個輸入。scheduler.yield 是專門為此設計的介面；讓出之後還能排在佇列前面繼續，不會被別的任務插隊。

08:19第二個辦法是分優先級。React 的 startTransition 把一次更新標記為可以打斷的：使用者在輸入框裡打字時，列表的篩選結果可以晚一點出來，但輸入框必須立刻回應。使用者感受到的是「跟手」。

08:33第三個辦法是搬走。Web Worker是另一條執行緒，沒有 DOM，但可以做任何計算：解析大檔案、建索引、搜尋、壓縮，都應該在 Worker 裡做，主執行緒（main thread）只負責畫。第四個是把渲染（render）本身搬走：OffscreenCanvas 讓 Worker 直接往畫布上畫，主執行緒（main thread）再忙，圖表也不卡。

08:56切片之後，同樣三百毫秒的工作，INP 從三百降到幾十，因為每一個影格（frame）都有機會回應。總時間沒少，但使用者感覺完全不同。

記憶體：長時間開著的洩漏 Memory: Leaks in Long Sessions

09:10桌面應用會被打開一整天。記憶體只漲不降，幾小時後分頁崩潰。這是桌面端特有的問題，內容網站的使用者待不到那個時候。

09:22洩漏的來源很固定：事件監聽器（event listener）加了沒移除；計時器設了沒清；閉包（closure）抓住了大物件；快取（cache）用 Map 只放不取；還有節點從頁面移除了，但 JavaScript 裡還有變數指著它，這叫分離的 DOM（detached DOM）。

09:39找洩漏的辦法是三次快照：記錄一次堆積快照（heap snapshot），做一組操作，再記錄，再做一組，比較三次，一直在增長、沒有被回收的物件類型，就是洩漏點。開發者工具可以直接看到是誰引用著它。

09:55防禦性的做法：元件（component）卸載時清理所有訂閱；用 AbortController 一次取消一組監聽；快取（cache）用 WeakMap，或帶上限的 LRU（least recently used）；大物件用完主動設為空值。長時間運作的應用，定期在線上取樣記憶體曲線。

圖形：Canvas、WebGL 與 WebGPU Graphics: Canvas, WebGL and WebGPU

10:14有些桌面應用本質上是畫圖：圖表、白板、地圖、三維預覽。它們要在 Canvas 2D、WebGL 和 WebGPU 之間選。Canvas 2D 夠畫幾千個圖形，API 簡單，每個影格（frame）重畫一遍就行。WebGL 把繪製交給 GPU，能畫幾十萬個點，但要寫著色器（shader）。WebGPU 是新一代介面，除了畫，還能做通用計算，例如在 GPU 上做物理模擬或矩陣運算。

10:44選擇的原則看數量級：幾千個物件，用 Canvas；幾十萬個，用 WebGL 或 WebGPU。需要和畫面互動時，例如點選、拖動，還要自己做拾取（picking），這是 DOM 免費提供、而畫布沒有的。

11:01一個常被忽視的細節是文字。在 Canvas 裡排版，每次測量文字寬度都很貴。2026 年出現的 Pretext 函式庫，用快取（cache）的字寬直接算換行，完全不碰 DOM，比傳統方法快兩個數量級。

資料：三層快取與請求 Data: Three Cache Layers and Requests

11:18優化的最後一塊是資料。桌面應用的資料快取（cache）分三層：記憶體裡的，關掉就沒了；瀏覽器儲存裡的，IndexedDB 或檔案系統，關掉還在；最後才是網路。讀的時候從近到遠：記憶體有就用，沒有查本地儲存，再沒有才請求；寫的時候反過來，先寫本地、立刻顯示，再同步到伺服器。這樣切換頁面是瞬間的，離線也能看。

11:50請求本身也可以優化：合併同一時刻的多個請求；取消已經離開頁面的請求；對列表用分頁或游標（cursor），而不是一次全拿。API 回傳的資料越少，解析越快，記憶體越省。

12:05Service Worker 可以攔截所有網路請求，做更徹底的離線。但它也是一個常見的坑：快取（cache）策略寫錯，使用者永遠拿不到新版本。桌面應用通常只用它快取（cache）靜態資源，資料層自己管。

收尾：把優化裝進管線 Wrap-up: Put Optimization into the Pipeline

12:22最後回到閉環。優化不能靠某一次突擊，要變成管線的一部分，否則三個月後一切回到原樣。

12:31效能預算（performance budget）：首屏腳本不超過多少、INP 不超過多少，寫進設定。持續整合（CI）裡跑：每次提交自動測套件體積和核心指標，超了就擋住合併。線上監控：真實使用者資料每天看，退步了（regression）就告警，告警要能定位到是哪次發布引入的。

12:51有了這條管線，效能就從一個人的責任，變成了系統的約束。下集講桌面級應用的架構，以及把它裝進用戶端。

開場：應用和內容網站是兩種東西 Opening: Apps vs. Content Sites

00:02桌面瀏覽器裡的應用，和內容網站是兩種東西。一個開十秒，一個開一天；一個是捲動，一個是拖曳、快速鍵、多面板、撤銷重做（undo/redo）；一個每次都是新的，一個要記住你上次的一切。

00:18這一集講桌面級應用怎麼搭：分層、版面、鍵盤、多執行緒、本地資料、多視窗，最後講怎麼把它裝進 Electron 或 Tauri 這樣的殼（shell），變成一個用戶端。

00:31本片的文稿和畫面由 AI 生成，配音由 AI 合成。圖表裡的數字，除特別說明外，都是示意或典型值。

分層與撤銷重做 Layering and Undo/Redo

00:42第一個決定是分層（layering）：把商業邏輯從介面裡拿出來。最裡面是領域層（domain layer），純資料和規則，不知道介面存在；中間是應用層（application layer），把使用者的操作翻譯成領域的命令；外面才是介面。

00:59這樣做的直接收益是撤銷重做（undo/redo）。把每一次操作做成一個命令物件（command object），有執行和撤銷兩個方法，放進一個堆疊（stack）；撤銷就是彈出堆疊頂端、呼叫它的撤銷方法，介面不需要知道任何細節。

01:14命令還帶來別的東西：操作可以記錄下來回放，可以合併成一個批次，可以變成快速鍵和選單項目共用的入口。編輯器類應用的每一個功能，最終都是一條命令。

01:28間接收益是測試：領域層沒有 DOM，可以用普通的單元測試（unit test）覆蓋，介面層只測它有沒有把命令發對。介面框架換掉，領域層一行不用改。

面板布局 Panel Layout

01:42桌面應用的介面是面板：可以拖動分割線調整大小，可以折疊，可以拖到另一邊停靠，可以拆成獨立視窗。實作的核心是 CSS Grid 加上容器查詢（container query）：Grid 負責把視窗分成區域，分割線拖動只改一個變數；每個面板裡的元件（component）用容器查詢（container query）回應自己面板的寬度，窄了就把標籤換成圖示。

02:08拖曳用指標事件（pointer events），而不是滑鼠事件，這樣觸控板和觸控螢幕都能用。拖的過程中只改 transform，放手時才真正改版面配置，這是上集管線的道理。

02:20面板的版面配置要持久化：使用者關掉再打開，面板應該在原來的位置。這是上集說的持久狀態（persistent state），存在本地儲存裡，並且要有版本號，版面結構改了才能遷移。

快速鍵與焦點管理 Keyboard Shortcuts and Focus Management

02:35桌面使用者大量用鍵盤。快速鍵系統要解決衝突：同一個按鍵在編輯器裡和在列表裡，可能是不同的命令，所以要有作用域（scope），也就是目前焦點在哪，哪一組快速鍵生效。還要避開瀏覽器自己的快速鍵。

02:51焦點管理（focus management）是無障礙（accessibility）的基礎：打開對話框，焦點移進去，關閉時回到原來的按鈕；樹狀控制項用方向鍵上下左右；表格用方向鍵移動儲存格；選單用 Esc 關閉。這些模式在 ARIA 規範裡都有定義，照著做就能讓螢幕閱讀器（screen reader）正常運作。

03:12原生的 dialog 和 popover 元素已經內建了焦點管理和關閉行為，優先用它們。

03:20無障礙（accessibility）不是額外工作。一個鍵盤能完整操作的應用，自動化測試也更容易寫，因為每個操作都有確定的入口。給螢幕閱讀器（screen reader）的標籤，也是給 AI 代理操作介面的標籤。

多執行緒：Worker 池 Multithreading: The Worker Pool

03:36中集說過要把計算搬到 Worker。桌面應用會把這做成架構：主執行緒（main thread）只跑介面，一個 Worker 池（worker pool）跑所有重活，任務排隊分發，哪個 Worker 空了就接下一個。

03:49主執行緒（main thread）和 Worker 之間傳訊息，預設是複製：傳一個大陣列會複製一份。用 Transferable 可以把所有權移過去，零複製，但原來那邊就不能再用了。用 SharedArrayBuffer 可以讓兩邊讀寫同一塊記憶體，適合即時資料，但要配合原子操作（atomics），頁面也要開啟跨來源隔離（cross-origin isolation）。

04:09訊息傳遞寫起來很囉嗦，所以有 Comlink 這類函式庫，把 Worker 裡的函式包裝成可以直接 await 的遠端呼叫，語法像本機函式，實際是跨執行緒。

04:21什麼該搬走：解析大檔案、建立搜尋索引、全文檢索、壓縮解壓縮、影像處理、語法上色（syntax highlighting）、Diff 計算。什麼不能搬：任何碰 DOM 的事。一個經驗法則：跑超過五十毫秒的純計算，就該在 Worker 裡。

本地資料與同步 Local Data and Sync

04:43桌面應用需要在本地儲存大量資料，選項有三個層次。IndexedDB 是鍵值資料庫（key-value database），老，但到處可用，適合結構化的記錄。來源私有檔案系統（Origin Private File System，OPFS），是瀏覽器給每個網站的一塊真正的檔案區，在 Worker 裡可以同步讀寫，速度接近原生。把 SQLite 編譯成 WebAssembly，放在 OPFS 上，就是一個完整的關聯式資料庫（relational database）跑在瀏覽器裡，可以跑 SQL。

05:13檔案系統存取 API（File System Access API）更進一步：經使用者授權後，可以直接讀寫使用者電腦上的資料夾。一個線上編輯器可以打開本機專案、存回去，不經過伺服器；授權可以記住，下次打開不用再問。

05:28資料存在本地，就有同步和衝突的問題：兩台裝置各改了一份，合併時誰贏？簡單的做法是最後寫入者勝（last write wins）；嚴格的做法是 CRDT（無衝突複製資料型別，conflict-free replicated data type），一種設計成無論以什麼順序合併，都得到同樣結果的資料結構，協作編輯器用的就是它。

多視窗 Multiple Windows

05:50桌面使用者會開多個視窗：一個視窗看列表，另一個視窗看詳情，拖到第二個螢幕上。這些視窗要互相知道對方的存在。

06:00BroadcastChannel 讓同一個網站的所有分頁互相發訊息，一個視窗改了資料，其他視窗立刻重新整理。SharedWorker 更進一步：所有視窗共用一個 Worker，網路連線、快取（cache）、本地資料庫都只有一份，不管開了幾個視窗。

06:16還有一個細節：分頁被切到背景時，瀏覽器會把計時器節流（throttling）到每秒一次，甚至凍結頁面。長時間運作的應用，要在回到前景時主動校準狀態，而不是假設時間一直在走。

用戶端：PWA、Electron 與 Tauri The Client: PWA, Electron and Tauri

06:32網頁做好了，使用者想要一個可以雙擊打開的用戶端。有三種辦法，能力依次增強，代價也依次增大。

06:40PWA（漸進式網頁應用程式，Progressive Web App）：瀏覽器把網頁安裝成應用，有圖示、有獨立視窗，能離線、能收通知。它最輕，沒有任何額外程式碼，更新就是重新整理。但能力受瀏覽器限制，例如不能讀任意檔案、不能註冊全域快速鍵、不能常駐系統匣（tray）。

06:58Electron：把一個 Chromium 和一個 Node.js 打包進應用。介面跑在渲染行程（renderer process），系統能力跑在主行程（main process），兩者用 IPC（inter-process communication）（行程間通訊）溝通。它什麼都能做，而且在所有系統上表現一致。代價是套件體積一兩百 MB、記憶體幾百 MB，每個應用都帶一份瀏覽器。

07:19Tauri：用 Rust 寫後端，介面用作業系統自帶的 WebView。套件體積幾 MB，記憶體小得多，啟動快。代價是不同系統的 WebView 版本不一致，CSS 和 API 的表現可能有差別，要做相容性測試。

07:35安全是殼最容易出事的地方。渲染行程裡跑的是網頁，網頁可能被注入惡意內容，所以規則是：渲染行程不能直接碰 Node 和系統。所有系統能力透過預載腳本（preload script）暴露成有限的介面，只開放需要的幾個方法，並開啟上下文隔離（context isolation）和內容安全策略（Content Security Policy，CSP）。

07:55發布和更新也是殼要解決的：簽署（code signing）、公證（notarization）、自動更新、增量下載。這些在 PWA 裡是瀏覽器替你做的，在殼裡要自己搭。

08:06選擇的原則：先問 PWA 夠不夠，不夠再問 Tauri 夠不夠，最後才是 Electron。能力越強，套件體積越大，攻擊面也越大。

工程體系 Engineering Practices

08:20大型前端的工程體系有幾個固定的部件。單一程式碼庫（monorepo）：應用、元件庫、工具套件放在一起，用 pnpm 的 workspace 管理；改一個公用套件，所有用到它的應用同時跑測試，不會出現改了函式庫、卻忘了升級應用。

08:37設計令牌（design token）：顏色、間距、字級定義成變數，元件庫只引用變數。換主題就是換一組變數，暗色模式是免費的；設計工具和程式碼共用同一份令牌，設計改了顏色，程式碼自動跟上。

08:54測試分層（test layering）：單元測試（unit test）覆蓋領域層；元件測試在 Vitest 的瀏覽器模式（Browser Mode）裡跑；端對端測試（end-to-end test）用 Playwright 真的把關鍵路徑點一遍。可觀測性（observability）：錯誤回報、效能資料、使用者行為，線上發生的事要能重現。

AI 時代的前端工程 Frontend Engineering in the AI Era

09:132026 年的前端開發，大量程式碼由 AI 代理寫出來。這改變了瓶頸：寫得快了，審得慢了。有研究統計，重複程式碼的比例在上升。有人把這叫做理解債（comprehension debt）：團隊產出程式碼的速度，超過了理解它的速度。（畫面註記：Addy Osmani 提出；GitClear：重複程式碼比例上升。）

09:30應對的辦法是把護欄（guardrail）做成自動的。型別（type）是第一道：AI 寫的程式碼必須通過型別檢查。程式碼檢查（lint）是第二道，Oxlint 裡有一組專門配合 React Compiler 的規則。測試是第三道：沒有測試覆蓋的改動不合併。

09:50前面講的分層也在這裡起作用：領域層的規則清楚，AI 寫的介面程式碼就不容易把商業邏輯寫錯位置；命令模式讓每個功能有確定的入口，AI 改一個功能不會碰到別的。

10:04工具本身也在適配。Vite+ 加的命令列，可以在 AI 代理的沙盒（sandbox）裡跑，讓代理自己裝依賴、跑測試、看結果，人只看最終的差異（diff）。

為什麼值得學

你不必會寫程式，也常聽到「網頁好慢」「這要重寫」「換個框架就好」這類爭論。講者的看法是：很多爭論，是把不同層的問題混在一起說P1 00:53。先知道問題落在哪一層，才知道該找誰、問什麼；也才看得出哪些「優化」其實在錯的層上白費力氣。

你可以帶走的重點

1. 先問「哪一層」出問題，再談解法

上集把前端分成四塊，由下往上：平台（事件迴圈（event loop）與渲染管線（rendering pipeline））、語言（TypeScript 與 CSS）、框架（反應式模型（reactivity model）、狀態（state）、渲染（render）位置）、工程（工具鏈（toolchain）與供應鏈（supply chain））。講者舉的例子：頁面卡頓是平台層的問題，換狀態函式庫沒用；重複送出請求是狀態層的問題，換打包工具（bundler）也沒用；套件太大是工程層的問題，優化元件（component）沒有意義P1 14:08。

2. 卡頓的本質：一件事占住「唯一的那條線」太久

瀏覽器的主執行緒（main thread）只有一條，要跑程式、處理點擊、還要把畫面畫出來。螢幕每秒更新 60 次，每個影格（frame）大約只有 16 毫秒；超過 50 毫秒的任務，瀏覽器稱為長任務（long task）P1 02:15。就像餐廳只有一位服務生：有人點了一桌複雜的菜，其他客人全都得等。

解法的共通想法是「切短」：把大任務拆成小塊，每塊做完就讓出主執行緒（切片，time slicing），讓瀏覽器有機會先處理你的點擊。總工作量沒少，但感覺完全不同P2 08:56。重活也可以搬去 Worker 這條另外的執行緒P2 08:33。

3. 先度量，再動手：三個「體感」指標

優化不是一次衝刺，而是閉環：先度量，找到最慢的那一層，改，再度量P2 00:13。瀏覽器廠商定義了三個核心指標（Core Web Vitals）：最大內容繪製（Largest Contentful Paint，LCP）看主要內容多久出現，累計版面配置位移（Cumulative Layout Shift，CLS）看載入時內容跳了多少，互動到下一次繪製（Interaction to Next Paint，INP）看你點下去之後多久有回饋P2 00:44。門檻是 LCP 兩秒半內、CLS 0.1 內、INP 兩百毫秒內，統計的是真實使用者的第 75 百分位（75th percentile）。對一開就是幾小時的桌面應用，最重要的是 INPP2 01:21。

4. 打開慢，多半是「帶太多東西」

瀏覽器載入網頁是一條鏈：下載 HTML、發現腳本、下載、執行、再去要資料、再渲染（render），每一步等上一步，這叫關鍵路徑（critical path）。縮短它的辦法包括：只載入首屏需要的程式碼（程式碼分割，code splitting）、讓瀏覽器提前並行去取資源（預先載入，preload）P2 02:27。另一半是套件體積：打包工具本來會做搖樹最佳化（tree shaking），把沒用到的程式碼丟掉，但常因桶檔案（barrel file）、副作用（side effect）、動態引用（dynamic reference）而失效P2 04:00。還有一個容易被忽略的事實：1 MB 的 JavaScript 下載可能只要 1 秒，但解析和執行在普通機器上可能要兩三秒，這段時間主執行緒（main thread）是滿的P2 05:01。

5. 長表格不是「全部畫出來」，而是「只畫看得到的」

十萬行、每行二十欄的表格，就是兩百萬個儲存格；全部做成 DOM，瀏覽器會直接卡死。辦法是虛擬化（virtualization）：只渲染（render）視口（viewport）裡的幾十行，捲動時重複使用這些行、換上新資料，再用一個占位元素撐出完整高度，讓捲軸看起來是真的P2 06:39。講者舉的量級：全部渲染（render）要十幾秒；虛擬化後首次渲染（render）幾十毫秒，捲動維持 60 影格（frame）P2 07:37。生活上的類比：用一扇小窗看一幅很長的捲軸畫，你只需要畫出窗口裡的那一段。

6. 「用久了越來越慢」多半是記憶體洩漏

桌面應用會被打開一整天，記憶體只漲不降，幾小時後分頁崩潰。洩漏的來源很固定：事件監聽器（event listener）加了沒移除、計時器設了沒清、閉包（closure）抓住大物件、快取（cache）只放不取，以及從頁面移除了卻還被引用的節點（分離的 DOM，detached DOM）P2 09:22。找法是三次堆積快照（heap snapshot）：做一組操作、記一次，重複三次，一直增長沒被回收的就是洩漏點P2 09:39。

7. 把效能寫成規矩，而不是靠一次突擊

優化若只靠某一次衝刺，三個月後一切回到原樣。講者的做法是把它放進管線：把效能預算（performance budget）寫進設定、在持續整合（CI）裡每次提交自動量套件體積和核心指標、超了就擋住合併；線上每天看真實使用者資料，退步（regression）就告警，並能追到是哪次發布引入的。這讓效能從一個人的責任，變成系統的約束P2 12:22。

8. 大型應用的骨架：領域在裡，介面在外

下集第一個決定是分層（layering）：最裡面的領域層（domain layer）只放資料與規則，不知道介面存在；中間的應用層（application layer）把使用者操作翻成命令；最外面才是介面。直接的好處是撤銷重做（undo/redo）：每個操作都是一個有「執行」和「撤銷」兩個動作的命令物件（command object），放進堆疊（stack），撤銷就是從頂端拿一個出來反做P3 00:42。間接的好處是好測試，而且換掉介面框架，領域層一行不用改P3 01:28。

9. 鍵盤、無障礙，也順便是給 AI 代理的入口

桌面使用者大量用鍵盤，所以快速鍵要有作用域（scope）：同一個按鍵在編輯器和列表裡可能是不同命令P3 02:35。焦點管理（focus management）是無障礙（accessibility）的基礎，照 ARIA 規範做，螢幕閱讀器（screen reader）就能正常運作。講者的觀察是：一個鍵盤能完整操作的應用，自動化測試也更容易寫；給螢幕閱讀器的標籤，同時也是給 AI 代理操作介面的標籤P3 03:20。

10. 把網頁變成「可以雙擊的軟體」：先輕後重

三種辦法，能力和代價一起上升：PWA（漸進式網頁應用程式）最輕，更新就是重新整理，但不能讀任意檔案、不能常駐系統匣；Tauri 用作業系統自帶的 WebView，套件只有幾 MB，但各系統版本不一，要做相容性測試；Electron 內含一整個 Chromium 與 Node.js，什麼都能做、各系統一致，但套件一兩百 MB、記憶體幾百 MB。講者建議的順序是：先問 PWA 夠不夠，不夠再問 Tauri，最後才是 ElectronP3 08:06。另外，殼最容易出事的是安全：渲染行程（renderer process）不能直接碰系統，系統能力要透過預載腳本（preload script）只開放必要的幾個P3 07:35。

11. AI 時代：寫得快了，審得慢了

講者說，2026 年的前端程式碼有很大一部分由 AI 代理寫出來，瓶頸從「寫」移到「審」。畫面上引用 Addy Osmani 提出的「理解債（comprehension debt）」：團隊產出程式碼的速度，超過了理解它的速度；並註記 GitClear 的統計顯示重複程式碼比例在上升（這些來源譯者未另查證）。應對辦法是把護欄做成自動的：第一道型別檢查、第二道程式碼檢查（lint）、第三道測試，沒有測試覆蓋的改動不合併P3 09:13。前面講的分層與命令模式，也讓 AI 改一個功能時不容易碰到別的地方P3 09:50。
