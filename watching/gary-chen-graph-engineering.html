開場：從 Loop Engineering 到 Graph From Loop Engineering to Graph

00:00上個月我們才聊完 Loop Engineering，最近 Peter Steinberger 在 X 上面又發了一篇貼文說：「Are we still talking loops or did we shift to graphs yet?」我們還在討論 loop 嗎？還是大家已經轉向 graph 了？

00:10怎麼又有新名詞了？但先別慌，Graph Engineering 是什麼全新的東西嗎？它很像 AI 代理（agent）、編排（orchestration），或者你如果用過 n8n 也會覺得很眼熟。任務拆解、條件分支、平行助理、狀態（state）管理、人工審核——這些東西早就在工作流程（workflow）、自動化（automation）和各種 AI 代理框架（agent framework）裡存在很久。

00:28但它也不全然只是一個 buzzword（流行術語）。對我來說，Graph Engineering 更像一種思考方式：把原本存在你腦袋裡的分工、路由（routing）、脈絡（context）和驗收機制畫出來、講清楚。它真正有幫助的地方，在於幫我們想清楚該怎麼使用 AI，或者指揮一群 AI 代理。

00:42很多人都希望把一個提示詞（prompt）丟給 AI 代理，他就能自動把所有任務搞定。但實際把 AI 代理放進真實工作流程之後，你就會發現最難的根本不是叫他做事，而是讓他搞清楚：現在做到哪裡了、下一步要做什麼、哪裡需要先檢查、做錯了又該回到哪一步去。

00:58如果沒有這些控制，AI 代理看起來像自動駕駛，實際上你整路都提心吊膽坐在旁邊幫他扶方向盤。他每走一步，就回頭問你：下一步呢？這份資料要放哪裡？這個結果可以直接用嗎？錯了要全部重來嗎？你原本是想把工作交出去給 AI，最後卻只是把自己變成了人肉路由系統（routing system）。

Graph Engineering 要處理的問題 The problem Graph Engineering addresses

01:17Graph Engineering 要處理的正是這個問題。他把複雜的工作拆成一張清晰的工作地圖，清清楚楚定義好誰負責什麼、資料怎麼交接、哪裡需要檢查、出錯了退回哪裡，以及什麼時候一定要由真人介入做決定。所以關鍵在於：當你拿到一個大任務的時候，一定要先停下來，想清楚工作要怎麼流動。

今天的路線 Today’s roadmap

01:37今天這支影片，我會先幫大家快速釐清 prompt、context、harness、loop 和 graph 這五個概念的差別；接著聊聊 Graph Engineering 最核心的三個零件，也就是 node（節點）、edge（連線）和 state（狀態）；然後我們會用一個旅行規劃的具體案例。我也會分享一般人要怎麼直接用幾個 AI 對話視窗，親手搭出自己的第一張 graph。

同一個核心問題：不穩定的 AI 如何做完整份工作 The unsolved core problem

02:00AI 圈之所以一直冒出新名詞，背後其實是因為同一個核心問題到現在都還沒被徹底解決：到底要怎麼讓輸出不穩定的 AI，可靠地把一整份複雜工作做完？傳統程式只要輸入跟規則不變，執行路徑跟輸出就絕對穩定；但 LLM 不一樣，同一個 prompt 你問兩次，就可能拿到兩個完全不同的答案。

02:19更麻煩的是，AI 講錯話的時候，通常不會自己舉手說「我這裡算錯了」。模型能回答，只代表它有能力產生文字，不代表這個結果可以直接交付。如果任務只有一步，你還可以一眼看出來；但當任務拉長到十個步驟，前面一個看似合理的小小錯誤，就可能一路滾雪球傳到最後。

五個概念：Prompt、Context、Harness、Loop、Graph Five concepts, five layers of protection

02:37所以 prompt、context、harness、loop、graph，這些東西其實本質上都是想替 AI 的不確定性，加上不同維度的防護網。

02:45Prompt Engineering 的重點在於：怎麼交代你要做什麼、有哪些限制、成功標準是什麼、最後要用什麼格式交回來。這些都是 prompt 的範圍。

02:55Context Engineering 的重點在於：你要在正確的時間給到 AI 代理正確且剛好足夠的資訊。不是資料越多越好，而是這一步真正需要什麼。你教 AI 寫一封客戶回信，它需要看到客戶的問題、公司政策和語氣要求，不需要順便讀整間公司三年來的會議紀錄。

03:12Harness Engineering 的重點則在於 AI 代理的整個工作環境（harness）：AI 代理能不能讀檔、能不能執行程式、有哪些權限，做完之後能不能跑測試、看到測試結果和 log。

03:22而 Loop Engineering 的重點在於：怎麼讓一個 AI 代理反覆工作和停止。做完先檢查結果，不合格就修改，再跑一次，直到通過。

03:30Graph Engineering 則是整體工作怎麼分工、交接和驗收：哪些工作一定要先做，哪些可以同時開始，還有這一步的 output 要送到哪裡。

它們不是互相取代 Not competitors, but layers

03:38這五個概念完全不是非此即彼的競爭關係。一張 graph 裡面可以包含好幾個 loop，而每一個 node 裡的 AI 代理也都需要自己的 prompt、context 和 harness。Graph 的出現絕對不代表 prompt 沒用了，更不代表 loop 過時了。每一層都在解決上一層管不到的盲點。

03:53前面四層主要是在優化單一執行者以後要怎麼做好一件事；而 Graph Engineering 則是站到制高點，解決多個執行者、工具、傳統程式和人類之間要怎麼分工協作。現在大家開始討論 graph，正是因為當任務變得越來越長、越來越複雜，問題已經不只是某一個 AI 代理聰不聰明，而是整體流程該如何協同作戰。

Graph 的本質，以及三個核心零件 What a graph really is

04:11要理解 Graph Engineering，最簡單的方法就是想像我們常看的流程圖：就是一個個方框，用箭頭連在一起，有些地方分叉，有些地方匯合。但千萬別以為畫一張流程圖就叫 Graph Engineering，畫圖是給人看的。Graph Engineering 真正要設計的，是這張圖背後一套真正能自動跑起來的系統結構。它必須明確告訴系統：每一步要做什麼、輸入什麼、輸出什麼、下一步往哪走、什麼條件才算完成，以及萬一失敗了該退回哪裡。

04:38而一張 graph 最核心的三個零件，就是 node、edge 和 state。接下來我會用規劃一趟旅行的具體流程來帶大家理解。

Node：獨立的工作單元 Node: a unit of work, not necessarily an agent

04:46我們先來看 node。Node 就是一個獨立的工作單元，也就是流程圖裡的一個方框。這個方框裡面執行的東西非常靈活，不一定非得是 AI。它可以是一次簡單的 LLM 呼叫、一段 Python 腳本、一個資料庫查詢，也可以是一個自帶 loop 的完整小 AI 代理，在裡面自動搜尋、檢查、重試（retry）；甚至連需要真人按確認的人工審核，本身也是一個 node。

05:09所以 node 不等於 AI 代理。Graph Engineering 並不是要你把所有環節都換成 AI。很多確定性的工作，像是加總預算、檢查日期格式、驗證網址有沒有缺漏，用傳統程式寫三行 code 就搞定了，速度快、成本是零，而且百分之百精準。硬要派一個大語言模型去幫你按計算機，除了浪費 token 跟增加出錯機率，沒有任何好處。

05:31一個設計良好的 node，核心就是三件事：清楚的 input（輸入）、嚴格的 output（輸出），和明確的完成條件。比方說負責找住宿的 node，它的 input 就是日期、人數、地點，和每晚預算；output 則固定是三個住宿方案，而且每個方案都必須包含價格、地點、取消條款，和原始訂房連結。

Edge：依賴關係與路由 Edge: dependency and routing, not just a line

05:50第二個零件是 edge。Edge 就是節點（node）之間的連線（edge），它決定了資料怎麼傳遞、下一步該往哪裡走。代表的是工作之間的依賴關係與路由邏輯，而不是單純拿一條線把兩個方框連起來。

06:01比方說住宿跟交通方案還沒出來之前，後面的合併 node 就絕對不能啟動，這就是一種依賴限制。而如果條件已經齊全，交通、住宿和景點三個 node 就可以同時觸發、平行執行，這也是由 edge 的路由規則來決定的。

06:16Edge 可以是單純的固定路徑，像是 A 做完直接交給 B；但也可以是條件式分支，比方說檢查通過就送去給真人確認，檢查不通過就把錯誤訊息退回給原本 node 要求重做。如果執行到一半發現必要資訊不足，edge 還可以把流程暫停，跳去向人類提問，拿到答案後再繼續往下走。

State：當前進度與最新資料 State: not a pile of chat logs

06:34第三個零件叫 state。最簡單的理解方式，想像你在玩大地遊戲，手上那張闖關卡就是 state：上面記錄著你的隊伍資訊、每一關收集到的結果、現在做到第幾關，還有關主的批改紀錄。每過一關，闖關卡上的內容就會更新一次。

06:50以旅行規劃來說，state 裡面存放的就是旅行日期、人數、總預算、交通候選名單、住宿候選名單、景點清單、合併後的第一版行程、查核抓到的問題清單，以及最後人類的審批結果。

07:03每個 node 不需要、也不應該看到整個 state 的全部內容。住宿 node 只需要讀取日期、人數、地點和住宿預算，找完後把住宿結果寫回 state；景點 node 只需要讀取同行者興趣和可用時段，產出後再寫回 state。這樣做可以讓每個 node 的 context 保持乾淨精準，出問題時，也立刻知道是哪筆資料被誰寫壞了。

07:23很多人會問，state 跟一般的聊天紀錄有什麼差別？聊天紀錄就像是把所有文件、便利貼跟草稿，一股腦全堆在同一張桌子上：前面的需求、中間的廢案、最後的定案全都混在一起，AI 越讀越容易產生幻覺。但正式的 state，就像一張有標準欄位的 Google Sheet 或資料庫：日期就是日期，預算數字就是預算數字，審核狀態就是審核狀態。它有嚴格的讀寫規則，可以隨時備份存檔、版本比對，甚至在出錯時直接倒帶恢復。

07:51我們快速複習這三大要素：node 負責把具體的事做好，edge 決定資料與流程下一步往哪走，state 隨時記錄當前進度與最新資料。這三者結合起來，你的 AI 系統才會真正擁有方向感：清楚知道自己在哪一站、手上有什麼資料、接下來該往哪裡去。

案例：四個朋友的東京五日遊 Case study: a five-day trip to Tokyo

08:07我們直接用規劃一趟多人旅行作為案例。假設四個朋友要去東京玩五天，每個人預算三萬元。有人想逛街買衣服，有人想看美術館，其中一個人吃素，還有一個人膝蓋不好，每天不能走超過兩萬步。

08:21如果你只是把這些條件通通丟給一個 AI，叫他「幫我排一份東京五天四夜行程」，他當然排得出來，但過程中或許會有很多規劃上的小瑕疵跟不細心。那如果換成 Graph Engineering 的架構來處理，整趟流程會長什麼樣呢？

08:37第一步進入需求 node。這個 node 先不急著排景點，而是專心把零散的需求規格化：整理出日期、出發地、目的地、人數、總預算，以及每個人的飲食和行動限制，還有哪些是絕對不能接受的雷點。Input 是大家七嘴八舌的需求，output 是一份標準結構的旅行規格書，並直接寫入 state，作為後續所有 node 的共同基準。

09:00第二步，工作開始平行分流。交通 node 負責搜尋來回航班、整理機場到市區的交通路線，並預估交通時間，產出包含班次、票價、轉乘方式與購票連結的選項。住宿 node 只拿日期、人數、預算和地點偏好，專注找出符合條件的飯店，產出價格、位置、取消條款，以及到主要商圈的車程。景點 node 則根據大家各自的興趣與空檔時段，篩選出候選景點清單、營業時間、建議停留時間和景點間的移動距離。

09:29在第一輪收集時，這三個任務需要的 context 截然不同，彼此也沒有先後依賴，所以完全可以平行同時跑。從同一個需求節點（node）分流成多條平行路徑，這在架構上就叫做扇出（fan-out）。

09:40第三步，當三條路徑都完成後，結果會匯流進合併 node。這個 node 會對照兩班機抵達時間、飯店 check-in 位置、景點營業時間，和每天的步行步數，把三組原本各自獨立的資料，組裝成一份完整的五天行程表。多條平行路徑重新匯合到一個節點（node），這就叫做扇入（fan-in）。

09:58但排完行程還不能直接結束，因為合併只代表資料排在一起了，不代表這份行程是可行的。所以第四步會交給驗證器（verifier）。驗證器會依照嚴格的邏輯標準進行全面稽查：交通跟住宿的 check-in 日期有沒有對上、景點當天到底有沒有開門、轉乘與移動時間算得合不合理、有沒有不小心踩到吃素或走太多路的地雷；最後把機票、住宿、門票和交通費全部精算加總，確認總金額有沒有超支。

10:25如果全部檢查合格，驗證器才會把行程推進到最後的人工審核（human approval）node，交給真人決定要不要採用。但如果查核沒通過，就會依據條件分支把任務退回。例如發現總預算超支了 5,000 塊，而且問題出在住宿太貴，系統不需要把整份行程全盤推翻，它只需要把問題精準退回給住宿 node，要求它在同一個區域找每晚便宜 1,000 塊的替代方案。住宿修改完畢後，再回到合併 node 去更新行程，接著再讓驗證器重驗一次。如果是某個景點公休，就只退回給景點 node；如果是轉機時間太趕，就只退回給交通 node。哪裡出錯，就退回哪裡修。

11:01從驗證器發現問題、退回前面 node 修改、再重新驗收，這條回溯路徑本身就是一個局部 loop。所以 graph 和 loop 不是二選一的關係：graph 負責宏觀的架構分工、資料流動與全局驗收，而 loop 負責微觀的迭代修正。一張大 graph 裡面，隨時可以嵌入好幾個局部的 loop。

11:19最後一步，就是 human approval，人工審核。AI 可以幫你列舉選項、找出時程衝突、自動修正邏輯錯誤，但最終的取捨——像是要不要為了省 3,000 塊住遠一點、要不要因為朋友膝蓋痛拿掉這個景點、要不要冒險買不能退改的特價票——這些關鍵決定要留給自己。

11:36整張工作地圖跑起來的邏輯非常清楚：先規格化需求，讓幾個 AI 代理去平行研究（research）交通、住宿以及景點，最後匯整成行程，嚴格查核時間、預算與來源，哪裡有 bug 就局部退回重修，最後由真人確認放行。

Graph 解決的三大難題 Three problems a graph actually solves

11:50看完這個案例，我們來總結一下 graph 到底解決了哪三大難題。

11:53第一個問題是脈絡污染（context 污染）與工具失焦。當你把所有任務塞在同一個長對話裡：前面是四個人的聊天需求，中間是航班搜尋紀錄，後面又貼了一堆飯店跟景點連結，中間再來回改了五六輪，此時模型的 context 會變得又長又髒，他根本分不清楚哪些是過期廢案、哪些才是最新決定。工具也是同樣道理：如果你把訂房、地圖、搜尋、算數學、串 API 全塞給同一個 AI 代理，他每走一步都要在十幾個工具裡猶豫不決，看似全能，注意力卻完全渙散。

12:22而 graph 的解法就是脈絡隔離（context isolation）與工具專業化。每個 node 都有自己負責的任務，只需要讀取自己需要的 state 資料，只配備自己需要的工具。住宿 node 專心找飯店，不需要讀景點介紹，也不用知道大家在群組裡吵了什麼。

12:36第二個問題是缺乏可觀測性，與無法局部重跑。如果讓單一 AI 代理一路蠻幹到底，只要他一開始選錯了飯店位置，後面排的景點順序跟移動時間都會全部連鎖崩盤。最後你拿到一份爛行程，你根本不知道到底該從哪裡改起：是要改 prompt，還是換飯店，還是乾脆整個重來？

12:53而在 graph 架構中，每個 node 的輸入、輸出、路由選擇和驗收紀錄，都會被清楚地保留在 state 裡。當驗證器發現移動時間過長，你可以立刻倒回去看住宿 node 當時依據什麼條件挑了這家飯店，然後只重跑住宿這個分支。問題可以被精準定位，除錯和修改的成本降到最低。

13:13第三個問題是把「做完」當成「做對」。LLM 最大的盲點，就是特別擅長完成表面任務。你叫他查最便宜的機票，他能噼哩啪啦生出一張以假亂真的報表，但實際上根本買不到那張票。Graph 讓你在關鍵節點（node）設立驗證機制，也就是前面說到的驗證器，還有人工審核節點（node）。雖然驗證器無法百分之百消滅所有幻覺，但它的價值在於把原本藏在你腦袋裡的驗收標準明確寫成規則，由系統嚴格執行。設計得好的 graph，能讓複雜任務井然有序、可追蹤、可修正。

普通人如何親手搭出第一張 Graph How to build your first graph by hand

13:43影片到這邊，我們已經聊完了 graph 的本質、它與其他概念的關聯、核心三大要素、具體案例，以及它解決的痛點。接著我們聊聊，普通人到底要如何親自動手，搭建出屬於自己的第一張 graph。如果你是新手，強烈建議你先從純手動版本開始跑起，一共分三步。

13:59第一步，先定義清楚最終交付物與成功驗收標準。以旅行計畫為例，你的目標是產出一份實際可行、符合預算、照顧到同行者需求，而且關鍵資訊都能追溯到原始來源的行程表。具體來說，可行代表每天交通時間合理、住宿沒有超支、景點營業時間對得上。這就是你的 output 與成功標準（success criteria）。

14:20第二步，把整份工作拆解成必要的 node。再次強調，node 不一定等於 AI 代理，它只是一個獨立的工作單元。你只需要為每個 node 寫清楚五件事：它負責什麼、需要什麼 input、交出什麼 output、完成後去哪裡，以及遇到什麼情況絕對不能放行。例如交通 node 必須交出航班選項、票價、時間與連結；如果少了來源網址或票價超支，就判定為不合格，禁止放行。

14:44第三步，直接打開幾個獨立的 AI 對話視窗，手動扮演這張 graph。開一個對話專門查交通、一個對話專門查住宿、一個對話專門排景點，把整理好的需求規格分別丟給他們。每個對話只專注入做好自己的任務，絕對不要讓任何一個 AI 去包辦整份行程。當三份結果都產出後，再打開第四個對話視窗負責合併，並依照時間、距離、預算和限制條件進行嚴格審核。如果發現住宿超支，就把問題丟回住宿對話要求重新推薦；景點時間排不下，就丟回景點對話重新調整；修改後再重新合併檢查，最後由你親自決定是否採用。

15:21在這個版本裡，你就是路由系統（routing system）：資料由你搬，下一步由你決定，state 可能只是一張表格或幾份文件，但你已經在實踐 Graph Engineering。先手動跑，才能看見這份工作到底怎麼運作；流程跑順後，再考慮把它自動化。不要想著一步登天。

結語：別被新名詞焦慮，也別每件事都硬套 Graph A closing caution

15:36最後也希望大家不要對各種新名詞產生焦慮。看完這支影片之後，你應該也能感受到，Graph Engineering 其實就是一種讓我們跟 AI 協作的架構思維，甚至很多人可能一年前就在使用了，只是從未被 AI 圈大佬點名過。

15:49另外，也絕對不是每一項任務都需要硬套 graph。AI 系統絕對不是越複雜越好。你要清楚知道，眼前這項任務到底適合哪種工具。如果是一次性的簡單任務、一個 prompt 就能搞定的事，就千萬別硬把它拆成七個 node、製造麻煩。像我剛剛舉的旅行案例，其實現在比較前沿的模型就能自己處理了，沒必要拆得這麼複雜。但各位還是可以拿一些簡單的任務練練手，感受一下當流程圖架構師的樂趣。

以下為譯者整理，非原片內容。

這支影片在說什麼

這支影片說明 Graph Engineering 不是什麼全新的流行術語，而是一種把複雜工作畫成可檢查、可退回、可分工的流程圖的思考方式。講者先釐清 prompt、context、harness、loop、graph 五個概念並不是互搶位置，再用「四個朋友去東京玩五天」當例子，拆解 node（節點）、edge（連線）和 state（狀態）。最後示範：一般人可以先開幾個 AI 對話視窗，親手演練第一張 graph，跑順了再考慮自動化。

為什麼值得學

很多人希望丟一個提示詞給 AI 代理，它就能自動做完整份工作；結果自己反而變成「人肉路由系統」——每走一步都要問下一步、資料放哪、能不能用。當任務變長、步驟變多，問題不再只是模型聰不聰明，而是流程怎麼協同、出錯了怎麼只修那一段。這套想法不要求你先學會寫程式，今天就能用對話視窗練習。

你可以帶走的重點

1. 五個概念是防護網的不同層，不是互相比賽誰比較新

Prompt 交代「要做什麼、限制是什麼、怎樣算成功」；context 是在對的時間給剛好足夠的資料；harness 是工作環境與權限（能不能讀檔、跑測試、看 log）；loop 是同一個人反覆做、檢查、再改到通過。Graph 則站在制高點，管多個執行者、工具、傳統程式和人要怎麼分工、交接、驗收。

一張 graph 裡可以有好幾個 loop；每個 node 裡的 AI 代理，仍然需要自己的 prompt、context 和 harness。Graph 出現，不代表 prompt 沒用了，也不代表 loop 過時了。

2. 一張能跑的 graph，靠 node、edge、state 三個零件

光畫流程圖給人看還不夠。系統必須說清楚：這一步做什麼、輸入什麼、輸出什麼、下一步往哪走、怎樣算完成、失敗了退回哪裡。

  • Node（節點）是一個獨立的工作單元，不一定是 AI。它可以是一次 LLM 呼叫、一段 Python、一次資料庫查詢、一個自帶迴圈的小 AI 代理，或是真人按確認的人工審核。加總預算、檢查日期這種確定的事，用傳統程式寫三行往往更快、更準、成本幾乎是零。
  • Edge（連線）不是一條漂亮的線，而是依賴與路由：住宿和交通還沒出來，合併就不能啟動；條件齊了，三條線可以同時跑；檢查不通過，就把錯誤退回原 node；資訊不夠，就暫停去問人。
  • State（狀態）不是把聊天紀錄堆在同一張桌子上。它比較像有標準欄位的試算表或資料庫：日期就是日期，預算就是數字。每個 node 只讀自己該看的欄位，寫回自己負責的結果。出問題時，才立刻知道是哪一筆被誰寫壞，也可以備份、比對版本，甚至倒帶恢復。

3. 用一趟東京旅行，看扇出（fan-out）、扇入（fan-in）和局部退回

案例是四個朋友去東京玩五天，每人預算三萬元：有人要逛街，有人要看美術館，有人吃素，有人膝蓋不好、每天不能走超過兩萬步。如果把這些條件一次丟給一個 AI 叫它排行程，它排得出來，但小瑕疵很容易一路滾下去。

換成 graph 會長這樣：先做「需求」node，把七嘴八舌的話整理成規格書並寫入 state；再扇出（fan-out）成交通、住宿、景點三條平行路徑（它們需要的資料不同，彼此也沒有先後依賴）；做完再扇入（fan-in）到合併 node，對照班機抵達、check-in、營業時間和步行步數，組出五天行程。接著交給驗證器（verifier）查日期有沒有對上、景點當天有沒有開門、會不會踩到吃素或走太多路、總額有沒有超支。

若總預算超支 5,000 塊而且是住宿太貴，系統不必整份推倒重來，只要退回住宿 node，請它在同一區找每晚便宜 1,000 塊的替代方案，再合併、再驗。景點公休就只退回景點，轉機太趕就只退回交通。哪裡出錯，就退回哪裡修。這條「檢查 → 退回 → 再驗」的路，本身就是一個局部 loop：graph 管宏觀分工，loop 管微觀修正，兩者不是二選一。

全部合格後，才進入人工審核。要不要為了省 3,000 元住遠一點、要不要因朋友膝蓋拿掉景點、要不要買不能退改的特價票，這些取捨留給人。

4. Graph 真正在解的三個麻煩

  • 脈絡被弄髒、工具對焦失敗。把需求、搜尋紀錄、飯店連結和來回修改全塞進同一個長對話，模型會分不清哪些是過期廢案。把訂房、地圖、搜尋、算數、串 API 全交給同一個 AI 代理，它每一步都要在十幾個工具裡猶豫。解法是脈絡隔離和工具專業化：住宿 node 專心找飯店，不必去讀景點介紹，也不必知道群組裡吵了什麼。
  • 看不見過程，也沒辦法只重跑一段。單一 AI 代理一路蠻幹，一開始選錯飯店，後面的景點順序和移動時間會連鎖崩盤，你也不知該改 prompt、換飯店，還是整份重來。在 graph 裡，每個 node 的輸入、輸出、路由和驗收都會清楚留在 state，可以倒回去看，只重跑出問題的分支。
  • 把「做完」當成「做對」。LLM 很會完成表面任務，也能生出一張看起來很真、其實買不到的便宜機票表。驗證器和人工審核，是把原本藏在你腦裡的驗收標準寫成規則，讓系統執行。驗證器無法消滅所有幻覺，但它讓複雜任務變得可追蹤、可修正。

5. 先手動跑，再談自動化；簡單任務不要硬拆

新手不必一開始就做自動系統。先寫清最終要交出什麼、怎樣算成功；再把工作拆成必要的 node，每個 node 寫五件事：負責什麼、要什麼輸入、交出什麼、完成後去哪、什麼情況絕對不能放行。然後打開幾個獨立的 AI 對話視窗來扮演這張圖：一個查交通、一個查住宿、一個排景點，第四個負責合併和審核。絕對不要讓任何一個 AI 包辦整份行程。這個版本裡，你就是路由系統，state 甚至只是一張表格。

也不是每件事都該套 graph。一次性、一個提示詞就能搞定的事，千萬別硬拆成七個 node。講者說，就連前面的旅行案例，現在比較前沿的模型有時也能自己處理；先拿小任務練手，感受當流程圖架構師的樂趣即可。不要對新名詞焦慮：這其實是一種跟 AI 協作的架構思維，很多人可能一年前就在用，只是還沒被點名。

怎麼開始

  1. 挑一件你這週真的要完成、而且步驟不只一項的事（例如排一趟短旅行、整理一份要給別人看的報銷）。先寫下：最後要交出什麼、怎樣叫做「可以交差」——每天時間合不合理、有沒有超支、關鍵數字能不能追到原始來源。
  2. 把工作拆成三到五個 node，不要一開始就拆七個。為每個 node 寫那五件事；能用計算機或試算表做的（加總、對日期），就不要交給大語言模型。
  3. 打開三到四個獨立的 AI 對話視窗，把同一份規格分別丟出去，各做各的。你自己當路由：把結果抄到一張表格當 state。哪一站不合格，只把問題丟回那一個視窗，改完再合併一次。
  4. 最後的取捨自己做決定，不要把「要不要冒險」也交給模型。手動跑過一輪、看出卡關的地方之後，再考慮要不要自動化。
