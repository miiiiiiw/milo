開場：AI 說要等 CI 檢查 Waiting for the CI Check

00:00你可能在用 AI 來開發你的產品的時候遇過這樣的狀況：AI 寫完一個功能，問你要不要開合併請求（PR）。你按下同意之後，AI 下一句突然回你：「好，那我們等持續整合（CI）檢查通過之後再合併（merge）。」

00:11對非技術背景的人來說，聽到這句話大概只會滿頭問號：我看過 Gary 有關於 Git 的影片，所以我知道合併請求（PR）是什麼，但持續整合（CI）又是什麼東西？為什麼要等它檢查？

00:20雖然持續整合（CI）聽起來很恐怖，但它其實是軟體開發裡超級重要的一環，也是你在 AI 時代打造自動化寫程式的軟體工廠（software factory）不可或缺的自動把關機制。

00:29今天這支影片，我想用最白話的方式帶你搞懂什麼是持續整合（CI）、什麼是持續部署（CD），以及它們到底重要在哪裡。因為只有在專案裡把這道防線建立起來，你才能比較放心地一直往上疊新功能，不會做 A 壞 B，陷入找 bug、打地鼠的無限迴圈。

開發流程五步 The Five-Step Development Flow

00:45要搞懂這件事，我們還是先從一般軟體開發的流程出發。一樣是我們的主角 Gary，他之前開發了一款記帳軟體，學會把自己在電腦裡寫好的程式碼推上 GitHub，也知道怎麼把這個專案部署在 Render 這個網站裡面，讓身邊的朋友都可以使用他的記帳軟體。

01:01這款記帳軟體朋友們用了都說很好用，所以 Gary 也加快腳步，一直往上迭代不一樣的新功能。加一個新功能看起來只要三步：先叫 AI 把功能寫完，推上 GitHub 開合併請求（PR），然後部署上線。但 AI 跟平台其實在背後默默幫你跑了一連串的自動檢查跟自動部署，而這整套機制就叫做持續整合／持續部署（CI/CD）。

01:21還是覺得有點抽象的朋友，我們直接把 Gary 開發新功能的整體流程拆開來看，你會比較好理解。

01:27當 Gary 今天想幫記帳軟體加一個「匯出月報表」的功能，他第一步會先開一條新的分支（branch）來寫這個新功能，避免把主線的程式碼搞得亂七八糟。等 AI 在這條分支（branch）上把功能寫好了，就會進到第二步，也就是把改好的程式碼推上 GitHub，開一張合併請求（PR），這就代表你把這個功能寫完了。

01:45要把這個功能真的加入到主線的正式程式碼中，但合併之前我們需要再做一次檢查，確保這份新程式碼放進去之後，整個專案還是可以正常運作，不會把舊功能搞壞。所以當你開完合併請求（PR）、打開 GitHub 頁面，你會看到畫面底下突然開始轉圈圈，自動跑出一排項目。

02:02這就是第三步，叫做持續整合（CI），英文是 Continuous Integration，中文叫持續整合。其實簡單講，就是 GitHub 在幫你測試你的軟體，把新舊程式碼合起來做一次通盤的檢查。

02:12當這些自動檢查全部跑完，而且都亮起綠燈後，才會進到第四步，也就是把這個程式碼正式合併進主線 main 的程式碼裡。

02:22而程式碼合併到主線後，事情還沒有結束，因為你最終是希望把這個做好的新功能交給真實用戶，讓朋友們收到這次的功能更新，所以還需要讓你的部署平台拿到主線最新的程式碼並更新網站。部署平台比較常見的有 Render、Vercel 或者 Netlify，而在我們前一部影片的案例中使用的是 Render，所以這支影片會繼續沿用這個案例。

02:42部署上去就是第五步，叫做持續部署（CD）。英文全名有兩種說法：一種是 Continuous Delivery，持續交付；或是 Continuous Deployment，持續部署。兩者的差別在於，持續交付是準備好隨時能上線，但最後要人工按確認；而現在像 Render 這類平台幫我們做到的，是更進一步的持續部署。

03:00白話講，就是電腦自動幫你把新版網站部署上線：當主線一更新，Render 就會自動接手，把最新版的記帳軟體重新打包、發布出去，讓朋友一打開網頁就用到新功能。

03:11所以講白話一點，持續整合／持續部署（CI/CD）在整個流程裡的角色，就是把原本最繁瑣的「檢查有沒有改壞」跟「打包傳上網站」這兩件事，全部變成自動化。

03:20反過來想，如果今天 Gary 沒有用持續整合（CI）跟持續部署（CD），他每次改完一個功能，就不能只推上 GitHub 然後拍拍屁股走人。你必須自己打開網頁，把所有功能從頭到尾手動測試一遍，結束後還要自己把整包檔案手動上傳到 Render 去更新網站。當產品越做越大、改版速度越來越快，這種手動流程不只花時間，還超級容易因為一時疏忽，就把有問題的版本直接更新出去。

CI 檢查清單 The CI Checklist

03:45看懂大方向的流程之後，我們接著往下挖持續整合／持續部署（CI/CD）的前半段，也就是持續整合（CI）到底在做什麼。其實持續整合（CI）沒有你想的那麼玄，它本質上就是一份自動化的檢查指令清單。

03:56既然它只是一份指令清單，就代表裡面要檢查什麼並不是系統寫死的，我們是可以客製化的。而現在這個用 AI 寫程式的時代，大多數時候你使用的 AI 代理，像是 Claude Code、Codex 或者 Cursor，都會幫你把這份檢查清單給設置好。

04:12以我這個專案為例，裡面有一個叫做 .github 的資料夾，點開底下的 workflows，裡面就會有像 ci.yml 的 YAML 檔案，這份檔案就是 AI 幫你寫好的持續整合（CI）檢查清單。只要你把專案推上 GitHub，GitHub 就會自動來讀這個資料夾裡的檔案，照著上面寫的步驟去執行自動化。

04:30這個持續整合（CI）的 YAML 檔案，通常保底都會跑三道基本檢查。

第一道：Lint 與 Typecheck Lint and Typecheck

04:33第一個檢查叫做程式碼檢查（Lint）跟型別檢查（Typecheck），在設定檔裡通常會寫成 npm run lint 跟 npm run typecheck。你可以把它想成是在抓 AI 寫程式的壞習慣，以及檢查資料有沒有填錯格式。

04:44先講程式碼檢查（Lint）。它解決的問題是 AI 寫程式常常圖快，留下垃圾或危險寫法。程式碼檢查（Lint）會去讀專案裡的 ESLint 規則檔，確保程式碼乾淨整齊。比方說 AI 改完程式後，常常忘記把用不到的舊元件清掉，程式碼檢查（Lint）掃過去就會發現這個東西是垃圾、存在沒有意義，然後提醒你刪掉。

05:03而且它不只能清垃圾，還能攔下那種語法看起來沒錯、但跑起來會出大事的寫法。就像我們在 pstack 那支影片提過的，AI 寫前端很愛用 useEffect，一不小心沒寫好，就會讓網頁一直重複更新，卡死在無限迴圈裡。所以 Lauren 直接把「禁止使用 useEffect」寫進程式碼檢查（Lint）規則裡，AI 只要一寫出來，跑 npm run lint 一秒鐘就會亮紅燈並退貨。

05:25而跟它搭配的 Typecheck，中文叫型別檢查，專門在抓程式裡資料類型對不上的錯誤。意思就是，程式裡的每一個資料欄位都規定好只能裝哪一種東西，比如只能放數字，或者只能放文字。如果 AI 寫一寫忘記這個規定，把錯誤類型的資料塞進去，程式跑起來就會當場報錯。

05:43舉個例子：記帳軟體要計算這個月總共花了多少錢，計算總額的地方規定只能用純數字來做加減，結果 AI 改另一個頁面時不小心寫錯了，把「100 元」這種純文字當成數字送去做加減。在程式裡這樣硬算，報表出來不是金額變成亂七八糟的字串，就是直接算成無效數字。

06:02型別檢查（Typecheck）只要花幾秒鐘把程式碼掃一遍，不用真的把網站跑起來，就能立刻把這種錯誤攔下來。

第二道：Test Test

06:08第二個檢查叫做測試（Test），也就是自動功能測試，對應的指令是 npm run test。平常我們請 AI 寫程式的時候，也會順便叫它在專案裡建好一堆測試腳本。這些測試腳本的目的，就像是先幫軟體寫好一份標準驗收考卷，把每個功能正常運作時該有的結果，全部寫成檢查題。

06:27跑 npm run test，就是讓電腦照著這份考卷自動考過一遍，確認這次的程式改動沒有把之前的功能改壞。

06:34比方說我們今天請 AI 加了匯出月報表的新功能，你怎麼知道它有沒有在改程式的時候，不小心把原本好好的新增記帳或會員登入給改壞了？這時候跑一次 npm run test，電腦就會扮演一位虛擬用戶，可能先幫你試記三筆假帳，看金額加總對不對，接著再試試看匯出報表跟登入功能正不正常。不管是新功能算錯錢，還是舊功能被意外搞壞，這一關都會馬上亮紅燈攔下來。

第三道：Build Build

06:58第三個檢查叫做打包（Build），對應的指令是 npm run build，白話叫做打包測試。為什麼需要打包？因為 AI 平常寫程式的時候，為了好修改，會把程式碼拆成幾百個零散的小檔案，而且裡面的內容是一般瀏覽器直接看會看不懂的開發語法。

07:13所以在網站正式上線之前，一定要先經過打包（Build）這道手續，把這幾百個零散的零件，全部翻譯成瀏覽器看得懂的標準語言，再壓縮組裝成一個完整的網站成品包。

07:23單看每一個小檔案或許很少出錯，但全部拼在一起的時候，才會發現東缺一個、西缺一個。所以在合併之前，必須先跑一次 npm run build 預演組裝，確定這批程式碼真的打包得起來，不會等推上線才發現整個網站打不開。

GitHub Actions GitHub Actions

07:36當我們在 ci.yml 裡面定義好了這三關檢查，每當有人把改好的程式碼推上來、開出合併請求（PR）的時候，幫我們做持續整合（CI）的工具，就會照著這份清單自動跑過一輪。

07:46而持續整合（CI）工具最常見的，就是我們管理程式碼的平台 GitHub 內建的自動化服務，叫做 GitHub Actions。前面我們講過，當 Gary 幫記帳軟體寫完匯出月報表的功能，一開完合併請求（PR），GitHub 頁面底下就會開始轉圈圈、跑出一排項目，背後在運作的其實就是它。

08:02只要把 ci.yml 設定檔放好，每次 Gary 一開合併請求（PR），GitHub Actions 就會自動在雲端借一台全新的空白電腦，把記帳軟體的程式碼下載下來，照著清單把剛剛說的檢查全部跑完。

08:13之所以要特地借一台空白電腦重跑，是因為 Gary 自己的電腦平常早就裝了一堆開發工具、舊套件跟暫存檔。有時候 AI 寫新功能用到了某個套件，剛好 Gary 的電腦以前裝過，卻忘記寫進專案的安裝清單裡，這時候在 Gary 自己的電腦上跑完全沒事，但一推到正式網站上，就會因為找不到套件而當機。所以為了排除這些殘留環境的干擾，我們得用一台完全乾淨的空白電腦，從零開始下載安裝，從頭跑一次，所有檢查測出來的結果才最準確。

08:44接著我們實際看一下，當 Gary 開完一張新功能合併請求（PR）之後，在 GitHub 畫面上會看到什麼。首先在合併請求（PR）的總列表上，每一張合併請求（PR）旁邊都會掛著一個小圖示跟數字，像是綠色的打勾寫著「3/3」，就代表這張合併請求（PR）要檢查的三個項目全部過關；如果看到紅色的叉叉寫著「2/4」，就是四個項目裡面只過了兩個。

09:04這時候點進這張合併請求（PR），切換到上方的 Checks 分頁，就能看到那台雲端電腦正照著設定一步一步執行，依序跑過 lint、test 跟 build。萬一匯出月報表在某一關亮了紅叉，只要點旁邊的 Details，就能看到具體的錯誤報告。

09:18Gary 甚至不用自己看懂全部的英文，直接請 AI 透過 GitHub 的連接器（connectors）去讀取報錯的訊息，叫它修好再重新推上來就行了。等到持續整合（CI）檢查全部亮綠燈通過，就可以安心按下 Merge，把匯出月報表的新功能合併回 main 主線了。

09:33不過 GitHub 其實只是保管程式碼的倉庫，按完合併後，它自己並不會去更新網站。記帳軟體的網站之所以會跟著變動，靠的是 Gary 當初把專案部署到 Render 或 Vercel 時，在後台綁定的連線。部署平台會在旁邊隨時盯著 main 主線，只要發現有新的程式碼合併進來，Render 就會自動把最新版抓過去、重新打包，直接發布成最新的正式網站。幾分鐘後，Gary 的朋友一打開網頁，就能直接用到最新的匯出月報表功能了。

09:59這整段「主線一更新就自動發布上線」的機制，就是前面說的持續部署（CD），英文叫 Continuous Deployment，持續部署。現在對於 Render 或 Vercel 這類平台，持續部署（CD）早就做成開箱即用的標準功能了，所以使用這類型平台的朋友們，就不太需要自己設定持續部署（CD），只要一開始有把 GitHub 的儲存庫（repo）跟你的部署平台綁定好，上線這件事，平台自然會幫你處理掉。

進階關卡 Advanced Gates

10:20搞懂最基礎的持續整合（CI）跟持續部署（CD）流程之後，我們最後再往下多看一步。在真實開發裡面，除了前面講的 lint、test 跟 build 這三道基本檢查之外，你的持續整合（CI）其實還可以根據產品需求，往上疊加更多進階的關卡。

10:33最常見的第一個，就是像 Playwright 這類的自動化瀏覽器測試（browser automation testing）：機器會在雲端真的把你的網站打開，模擬真實使用者從頭到尾點一遍，確認畫面沒白屏、按鈕也真的點得動。

10:45不過如果你把網站每個頁面、每個按鈕都塞進 Playwright，每次開合併請求（PR）光等測試就要超級久，開發進度會大幅降低。所以加 Playwright 有一個很簡單的原則：只有流程已經穩定，而且壞掉會直接影響核心體驗的路徑才要加，像是登入、付款，或記帳軟體的匯出報表。至於還在摸索排版的早期原型，或是隨時會大改的實驗功能，就先不用寫進 Playwright 裡。

11:08而如果你開發的是像 ChatGPT 這類的 AI 產品，比如你在記帳軟體裡加了一個 AI 理財顧問，讓使用者問：「我這個月吃飯花了多少？該怎麼省？」因為 AI 每次生成的文字都不一樣，傳統的測試（test）只會檢查一加一是不是等於二，根本測不出這段回答寫得好不好。

11:24這時候就可以在持續整合（CI）裡加上第二種武器，叫做 LLM 擔任評審（LLM as a judge）。做法是準備二十題常見的使用者提問，只要你有改到 AI 相關的提示詞（prompt）或邏輯，就讓你的 AI 顧問全部答一遍，再把這些回答連同原始帳目數字，以及你定好的評分標準，交給另一個專門當裁判的 AI 模型去打分數，檢查它有沒有算錯金額、有沒有答非所問或瞎編數字。只要通過率低於設定的門檻，持續整合（CI）就直接亮紅燈退貨。

11:49你不一定要知道所有的這些程式碼具體該怎麼一行一行寫出來，但一定要知道持續整合（CI）的工具箱裡有哪些武器，才有能力根據你的專案需求去跟 AI 溝通，叫它幫你把這些防線加上去。

兩層防線 Two Layers of Defense

12:01說到底，不管往持續整合（CI）裡塞了多少檢查，目的都只有一個：就是確保你的產品永遠處於「真的能用、體驗沒壞」的狀態才被發布出去，有問題就在持續整合（CI）這一端直接攔下來。

12:12不過最後也要提醒大家一件事：上面這些持續整合（CI）關卡不管加得多嚴格，它們能攔住的，全都是你事先定義好的問題。就像我們在 pstack 那支影片提過的，在 Lauren 的工作流程裡，持續整合（CI）全部亮綠燈其實只是一個最低底線，不代表你的產品發布出去就一定沒問題。因為真實世界是混亂的，使用者不會照著你事先寫好的測試劇本一步一步點，他們會在各種意想不到的狀態下操作你的軟體。

12:37所以她才會在持續整合（CI）全綠之上，進一步用 /create-verification-skill 建立一套讓 AI 親自操作產品的標準指南。在合併之前，再派另一批完全沒寫這段程式的獨立 AI，像真實用戶一樣進到軟體裡到處點擊驗證，錄下實機證據，確認玩不壞才放行。

12:53所以你可以把整套開發流程想成兩層防線：底層靠持續整合（CI）跟持續部署（CD）這套自動化流水線（pipeline），確保每次改動都能安全打包、順利上線；上層再用 Lauren 的方法實機驗證，去補齊真實世界的各種意外。

13:06在 AI 寫程式越來越快的時代，越來越多人的開發瓶頸變成：你有沒有足夠的品管機制去接住 AI 的產出。把這道防線建立起來，才不用每次加一個新功能就提心吊膽，也才能真正放手讓 AI 幫你把產品越做越大。

以下為譯者整理，非原片內容。

這支影片在說什麼

AI 寫完功能常說「等持續整合（CI）檢查通過再合併（merge）」，這支影片用 Gary 的記帳軟體，白話拆解這句話背後的持續整合／持續部署（CI/CD）：持續整合（CI）是開合併請求（PR）之後自動跑的一份檢查清單，持續部署（CD）是程式碼合併進主線後自動部署上線。最後提醒：持續整合（CI）全綠只是品管的底線，不是保證。

為什麼值得學

用 AI 寫程式越來越快，真正的瓶頸變成「你有沒有足夠的品管機制接住 AI 的產出」13:06。你不必會寫設定檔，但看得懂持續整合（CI）在擋什麼、看得懂 GitHub 上的綠勾和紅叉，才知道什麼時候能放心合併，也才能開口請 AI 幫你加上需要的關卡11:49。

你可以帶走的重點

1. 加一個新功能，其實有五步，其中兩步是自動的

開分支（branch） → 開合併請求（PR） → 持續整合（CI）檢查 → 合併進主線（main） → 持續部署（CD）部署01:27。前兩步和合併由你或 AI 操作；持續整合（CI）和持續部署（CD）由機器自動完成：持續整合（CI）是 GitHub 把新舊程式碼合起來做一次通盤檢查02:02，持續部署（CD）是部署平台（例如 Render）盯著主線，一有更新就自動打包上線03:03。

例子：Gary 想加「匯出月報表」。AI 在新分支寫好、開出合併請求（PR）後，GitHub 頁面底下會開始轉圈圈跑檢查；全綠才合併，合併後幾分鐘，朋友打開網頁就用得到新功能09:54。

2. 持續整合（CI）就是一份檢查清單，通常有三道基本關卡

持續整合（CI）沒有那麼玄，它就是專案裡 .github/workflows 底下像 ci.yml 這樣的檔案，寫著每次開合併請求（PR）要跑哪些指令，而且可以客製化。現在多半由 Claude Code、Codex、Cursor 這類 AI 代理幫你寫好04:02。三道基本關卡是：

  • 程式碼檢查（Lint）＋型別檢查（Typecheck）：抓 AI 圖快留下的垃圾和危險寫法，以及資料類型放錯，例如把「100 元」這種文字當數字加總04:3305:43。
  • 測試（Test）：一份事先寫好的「驗收考卷」，確認新功能沒算錯，舊功能也沒被改壞06:08。
  • 打包（Build）：先預演一次把幾百個小檔案組裝成網站，免得上線後才發現網站打不開06:58。

3. 為什麼要借一台空白電腦重跑

GitHub 內建的 GitHub Actions 每次都在雲端借一台全新的電腦，從零下載安裝再跑檢查08:02。原因是你自己的電腦早就裝了一堆舊套件，AI 用到某個套件卻忘了寫進安裝清單時，在你電腦上沒事，一上正式網站就當機08:21。空白電腦測出來的結果才準。

4. 看懂 GitHub 上的綠勾和紅叉

合併請求（PR）列表上，綠勾「3/3」代表三項檢查全過；紅叉「2/4」代表四項只過兩項08:49。點進合併請求（PR）的 Checks 分頁、再點 Details，就能看到錯誤報告；看不懂英文也沒關係，請 AI 透過 GitHub 的連接器（connectors）讀報錯、修好再推上來09:13。至於持續部署（CD），Render、Vercel 這類平台已經開箱即用，只要一開始把 GitHub 的儲存庫（repo）綁好就行10:06。

5. 進階關卡：依產品需要再往上疊

基本三關之外，持續整合（CI）還能加兩種常見的武器10:22：

  • Playwright 這類自動化瀏覽器測試（browser automation testing）：在雲端真的打開網站、從頭點到尾。但全部塞進去會讓每次開合併請求（PR）等很久，所以只加「流程已穩定、壞了會傷核心體驗」的路徑；早期原型和實驗功能先不用10:45。
  • LLM 擔任評審（LLM as a judge）：AI 的回答每次都不一樣，傳統測試只能檢查一加一等不等於二。做法是準備約二十題常見提問，改到提示詞（prompt）或邏輯時就讓 AI 全部答一遍，再交給另一個 AI 依評分標準打分，查有沒有算錯金額、答非所問或瞎編11:24。

6. 持續整合（CI）全綠只是底線：再加一層實機驗證

持續整合（CI）再嚴格，也只能攔住你事先想到的問題；真實使用者會在各種意想不到的狀態下操作12:12。講者引用 Lauren 在 pstack 的做法：持續整合（CI）全綠之後，再用 /create-verification-skill 寫一套操作指南，派完全沒寫這段程式的獨立 AI 像使用者一樣到處點、錄下實機證據，玩不壞才放行12:37。

怎麼開始

  1. 打開你的專案，看看有沒有 .github/workflows 資料夾和 ci.yml；沒有的話，請你的 AI 代理幫你建一份，至少包含 lint、typecheck、test、build。
  2. 下次 AI 說「等持續整合（CI）過了再合併」，打開那張合併請求（PR）的 Checks 分頁看一看；遇到紅叉，把 Details 的錯誤報告交給 AI 修。
  3. 列出你產品裡「壞了最痛」的兩三條路徑（例如登入、付款），問 AI 要不要替這幾條加上 Playwright 測試。
