定義與解釋 What Loop Engineering is

00:00六月初，OpenClaw 的創辦人 Peter Steinberger 發了篇 X 貼文。主要內容是說：你不應該再替 coding agent 寫 prompt，你應該設計 loop，讓 loop 去 prompt 你的 agent。

00:12差不多同一段時間，Claude Code 負責人 Boris Cherny 也講了類似的東西。他說自己不再給 Claude 寫提示詞了，他的工作已經變成寫 loop，讓 loop 來做這個工作。

00:20然後 Google 的 Engineering Lead Addy Osmani 接著又發布了一篇長文，把這件事整理成一個框架，叫 Loop Engineering。

00:29所以這支影片想跟各位聊三件事。第一，Loop Engineering 到底是什麼；第二，它和 Prompt、Context、Harness Engineering 的關係；第三，為什麼我認為不是每個人都要去做 agentic loop。

00:41那我們直接開始，先講定義。Loop Engineering 裡面的 loop，可以先理解成一個反覆循環的工作方式。在過去，你會打字和 AI 說「幫我修這個 bug」，AI 修一下、回你一段；你看完發現測試還是壞的，再說這裡不對，然後它再修，你再看。審核、給修改意見的是你本人。

00:59而 Loop Engineering 的做法是：你讓 agent 自己改程式、自己跑測試、自己讀錯誤、自己再改，直到測試過，或者連續幾次都沒有進展，就停下來回報、告訴你它做完了。

01:08審核的角色一部分由 AI 取代。你不用每一輪都自己來，而是一開始就告訴它：目標是什麼、可以用哪些工具、怎麼驗證、什麼狀況算完成、什麼狀況要停下來找人。

01:20舉個簡單的例子，你可以直接跟 agent 說：幫我做十張 YouTube 封面圖。評分標準有四個，包含能不能讓觀眾一眼看懂影片在講什麼、能不能勾起好奇心、視覺對比夠不夠強、跟影片內容符不符合。做完之後用這四個標準幫每一張打分，把沒過關的挑出來重做一版，改完再用同一套標準重新打分。這樣跑兩輪，最後把分數最高的三張發給我。

01:43像這樣只是一句完整的 prompt，但是它代表了重複觀察、執行、驗收、修正四個步驟，也是 loop 的精髓所在。

01:49和以往不同的是工作重心的改變。一直以來，我們在和 AI 協作的時候，本來就不是一次做到完美：是它寫一版，你看一下，覺得哪裡怪怪的，叫它改一版，你再看一下，它再改一版。品質是這樣慢慢從 60 分修到 100 分的。

02:06那既然這種來回修改的過程本來就會發生，為什麼一定要每一輪都由人類坐在螢幕前面按下一步呢？是不是有些檢查和修正，可以先讓 agent 自己跑幾輪？雖然它不會保證一次到 100 分，但這樣做或許可以讓 agent 第一次交到你手上的版本，是從 85 分開始。而這就是 Loop Engineering。

02:20以前，執行、觀察結果、再執行並且迭代的這個 loop 由你負責推動；但 Loop Engineering 強調的是，由使用者設計這個 loop，然後讓 agent 自己推動。

名詞之間的關係 How the terms relate

02:30講完定義後，我想要名詞比較一下。因為 AI 圈子這一兩年真的蹦出太多名詞了，所以 Loop Engineering 和我們前面講過的其他名詞是什麼關係、又有什麼差別呢？

02:38一開始的 Prompt Engineering 強調跟 AI 溝通的技巧：要使用者把話說清楚，你要 AI 幫你做什麼、語氣、格式、限制、輸出長什麼樣。講得越清楚，結果越符合你的期望。

02:50Context Engineering 則是強調在對的時機給到 AI 正確、而且不多不少的資訊，讓 AI 有足夠的背景知識可以幫你做事。

02:57後來 AI agents 的觀念興起，人人都想要一個貼身的 AI 助理，幫忙管理生活大小事。但我們發現，模型本身再聰明，如果沒有一個可靠的環境，AI 就無法在現實生產環境中穩定運作。所以有了 Harness Engineering。

03:11在 Harness Engineering 中，我們設定規矩和邊界。可以想像你是老闆，要讓員工有效率工作，不能只叫他努力，還要給他辦公室、工具、流程和權限。關於 Harness Engineering，我也有做一支教學影片，有興趣的朋友可以去看看。

03:28而今天講的 Loop Engineering，則是專注在把 human in the loop 變成 agent in the loop。從過去的人類審核後給 feedback，Loop Engineering 強調的是：人類把自己提供 feedback 的邏輯標準化，或者說講清楚，讓 agent 自行 review 並迭代。

啟停條件 Trigger and verifiable goal

03:42Loop 的形成，可以從兩個問題去決定：第一個是什麼時候開始，第二個是什麼時候停止。而這兩個問題分別對應兩個名詞，就是 trigger 和 verifiable goal。

03:51Trigger 是觸發機制，決定這個 loop 什麼時候開始。它可以是一個事件，比如 GitHub 上有人開了一個 PR，agent 自動開始檢查；它可以是一個排程，比如每天早上跑一次資料整理、每 30 分鐘檢查一次任務狀態；它也可以由你手動啟動——你今天覺得這件事值得跑，就按下去。

04:10而停下來靠的是 verifiable goal，也就是可驗證的目標。白話講，就是 AI 做到什麼程度時，系統可以判斷它完成了，然後把這個 loop 停掉。Verifiable goal 又可以拆成兩個問題：第一，什麼叫做完成？第二，AI 要怎麼檢查自己完成了？

04:26在 coding 任務裡比較好理解。比如所有測試通過、TypeScript 沒有報錯、lint 沒有違規、build 成功。這些判斷很乾脆，機器可以檢查。但很多任務沒那麼乾淨：比如你叫 AI 寫一篇文章，什麼叫寫好了？你叫 AI 改個產品頁，什麼叫改好了？把抽象的概念變成清楚的標準，是大多數人在實作時比較常遇到的卡點。

04:46舉例來說，如果你希望 AI 幫你把文章改得更順，比較常見的做法有兩種。一種是 rubric 評分：先選定幾個面向，例如風格人設、語法用詞、內容主題，再替每個面向寫出分級定義。以風格人設為例，滿分五分代表完全符合你設定的人設、用詞語氣一致；三分代表有點像，但偶爾會出戲；一分則代表根本沒有你的風格在裡面。關鍵在於每個分數都要定義清楚你的評分標準，AI 才會有依據可循，而不是隨意給分。

05:17另一種方法是二元檢查清單：把品質拆成一串 yes or no 問題，像是開頭三句有沒有抓住重點、有沒有冗詞贅字、專有名詞有沒有用錯。這種方式比打分數更穩定，也更容易判斷有沒有過關。不論用哪一種，最後都要收斂成一個明確的完成條件，例如三個面向的 rubric 都達到四分以上，或檢查清單全部通過，才算真正的完成。

判斷任務是否值得 Which tasks are worth a loop

05:39那什麼樣的任務值得做 loop 呢？每次 AI 圈出現一個新詞，很多人會立刻把它用到所有地方。尤其你看到一些高手在展示四、五個 agent 同時跑，一個 manager agent 指揮一堆 helper agents，整套看起來像一個 24 小時不睡覺的小公司，你就很容易心動，也想自己搞一個來玩玩。

05:55但對於所有新功能，我建議的 approach 都是：先去了解這個功能運作的底層邏輯，然後再去思考自己的工作流有沒有可以套用的地方。通常一半以上的功能對我們來說都沒有用武之地，因為這些功能的設計師，以及這些功能的需求來源，可能大多數來自 OpenAI 跟 Anthropic 的工程師；而這些人幾乎是世界上最頂尖的人才，他們用得到的東西，我們不一定用得到。因此絕對不要盲目跟風。

06:18一個任務值不值得做成 loop，我會先看三件事。第一，它是不是會重複發生。如果是一次性任務，直接寫一個一般的 prompt 就好了，比如你臨時要查一個錯誤訊息，或者改一段小文案，沒必要為它設計一整套 loop。Loop 對那些會反覆發生、每次流程差不多、但每次細節又不完全一樣的任務來說，會比較有價值。

06:40第二，完成標準清不清楚。這是最關鍵的：你要能講出什麼叫這件事做完了。可以是把網站部署到指定網域，並確保載入時間低於兩秒；或在程式碼開發時，修復所有 CI 錯誤，直到狀態變回綠色。針對較抽象或者主觀的東西，可以用我剛剛講到的 rubric 或者 yes or no 方法來寫驗收標準。

06:59第三，token 的花費你是否扛得住。Loop 不是免費的：每跑一輪，AI 要讀東西、想下一步、呼叫工具，可能還要再請 reviewer 檢查。你原本手動 prompt 三次就能解決的事，如果做成 loop，跑了 20 輪還沒有停，這個帳單會非常有教育意義——教育你下次不要這樣。

07:17除了以上三點，另外還有一種情況是：你想快速做一個 demo，核心 feature 的驗收標準很清楚。比方說你就是希望做一個網站，讓使用者可以在上面搜尋到最新的新聞，其他細節先不追求完美。這時候可以用 loop 先把主功能跑出來，其他細節再由人接手調整。

07:36所以普通人學 Loop Engineering，第一步不是馬上自己搞一個，而是怎麼判斷哪些需求可以用上、有沒有想清楚最後的目標。但坦白說，比起 agentic loop，我自己還是更喜歡 human in the loop。因為大多數人其實不需要一個 AI 不眠不休地跑 27 小時，還有剛剛說的成本問題。如果我像 OpenAI、Anthropic 的工程師一樣，有接近無上限的 token 預算，我也會一直用；但一般人都沒有無上限的預算，所以 human in the loop 往往更準、更有效率，也更便宜。

失控風險 How loops go wrong

08:02最後是 loop 最大的問題：人很難一次把所有偏好、細節、例外狀況都講完。所以你讓 agent 自己迭代一整個晚上，如果一個不小心，可能會偏到十萬八千里遠。

08:11Loop Engineering 真正的難點是：如果標準不清楚，loop 會跑出三種問題。第一種問題是，它不知道什麼時候該停。你跟 AI 說「幫我把這個 app 優化一下」，它改了一點、跑一下，看起來還能再優化，再改一點，又覺得還能再改。因為你沒有告訴它什麼是所謂的優化——是前端視覺，還是後端回覆的速度。沒有定義清楚，它就不知道終點在哪裡，最後就變成 token 黑洞。

08:38所以第一條規則是：一定要有 hard stop，也就是硬性的停止條件。最多跑幾輪、最多跑多久、最多花多少 token；三輪都沒有進展，就停下來回報。這些限制聽起來保守，但它們正是 loop 不失控的關鍵。

08:52第二個問題是，它可能把不該碰的東西也改掉。你說優化效能，它可能開始重構一堆本來不該碰的架構；你說改善 UX，它可能順手把元件拆掉重做；你說修 bug，它可能為了讓測試過，改掉一堆旁邊的東西。

09:08所以第二條規則是要定義邊界。你不能只說測試要過，你還要說：不能刪測試、不能改公開 API、不能動資料庫 schema、不能碰某些核心檔案。

09:18最後一個問題是 verifier 失效。Loop 之所以能停下來，是因為它有某種驗收機制。目標模糊到不能用 verifier agent，就只能用很主觀的方式去判斷，比方說它可能會問自己：「這樣改完後看起來是不是差不多了？」而這樣做的壞處是非常不可控。

09:33所以第三條規則是：驗收標準要盡量變成可以檢查的東西。測試、效能數字、審稿清單，都比「看起來不錯」具體。真的很主觀的任務，也要拆成剛剛講到的 rubric，比如語氣是否符合、主題有沒有偏、格式有沒有對。反正不管你打算怎麼驗收，就是要想辦法讓它驗得出來。

09:51但這裡也要小心：不是有分數就代表客觀。如果你叫 AI 做任務，然後 AI 自己評分，那就是球員兼裁判。所以比較好的做法是把產出跟檢查分開：一個 agent 負責產出，另一個 agent 負責檢查；或者乾脆在關鍵節點（node）保留 human in the loop。不然從指標上看測試過了，但實際上產品沒有變好，反而更糟。

10:12總結來說，Loop Engineering 的核心不是讓 AI 自己跑，而是你能不能把一個模糊意圖，翻譯成 AI 可以執行、可以驗收、可以停止，而且不會鑽漏洞的條件。

10:22如果你現在手上就有一個任務，但不知道可不可以把它做成可控的 loop，我在 Patreon 有撰寫完整的文章和提示詞模組，幫你理清你手頭的 project 是否適合做成 loop；也會提到，除了 trigger 和 verifiable goal 之外，loop 的六大骨架，讓你可以自己動手搭建一個自己的 loop。有興趣的可以在影片下方資訊欄找到連結。

成本問題 Cost, and a closing caution

10:40那我們繼續。最後想聊一下 loop 最現實的問題，就是成本。Loop 迷人，它會讓人覺得按一下按鈕後，事情就會自己往前走。但每一次自動往前走，背後都有成本：它要讀 context、要呼叫工具、要跑測試、要解讀錯誤、要重試（retry）。你如果再加 reviewer agent、sub agent、多輪驗證，成本就會不斷往上疊加。

11:02連 Google 的 Engineering Lead Addy Osmani 都說，目前 Loop Engineering 還處於早期階段，他保持謹慎的態度，必須非常注意 token 的成本。更何況就像我剛剛提到的一樣，絕對不是每個人都需要一整套 multi-agent 協作系統，也不是每個任務都值得用 loop 燒。事實上我覺得，至少在這個時間點，大多數的人都不會需要這個功能。

11:20所以如果真的想玩玩看，我建議你可以先從一個小任務開始：做一個範圍小、目標清楚、工具有限、停止條件明確的 loop。比如每天整理一次固定資料夾、針對某個測試項目進行修復，或者針對一篇文章跑固定的品質檢查 checklist。這些小型的任務不會讓成本失控，但也會讓你體驗到 loop 的精髓：像是要怎麼定義目標、怎麼設計驗收、怎麼控制權限、怎麼讓 AI 在正確的地方停下來。

11:43Loop 把人的工作往上移。以前你是 prompt 操作者，一輪一輪地跟 AI 對話，看它做了什麼再決定下一步；現在你更像是一個系統設計者，你要定義目標、設計驗證、設定邊界、控制成本。你用力的地方不一樣了。

11:58Loop Engineering 的重點不在於 AI 能不能自己做事，而是你有沒有能力定義一件事應該怎麼被完成。如果把 Loop Engineering 往更高階推，可能會走向所謂 software factory，也就是軟體工廠：工程師不再只是寫一段程式，而是在設計一套可以生產、測試、修正、部署軟體的系統。就像業界在研究讓 AI 模型更會自我提升一樣。但回到現在，這對我們一般人來說確實太遙遠了。

12:18就像我這支影片中不斷提到的：大多數人並不需要一個 agent 不眠不休地幫你跑 27 小時，而是當 agent 跟你說他做完的時候，你不用再來回調整，可以直接把成果發給老闆。

12:33所以這就是我對 Loop Engineering 的看法。不論這個觀念有沒有出現，做一個好 loop 的能力，也是現在 AI 工作者的必備條件：包含讓 AI 知道什麼時候開始、知道什麼叫完成、知道哪些事情不能做、知道失敗時要停下。而我們大多數人並不需要去追求這些最新的功能、技術，更不要因為很多人在討論，所以逼著自己去用。因為到頭來，最新的方法不一定是最好的方法，能解決你問題的方法才是好方法。

12:58那以上就是今天的內容。各位喜歡的話，記得幫我按讚、追蹤加分享，這是我持續創作下去的動力。我是 Gary，我們下次見。

以下為譯者整理，非原片內容。

這支影片在說什麼

這支影片說明 Loop Engineering 不是叫你從此不寫提示詞，而是把「執行、檢查、再改」這條本來由人推動的迴圈，改成由你先設計好，再讓 AI 代理自己跑。講者從 Peter Steinberger、Boris Cherny 和 Addy Osmani 的討論出發，釐清它和 Prompt、Context、Harness Engineering 的差別，拆解 trigger 與可驗證目標，並提醒：不是每個任務都值得做成 loop，也不是每個人都需要一套不眠不休的多代理系統。

為什麼值得學

很多人一看到高手同時開四、五個 agent，再加一個 manager 指揮一堆助手，整套像 24 小時不睡覺的小公司，就想照做。可是迴圈每走一步都要讀脈絡、呼叫工具、跑測試，token 會往上疊；標準一寫不清楚，它還可能停不下來、改到不該碰的地方，或用「看起來差不多了」這種主觀感覺當驗收。先學會判斷「這件事值不值得做成 loop」，比急著上線一套自動化更有用。

你可以帶走的重點

1. Loop 的精髓，是把本來就會發生的來回修改，提前交給 agent

和 AI 協作本來就很少一次到位：它寫一版，你看，覺得怪，再叫它改，品質往往是從 60 分慢慢修到 100 分。Loop Engineering 問的是：既然這條路本來就會走，為什麼每一輪都要人坐在螢幕前面按下一步？你先講清目標、可用工具、怎麼驗證、何時算完成、何時該停下來找人，然後讓 agent 自己改程式、跑測試、讀錯誤、再改。它不保證一次到 100 分，但第一次交到你手上的版本，有機會從 85 分開始。

一句「做十張 YouTube 封面，用四個標準打分，沒過關就重做兩輪，最後交分數最高的三張」，看起來只是一則 prompt，其實已經包含觀察、執行、驗收、修正。以前這條 loop 由你推動；現在是你設計，agent 自己推動。

2. 四個名詞不是互搶位子；Loop 管的是「誰來迭代」

Prompt Engineering 是把話說清楚：要做什麼、語氣格式、限制和輸出長什麼樣。Context Engineering 是在對的時機給剛好足夠的資訊。Harness Engineering 是可靠的工作環境與權限（harness），像給員工辦公室、工具和流程，而不只是叫他努力。Loop Engineering 則把焦點放在：把過去「人審核後給 feedback」的邏輯寫清楚，讓 agent 自行 review 並迭代，也就是從 human in the loop 走向 agent in the loop。

這些層是疊加的。有了 loop，不代表 prompt 或 harness 沒用了；你還是要把目標講清楚，也還是要給它能跑測試、讀錯誤的環境。

3. 一條能停下來的 loop，靠 trigger 和可驗證的目標

什麼時候開始、什麼時候停止，分別對應 trigger 和 verifiable goal。Trigger 可以是事件（例如 GitHub 上有人開了 PR，agent 自動開始檢查）、排程（每天早上整理資料、每 30 分鐘看一次任務狀態），或你手動按下去。停下來則要靠可驗證的目標：系統要能判斷「做到什麼程度算完成」，而不是靠感覺。

寫程式時，測試通過、TypeScript 沒報錯、lint 沒違規、build 成功，機器就可以檢查。寫文章、改產品頁就沒那麼乾淨。這時可以把抽象品質寫成 rubric（例如風格人設、語法用詞、內容主題，每一級分數都有定義），或拆成 yes／no 檢查清單。兩種做法最後都要收斂成一句明確的完成條件，例如三個面向都達四分以上，或清單全部勾過。

4. 不是每個任務都值得做成 loop；先看重複、標準和帳單

講者建議，面對新功能先弄懂它的底層邏輯，再問自己的工作流用不用得上。很多功能其實是為 OpenAI、Anthropic 那些幾乎有無上限 token 預算的工程師設計的，他們用得到的，我們不一定用得到。

  • 會不會重複發生。臨時查一則錯誤訊息、改一小段文案，寫一則普通 prompt 就好，不必為一次性任務設計整套 loop。比較有價值的，是會反覆發生、流程差不多、但每次細節又不一樣的工作。
  • 完成標準清不清楚。你要能講出什麼叫「做完了」，例如網站部署到指定網域且載入低於兩秒，或 CI 全綠。主觀任務就用 rubric 或是非清單來寫驗收。
  • token 成本扛不扛得住。每跑一輪都要讀資料、想下一步、呼叫工具，可能還要再請 reviewer。原本手動三次就能解決的事，做成 loop 跑了 20 輪還不停，那張帳單會很有教育意義。

若你只是想快速做一個 demo，核心功能的驗收很清楚，也可以先用 loop 把主功能跑出來，細節再由人接手。講者自己仍更喜歡 human in the loop：大多數人並不需要一個 AI 不眠不休跑 27 小時，人在迴圈裡往往更準、更有效率，也更便宜。

5. 標準一不清楚，loop 會跑出三種問題；用三條規則卡住它

人很難一次把所有偏好、細節和例外都講完。讓 agent 迭代一整晚，一個不小心就可能偏到十萬八千里遠。

  • 停不下來。你只說「把這個 app 優化一下」，它就會改一點、再改一點，因為你沒定義優化是指視覺還是後端速度，最後變成 token 黑洞。規則是一定要有 hard stop：最多幾輪、多久、花多少 token；連續三輪沒進展就停下來回報。
  • 亂改邊界。你說優化效能，它可能開始重構不該碰的架構；你說改善 UX，它可能把元件拆掉重做。規則是寫清邊界：不能只說測試要過，還要說不能刪測試、不能改公開 API、不能動資料庫 schema、不能碰某些核心檔案。
  • 驗收失效。目標模糊到只能問「看起來是不是差不多了」，迴圈就不可控。規則是把驗收變成可檢查的東西：測試、效能數字、審稿清單都比「看起來不錯」具體。真的很主觀，也要拆成 rubric。

有分數也不等於客觀。叫同一個 AI 又做又打分，就是球員兼裁判。比較好的做法是一個 agent 負責產出、另一個負責檢查，或在關鍵節點（node）保留 human in the loop。否則指標上測試過了，產品卻可能變得更糟。

6. 核心不是讓 AI 自己跑，而是你能不能定義「這件事該怎麼被完成」

Loop 迷人的地方，是按一下按鈕後事情好像會自己往前走；但每自動走一步，背後都要讀 context、呼叫工具、跑測試、解讀錯誤、重試（retry）。再加 reviewer、子代理（sub agent）和多輪驗證，成本就會不斷疊加。連 Addy Osmani 都說，這件事還在早期，必須非常注意 token 成本；不是每個人都需要一整套 multi-agent 協作系統，也不是每個任務都值得用 loop 燒。

若真的想試，先做一個範圍小、目標清楚、工具有限、停止條件明確的小 loop：例如每天整理固定資料夾、修某一項測試，或對一篇文章跑固定的品質檢查清單。這不會讓成本失控，卻能練到定義目標、設計驗收、控制權限，以及讓 AI 在正確的地方停下來。

人的工作因此往上移：以前是 prompt 操作者，現在更像系統設計者。若再往更高階推，可能走向 software factory（軟體工廠），可是對現在的一般人來說還太遠。大多數人需要的不是一個跑 27 小時的 agent，而是當它說做完的時候，你不用再來回調整，可以直接把成果交給老闆。最新的方法不一定是最好的方法；能解決你問題的方法，才是好方法。

怎麼開始

  1. 先挑一件你會反覆做、而且講得出「怎樣算做完」的小事，不要一開始就做 24 小時的多代理小公司。寫下目標、可用工具、驗收方式，以及最多跑幾輪、花多少 token、連續沒進展時要不要停。
  2. 完成標準盡量寫成機器或另一個 agent 檢查得到的東西：測試是否通過、清單是否全勾、rubric 是否達到指定分數。不要只寫「優化一下」或「看起來不錯」。產出和評分不要讓同一個角色兼任。
  3. 明確寫出不能碰的邊界：不能刪測試、不能改公開 API、不能動資料庫 schema、不能重構不相干的檔案。跑起來之後看帳單與結果，再決定要不要擴大範圍，或乾脆回到 human in the loop。
