例子：Nate 從零開始時，會說「給我 11 種不同的字型、顏色與視覺風格」；看完再說「第一個和第三個各有一點喜歡，請依這兩個再給我五個」01:46。簡報也一樣：先探索視覺風格，因為整份做完才發現不喜歡，令牌（token）就得再花一次04:32。

2. 為什麼 Claude 會有「Claude 味」，又怎麼對付

Nate 的解釋是：Claude 每次接到任務都像第一次，它很用力想「發明最厲害的視覺風格」，結果每次都落在同一組選擇（襯線字體、米白底、橘色、卡片邊緣的色條），自己卻覺得完全原創19:08。他們的對策是在 Claude Design 的提示詞（prompt）裡直接寫出模型的失敗模式：「你特別容易偏向這兩種字型和兩種顏色，除非使用者要求，否則不要用」。他說，因為模型根本不知道自己有哪些偏見，這樣做效果很好19:39。

長期的解法在你這邊：和 Claude 一起為自己的產品或品牌建立識別，或直接帶入既有的品牌規範，就不必擔心模型在沒有素材時的預設傾向20:55。

3. 從程式碼出發，設計稿與實作不會脫節

已經有產品時，Nate 的做法是讓 Claude 讀程式碼庫（codebase），照程式碼把現有畫面重建在畫布上，再從那裡「即興發揮」出新版本。他說程式碼才是唯一可信的依據（source of truth），以前用舊式設計工具得手動截圖重做；現在要設計時才重建一次，不長期維護畫布檔02:1202:4117:19。

因為設計是在連著程式碼庫的 Claude Code 工作階段（session）裡做的，要實作時只要說「開始做」，它就知道確切的樣式、尺寸、字型與版面，轉譯幾乎沒有損失08:33。

4. 回饋可以很隨便，但要保留多個方向

Nate 的回饋像「後座指揮」：只給高層次的指示，不必寫完美的提示詞（prompt）。他會把探索過的所有版本留在畫布上，需要時叫 Claude 複製某個版本再改（例如「做一個更密的卡片清單版」），舊版留著比較。他現在也常用語音筆記，說「亂講一通」反而是最快把想法倒出來的方式07:4309:3910:24。手機上不能直接編輯，但可以留言、操作互動式原型（interactive prototypes）10:45。

5. 試算表變儀表板：成果物（artifact）＋連接器（connector）

示範：把紐約地鐵（MTA）每日搭乘人次的大型 CSV 放進 Google Sheets，用 Google Sheets 的連接器，只對 Claude 說「用這個做一個儀表板」。Claude 先說明數字只是已儲存的副本，不會自動更新，再改成即時讀取。Nate 說這就是接 BigQuery、Amplitude 這類真實資料來源時的做法23:0123:52。

他們內部大約六到八個月前就不再用現成儀表板工具，而是直接叫 Claude 透過模型上下文協定（MCP）抓資料、寫出符合需求的畫面。「來源模式（sources mode）」可以點一個數字，看它從哪裡來、用了什麼程式碼；懂資料的人可以藉此檢查數字是不是你以為的那個來源23:0124:43。Peter 的建議是：想看洞見時，不要指定得太死，反而會得到驚喜25:35。

6. 做動畫：先分鏡、先選風格，再用「人的速度」修

先花很少的令牌（token）看分鏡和風格，再決定方向。Nate 的看法是：現在的動畫「不算差，但也不算好」，要花很多功夫調整。最常見的毛病是 Claude 讓畫面上同時有很多東西在動，它沒有真正體會人類眼睛一次只能看一個地方，所以要在提示詞（prompt）裡提醒：文字要留足閱讀時間、下一個動作要出現在視線所在的位置26:5028:56。

修細節時用留言工具：直接在影片時間點或畫布位置點一下，說「這裡文字重疊」，比寫「第 17 秒左上角那段」快很多30:21。

7. 把做法存成技能（skill），再用「臨時評估」測它

Nate 做了一個專門做 Anthropic 風格宣傳短片（sizzle reel）的技能（skill）：他把一批內部發表影片放進 Google Drive，請 Claude 分析畫面、停頓時間並寫下來。這個技能在公司內很受歡迎，大家用它為點子造勢31:26。

測試技能的方法：請 Claude 開幾個全新的工作階段（session），只給技能和一句提示詞（prompt），例如「為模型選擇器做一支宣傳短片」，再自己看輸出。他說這是一種臨時湊出來的評估（ad hoc eval），因為為好的動態設計寫評估，比直接看幾個例子更費工32:4833:44。

8. 評估怎麼寫：是／否比一到五分好用

Nate 說，分級評分就像設計員工績效考核：想清楚、講清楚就行。但設計本身很難自動評估，因為如果你認為模型沒有出色的品味，就不能讓它主觀評判設計好不好；他們只評估基本項目，其餘靠人讀對話紀錄、看輸出、再修改34:1235:22。

9. 工作方式：先獨立、再併回；一個長對話勝過很多小對話

Claude Design 先做成獨立產品，是因為能快速迭代、掌握整個技術堆疊，不必擔心影響核心產品；等到使用者問「為什麼是另一個工具、手機上為什麼不能用」成為最大問題，再併回主產品。他們的原則是：不因「必須整合」而擋住新功能，但成功就要併回去13:2218:16。另外，Claude Design 預設會先問大約八個問題，Nate 說大家很愛被問，這比自己想「設計師會問我什麼」容易得多16:37。

他的大型設計專案通常只開一個 Claude Code 執行緒（thread），讓它啟動子代理（sub-agents）；有一次單一對話累積了 36 個設計成果物（artifact），不算理想，但共用脈絡（context）很省心。他也常用 Claude Tag（Anthropic 的 Slack 整合）：把它當成「同一個人」，不去管脈絡37:4738:55。

10. 品味不會消失，但會從「精緻」變成「真實」

Nate 認為，AI 做出雷同、濫作（slop）的輸出（例如到處可見的 ChatGPT 熟食店貝果廣告）會減少，模型會越來越多樣；但當一個人真的有話想說，那份心意仍會傳達出來。他預期未來的品味比較像「真實感」，像手寫、像他現在反而更重視電子郵件裡的錯字，因為那是「有人真的花時間打」的證明35:4736:57。

怎麼開始

  • 第一次先要很多：下次請 Claude 設計時，同時給它截圖、參考頁面和過往作品，並要求 10 種風格不同的選項，再挑喜歡的混搭01:46。
  • 把「你的老毛病」寫進提示詞（prompt）：例如「不要預設使用襯線字體、米白底、橘色與卡片邊緣色條」，並說明除非我要求才可使用19:39。
  • 已有產品就先重建：讓 Claude 讀程式碼庫，把現況放到畫布上，再從那裡設計；不必維護長期的設計檔02:12。
  • 做影片或動畫前先要分鏡與三種風格：挑好再做，並提醒 Claude 留時間給人閱讀26:50。
  • 評估先從是／否開始：寫成可以直接回答「是」或「否」的問題，例如「有沒有文字重疊」34:12。
