開場：一個太簡單的技巧爆紅 A too-simple technique goes viral

00:00有一個技巧我已經用了好一陣子，一直覺得它太無聊、太理所當然，不值得發文。後來這個星期，我帶的梯次班（cohort）有一堂答疑時段（office hours），我把它示範出來，大家都說：「哇，這真的很酷，我從沒想過可以這麼簡單。」然後我把它發到 Twitter 上，結果整個爆紅。所以顯然這是大家需要聽聽的東西。

00:19這個技巧解決的問題是：你要怎麼同時在多個儲存庫（repo）裡和 AI 代理一起工作？那我們就來把它設定起來。

多儲存庫的 AI 代理問題 The multi-repo agent problem

00:27假設你的組織長這樣，大多數組織都是這樣：有很多不同的儲存庫（repo），各自負責不同的事。有一個是店面前台（storefront），一個是付款 API（payments API），一個是管理後台（admin dashboard），另外還有 20 個你偶爾需要進去看看的儲存庫（repo）。

00:45如果你只需要改其中一個儲存庫（repo），這很容易，直接在 storefront 裡執行 AI 代理就好。就算你在 storefront 工作時，發現也得改付款 API，也還算容易，因為你可以讓 AI 代理同時在多個目錄裡工作。這代表你最後會在 Acme storefront 裡有一個合併請求（pull request），在付款 API 裡有另一個合併請求（pull request），而且都來自同一個工作階段（session）。

01:07這樣沒問題，也行得通，但問題在於：那些資料、引導檔案（steering files），還有你想讓 AI 代理在每一個工作階段（session）都擁有的東西，該怎麼處理？

01:18常見的情況是，你的 skill（技能）、工具（tooling）、AGENTS.md，甚至 wiki 連結之類的東西，全都在多個儲存庫（repo）裡各複製一份。這代表每次你啟動 AI 代理的工作階段（session），都能用到這些東西。所以從 storefront 啟動，你還是會有同樣的 skill 和工具（tooling）。但這是個很大的痛點，因為你得讓所有這些 skill、所有這些工具（tooling），在不同儲存庫（repo）之間保持同步，而且可能是 30、40 個儲存庫（repo）。

01:44你也可以把這些 skill 和工具（tooling）放在每個人的本機，也就是使用者目錄（user directory）裡，這樣每一個儲存庫（repo）都能用到。但因為它對使用者來說是看不見的，所以不會隨著時間更新，很可能會落後於全域設定。而且我把使用者目錄看成是使用者可以依自己的工作方式調整設定的地方，而不是依團隊希望的方式。

02:12所以這些解法沒有一個特別讓人滿意，也就是說，在多儲存庫（multi-repo）環境工作的人覺得自己沒有好的選擇。

解方：home repo The home repo solution

02:19所以我提出的解法叫做 home repo。這是我用了一陣子的技巧：我只有一個儲存庫（repo），那就是「家」，我所有的 skill、所有的引導檔案（steering files）、一個 wiki，還有一大堆自訂工具（custom tooling），全都放在這一個儲存庫（repo）裡。

02:34這代表每當我執行 AI 代理，我永遠是在 home repo 裡執行。於是在 home repo 裡運作的 AI 代理（home repo 本身就像一般的儲存庫〔repo〕），可以連到 storefront 和付款 API，同時跨很多不同的儲存庫（repo）作業，並把它需要的所有脈絡（context）拉進來。

我的 home repo 導覽 Tour of my home repo

02:53你大概在想：可以看看你的 home repo 嗎？好，就是這個。這裡最需要注意的，當然是這裡面的 CLAUDE.md（等一下會講到），還有最上面關鍵的 skill，也就是 .claude/skills。這些是私有的 skill，也就是出於某些原因我不想公開發布的 skill，因為它們非常好用，而且對我的事業非常敏感。這代表這些 skill 在每一個工作階段（session）都能用。

03:22所以如果你的組織有一份想加入的 skill 清單，就該把它們加進這裡的 home repo。

03:28這裡也是你可以用有版本控制的方式設定組態的地方。所以如果你在這裡一致地運行同一個 AI 代理，你的 settings.json 裡的設定，可以立刻擴散到整個組織。

03:40主要的結構性內容來自這裡的 CLAUDE.md，或是 AGENTS.md。在裡面你可以看到，指向我日常會碰到的所有重要儲存庫（repo）的導覽指標（navigation pointers）。例如，如果有 skill 要改，就在 repos/ai/skills；我的課程影片管理器（Course Video Manager，CVM）有要更新的東西，那大概是我提交（commit）最頻繁的儲存庫（repo），就放在那裡；還有 Cohort 005 專案、AI 程式開發速成班（AI coding crash course）儲存庫（repo）的東西也一樣。

04:09所以我說的從 home repo 連到其他儲存庫（repo）的連結，做法就是這樣：就只是 AGENTS.md 裡的一個路徑。在一台全新的機器上，AI 代理會做的是：如果 Sandcastle 不在這個位置，就把它 clone 下來。如果同時有好幾個 AI 代理在跑，它就會在同一個儲存庫（repo）裡使用工作樹（worktree）。所以基本上是零設定，自己就能運作，只是到最後，你得像平常一樣做一些工作樹（worktree）清理。

04:37如果我想再加一個儲存庫（repo）到清單裡，只要編輯 AGENTS.md，它就自動納入同一套設定。

擴充規模，以及為什麼不用單一儲存庫 Scaling and why not monorepos

04:42這個做法大概可以撐到 20、30、40 個儲存庫（repo），或許更多。但撐不到 400 個。遇到那種情況，我會加一點漸進式揭露（progressive disclosure）：在你的 AGENTS.md 裡，不要直接連到一個個儲存庫（repo），而是寫「這些是前端儲存庫（repo），這些是後端儲存庫（repo），這些是內部工具用的內部儲存庫（repo）」，然後在那些檔案裡，再連到各個儲存庫（repo）。這樣 AI 代理光靠簡單的檔案系統手法，就能找到對的儲存庫（repo）。

05:13順帶一提，我必須說，我很愛單一儲存庫（monorepo）。如果這一切都能放在一個儲存庫（repo）裡，我就會這麼做。我以前在 Vercel 擔任 Turborepo 的開發者關係（DevRel），所以我非常熱愛單一儲存庫（monorepo）。但你不是總能做到，尤其是有些儲存庫（repo）必須公開、有些必須私有的混合情況。所以我的建議是：如果你能把這一切搬進單一儲存庫（repo），那太好了。如果不行，而且多半是因為缺乏政治意願（political will）而做不到，那 home repo 就是正確的做法。

個人 wiki 與自訂工具 Personal wiki and custom tooling

05:43關於 home repo 還有一件事要說：我發現自從採用 home repo 之後，我為 AI 代理打造的工具（tooling）可以大膽很多。我把我的 home repo 叫作我的個人 wiki（personal wiki），因為它是一個龐大的 wiki，裝著所有對我的事業比較敏感的資料。它放在這裡的 wiki 資料夾裡，基本上是一個 LLM Wiki，Karpathy 風格，裡面有一大堆 Markdown 檔，內容是我的觀眾覺得很酷、覺得有意思的東西。

06:11我會在之後的影片講我怎麼產生這個 wiki、怎麼讓它保持最新，因為大家對這個點子很著迷。但總之它對我的事業非常重要，因為我可以查詢它、從中取出非常豐富的資料，用在課程製作、內容製作等等。而且因為有了這個 home repo，它自然就成了放這個 wiki 的明顯位置。

06:34我也一直把工具（tooling）這個重點埋著沒講，因為工具（tooling）絕對是關鍵：給你的 AI 代理自訂的工具，讓它能和你事業用到的東西介接。如果我在我的個人 wiki 目錄裡執行 wiki help，可以看到有一大堆東西，整合了 Gmail、Slack、Discord、YouTube、GitHub、Google 日曆（GCal）、AI Hero，以及用 Cold Turkey 來處理我的封鎖設定（blocks）之類的。我還有發布一次性 HTML 報告、新增到 Buffer 的功能。

07:01這些東西能在個人 wiki 裡自然長大，加進這個我能在其上建造的龐大生態系，是因為我把它全部集中，而且永遠在同一個地點執行。這代表我可以做很瘋狂的事，例如說：好，去查 Discord 上的這則訊息，然後到速成班（crash course）儲存庫（repo），做個修正，用你已經有的所有現成 skill。接著，你可以用我放在課程影片管理器（Course Video Manager）裡的 CVM skill，它就在這上面某處，去實際編輯課程來完成修正。

07:42換句話說，home repo 成了把你事業各個部分串起來的工具（tooling），不只是程式碼，也讓 AI 代理能取用非常豐富的資料來源和工具，做出更好的工作。

如何自己建一個 How to set one up

07:56那你要怎麼替自己設定一個？我寫了一篇文章，叫 The Home Repo Pattern（home repo 模式）。文章裡我放了一段提示詞（prompt），你可以拿來設定。它基本上就是不斷追問（grilling）你自己的設定，查看你需要關心的所有儲存庫（repo），然後開始把東西搬進 home repo。當然，連結在下方。

08:19順帶一提，如果你喜歡我在這裡分享的東西，你會很喜歡我的自學式 AI 程式開發速成班（AI coding crash course）。如果你想了解 AI 代理，也許從沒試過使用 AI 代理，或只是覺得自己在這個令人興奮的大世界裡落後了，這門課是最好的入門。

08:35總之，這就是 home repo，一個我原本覺得太基本、不值得發的模式，但現在講過之後，我發現它其實解決了很多人真的遇到的問題。所以好好享受，享受把它設定起來，也享受你的新家，我想。幹得好，我們下支影片見。

這支影片在說什麼

公司或個人的專案常常拆成很多個「儲存庫（repo）」，可以想成很多個各自獨立的專案資料夾（下文多半簡稱「專案」）。Matt Pocock 分享一個很簡單的做法：另外開一個專屬的「家」，叫 home repo，把 AI 代理要用的技能（skill）、規則檔（引導檔案，steering files）、筆記和工具（tooling）全放在這裡，每次都從這個家出發去操作其他資料夾。他說這個做法太簡單，原本覺得不值得發文，結果在 Twitter 上爆紅00:00。

為什麼值得學

只要你同時用 AI 代理處理好幾個專案，就會遇到同一個麻煩：每個專案都有一份相同的規則和工具，改一處就得改所有地方，久了一定不同步。這支影片的做法不用買新軟體，也不用重整程式碼，只是改變「從哪裡開工」和「怎麼寫一份導覽清單」。就算你不寫程式，這個「把共用的東西集中在一處、其他地方只放指路牌」的想法，也能套用在文件、範本和工作流程上。

你可以帶走的重點

1. 問題：同樣的東西複製在每個專案裡，很難維持一致

講者舉的例子是一家公司有店面前台、付款系統、管理後台，再加 20 個小專案。要讓 AI 代理在每個專案都有同樣的 skill 和工具（tooling），最直接的方法是每個專案各放一份，但專案多到 30、40 個時，要讓它們保持同步非常痛苦01:18。把東西放在每個人自己的電腦裡也不理想：別人看不見、不會更新，而且那是個人依習慣調整的地方，不是團隊統一規則的地方01:44。

2. 解法：有一個「家」，AI 代理永遠從這裡出發

home repo 本身就是一個普通的儲存庫（repo），裡面放 skill、規則檔、筆記（wiki）和自訂工具（tooling）。講者每次啟動 AI 代理，都是在這個家裡啟動，再由它去存取其他專案、拉進需要的資料02:19。這樣一來，同一個工作階段（session）可以橫跨好幾個專案，一次改好前台和付款系統。講者的貼文列出的三個好處是：共用的東西放一處、所有 AI 代理在同一處執行、能一次處理跨專案的改動00:20。

3. 連結方式簡單到只是一份「路徑清單」

家怎麼知道其他專案在哪？講者只是在規則檔（AGENTS.md 或 CLAUDE.md）裡，一行寫一個專案和它在電腦裡的位置，像通訊錄一樣。AI 代理到新電腦上發現位置沒有東西時，會自己把專案下載（clone）下來；要同時開好幾個 AI 代理，就用工作樹（worktree）各做各的。要新增專案，只要多加一行03:4004:09。

4. 專案多到幾百個時，改成分層清單

講者說這個做法大約撐得住 20 到 40 個專案，到 400 個就太多了。那時要加一層目錄，這就是漸進式揭露（progressive disclosure）：先把專案分成前端、後端、內部工具幾類，各寫一份小清單，AI 代理先找到類別，再找到專案，像從「樓層導覽」走到「店家」04:42。

5. 它不是要取代「全部放同一個專案」，而是做不到時的替代方案

講者很喜歡把所有東西放進同一個專案（單一儲存庫，monorepo），能這樣做就該這樣做。但現實中常因為有些專案要公開、有些要保密，或是公司內部沒有共識，就做不到；這時 home repo 就是正確選擇05:13。

6. 集中之後，筆記與工具也會自己長出來

因為永遠從同一個地方開工，講者敢投資做更多工具：他的 home repo 同時是個人知識庫（wiki），也有一組指令，能連到 Gmail、Slack、Discord、YouTube、GitHub、行事曆等服務。於是他能一口氣說：「去 Discord 找這則訊息，到課程專案修正，再用課程影片管理器的 skill 改課程」，AI 代理一路做完06:3407:01。

怎麼開始

  • 先盤點：列出你（或團隊）常碰的專案資料夾有幾個、哪些有重複的規則或工具。數量在 40 個以內，這個做法就適用04:42。
  • 開一個新的私有儲存庫當家：講者文章裡的提示詞建議放在其他儲存庫旁邊；先放共用的 skill 和一份規則檔就夠了。
  • 在規則檔寫一行一個專案：專案名稱、電腦上的位置、必要時加一句提醒（例如「改之前先讀它的說明」）；之後多一個專案就多加一行04:09。
  • 直接用講者的提示詞：他在文章 The Home Repo Pattern 附了一段提示詞，AI 代理會先盤點你的專案、不斷追問你、讓你確認計畫才開始搬東西07:56。
  • 之後再慢慢加工具：等家穩定了，再把常用服務（信箱、聊天、行事曆）做成指令放進去，講者說他是這樣一步步長大的06:34。

片中「撐到 20～40 個專案、400 個就需要分層」是講者的個人經驗，譯者未另查證；講者文章也說明，那段提示詞在你批准計畫之前只會讀取、不會改動任何東西。
