用 GitHub、Workers 與 D1 部署網站

這份指南說明如何把放在 GitHub 的程式部署到 Cloudflare Workers，並用 D1（Cloudflare 提供的 SQLite 資料庫）儲存資料。設定完成後，每次 push 到 GitHub，網站就會自動更新。

01運作方式

三個服務各有分工：GitHub 存放程式碼；Workers 執行後端程式，也能同時提供前端的靜態檔；D1 存放資料。

你在本機開發後 push 到 GitHub，Cloudflare 的 Workers Builds 會自動建置並部署 Worker。使用者的請求進到 Worker 後，Worker 透過名為 DB 的 binding 查詢 D1，不需要連線字串，也不必另外架設資料庫伺服器。

02建置步驟

開始前需要準備 Cloudflare 帳號、GitHub 帳號，以及已安裝 Node.js 的電腦。步驟 01 會建立專案資料夾，之後的指令都在該資料夾中執行。

  1. 本機建立專案

    選 Worker 範本；需要前端的話選框架範本，例如 React 或 Astro。

    npm create cloudflare@latest
  2. 建立 D1 資料庫並綁定

    執行後把輸出的 database_id 填進 wrangler.jsonc。binding 的名稱就是程式裡 env.DB 的名字。

    npx wrangler d1 create my-db
    "d1_databases": [
  { "binding": "DB", "database_name": "my-db", "database_id": "xxxx" }
]
  3. 用 migration 建表

    先建立 migration 檔，在產生的 .sql 裡寫 CREATE TABLE，再套用。加 --remote 套用到正式環境；不加則套用到本機測試庫。

    npx wrangler d1 migrations create my-db init
npx wrangler d1 migrations apply my-db --remote
  4. 在程式中查詢

    透過 binding 存取資料庫。參數一律用 bind() 傳入，不要拼接字串，以防 SQL injection。

    const { results } = await env.DB
  .prepare("SELECT * FROM users WHERE id = ?")
  .bind(id).all();
  5. 本機測試

    會使用本機模擬的 D1，不會動到正式資料。

    npx wrangler dev
  6. 接上 GitHub 自動部署

    程式碼推上 GitHub 後，到 Cloudflare 後台「Workers & Pages → 建立 → 匯入 Git repository」選擇該 repo。

    注意：自動部署只更新程式碼，資料表變更仍要另外執行 migration。可以手動跑，或把 wrangler d1 migrations apply --remote 加進部署指令。

  7. 設定機密資訊

    API key 等機密用下列指令設定，不要寫進 repo。

    npx wrangler secret put 名稱

程式碼與資料表是兩條各自的更新路線

步驟 06 最容易漏掉。push 會自動讓新程式上線，但 D1 的資料表結構不會跟著變。若新程式要用到新欄位，應先套用 migration 再 push，否則新程式上線時會查不到欄位而出錯。

03需要留意的限制

項目免費方案Workers Paid
單一資料庫容量上限500 MB10 GB
每次 Worker 請求可執行的查詢數501,000
Time Travel 時間點還原7 天30 天
  • 單一資料庫的 10 GB 上限無法再提高。資料量大時，改為依使用者或租戶拆成多個資料庫。
  • 免費方案的每日讀寫或儲存額度用完後，D1 會回傳錯誤；升級到 Workers Paid 後，限制通常幾分鐘內解除。

併發：每個 D1 資料庫一次只處理一個查詢

同時湧入的請求會先排隊；佇列滿了就直接回傳 overloaded 錯誤。寫入量大的應用要減少每個請求的查詢數，或把資料拆到多個資料庫，分散負載。

04補充：要不要做快取

剛上線時不一定需要。建議先處理成本低、效益明確的前端快取；等流量變大，或發現同一批資料被大量重複查詢時，再加後端快取。

前端快取：先處理靜態檔

Workers 提供靜態檔時，預設會帶 Cache-Control: public, max-age=0, must-revalidate 和 ETag。瀏覽器每次使用前都會向伺服器確認；檔案沒變就只回小小的 304，不必重新下載整個檔案。

建置工具輸出的 JS、CSS 檔名通常帶有雜湊值（例如 app.3f9a1c.js），內容一改檔名就跟著變，所以可以放心讓瀏覽器長期快取。在靜態檔目錄（例如 public/）新增一個名為 _headers 的檔案：

/assets/*
  Cache-Control: public, max-age=31536000, immutable

注意：index.html 這類檔名不會變的頁面不要設長快取，否則使用者可能拿不到新版。另外，_headers 只對靜態檔有效；API 這類由 Worker 程式產生的回應，要在程式中自行設定標頭。

後端快取：減少重複查詢 D1

適合「很多人讀同一份資料、資料不常變」的情境，例如文章列表、商品目錄、設定值。快取命中時不必查 D1，能降低延遲，也能減輕 D1 一次只處理一個查詢造成的排隊。

常見的三種做法：

  • Cache API（caches.default）：把整個 GET 回應存在 Cloudflare 的機房，不必額外建立資源。快取只存在處理請求的那個機房，不會同步到其他地方；cache.delete 也只清得掉該機房的副本，所以通常靠較短的有效期限讓資料自然更新。官方文件列出的可用環境是自訂網域，在後台編輯器的預覽中則不會生效，建議綁定自訂網域後再使用。
  • Workers KV：全球分散的鍵值儲存，讀取快，適合放查詢結果或設定值。寫入後，其他地區可能要 60 秒以上才讀得到新值，不適合需要即時一致的資料。
  • D1 讀取副本（read replication）：這不是快取，而是在多個地區建立唯讀副本，縮短各地使用者的讀取延遲，而且不另外收費。寫入仍集中在主資料庫；搭配 Sessions API（env.DB.withSession()）可確保讀得到自己剛寫入的資料。這項功能推出時是公開測試版，使用前請先到官方文件確認目前狀態。

不要快取：登入後的個人資料（例如帶有 Authorization 的請求）和寫入操作（POST、PUT、DELETE）。cache.put 只接受 GET 請求，而且帶 Set-Cookie 的回應不會被存入快取。
